## ブロッキング判定条件

次のいずれかに当たる行だけがブロッキングになれる。それ以外は非ブロッキング指摘へ記録する。

1. **未実装** — 受入条件に対応する実装が、この PR の差分にも、スタックの他段にも存在しない。「探した範囲」にファイルと検索語を記録していること。探索の記録がない「見当たらない」はブロッキングにできない
2. **実装あり・検証なし** — 実装は存在するが、その受入条件を検証するテストが無い。ブロッキングにするには次を示すこと:
   - 実装の所在（`file:line`）
   - 検証しうるテストを探した範囲（ファイル・検索語）
   - **テストが存在する場合のみ** — 見つかったテストがその受入条件を検証していない理由（アサーションが別の性質を見ている、入力が受入条件の境界に触れていない 等）

   探索の記録があり、該当するテストが 1 件も無いことを示せれば、それだけでブロッキングにできる。「テストが少ない」「カバレッジが低い」はブロッキングにできない

3. **未解消の既出指摘** — 前回ラウンドで出した指摘が解消されていない（`tayk-review-convergence` 条件 1）

## 常に非ブロッキングにするもの

- **受入条件にない変更**（スコープ膨張）— `existing-system-respect` に反するが、成果物を無効化しない（`tayk-review-convergence` 条件 2 に当たらない）。非ブロッキング指摘に記録し、起票の要否は呼び出し側が判定する
- **上段で実装済み** — この PR 単体では受入条件を満たさないが、スタックの上段で実装されている。ブロッキングにはしない（スタック全体では満たされる）。ただし**非ブロッキング指摘に記録する** —— 段ごとに個別マージする運用では、この PR だけがマージされた時点で受入条件が満たされない
- **下段で実装済み** — この PR の責任範囲外。判定表に記録するだけで指摘にしない
- 実体は受入条件を満たしており、文書側の記述が追随していないだけの乖離
- より良い実装方法の提案

## 判定

- ブロッキング条件に当たる行が 1 件以上 → REJECT
- 0 件 → APPROVE（非ブロッキング指摘が残っていてもよい）
- 受入条件が確定しない → 判定不能（**APPROVE ではない**）

## 種別の集計（synthesis が読む）

結果の直後の「内訳」行に、ブロッキング指摘の種別ごとの件数と判定不能フラグを書く。**呼び出し側はこの内訳で「人間の判断が要るもの」と「機械的に直せるもの」を切り分ける**ため、省略できない。

- 「未実装」は受入条件の解釈が要るため人間へ回る
- 「検証なし」はテストの追加で閉じるため自動修正の対象になれる
- 「判定不能」が `true` のとき、ブロッキング 0 件でも自動修正を走らせてはならない（受入条件を一度も確認できていない状態を「問題なし」と読ませない）

## 出力整合性

- 受入条件の照合表は、レビュー対象レポートの「受入条件」表と**行数が一致**していること
- 判定が「満たす」「責任範囲外」以外の行は、ブロッキング指摘か非ブロッキング指摘のいずれかに現れること
- 所在が「なし」の行には「探した範囲」があること
- 内訳行の 3 種別の合計は、ブロッキング指摘表の行数と一致していること
- 受入条件が確定しない場合の結果は「判定不能」であり、APPROVE にしない

**認知負荷軽減ルール:**

- APPROVE → 結果 + 内訳 + サマリー + 受入条件の照合表 + 再走査証跡（2 回目以降）+ 非ブロッキング指摘（あれば）
- REJECT → 上記に加えてブロッキング指摘と探した範囲
- **受入条件の照合表は結果にかかわらず全行維持する。** 削ると「照合していない」と「問題なし」が区別できない
