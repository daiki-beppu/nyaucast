run 監査レポートの発見を仕分け、**根拠を示せるものだけ**を重複照合の上で起票してください。**ファイルは触りません。**

発見をレポートに書いたまま終わると、監査のたびに同じ欠陥が再発見されるだけで直りません。ここが逃がし口です。

> タスククローンには git remote が無いため、`gh` はリポジトリを自動解決できない。**すべての `gh` コマンドに `-R daiki-beppu/tayk` を付ける。** remote が無いこと自体は正常であり、失敗の理由にしない。

## spillover 規約との差分

この step は tayk-feature / tayk-fix の spillover と同じ起票規約に従う。ただし read-only 監査には「今回の差分」が存在しないため、**3 条件のうち ①（今回の変更と因果関係がない）は適用しない**。②（実害）③（根拠）だけで仕分け、差し戻しも行わない。

## 手順

### 1. 集める

分析レポートの Findings と Suggested Issue Titles を対象にする。Follow-up Notes に実害のある観測が紛れていないかも確認する。

**Token Usage 節は収集対象にしない。** 費用の偏り・突出 step は起票せず、レポート記録のみとする — 「見合うか」「step を削るか」は人間の判断（ADR-0008 Consequences）。費用偏りの原因が根拠付きの欠陥（例: 差し戻しループによる浪費）として Findings に載っている場合は、その Finding を通常どおり仕分ける。

### 2. 重複を畳む

同じ問題を指している発見を 1 件にまとめる。別パートのアナリストが同じパターンを別の run で観測していることがある。畳んだときは、該当 run と根拠を両方から引き継ぐ。

### 3. 2 条件で仕分ける

| 条件                   | 判定方法                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| ② 放置すると実害がある | 「どの workflow 実行で何が再発するか」を 1 文で書けるか。書けないなら実害なし                                            |
| ③ 根拠を示せる         | **run 名 + trace.md / meta.json / monitor.json の引用**（定義監査の発見は**定義ファイルのパス + 該当行の引用**）があるか |

定義監査（Audit Targets #1〜#3）の発見について:

- **検査 E（spillover 複製）の乖離は原則起票する。** 「複製された定義は必ず片方だけ更新される」は ADR-0008 が Considered Options で自認する失敗様式の現物であり、②は自動的に満たす。差分そのものが③になる
- 「決定的に検査できる」提案（#104 の 2 分法で `bun test` へ切り出すもの）も、他の発見と同じ 2 条件で仕分けて起票する。この workflow に検査を抱え込まない

② ③ を満たさないものは起票せず、**レポートに記録のみ**とする（破棄ではない。監査レポートには残る）。満たさなかった条件と理由を記録する。

「Loop Monitor 不発の疑い」節で**判定が「起票対象（高確度）」**の行（現行定義に step が存在し `{step_iteration}` 自前上限が無い）は、② を「現行定義のまま該当 workflow を実行すると同じ再入で上限が効かず反復する」、③ を遷移系列の引用で満たす高確度発見として扱う。**「記録のみ」の行は起票しない**（自前上限あり = 二重化が機能している / 現行定義に無い = 直す対象が無い）。

### 4. 既存 issue と照合する

起票対象それぞれについて、既存の open issue を検索する:

```
gh issue list -R daiki-beppu/tayk --state open --search "<発見の要約から抜いた語>" --json number,title,body
```

検索語は 1 つに絞らず、workflow 名・症状・step 名の 3 方向から引く（定義監査の発見は workflow 名・facet / step 名・観点名 — spillover / レポート境界 / drift — から引く）。既存が見つかったら**起票せず**、その issue へ観測をコメントで足す:

```
gh issue comment <N> -R daiki-beppu/tayk --body "<今回の監査で確認した観測。run 名とトレース引用>"
```

### 5. 起票する

重複がないものだけを起票する。**1 発見 = 1 issue**。

```
gh issue create -R daiki-beppu/tayk --title "<種別>: <1 行で問題>" --body "<本文>"
```

本文には、分析レポートから以下をそのまま転記する:

- **該当 run** — run 名（複数なら全部）。定義監査の発見は該当する定義ファイルのパス
- **観測された問題** — 何が起きたか / どんな経路で失敗したか
- **実害** — どの workflow 実行で何が再発するか
- **根拠** — トレース引用（trace.md の該当箇所）。定義監査の発見は定義ファイルの該当行の引用（検査 E は両ファイルの差分）
- **発見の経緯** — 「`tayk-audit-runs` の run 監査（issue #N 起点）で発見」

ラベルは付けない（triage は人間の判断。`docs/agents/triage-labels.md`）。

### 6. 記録する

起票した issue 番号・既存へ追記した issue 番号・記録のみとした発見を、レポートに残す。

## 制約

- **ファイルを変更しない。** この step が触るのはレポートと GitHub issue のみ
- 発見をまとめて 1 つの issue にしない（着手単位が壊れる）
- 「調査してください」だけの issue を立てない。根拠を示せない発見は記録のみとする
- 既存 issue の close / edit を行わない（起票とコメントのみ）

## 判定

- 仕分けが終わり、起票・追記・記録のみをすべて記録した → 完了（起票対象ゼロの場合を含む）
- `gh issue` の操作に失敗した（権限・ネットワーク）→ 失敗した発見と手動起票用のコマンドを**レポート**に残して完了。**起票失敗を理由に workflow を止めない**（レポートは publish 済みで、発見は追跡可能な形で残る）。ただし成功した場合とは別の判定として報告すること — 実行ログ上で区別がつかなくなるため
