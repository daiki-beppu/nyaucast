この workflow の途中で見つかった**スコープ外の発見**を集め、起票するものと捨てるものに仕分けてください。**コードは触りません。**

発見をレポートに書いたまま終わると、workflow の実行ログとともに埋もれます。ここが最後の逃がし口です。

## 手順

### 1. 集める

Report Directory 内の**すべてのレポート**を Read で開き、「スコープ外の発見」節を探す。診断 / 計画 / 実装 / 各レビューのどのレポートにもありうる。

節が無いレポートも「読んだが無かった」として収集元の表に記録する。読んでいないレポートを残さない。

### 2. 重複を畳む

集めた発見のうち、**同じ問題を指しているもの**を 1 件にまとめる。別々のレビュアーが同じ箇所を別の言葉で書くことがある。畳んだときは、根拠を両方から引き継ぐ。

### 3. 3 条件で仕分ける

Policy のスコープ外発見ポリシーの 3 条件に照らす。

| 条件                         | 判定方法                                                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| ① 今回の変更と因果関係がない | 今回の差分（`git diff`）を実際に確認する。差分が触れている箇所・触れている関数の呼び出し元に該当するなら「因果あり」 |
| ② 放置すると実害がある       | 「誰に何が起きるか」を 1 文で書けるか。書けないなら実害なし                                                          |
| ③ 根拠を示せる               | 再現手順か、`file:line` のコード引用があるか                                                                         |

**① で「因果あり」と判定した発見は、スコープ内へ引き戻す。** 起票して先送りしてはならない。引き戻した発見が 1 件でもあれば、この step は差し戻しになる。

② ③ を満たさないものは破棄し、破棄した事実と理由をレポートに残す。

### 4. 既存 issue と照合する

起票対象それぞれについて、既存の open issue を検索する:

```
gh issue list --state open --search "<発見の要約から抜いた語>" --json number,title,body
```

検索語は 1 つに絞らず、場所（ファイル名）・症状・関連する tool 名の 3 方向から引く。既存が見つかったら**起票せず**、その issue へ観測をコメントで足す:

```
gh issue comment <N> --body "<今回の workflow で再確認した観測。file:line と根拠>"
```

### 5. 起票する

重複がないものだけを起票する。**1 発見 = 1 issue**。

```
gh issue create --title "<種別>: <1 行で問題>" --body "<本文>"
```

本文には、発見時のレポートから以下をそのまま転記する:

- **場所** — `file:line`
- **観測された問題** — 何が起きるか / 何が壊れているか
- **実害** — 誰に何が起きるか
- **根拠** — 再現手順、またはコード引用
- **発見の経緯** — 「issue #N の作業中に発見。当該変更とは因果関係なし」

ラベルは付けない（triage は人間の判断。`docs/agents/triage-labels.md`）。

### 6. 記録する

起票した issue 番号・既存へ追記した issue 番号・破棄した発見を、レポートに残す。

### 7. PR 本文へ転記する

`delivery` が済んでいるので PR は既に存在する。起票結果をその本文へ追記する。

```
gh pr view --json number,body
gh pr edit <N> --body "<取得した本文 + 切り出した issue の節>"
```

追記するのは以下:

- 起票した issue 番号と、今回のスコープ外とした理由
- 既存 issue へ観測を足したもののその番号
- `gh` の操作に失敗して起票できなかった発見があれば、**その事実と手動起票用のコマンド**

**既存の本文を消さないこと。** `--body` は全文置換なので、必ず `gh pr view --json body` で取得した本文に節を足した全文を渡す。

この転記が、発見から issue への追跡が PR 上で辿れる唯一の経路です。`spillover` が `delivery` の後ろに置かれているのはこのためで、PR が存在しない状態では転記できません（ADR-0006 決定 11）。

## 制約

- **コードを変更しない。** この step が触るのはレポートと GitHub issue のみ
- 発見をまとめて 1 つの issue にしない（着手単位が壊れる）
- 「調査してください」だけの issue を立てない。根拠のない発見は破棄する
- 既存 issue の close / edit を行わない（起票とコメントのみ）
- wayfinder の map / ticket を書き換えない（wayfinder セッションの責務）

## 判定

判定は上から順に評価してください。「因果ありの発見が残っている」ことは、仕分けが完了していることと両立します。**仕分けが終わったからといって、引き戻すべき発見を抱えたまま先へ進んではいけません。**

- **因果ありと判定した発見がある**（スコープ内へ引き戻すべきものが残っている）→ **計画へ差し戻す**（feature なら再計画、fix なら再診断）。修正へ直接戻さないのは、因果のある問題には要件 ID が要るためであり、採番は計画・診断の責務だからです
- 仕分けが終わり、起票・追記・破棄をすべて記録し、PR 本文へ転記した → 完了
- 発見が 1 件もなかった → 完了（収集元を読んだ記録は残す）
- `gh issue` の操作に失敗した（権限・ネットワーク）→ 失敗した発見と手動起票用のコマンドを、**レポートと PR 本文の両方**に残して完了。**起票失敗を理由に workflow を止めない**（実装と PR は完了しており、発見も追跡可能な形で残る）。ただし成功した場合とは別の判定として報告すること — 実行ログ上で区別がつかなくなるため
