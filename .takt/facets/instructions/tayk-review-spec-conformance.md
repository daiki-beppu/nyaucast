PR の差分が、linked issue の受入条件を満たしているかを判定してください。**コードは変更しません。**

この PR には設計ゲート（計画・テスト設計）を通っていないものが含まれます。**要求と成果物の対応を見る工程はこのレビューしかありません。**

## 1. 受入条件を確定する

レビュー対象レポートの「受入条件」表を読みます。表が無い（linked issue を解決できなかった）場合、**判定不能**として結果を返します。推測で受入条件を作ってはいけません。

受入条件は issue の文言のまま扱います。言い換えると、言い換えた側の解釈が基準になってしまいます。

## 2. 受入条件ごとに 3 列を埋める

| 列             | 埋め方                                                 |
| -------------- | ------------------------------------------------------ |
| **実装の所在** | 差分の中で、その条件を満たしているコードの `file:line` |
| **検証の所在** | その条件を検証しているテストの `file:line`             |
| **探した範囲** | 所在が無い場合のみ。どのファイル・どの検索語で探したか |

**実装の所在と検証の所在は別々に埋めます。** 実装があってもテストが無ければ「検証されていない」であり、CI が緑でもその受入条件は守られている証拠がありません。この 2 列の非対称が、このレビューの検出力の中心です。

所在が見つからない場合、**探した範囲を必ず書きます**。探索の記録がない「見当たらない」は指摘として無効です。

## 3. スタックの段を考慮する

レビュー対象レポートの「スタック位置」に下段がある場合、その PR は段の一部です。

`gh pr diff` が返すのは base（= 下段のブランチ）との差分なので、**下段で実装済みのものは差分に現れません**。差分に無いことを理由に「未実装」と判定する前に、下段で実装されている可能性を確認してください。

```bash
gh pr diff {下段の PR 番号}
```

下段で実装済みだった場合、その受入条件は**この PR の責任範囲外**です。判定表には「下段 #N で実装済み」と記録し、指摘にはしません。

## 4. 受入条件にない変更を洗い出す

差分のうち、どの受入条件にも紐づかない変更を列挙します。

判定は 2 つに分かれます:

- **受入条件の実現に必要な副次的変更**（型定義の追加、呼び出し側の追随、テストヘルパー）— 正常です。指摘しません
- **どの受入条件とも因果のない変更**（ついで直し、無関係なリファクタ）— `existing-system-respect` に反します

## 5. 2 回目以降のラウンド

レビュー対象レポートに「前回ラウンドからの引き継ぎ」がある場合、`tayk-review-rescan` policy の義務が発生します。

1. 引き継いだ指摘が解消されたかを、`file:line` の証跡つきで確認する
2. そのうえで、**受入条件の全行を再照合する**（前回からの差分だけを見て承認しない）
3. 再照合した範囲を「再走査証跡」に記録する

ブロッキングにできる指摘の範囲は `tayk-review-convergence` policy が定めます。2 回目以降に見つけた新規指摘は、成果物の無効化を示せない限り非ブロッキングです。

## 禁止

- コードの変更
- 要件 ID (`REQ-<issue番号>-<2桁連番>`) の不在を指摘すること（ADR-0008 決定 14。この workflow が見る PR には要件 ID を持たないものが含まれ、その不在は規約違反ではない）
- 受入条件に書かれていない「あるべき姿」を要求すること
- 探した範囲を書かずに「実装が見当たらない」と指摘すること
