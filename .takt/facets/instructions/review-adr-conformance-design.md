Report Directory の実装計画（`plan.md`）とテスト設計（`test-design.md`）が **tayk の ADR に整合しているか** だけをレビューしてください。コードはまだ存在しません。設計の段階で規約違反を止めるのがこの step の役割です。

他のレビュアーの有無を前提にしないでください。コーディング作法・テスト品質はこのレビューの担当外です。

## 手順

1. Knowledge の Source Path を Read で開き、**ADR 本文を全文取得する**。要約や記憶で判定しない
2. `docs/adr/` を Glob で確認し、Knowledge の索引にない ADR が増えていないかを見る
3. 各 ADR の Decision 節を列挙する（取捨選択しない）
4. 列挙した決定を実装計画の「実装方針」と 1 対 1 で照合する
5. 計画の「ADR 整合性の事前申告」が、実際の方針と一致しているかを検証する。**申告漏れは違反として扱う**
6. `CONTEXT.md` の用語が正書どおりに使われているか、`_Avoid_` 語が混入していないかを確認する
7. データ 4 分類に照らし、新しく置くデータの SSOT が正しいかを判定する
8. v0.1.0 のゲート外の機能が計画に紛れ込んでいないかを確認する

**これは {step_iteration} 回目のレビューです。**
初回は全 ADR の全決定を網羅してください。2 回目以降は前回の open findings とその修正箇所を確認したうえで、承認を出す前に必ず全決定を最終照合し、照合した決定と根拠を「再走査証跡」に記録してください（APPROVE でも省略不可）。

## 判定の 3 値

| 判定 | 条件 |
|------|------|
| 整合 | ADR の決定に沿っている |
| 要 ADR 改訂 | 逸脱に技術的正当性はあるが ADR が未改訂、または計画の申告が不十分。**差し戻す** |
| 違反 | 正当性のない逸脱、または正当性が示されていない逸脱。**差し戻す** |

## 禁止

- ADR に書かれていない設計上の好みを指摘すること
- ADR 本文を引用できない指摘を出すこと
- 「既存コードがそうなっている」を正当性として受け入れること
- Python 版（旧リポ）の実装との差分を根拠にすること
