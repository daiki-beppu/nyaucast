run 監査の supervise → review サイクルが {cycle_count} 回繰り返されました。**再分析を挟んで回しても supervise の approve が出ていない状態です。**

監査が収束に向かっているかを判断してください。

**確認すること:**

1. 計画レポート（`01-runs-audit-plan.md`）の Audit Targets の行数（= 全対象数）
2. 分析レポート（`02-runs-audit.md`）の Audit Scope で ✅ の行数と、その推移
   - 直近の supervise の判定（targets_audited / blocking_issues）が前段レスポンスや実行履歴にあれば、サイクル間の増加量を比較する

**判断基準:**

- 全対象が ✅ で、Findings が根拠（run 名 + トレース引用）付きの Issue 直貼り品質に達しており、Token Usage 節（トークン消費集計）が埋まっている
  - 実質完了している。**publish へ進めてよい**
- ✅ の行数がサイクルごとに増えている
  - 健全。1 サイクル最低 4 対象の前進義務が守られていれば、残り iteration 数 × 4 で残対象を回収できるかを確認し、回収できるなら継続
- ✅ が増えていない、または同じ対象への差し戻しが繰り返されている
  - 非生産的。再分析が分析ではなくレポートへの講評に化けていないか（Audit Scope が計画と一対一でない・レポート自身を根拠にした Finding がある）を確認する。構造が壊れたまま回っているなら**打ち切る**
- 残り iteration 数では全対象を回収できない
  - 容量不足。**打ち切る**。このケースは plan の対象数上限（24）が守られていないか、1 対象に束ねた run が多すぎたことを意味するので、報告に「次回は plan で対象をどう束ね直すべきか」を明記する

**打ち切りを選ぶときは、何サイクルで何対象が進んだか（例: 3 → 3 → 7 → 12）と、停滞の原因を報告に明記してください。** 人間が workflow 定義側を直すための判断材料になります。
