CI の失敗を修正してください。

失敗内容:

- PR: `#{structured:ci_check.pr_number}`
- 状況: {structured:ci_check.summary}

**これは {step_iteration} 回目の CI 修正です。**

## 手順

1. `{structured:ci_check.failed_checks}` の各項目について、`cause` と `location` を確認する
2. `cause` が「ログから特定できず」のものは、自分で `gh run view <run-id> --log-failed` を実行して原因を特定する
3. **原因を特定してから直す。** 症状に対する場当たり的な修正をしない
4. 修正が済んだら、ローカルで同じ検証を再現する（`nr test` / `nr lint` / `nr build` 等、CI が実行しているコマンドと同じもの）
5. ローカルで通ったら commit・push する:
   - 日本語 Conventional Commits + タイトル末尾に `(#<N>)`
   - `fix:` ではなく、元の変更の一部なら `feat:` 等を維持する。CI 修正だけの commit なら `ci:` または `fix:`

## 禁止

CI を通すために以下を行ってはならない。行った時点でこの workflow の目的が失われる。

- テストの削除・`skip` / `todo` 化・コメントアウト
- アサーションを緩めること（期待値を実際の出力に合わせて書き換える）
- lint ルールの無効化（`eslint-disable` / `oxlint-disable` 等）で警告を消すこと
- 型エラーを `as any` / `@ts-ignore` で潰すこと
- CI 設定ファイルを変更してチェック自体を外すこと

上記が唯一の解に見えるときは、それは実装かテスト設計に誤りがあるということである。**修正せず差し戻すこと。**

## 判定

**ラウンド上限は 3 回です。** `{step_iteration}` が 4 以上なら、内容にかかわらず差し戻してください。3 ラウンド直して緑にならない CI は、この step で扱える範囲を超えています（ADR-0008 決定 6）。flaky と判断して戻った回もラウンドに数えます。

- `{step_iteration}` が 4 以上 → **差し戻す**。何が落ち続けたか、各ラウンドで何を試したかを報告に残す
- 原因を特定して修正し、ローカル検証が通り、push した → CI 確認へ戻る
- 失敗が flaky（再実行で解消する類）と判断した → その根拠（同一コミットで結果が揺れた記録等）を示したうえで CI 確認へ戻る
- 実装またはテスト設計の誤りが原因で、この step では直せない → 差し戻す
