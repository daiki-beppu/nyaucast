PR に付いたレビュー指摘を収集し、**対応する / 対応しない** に分類してください。この step では修正しません。

**これは {step_iteration} 回目のトリアージです。**

## 手順

1. PR のレビューとコメントを収集する:
   - `gh pr view --json number,reviews,comments,reviewDecision`
   - 行コメント: `gh api repos/{owner}/{repo}/pulls/<N>/comments --jq '.[] | {user: .user.login, path, line, body, in_reply_to_id}'`
2. **解決済みスレッドを除外する。** 返信で解消済みのもの、`resolved` 状態のものは対象外
3. 前回のトリアージ以降に**新しく追加された指摘**を特定する（2 回目以降）
4. 各指摘を分類する:

| 分類       | 条件                                                                  |
| ---------- | --------------------------------------------------------------------- |
| actionable | 事実として正しく、対応すべき指摘                                      |
| dismissed  | 事実誤認、ADR / 仕様上そうしている、スコープ外 — **理由の記載が必須** |

5. actionable には severity を付ける:
   - `blocking`: 正しさ・安全性に関わる。マージを止める
   - `should`: 直すべきだが動作は壊れていない
   - `nit`: 軽微（命名・書式）

## status の判定基準

| status       | 条件                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| `actionable` | 未対応の actionable が 1 件以上ある                                                                           |
| `awaiting`   | 自動レビュー（CodeRabbit 等）がまだ走っている、またはレビュー依頼から十分な時間が経っておらず結論が出ていない |
| `clean`      | 未対応の actionable がなく、待つべきレビューもない                                                            |

## 制約

- **保留を残さない。** すべての指摘を actionable か dismissed のどちらかに分類する
- dismissed の理由は「対応不要」では足りない。ADR の該当決定・仕様の該当箇所・事実誤認の根拠のいずれかを示す
- 自分（tayk workflow）が過去に付けたコメントを指摘として数えない
- レビュアーへの返信コメントをこの step で投稿しない（finalize が一括で行う）
- `nit` だけが残っている状態で `blocking` がなければ、`nit` も actionable として扱う（軽微でも直せるものは直す）
