Report Directory のゲート段レポート（feature では設計、fix では診断）が **tayk の ADR に整合しているか** だけをレビューしてください。コードはまだ存在しません。実装に入る前に規約違反を止めるのがこの step の役割です。

対象は呼び出し元の workflow によって変わります。Report Directory にあるものを読んでください。

| workflow | 対象レポート | 照合する節 |
|----------|------------|-----------|
| `tayk-feature` | `plan.md` + `test-design.md` | 「実装方針」「ADR 整合性の事前申告」 |
| `tayk-fix` | `diagnosis.md` | 「原因」「修正方針」「回帰テスト設計」「ADR 整合性の事前申告」 |

他のレビュアーの有無を前提にしないでください。コーディング作法・テスト品質はこのレビューの担当外です。

## 手順

1. Knowledge の Source Path を Read で開き、**ADR 本文を全文取得する**。要約や記憶で判定しない
2. `docs/adr/` を Glob で確認し、Knowledge の索引にない ADR が増えていないかを見る
3. 各 ADR の Decision 節を列挙する（取捨選択しない）
4. 列挙した決定を、設計レポートの方針（feature は「実装方針」、fix は「修正方針」）と 1 対 1 で照合する
5. 設計レポートの「ADR 整合性の事前申告」が、実際の方針と一致しているかを検証する。**申告漏れは違反として扱う**
6. `CONTEXT.md` の用語が正書どおりに使われているか、`_Avoid_` 語が混入していないかを確認する
7. データ 4 分類に照らし、新しく置くデータの SSOT が正しいかを判定する
8. v0.1.0 のゲート外の機能が設計レポートに紛れ込んでいないかを確認する
9. **fix のときのみ**: バグの原因そのものが ADR 逸脱（registry の設置、`Result` 型の導入、adapter への業務ロジック混入、YAML でのデータ保存など）であるかを判定する。逸脱が原因なら、その事実が「原因」の記述に含まれ、修正方針が逸脱の解消になっているかを確認する。**逸脱を残したまま症状だけ直す方針は「違反」として差し戻す**

**これは {step_iteration} 回目のレビューです。** 再走査の対象は **全 ADR の全決定**です。Policy の再走査ポリシーに従ってください。

## 判定の 3 値

| 判定 | 条件 |
|------|------|
| 整合 | ADR の決定に沿っている |
| 要 ADR 改訂 | 逸脱に技術的正当性はあるが ADR が未改訂、または計画の申告が不十分。**差し戻す** |
| 違反 | 正当性のない逸脱、または正当性が示されていない逸脱。**差し戻す** |

## 禁止

- ADR に書かれていない設計上の好みを指摘すること
- ADR 本文を引用できない指摘を出すこと
- 「既存コードがそうなっている」を正当性として受け入れること
- Python 版（旧リポ）の実装との差分を根拠にすること
