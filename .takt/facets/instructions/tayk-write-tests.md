承認されたテスト設計（`{report:test-design.md}`）に従って、**プロダクションコードの実装前にテストを書いて**ください。

## 手順

1. テスト設計の「要件 ↔ テストケース対応」表を読み、**自動テスト化すると決めたケースをすべて実装する**（取捨選択しない）
2. テスト設計の「テストファイル配置」に従ってファイルを作る。**1 tool = テスト 1 ファイル**（ADR-0001）
3. 各テストに、対応する要件 ID とケース ID をコメントまたは describe/it の名前で埋め込む:
   ```ts
   // REQ-55-01 / TC-01
   test('benchmark.collect は min_views 未満の動画を除外する', () => { ... })
   ```
   これにより、後段のレビューが要件とテストを機械的に突き合わせられる
4. テストを実行し、**現時点で失敗する（red である）ことを確認する**:
   ```
   bun test
   ```
   実装がまだ無いので失敗するのが正しい。ここで通ってしまうテストは、要件を検証していない
5. 「検証不能な要件」として設計され、`test-design-review` が承認したものはテストを書かず、レポートの「承認済みの非テスト化ケース」に分けて記録する。「自動テスト化すると決めたが書けなかったケース」と混ぜない

## 制約

- **プロダクションコードを実装しない。** この step で書くのはテストのみ
- テストが通るようにするために、テスト側の期待値を緩めない。red のまま次へ渡す
- 外部サービス（YouTube API / 生成 AI）へ実アクセスしない。テスト設計のモック方針に従う
- 設計にないテストを追加しない。必要だと考えるなら、その理由を報告に書いてテスト設計へ差し戻す
- 未実装を示す fail / import error は、この step で確認すべき想定内の red である。失敗件数や red の存在そのものを、テスト設計への差し戻し根拠にしない

## 判定

- 自動テスト化すると決めた全ケースを実装して red を確認し、未作成が承認済みの非テスト化ケースだけである → 実装へ
- 自動テスト化すると決めたケースを実装できない（設計自体に誤りがある / 依存する基盤が未実装）→ **テスト設計へ差し戻す**

**承認なしにテストを持たない要件を抱えたまま実装へ進んではいけません。** 1 要件に最低 1 テストケースが ADR-0008 決定 5 の原則です。本当に自動検証不能なら、その理由と代替検証をテスト設計に明記させ、設計レビューの承認を得てから実装へ入ります。承認済みの非テスト化ケースだけが残る状態は設計どおりであり、差し戻しません。「基盤が未実装だから今は書けない」を実装へ進む理由にしないでください — その判断はテスト設計とそのレビューが行います。
