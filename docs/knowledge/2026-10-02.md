## 解説動画のカット 3 種の描き方を、「秒を誰が書くか」から逆算して決めた話

解説動画から書き出す 3 種類の動画ファイル（カット）の描き方を決めたときの学び。3 種類は、横長の長尺、長尺の一区間を縦型にした切り抜きショート、縦型に組み直した専用ショートだ。nyaucast の動画は、HTML 1 枚で書いた絵コンテ（composition）を headless Chrome で 1 フレームずつ撮り、エンコードして作る。composition は `window.__hf` というオブジェクトで、全体の長さと `seek(t)`（時刻 t の絵にする関数）を公開する。問いは 6 つあった。長尺をどう 1 本にするか、切り抜きを描き直すか再エンコードするか、専用ショートと長尺で何を共有するか、字幕をどこで描くか、作り直しを判定するキャッシュの鍵、描画とプレビューの 2 つの tool の範囲だ。

- 決定の記録: [カット 3 種の描画方式と字幕の焼き込み](https://github.com/daiki-beppu/nyaucast/issues/467)
- 用語集と ADR の更新: [PR #493](https://github.com/daiki-beppu/nyaucast/pull/493)（「図解」「ショートの候補」「フック」を足し、ADR-0005 に決定 12・13 を加えた）

質問は 3 ラウンドで 14 問出し、運営者の返事は 3 回とも「すべて推奨」だった。前日に決めたナレーションの時間合わせ（[前日のエントリ](./2026-10-01.md#narration-timing)）と、同じ運営者の `life` リポジトリにある、同じ型の動画の先行実装が、推奨の根拠をほぼ用意していたからだ。この回の学びは、問いの立て方と、既存の決まりとの折り合いの付け方にある。

### 1. 引き継がれた「どこで計算するか」の問いは、「誰がその成果物を書くか」の問いに読み替える

前日のチケットからは、「台本上の位置（段落 2 の 3 番目の句、など）を秒に直す処理を、描画の tool の中でやるか、別の組み立ての tool でやるか」という問いが渡ってきていた。計算の置き場の問題に見えるが、実際には **composition を誰が書くか** の問題だった。

- エージェントが composition 全体を書くなら、エージェントは秒の入った `seek` を書くことになる。前日に退けた「エージェントが時刻表から秒を写す」事故が戻ってくる
- エージェントがシーンごとの絵（図解）だけを書き、nyaucast が composition を組み立てるなら、秒への変換は組み立ての側に自然に入る

`life` の動画ダイジェストは後者の形で動いている。LLM はシーンごとの HTML の断片を書き、演出の時刻は `data-beat="2.3"`（2 段落目の 3 番目の句）のように宣言だけする。断片では `<script>` が禁止されている。時間軸・字幕・枠は、決定的なビルダーが組み立てる。nyaucast もこの形にし、断片を「図解」と呼ぶことにした。

**「どこで計算するか」と聞かれたら、計算の入力と出力のファイルを誰が書くかまで遡る。** 書き手が決まれば、計算の置き場はその後で決まる。

### 2. 先行実装が既存の ADR の一文とぶつかったら、改訂の範囲を制作物の種類で絞る

この形には障害が 1 つあった。nyaucast の ADR-0005（メディア処理の基盤の決定）の Consequences に、「決定論化の手段はエージェントが composition に埋め込み、nyaucast 本体はブラウザ内で動く runtime を持たない」と書いてある。図解から `seek` を動かすには、時間軸を組み立てる JavaScript の runtime が要る。それを nyaucast が持つことになる。

nyaucast には「ADR から黙って逸脱しない。逸脱するなら、ADR の改訂を同じ差分に含める」という規約がある。そこで ADR-0005 に決定 12 を足し、改訂の範囲を次の 3 点で絞った。

- 対象は解説動画だけ。もう 1 種類の制作物（BGM 動画）は、今どおりエージェントが composition 全体を書く
- runtime は、組み立ての tool が composition にインラインで埋め込む。ADR-0005 の別の決定（共通ライブラリに置いてよいのはプロトコルの汎用部分だけで、業務ロジックは tool のファイルに同居させる）に合わせ、tool の実装ファイルに同居させる
- 組み立ての tool は Chrome を使わない。Chrome への依存を描画とプレビューの 2 tool に限る決定は、広げない

**ADR の一文と衝突したら、ADR 全体を書き換えるのではなく、例外にする対象を名前で列挙して改訂する。** 範囲を絞っておけば、改訂の影響を受けない側（ここでは BGM 動画）の実装を読み直さずに済む。

### 3. 描画の関数を純関数にしておくと、切り抜きは「時間軸をずらして描き直す」だけで作れる

切り抜きショートは、9:16 の縦型の中央に長尺の 16:9 の絵を置き、上の帯に見どころを言い切る一文（フック）、下の帯に字幕を出すレイアウトだ。作り方の候補は 2 つあった。

| 案                                                              | 必要になるもの                                                |
| --------------------------------------------------------------- | ------------------------------------------------------------- |
| 長尺の mp4 を切り出し、縦型の枠に配置して再エンコードする       | 動画を合成する処理を、Chrome の外（エンコード層）に新しく持つ |
| 長尺の図解を縦型の composition に置き直し、もう一度撮る（採用） | 長尺のタイミング表を、区間の開始の秒だけずらして使うこと      |

2 つ目の案が成り立つのは、composition の契約が `seek(t)` を **t だけの関数**（呼び出しの順序や時計に依存しない）と定めているからだ。区間がシーンの途中から始まっても、`seek(区間の開始 + t)` を呼べば、それまでの演出が出そろった状態から正しく描ける。

区間は秒ではなく **段落の範囲**（段落 m の読み始めから段落 n の読み終わりまで）で指すことにした。音声も段落の範囲で切り出して BGM と混ぜ直すので、映像と音声の切れ目が必ず一致する。長尺の最終の音声を秒で切ると、BGM が曲の途中から始まり、ラウドネスも長尺全体で合わせた値のままになる。

**描画を純関数として契約しておくと、「既存の絵の一部を別のレイアウトで使う」が描き直しで済む。** 純関数性の検証（同じ t に 2 回 seek して、撮った画像をバイト比較する）は、決定論のためだけではなく、再利用のための投資でもあった。

### 4. 失敗したときに止めるか続けるかは、その場で直せる人がいるかで決める

`life` では、図解が安全性の検査（`<script>` や外部 URL の禁止、文字数の上限など）に落ちると、そのシーンだけ見出しだけの縮退表示にして、動画全体の書き出しは止めない。nyaucast では逆に、違反をすべて列挙して throw する（エラーで止める）ことにした。

理由は運用の違いにある。`life` は毎朝の無人配送なので、1 シーンのために配送が止まるほうが損害が大きい。nyaucast は、エージェントがその場で図解を書き直せる。しかも公開の前に、人間がプレビューを見て公開するかを決める関門（公開ゲート）がある。縮退したシーンが、気づかれないまま関門を通るほうが危険だ。

**同じ検査でも、失敗時の振る舞いは運用の形で変わる。** 先行実装から検査の規則は引き継ぎ、落ちたときの振る舞いは、直す人がその場にいるかどうかで決め直す。

### 5. ある種類の制作物のために決めた既定値は、新しい種類に当てはめる前に意味を確かめる

プレビューの tool は、composition の区間（segments）ごとに 1 枚ずつ PNG を撮る。撮る時刻は、規約で **各区間の中点** と決まっていた。これは BGM 動画のために決めた値で、BGM 動画の区間はほとんどが静止画（どの時刻でも同じ絵）だった。中点で撮っても、どこで撮っても同じだった。

解説動画では区間がシーンに当たり、シーンの中で図が 1 つずつ組み上がっていく。中点で撮ると、図が組み上がる途中の絵がプレビューに出る。そこで **各区間の終わる直前** を撮るように変えた。静止画の区間ではどの時刻でも同じ絵なので、BGM 動画のプレビューは変わらない。

**既定値は、それを決めたときの対象の性質（ここでは「区間の中で絵が動かない」）に依存している。** 新しい種類の対象に使う前に、その性質が成り立つかを確かめる。変えるときは、古い対象で結果が変わらないことを示せると、改訂が安全になる。

### 6. キャッシュの鍵が連鎖しないように、共有は参照ではなくコピーにする

専用ショートは、長尺の図解を流用して作ることがある。流用の方法として、長尺の図解ファイルを参照する案と、コピーして書き換える案があった。nyaucast の tool は「入力のハッシュが前回と同じなら、作り直さずに既存の成果物を返す」という鮮度付きの冪等性を持つ。参照で共有すると、長尺の図解を 1 枚直しただけで、それを参照する専用ショートの鍵まで変わる。結果として、直すつもりのなかったカットまで作り直しになる。

コピーにすると、長尺の修正は専用ショートに伝わらない。専用ショートは自分の台本と音声を持つ別のカットなので、伝わらないほうが正しい。

**ハッシュで作り直しを判定する仕組みでは、参照は依存関係そのものになる。** 一緒に変わってほしくないものは、コピーして切り離す。

## サムネイルを企画の段階に前倒しし、文字も画像生成に描かせると決めた話

解説動画の長尺カット（横長の本編の動画ファイル）につけるサムネイルの作り方を決めたときの学び。前提は 2 つあった。ADR-0009（解説動画と多 SNS 配信の決定）が、サムネイルを HTML で描かずに画像生成で作ると決めていた。ADR-0005 が、headless Chrome を使ってよい tool を描画とプレビューの 2 つに名前で限っていた。チケットの問いは 5 つあった。画像生成 API の選定、文字を生成に描かせるか後から重ねるか、320px に縮めても読めるかの検証を誰がするか、作り直しと差し替えの経路、BGM 動画（音楽チャンネルの動画）のサムネイル生成と共通にするかだ。

- 決定の記録: [長尺サムネイルの生成方式](https://github.com/daiki-beppu/nyaucast/issues/468)
- 用語集と ADR の更新: [PR #496](https://github.com/daiki-beppu/nyaucast/pull/496)（「サムネイル」「サムネイルの文言」「サムネイルの候補」「サムネイルの選択」「サムネイルの型」を足し、ADR-0009 に決定 8 を加え、ADR-0002 を改訂した）

質問は 5 ラウンドで 17 問出した。直前のエントリの回と違い、運営者は 4 か所で推奨を覆した。覆された場所と、そこから連鎖して変わった決定が、この回の学びのほとんどになっている。

### 1. 成否の大半を決める成果物は、費用のかかる工程より前のゲートで見せる

解説動画の制作は、人間の 2 つのゲートで区切られている。企画の後の企画ゲート（作るか作らないか）と、プレビューの後の公開ゲート（出すか出さないか）だ。ADR-0009 は、サムネイルを公開ゲートで確定するとしていた。

最初のラウンドで「サムネイルに載せる文言を誰がどこに書くか」を聞いた。推奨は「制作の途中でエージェントが書き、公開ゲートで画像と一緒に見る」だった。運営者の答えは「サムネが 8 割と言われているので、サムネを先に決める」だった。

前倒しの深さには 3 案あった。文言だけを企画に入れる案、画像まで作って企画ゲートで見る案、サムネイル専用のゲートを 1 つ足す案だ。画像まで作る案を採った。文言だけでは、縮小表示でどう見えるかを判断できない。ゲートを足す案は、ゲートを 2 つに絞った既存の決定を崩す。画像生成は 1 枚数セントで、台本・音声合成・描画にかかる費用に比べれば小さい。

**クリック率のように成否の大半を決める成果物は、それを作る費用が後続の工程より安いなら、最初のゲートの判断材料に含める。** 「勝てないサムネイルしか作れない企画」を、描画まで済ませた後で見つけることがなくなる。

### 2. 先行実装を参照するときは、既定値が変わった理由まで読む

運営者は「基本は youtube-automation を参考に」と指示した。同じ運営者が音楽チャンネル向けに Python で作った先行のツールキットで、サムネイル生成の運用が長い。サブエージェントに調べさせると、文字の扱いに 2 つの経路があった。文字入りの画像を AI に描かせる経路（既定）と、文字のない背景に実フォントで重ねる経路（opt-in）だ。変更履歴によると、一度は実フォントの経路を既定にしたが、後で文字入りに戻していた。

戻した理由を issue 本文まで読むと、品質の問題ではなかった。上流の手順書が文字入りを前提に書かれたままで、エージェントがどの章を読んだかで順序がぶれていた。その記述と既定をそろえただけだった。実フォントの経路は「AI がフォント名を再現できず書体がぶれる」問題の解決策として残されていた。

この事実を根拠に、実フォントで重ねる経路だけにする案を推奨した。日本語の誤字はサムネイルとして致命的で、どの画像生成 API も日本語の文字の精度を公式には保証していなかったからだ。運営者は覆し、文字も AI に描かせると決めた。文字を含めた構図で判断したいという理由で、ADR には不採用の案として残した。

**先行実装の既定値は、変更履歴の 1 行ではなく、変更した issue の理由まで読む。** 今回は理由が「品質」ではなく「手順書との整合」だったので、先行実装の既定値にそのまま従う根拠にはならなかった。それでも、最終的に決めたのは運営者の好みだった。推奨の根拠を事実で固めることと、判断を委ねることは別の作業になる。

### 3. 前提の決定が覆ったら、それに依存して決めた答えを聞き直す

最初のラウンドで「1 回に何枚作るか」を聞き、「1 枚ずつ作り、ダメなら作り直す」で確定していた。根拠は、文字を後から重ねるなら文言の直しに画像生成が要らず、背景だけを作り直せば済むことだった。

文字も AI に描かせると決まった時点で、この根拠は消えた。文言を 1 文字直すにも画像を作り直すことになり、誤字も偶然で出る。そこで確定済みの問いを「候補を N 枚作り、企画ゲートで人間が選ぶ」に改めて聞き直し、運営者も同意した。この変更で、候補から 1 枚を選んだ事実をどう記録するかという問いが新しく生まれた（4 節）。

**ある答えを確定したら、その答えの根拠がどの決定に依存しているかを覚えておく。** 依存先が覆ったら、確定済みでも聞き直す。決定の木の上流を変えると、下流の答えは静かに古くなる。

### 4. 選択はゲートの記録に混ぜず、独立した追記型の事実にする

候補を複数作ると、どれを選んだかを記録する必要がある。案は 2 つあった。

- 企画ゲートを承認するコマンドに、選んだ候補を引数で渡し、ゲートの記録の表に列を足す
- 選ぶ操作を独立した CLI にし、「サムネイルの選択」として追記型（append-only）の記録に積む

後者を採った。ゲートの記録は、BGM 動画の側と同じ形（id・ゲート・時刻）にそろえると決めてあったからだ。追記型にすると、公開ゲートで作り直した候補を選び直す操作と、人間が用意した画像に差し替える操作（画像を候補に足して同時に選ぶ）が、同じ「選択」の経路にまとまる。鮮度の検査も「公開ゲートの承認が最後の選択より新しいこと」の 1 本で済む。

**ゲートの承認に付随する選択は、承認の記録の列ではなく、承認より前に積む独立の事実にする。** 承認の記録の形を種類ごとに変えずに済み、選び直しの経路も 1 本になる。

### 5. 「core は LLM を呼ばない」の線は、文言や判断を生むかどうかで引く

運営者は、画像生成の経路として、Gemini の画像生成 API に加えて codex CLI 経由も v0.1 で作ると決めた。codex CLI は ChatGPT のサブスクリプションで認証して画像を生成できる。ただし codex は画像生成の API ではなく、LLM で動くエージェントだ。nyaucast には「core（MCP tool の処理本体）は LLM を呼ばない。文言の生成と判断は、tool を呼ぶ側のエージェントの仕事にする」という ADR-0002 がある。

調べ直すと、この線引きはすでに曖昧だった。チケット本文には「生成 API の呼び出しは primitive tool（単一の操作を行う細粒度の MCP tool）に置いてよい（ADR-0002 の運用）」と書いてあった。しかし ADR-0002 自身にはその一文が無かった。前日に音声合成の Gemini TTS を tool から呼ぶと決めたときも、ADR は改訂されていなかった。

そこで ADR-0002 を次のように改訂した。音声合成と画像生成のモデルは、エージェントが渡した文言と描写をメディアに変えるだけで、文言も判断も生まない。だから「LLM を呼ぶ」には当たらない。codex CLI も、tool が組み立てた決まった形のプロンプトと参照画像を渡し、画像の生成だけに使う限り同じ扱いとする。文言の生成・候補の選別・成否の判断はさせない。

逆の案として、「codex はエージェントの側で動かし、できた画像を tool に登録だけさせる」も検討した。ADR の線引きは単純になる。しかし、プロンプトの禁止語の検査や版権を避ける定型句を、tool が保証できなくなる。youtube-automation では、お手本の画像に写っていた署名がそのまま描かれた事故や、無関係な語がプロンプトに混入した事故が起きている。

**「LLM を使うか」ではなく「その呼び出しが文言や判断を生むか」で境界を引く。** 前者で引くと、生成モデルや agent CLI が出てくるたびに例外が増える。後者なら同じ基準で説明できる。

### 6. 生成モデルの調査は、まず今日の日付で生存確認をする

画像生成 API の調査で最初に分かったのは、候補に挙げそうなモデルのうち 2 つが既に使えないことだった。Imagen 4 は 2026-08-17 に終了していた。`gemini-2.5-flash-image` は調査したその日（2026-10-02）に終了する予定だった。生き残っていたのは `gemini-3.1-flash-image` などで、16:9 の 1K で 1 枚 $0.067 だった。

ほかに、方針に効いた事実が 2 つあった。どの画像生成 API も、日本語の文字の精度を公式には保証していない。YouTube のポリシーは、生成 AI でサムネイルを作ることを「制作の補助」とし、AI 生成の開示を求めていない。

モデルの世代交代がこの速さなので、前日の音声合成と同じく、画像生成もアダプタの境界の後ろに置いた。モデル名はチャンネル設定とアダプタの中だけに閉じ込める。

**生成モデルを選ぶ調査では、価格や品質を比べる前に、候補の終了予定を公式の廃止予定ページで確かめる。** 記憶やブログ記事にあるモデル名は、数か月で使えなくなっている。

<a id="codec-distribution"></a>

## エージェント向けの手順書を npm パッケージに同梱し、tool との版のずれを構造で消した話

knowledge codec の置き場と、下流のリポジトリへの配り方を決めたときの学び。knowledge codec は、エージェント（Claude Code や Codex）が読む手順書で、「いつ、どの MCP tool を、どう使うか」を書く。SKILL.md 形式の skill として書く。nyaucast は、区間をまとめて回す粗い tool を持たないと決めているので、制作の手順を持てるのは codec だけになる。v0.1 では解説動画の lifecycle を歩く `explainer-lifecycle` と、SNS への投稿の作法を書く `distribution` の 2 本を書く。下流とは、nyaucast を使って運営するチャンネルごとのリポジトリのことだ。チケットの問いは 5 つあった。リポのどこに置くか、どう配るか、Codex でも読めるか、codec と tool の版がずれたらどうするか、どう検証するかだ。

- 決定の記録: [knowledge codec の置き場と下流への配り方](https://github.com/daiki-beppu/nyaucast/issues/471)
- ADR と用語集の更新: [PR #498](https://github.com/daiki-beppu/nyaucast/pull/498)（ADR-0010 を足し、用語集の「knowledge codec」に配り方を 1 文加えた）

質問は 3 ラウンドで 9 問出した。運営者は推奨をすべて受け入れたが、途中で 2 回、調べ直しを求めた。「node_modules に含めるのが流行っているみたいなので確認して」と「Hono がどうしているかも確認」だ。この 2 つの調べ直しで、推奨の根拠が大きく固まった。

### 1. 版のずれは、警告で気づかせるより、同じパッケージから出して起きない形にする

codec で一番避けたい事故は、codec と MCP tool の版がずれて、**codec が存在しない tool を呼ぶ**ことだ。旧仕様には、この事故への備えが決めてあった。codec は skills CLI（GitHub のリポから skill を入れる外部ツール）でリポを直接指定し、全リポ共通のグローバルな場所に入れる。nyaucast の MCP server が起動するたびに、パッケージに同梱した codec と、入れてある codec の版を比べ、古ければ警告する。版の比べ方まで決めていた。パッケージの版で比べると、codec が変わっていないリリースでも警告が出て狼少年になる。そこで codec に独自の版を振り、冒頭にエージェント向けの変更履歴を置く、という内容だった。

1 つのずれに対して、仕組みが 3 つ要っていた。独自の版、変更履歴、起動時の比較だ。どれも、codec と tool が別々の経路で届くことから生まれている。

今回は経路を 1 本にした。codec を nyaucast の npm パッケージの `skills/` に同梱する。下流リポは nyaucast を版を固定して devDependency に入れ、MCP server も codec も、その `node_modules` の同じパッケージから使う。lockfile 1 つで両方の版が決まるので、ずれが起きる場所が無い。上の 3 つの仕組みはすべて要らなくなり、版を上げる操作も `package.json` の 1 行と install で済む。

**2 つの成果物の版がずれる事故には、ずれを検知する仕組みを足す前に、同じ配布物に入れて経路を 1 本にできないかを考える。** 検知の仕組みは、それ自体が版の振り方や警告の出し方という新しい決めごとを連れてくる。

### 2. 複数のエージェントに配るなら、どれもが自動で読む面の共通部分から選ぶ

Claude Code と Codex の両方で読めることが条件だった。調査で分かった事実は次のとおり。

| 面                           | Claude Code              | Codex                            |
| ---------------------------- | ------------------------ | -------------------------------- |
| リポ内の skill ディレクトリ  | `.claude/skills/` を読む | `.agents/skills/` を読む         |
| symlink                      | たどる                   | たどる                           |
| `node_modules`               | 自分では探さない         | 自分では探さない                 |
| MCP の prompts               | スラッシュコマンドになる | 実装が見当たらない               |
| MCP server の `instructions` | 自動で読む               | 自動で読む（512 文字以内を推奨） |

MCP の prompts で手順書を配る案は、Codex に実装が無いので外れた。Claude Code の plugin で skill と MCP の設定をまとめて配る案は、Codex でローカルの MCP が動くかを確かめられず、pnpm の lockfile では plugin の依存が入らないことも分かって外れた。残ったのは、両方が読むリポ内の skill ディレクトリと、両方が自動で読む `instructions` の 2 つだった。

そこで、下流リポには相対 symlink を 2 本置いてコミットする。`.agents/skills/<codec>` が `node_modules/nyaucast/skills/<codec>` を指し、`.claude/skills/<codec>` は `.agents/skills/<codec>` を指す。`node_modules` は gitignore したままでよい。install するたびに、リンク先の中身が固定した版に合わせて入れ替わる。`instructions` には、codec の名前とどの区間で読むかだけを書いて、codec を読まずに tool を直接呼ぶエージェントへの道案内にする。

**配り先のツールが複数あるときは、ツールごとの便利な機構ではなく、全部が黙って読む場所の共通部分に置く。** 便利な機構は片方にしか無いことが多く、片方専用の経路を 2 本持つと、版のずれの問題が経路の数だけ戻ってくる。

### 3. 「流行っている」方式は、提供する側と利用する側を分けて確かめる

運営者の「node_modules に含めるのが流行っているみたい」という一言で調べ直すと、提供する側と利用する側で状況が違っていた。

提供する側の書き方は、ほぼ揃っていた。パッケージに `skills/<名前>/SKILL.md` を置き、`package.json` の `files` に `skills` を入れる。TanStack の Intent、antfu の skills-npm、Prisma 8 の rc 版、`chrome-devtools-mcp` がこの形で同梱している。`chrome-devtools-mcp` は、MCP server と CLI と skill を 1 つのパッケージで出していて、nyaucast と同じ形だった。宣言と中身が食い違う例もあった。`@vueuse/skills` は `files` に `skills` を宣言しているのに、npm の tarball には skill が入っていなかった。調査では、各パッケージの tarball を実際に取得して中身を確かめている。

利用する側の読ませ方は、3 つに割れていた。

- 相対 symlink をコミットする（skills-npm v2。skills CLI の RFC #2323 も同じ方向）
- `node_modules` からコピーする（skills CLI の `experimental_sync`。正式化の PR は未マージ）
- AGENTS.md に「このコマンドで読め」と書く（TanStack Intent。alpha）

nyaucast はこの差に合わせて決めた。提供する側は、揃った書き方にそのまま合わせる。そうすれば、利用する側の標準がどれに落ち着いても見つけてもらえる。利用する側は、まだ割れているツールには依存せず、symlink を手で作る。その形を RFC と同じにしておけば、標準が固まった時点で、下流リポはそのツールに置き換えられる。

**流行を確かめるときは、「何が揃っていて、何がまだ割れているか」を、配る側と使う側に分けて見る。** 揃っている側には合わせ、割れている側には依存しない。

### 4. 有名プロジェクトの配り方は、自分が避けたい事故に照らして読む

Hono（Web フレームワーク）は、skill を npm に同梱していなかった。`hono` にも `@hono/cli` にも SKILL.md は無い。skill は別のリポ（`honojs/skills`）に置き、Claude Code の plugin marketplace か skills CLI で配っている。ほかに、ドキュメントを `llms.txt` で出している。この構造では、ライブラリと skill の版が連動しない。

Hono にとっては、それで困らないのだろう。skill の中身は、版が変わってもほぼ通用するフレームワークの使い方だからだ。nyaucast の codec は違う。tool の名前を挙げて「次はこれを呼ぶ」と書く手順書なので、版のずれがそのまま「存在しない tool を呼ぶ」事故になる。Next.js も別の道を選んでいた。版に一致したドキュメントを `node_modules/next/dist/docs/` に同梱し、AGENTS.md にその参照を書く。知識は版に合わせ、ワークフローの skill だけを別に配っている。

**有名プロジェクトの方式は、「誰がやっているか」ではなく「その方式がどの事故を許しているか」で読む。** 自分が一番避けたい事故を許す方式なら、どれだけ有名でも採らない。

### 5. 決定が成り立つ前提は、ADR に再検討の条件として書く

推奨を出し終えたところで、運営者から「MCP はローカルの想定で合ってる？」と聞かれた。合っている。今の MCP server は stdio だけで動き、エージェントが下流リポの中で子プロセスとして起動する。版のずれが起きないという 1 節の結論は、まさにこの前提の上に立っていた。MCP server をリモートで動かすことになれば、server の版は下流の lockfile から外れ、ずれが戻ってくる。そこで ADR-0010 の Consequences に「リモート MCP にするなら配り方を決め直す」と書いた。

この質問への最初の返事はうまくいかなかった。関連チケットの名前を 3 つ挙げて、クラウド VM で動かす場合や v0.2 の構想まで説明した結果、運営者の返事は「？」の 1 文字だった。2 回目は「はい、ローカルで合っている」と「それが版の一致に効いている」の 2 行に絞り、それで通じた。

**決定の結論を支えている前提は、ADR に「この前提が崩れたら見直す」という条件として書いておく。** 前提を確かめる質問には、まず yes か no と、それが結論のどこに効くかの 2 点だけで答える。周辺の事情は、聞かれてから足せばよい。

<a id="tiktok-out-of-gate"></a>

## 「API で投稿できないなら TikTok はやらない」と決め、リリースのゲートを 3 SNS に減らした話

TikTok への配信を、v0.1.0 のリリースゲートでどう扱うかを決めたときの学び。nyaucast の v0.1.0 のゲートは、自分の解説動画チャンネルで動画を 1 本作り、YouTube・TikTok・Instagram・X の 4 つの SNS に公開するまでを nyaucast だけで走りきること（dogfood）だった。調べてみると、TikTok は自分専用の投稿ツールを公式に認めていなかった。最終的に TikTok をゲートから外し、ゲートを 3 SNS に減らした。

- 決定の記録: [TikTok の配信経路と v0.1.0 ゲートでの扱い](https://github.com/daiki-beppu/nyaucast/issues/472)
- ADR と用語集の更新: [PR #503](https://github.com/daiki-beppu/nyaucast/pull/503)（ADR-0009 の決定 2・3・5 を改訂）
- 先送りした先: [[v0.2] TikTok への配信（本番のアプリ審査と Direct Post の監査を含む）](https://github.com/daiki-beppu/nyaucast/issues/502)

### 1. 「監査が要らない」と書く前に、その経路にかかる門を全部数える

ADR-0009（SNS 配信の方針の決定）には、「TikTok は、監査なしで公開まで運用できる Upload（受信箱への下書き）方式から始める」と書いてあった。TikTok の Content Posting API には 2 つの方式がある。

- Direct Post: API から直接公開する。使うには監査（audit）が要る
- Upload: 動画をアプリの受信箱に下書きとして送り、人間がアプリから仕上げて投稿する。監査は要らない

ここまでは正しかった。ところが、一次情報を調べると、門はもう 1 つあった。Upload が使う `video.upload` スコープも、本番のアプリ審査（App Review）を通らないと使えない。審査なしで使えるのは Sandbox だけだ。そして、審査の基準と投稿ガイドラインには、次の一文がある。

- 審査の基準: "Apps must not be for private or personal use."
- 投稿ガイドラインの不可の例: "A utility tool to help upload contents to the account(s) you or your team manages."

自分のチャンネルにだけ投稿する nyaucast は、この不可の例にそのまま当てはまる。「監査が要らない」は Direct Post の監査についてだけの話で、アプリ審査という手前の門を数えていなかった。調べると、もう 1 つ食い違いが出た。Upload の初期化のリクエストには投稿の情報（`post_info`）が無い。そのため、AI 生成の開示（`is_aigc`）は Direct Post でしか付けられない。ADR の「AI 生成であることは全 SNS で常に開示する」とも合わない。

**外部のプラットフォームについて「この方式なら○○が要らない」と書くときは、その方式にかかる門（スコープの審査、アプリの審査、方式ごとの監査）を全部並べ、どの門の話かを書く。** 1 つの門が無いことを、経路全体が開いていることと取り違えやすい。

### 2. 代替の経路が原則を崩すなら、ゲートの数字のほうを動かす

最初の推奨は、ゲートの「4 SNS」を守る方向に寄っていた。

- まず Sandbox アプリで、受信箱への Upload を試す
- だめなら、nyaucast は素材と投稿文を作るだけにして、人間が TikTok アプリから手で投稿する
- どちらの場合も、人間が投稿した URL を記録すれば完走とみなす。dogfood の定義には「TikTok だけ人間が投稿する」例外を書き足す

運営者の返事は「api 経由できないなら tiktok はいらないかも」だった。これで選択肢がまとめて片づいた。振り返ると、この推奨は ADR-0009 の別の決定とぶつかっていた。その決定は「投稿の実行は決定的な API クライアントの tool が担い、ブラウザ操作による投稿はしない」というものだ。手で投稿した分をゲートに数えると、この原則に TikTok だけの例外ができる。Sandbox の案も同じ問題を抱えていた。受信箱から投稿するのは結局人間なので、成功しても「API で投稿した」ことにはならない。

ゲートの「4 SNS」は、方針を決めた時点の見積もりにすぎない。一方、「投稿は tool が決定的に行う」は、critical regression（リリースを止める欠陥。投稿先アカウントの取り違えなどの誤公開を含む）を防ぐための原則だ。

**ゲートを満たす代替の経路が、プロジェクトの原則に例外を作るなら、例外を足すのではなく、ゲートの数字を動かす。** 数字は見積もりで、原則は事故を防ぐための決まりだ。

### 3. 「窓口は開けておきたい」のような曖昧な希望は、コストの違う選択肢に割って選んでもらう

運営者の返事には続きがあった。「やりたい人用に窓口は開いておきたい気持ちもあるが」。この「窓口」は、どうとでも取れる。そこで、v0.1 で払うコストの順に 3 つに割って聞いた。

- (A) 設計の上でだけ開けておく。投稿の状態モデルと SNS ごとの API アダプタの境界を、SNS を後から足せる形にする。TikTok のコードは書かない
- (B) 審査に通ったアプリを持つ人だけが有効にできる、opt-in の TikTok アダプタを v0.1 で実装する
- (C) SNS を問わず、素材を書き出して人間が投稿し、URL を記録する汎用の経路を作る

(B) は、ゲートに要らないものを v0.1 で作ることになり、「1 リリース 1 テーマ」の方針に反する。(C) は、直前に決めた「API でなければやらない」と矛盾する。推奨は (A) にし、そのまま採用された。

**曖昧な希望は、そのまま要件に写さない。v0.1 で払うコストの違う具体案に割り、既存の決定と矛盾しない一番安い案を推奨する。** 「開けておく」の多くは、境界を閉じないことで足りる。

### 4. 審査に落ちる理由がプロダクトの形にあるなら、その形が変わるまで申請しない

本番審査を v0.1 と並行して出してみる案もあった。落ちても失うのは手間だけ、という考え方だ。これは採らなかった。

TikTok の審査が退けているのは「私的利用のアプリ」だ。運営者には、nyaucast を将来は有償のツールとして公開する意向がある。そうなれば、複数のクリエイターが認可して使うアプリとして審査に出せ、不可の例から外れる可能性がある。今出すと、自チャンネル専用のアプリとして審査されて落ちる見込みが高い。審査を通るかどうかで実装の方式（Upload か Direct Post か）も変わるので、審査と実装は 1 本の v0.2 の issue にまとめた。着手の条件は「有償配布の形が決まること」にした。

**審査に落ちる理由が、自分のプロダクトの形（誰が使うか）にあるなら、試しに出すのではなく、形が変わる時点を着手の条件にして先送りする。**

### 5. スコープを削る決定は、数字が書かれた場所と、消える分岐を数えてから閉じる

TikTok を外すと、「4 SNS」という数字が書かれた場所を全部直すことになる。`git grep` で探すと、ADR-0009（タイトル、決定 2・5）、用語集の「dogfood」と冒頭の説明、エージェント向けの規約ファイル（CLAUDE.md）、README の 4 か所にあった。計画の地図（GitHub の issue）のタイトル・目的地・各チケットの本文にもあった。

同時に、後に続く 3 つの決定（認証の置き場、投稿の状態モデル、公開ゲートの CLI）から、TikTok のためだけにあった論点が消えた。

- 受信箱に送った後の「人間の投稿待ち」という状態。人間が投稿したかを API で観測できるかも未確認だった
- 受信箱は 24 時間で 5 件までという上限の計算
- Direct Post の監査の UX 要件（公開範囲を既定値なしで人間に選ばせる、など）
- TikTok だけ hex 表現で送る PKCE（OAuth の認可コードを守る仕組み）の challenge

どれも実装してから外すと、状態モデルとテストまで巻き戻ることになる。

**スコープを削る決定は、計画の段階で、数字が書かれた全部の場所と、後に続く決定から消える分岐を数えてから閉じる。** 消えた分岐は、後続のチケットの本文からも同じときに外す。外し忘れると、次のセッションが消えたはずの論点を拾い直してしまう。

<a id="state-placement"></a>

## 「Devin の VM でも動かしたい」を、決めることと確かめることに分け、v0.1 は Mac に残した話

nyaucast の状態を、実行環境の外に置くかどうかを決めたときの学び。状態とは、local store（チャンネルごとの SQLite 互換の DB。企画・ゲートの承認・投稿の状態などを持つ）と、生成した成果物のファイルのことだ。実行環境は、ローカルの Mac と、Devin（Cognition のクラウドで動くコーディングエージェント）の VM のような使い捨てのクラウド VM を指す。状態を外に置けば、別の環境のエージェントが手順を頭から歩き直すだけで続きを進められる。nyaucast は、再開の専用の API を持たず、tool が冪等に受け止める形をとっているからだ。結論として、v0.1 は Mac だけで動かし、引き渡しは v0.2 に回した。Instagram に渡す動画の一時公開の置き場だけを、GCS から R2 に変えた。

- 決定の記録: [実行環境の間で引き渡せるように、状態を実行環境の外に置く](https://github.com/daiki-beppu/nyaucast/issues/473)
- ADR の更新: [PR #507](https://github.com/daiki-beppu/nyaucast/pull/507)（ADR-0009 の決定 3・4 を改訂）
- 先送りした先: [[v0.2] 実行環境の間で引き渡せるように、local store と成果物を実行環境の外に置く](https://github.com/daiki-beppu/nyaucast/issues/505)、[Devin の VM で nyaucast を動かす検証](https://github.com/daiki-beppu/nyaucast/issues/506)

### 1. 大きな問いに含まれている、答えが変わらない小さな問いは、先に切り出して決める

チケットには 7 つの論点があった。local store の置き場、成果物の置き場、認証情報、ゲートの承認、定期実行、同時実行、版のそろえ方だ。この中に 1 つ、外に置くかどうかと関係なく答えが要る問いが混ざっていた。Instagram に渡す動画の一時公開の置き場だ。Instagram Login 方式の API は動画を直接受け取らず、公開 URL を渡す必要がある。Mac だけで動かしても、どこかに一時的に公開する場所が要る。

そこで、この問いを最初のラウンドで大きな問いと並べて出し、独立に決めた。候補は R2 と GCS の署名付き URL で、R2 は外向きの転送が無料だ。決め方には、事前の調査で残った未確認の事実（Meta がクエリ文字列付きの URL を受け付けるか）を織り込んだ。

- 受け付けないときの代わりの方法（推測できないキーで一時的に公開する）を、決定に最初から含める
- 実機での確認は、実装 ticket の受け入れ条件に入れる

置いた動画の後始末も、「投稿が完了したら tool が消す」と「R2 のライフサイクルルールで 7 日後に消える」の両方にした。前者だけだと、失敗や中断で残ったものが消えない。

**大きな問いを決める前に、その答えに左右されない小問を探して先に決める。** 未確認の事実が残る決定には、外れたときの代わりの方法と、確かめる場所（受け入れ条件）を一緒に書く。

### 2. 「後で移せるように」の約束は、今のコードで払うコストを測ってから結ぶ

推奨は「v0.1 は Mac だけ」だった。v0.1.0 のゲート（解説動画を 1 本作り、3 つの SNS に公開するまでを nyaucast で走りきること）は Mac 1 台で完走できる。外に置くと、次の 5 つがまとめて v0.1 に乗る。

- オフラインで動かない
- DB ファイルを `cp` するバックアップの作り直し
- 同時実行の排他
- VM での secret の扱い
- VM で動画処理のライブラリ（node-av）と headless Chrome が動くかの未検証

代わりに、後から移せるように 2 つの約束を結んだ。DB を開く口を 1 か所にして接続先の URL を差し替えられるようにすることと、成果物をチャンネルルートからの相対パスで記録することだ。約束を ADR に書く前にコードを確かめると、DB を開く処理（`createClient`）はすでに 1 か所にしか無かった。成果物の path を書く tool は、まだ 1 つも無かった。どちらの約束も、今のコードには追加のコストがかからず、これから書く tool への制約になるだけだった。

**「将来の移行を塞がない」約束は、今のコードで実際に何を変える必要があるかを確かめてから結ぶ。** コストがかからない約束なら、迷わず ADR に書ける。コストがかかるなら、それはもう「今やる移行」の一部だ。

### 3. 「〜で動かしたい」と聞いたら、頭を動かすのか道具を動かすのかを先に分ける

ここで判断が 1 度外れた。運営者の懸念は「cloud VM で動かしたい時に Turso で大丈夫か」だった。Turso は libSQL（SQLite のフォーク）をネットワーク越しに使えるデータベースで、nyaucast はすでに libSQL を使っている。事実を並べて答えると、運営者は「DB を MCP で読み書きさせることで、ローカルとクラウドの中間点のようなものを作るイメージ」と続けた。

私はこれを、2 つの構成のどちらかと読んだ。

- (i) Mac 上の nyaucast を remote MCP として公開し、クラウドのエージェントはそこへつなぐだけ
- (ii) 状態だけを Cloudflare Worker の上の API に置く

そのうえで、クラウド VM を使いたい理由を聞いた。返事は「devin がすごいんだって」。私はこれを「エージェントとして Devin を使いたい」と読み、(i) を推して、Devin の remote MCP の対応状況を調べるサブエージェントまで走らせた。(i) なら、状態も重い処理も認証情報も Mac に残り、Turso の不安自体が消えるからだ。

運営者の次の返事で、前提が外れていたと分かった。「agent がということではなく、devin の VM でこのツールが問題なく動くかどうか、かつナレッジが共有できるかどうか」。問いは、エージェント（頭）をどこで動かすかではなく、nyaucast というツール（道具）が Devin の VM の中で動くか、だった。走らせていた調査は止めた。

外れた原因は、理由（なぜ VM か）を聞いて、何をどこで動かすかを聞かなかったことにある。「Devin がすごい」は、頭の話とも道具の話とも読める。

**「〜で動かしたい」と言われたら、動かすのがエージェント（考える側）か、ツール（実行する側）か、状態か、を先に分けて聞く。** 理由を聞いても、どれを動かしたいかは決まらない。

### 4. 「動くか分からない」という不安は、grilling で決めずに検証の task にする

問いが「Devin の VM で動くか」と分かると、これは決めることではなく、確かめる事実だった。今の依存（libsql・MCP SDK・drizzle・Google の認証ライブラリなど）を見ると、危ないと見ていた node-av と headless Chrome は、描画が未実装なのでまだ依存に入っていない。そこで、推奨と決定を次のように分けた。

- 決めること: v0.1 の要件にするか（しない）、共有したいのは何か（local store の中身と成果物のファイル）
- 確かめること: Ubuntu と macOS の VM で、今の nyaucast と、node-av と headless Chrome の最小スクリプトが動くか。これを HITL（人間が回す）の task として地図に足し、7 項目の手順を書いた。Devin のアカウントを持っているのは運営者なので、エージェントには回せない

Turso の不安も同じ扱いにした。リモートの DB で起動時のマイグレーションが動くか、トランザクションの 5 秒の制限、`cp` バックアップの代わり、クエリごとの往復の遅延、Free プランで使われない DB のアーカイブ、オフラインでの振る舞い。どれも小さなスパイクで確かめられる事実なので、v0.2 の issue に検証項目として書いた。

**「大丈夫か分からない」は、決定の材料が足りないのではなく、確かめていない事実がある状態だ。** 決めることと確かめることを分け、確かめることは検証の task にする。検証の結果が今の決定を変えないなら、要件にはせず、次の決定の材料として使う。

### 5. 認証トークンを DB に置くかは、「トークンが入れ替わるか」と「置き場が何か所あるか」で決まる

途中で、運営者から「OAuth の key を DB に突っ込むのは悪手？」と聞かれた。ADR-0009 は、静的なクライアントのシークレットを 1Password に、更新されるトークンをアカウントごとに権限 0600 のファイルに置くと決めている。

答えは「条件付きで悪手ではない。むしろ、複数の環境で動かすなら DB の方が正しくなる」だった。X の OAuth 2.0 の refresh token は、使うたびに入れ替わる。トークンをファイルで各環境に持つと、Mac で更新した瞬間に Devin 側のトークンが無効になる。2 つの環境が同時に更新すると、片方の新しいトークンが失われて認証が壊れる。DB なら `UPDATE … WHERE version=?` で、勝った側だけが書く形にできる。

ただし、DB に入れるには 4 つの条件が要る。

- 暗号化し、鍵は DB の外に置く。DB の接続トークンが 1 つ漏れただけで、全 SNS のアカウントを乗っ取られる構造を避ける
- 読み取りの面（read model と MCP）には出さない。エージェントが読めると、ログや会話に流れる
- バックアップに入る前提にする
- 静的なクライアントのシークレットは入れない

v0.1 は Mac 1 台なので今のファイルのままでよく、この結論は認証を扱う別のチケットへの申し送りにした。

**トークンの置き場は、「使うたびに入れ替わるか」と「置き場が何か所あるか」で決まる。** 入れ替わるトークンが 2 か所以上で使われた瞬間に、それは設定ではなく、排他つきで書く共有の状態になる。

<a id="credentials"></a>

## SNS の認証情報の置き場を決め、投稿先の取り違えを設定ではなく照合で防ぐことにした話

YouTube・Instagram・X の 3 つの SNS について、認証情報をどこにどう置くかを決めたときの学び。nyaucast では、コンテンツの人格の単位を「チャンネル」、SNS 上の投稿先で認証の単位を「アカウント」と呼ぶ。1 つのチャンネルが複数の SNS のアカウントを束ねる。問いは 5 つあった。トークンの置き場、クライアントのシークレットの解決、アカウントとチャンネルの対応づけ、`nyaucast auth` コマンドの形、トークンの更新に失敗したときの検知だ。そこに、前のチケットから申し送られた 2 つが加わった。codex CLI のログイン状態の扱いと、R2 のアクセスキーの置き場だ。

- 決定の記録: [認証情報の置き場とアカウント単位の auth](https://github.com/daiki-beppu/nyaucast/issues/464)
- ADR の更新: [PR #509](https://github.com/daiki-beppu/nyaucast/pull/509)（ADR-0009 の決定 6 を改訂し、用語集の「アカウント」に識別の方法を足した）

### 1. ADR とコードが食い違っていたら、どちらに合わせるかを決める前に、手元の実データを数える

出発点には食い違いが 1 つあった。ADR-0009 はトークンを `~/.config/nyaucast/credentials/` にアカウント別に置くと決めている。一方、既に動いている YouTube の認証のコードは `~/.config/nyaucast/<channel>/` に `client_secrets.json` と `token.json` を置いていた。どちらに合わせても理屈は立つ。コードに合わせるなら ADR を改訂し、ADR に合わせるなら既存のトークンを移す仕組みが要る。

比べる前に `~/.config/nyaucast/` の中身を見ると、`channels.json`（チャンネルの一覧）しか無かった。YouTube のトークンは、まだ 1 つも発行されていなかった。移すものが無いので、ADR に合わせる側のコストはゼロになり、問いは比べるまでもなく片づいた。

**決定とコードが食い違ったら、コードだけでなく、そのコードが作ったデータが実際にいくつあるかを数える。** 移行のコストはコードの量ではなく、データの量で決まる。ゼロなら、決定に合わせて書き直すだけで済む。

### 2. ファイルのパスの切り方は、今のスコープで何が 1 つに決まるかで選ぶ

置き場を ADR に合わせると決めたあと、ファイルの単位を 2 案から選んだ。

- (a) `credentials/<channel>/<platform>.json`
- (b) `credentials/<platform>/<アカウント ID>.json`

(b) は、1 つのチャンネルが同じ SNS に複数のアカウントを持つときに要る形だ。v0.1 にはそういうチャンネルが無く、チャンネルと SNS の組でアカウントが 1 つに決まる。そこで、ADR に「v0.1 では 1 チャンネルが 1 つの SNS に持つアカウントは 1 つまで」と前提を書いたうえで (a) を選んだ。

運営者からは「YouTube をやらないケースを考えたら (a) がいいのかな？」と聞かれた。(a) なら、YouTube を持たないチャンネルでは `youtube.json` が作られないだけで済む。どのアカウントを持つかはチャンネル設定に宣言し、宣言は SNS ごとに任意にした。宣言していない SNS への投稿は、SNS ごとの API の処理（アダプタ）に入る前で拒む。

**パスの階層は、将来ありうる多重度ではなく、今のスコープで何が 1 つに決まるかで切る。** その前提を決定に書いておけば、崩れたときにどこを直すかが分かる。

### 3. 投稿先の取り違えは、設定の宣言ではなく、SNS への問い合わせとの照合で防ぐ

nyaucast は、リリースを止める欠陥を 3 種類に限っている。その 1 つが「誤公開」で、投稿先のアカウントの取り違えを含む。チャンネル設定でアカウントとチャンネルを対応づけるだけでは、この事故を防げない。設定に書いたアカウントと、トークンが実際に指すアカウントがずれる経路が残るからだ。たとえば、ブラウザで別のアカウントにログインしたまま `nyaucast auth` を実行すると、そのアカウントのトークンが保存されてしまう。

そこで、次の 2 つを決めた。

- 宣言の識別子は、表示名の handle ではなく、SNS 上で変わらない ID にする。YouTube のチャンネル ID（`UC…`）、Instagram と X の user id だ。handle は変えられるので、照合の鍵に使えない
- 照合を 2 回行う。1 回目は `nyaucast auth` の完了時で、取得したトークンで「自分は誰か」を SNS に問い合わせ、宣言と違えば保存しない。2 回目は投稿の直前で、トークンに記録した ID と宣言とを比べ、違えば投稿しない

**取り違えの事故は、設定の正しさを信じる形ではなく、外部の実際の状態に問い合わせて照合する形で防ぐ。** 照合の鍵には、人が変えられる名前ではなく、変わらない ID を使う。

### 4. 外部サービスと用語が重なって違和感が出たら、具体例を見せ、名前を変えるかを別の問いに切り出す

(a) に決めたあと、運営者から「channel っていうディレクトリ名はやや実態とズレる？」と聞かれた。私は用語集を根拠に答えた。nyaucast の「チャンネル」は複数の SNS のアカウントを束ねる単位で、YouTube のチャンネルはアカウントとして扱うと定義済みなので、ズレてはいない、と。

すると、運営者は「YouTube がないケースでは？」と聞き直した。定義の説明では、違和感は消えていなかった。YouTube を持たないチャンネルで「チャンネル」と呼ぶ姿を、具体的に思い描けていなかったのだと思う。そこで、2 つのことをした。

- X と Instagram だけのチャンネルのディレクトリを実際に書いてみせた（`credentials/tech-explainer/` の下に `instagram.json` と `x.json` だけが並ぶ）
- 違和感の対象はディレクトリ名ではなく、ドメイン用語の「チャンネル」そのものだと切り分けた。この用語は、用語集・チャンネルの一覧・チャンネルのリポジトリ・チャンネル設定に広く使われている。名前を変えるなら別の issue にする、と選択肢を出した

運営者の答えは「このままでいい」だった。

**用語に違和感があると言われたら、定義で説得する前に、違和感の出る具体例をそのまま書いてみせる。** それでも残る違和感は、局所的な名前の問題ではなく用語そのものの問題なので、今の問いとは分けて扱う。

### 5. 将来に移す予定がある状態は、置き場を決めるときに読み書きの口を 1 つにしておく

前のチケットで、v0.1 は Mac だけで動かし、複数の環境で動かすときは、入れ替わるトークンを共有の DB に移すと決めていた（[状態の置き場のエントリ](#state-placement)）。今回は v0.1 なので、トークンはファイルのままでよい。ただし、トークンの読み書きと更新を、SNS をまたぐ 1 つのモジュールにまとめ、アダプタはファイルの場所を知らない形にした。こうしておけば、置き場を DB に変えるとき、直すのはそのモジュールだけで済む。

ほかの静的なシークレットも同じ考え方で扱った。各 SNS のクライアントのシークレット、Gemini の API キー、R2 のアクセスキーだ。どれも 1Password の参照を `op read` で解決し、同じ名前の環境変数があればそちらを優先する。環境変数は、将来 VM や CI に移すときの入口になる。一方、codex CLI のログイン状態は codex 自身の管理に任せ、nyaucast は実行の前にログインを確かめるだけにした。VM への渡し方は v0.2 の issue に申し送った。

**今は動かさないが将来移す状態は、今の置き場で実装するときから、読み書きの口を 1 か所にしておく。** 移す日に払うコストが、その 1 か所の差し替えに限られる。

<a id="post-state"></a>

## 投稿の状態を追記型の事実から導き、予定時刻の実行は「定期実行なし」で始めると決めた話

SNS への投稿の状態の持ち方と、予定時刻が来た投稿の実行方法を決めたときの学び。nyaucast では、1 本の動画ファイル（カット）を 1 つの SNS のアカウントへ公開する単位を「投稿」と呼ぶ。投稿は予定時刻を持ち、時刻が来たら公開する。問いは 6 つあった。状態をどの記録から導くか、公開前の検査をどこに置くか、YouTube の予約投稿をどう使うか、予定時刻からの遅れをどこまで許すか、定期実行をどう組むか、投稿文をどこで検証するかだ。続いて、二重投稿の防ぎ方、エラーの分け方、人間が投稿ごとに使うコマンド、Instagram に動画を渡す手順を決めた。

- 決定の記録: [投稿の状態モデルと予定時刻の実行](https://github.com/daiki-beppu/nyaucast/issues/469)
- ADR の更新: [PR #512](https://github.com/daiki-beppu/nyaucast/pull/512)（ADR-0009 の決定 4 を改訂し、投稿の状態と実行を決定 9 として足した。用語集に「予定時刻」「投稿の試行」「許容時間」「確認待ち」を足した）
- 先送りした定期実行: [[v0.2] 予定時刻が来た投稿を launchd の定期ジョブで実行する](https://github.com/daiki-beppu/nyaucast/issues/511)

### 1. 「SNS は予約投稿を持たない」のような一括りの前提は、SNS ごとに確かめる

ADR-0009 には「SNS が予約投稿を持たないため、投稿の予定時刻は local store（チャンネルごとのローカル DB）に持つ」と書かれていた。私はこの一文を前提に問いを立てた。最初のラウンドで出した「YouTube の `publishAt`（private の動画を指定時刻に公開する引数）をどう使うか」という問いも、例外の扱いとして出したものだ。前の調査で、YouTube が予約投稿を持つことは分かっていた。それでも、ADR の前提そのものを疑ってはいなかった。

運営者の返事は「YouTube は予約投稿でいいから、他の API でも同様の機能がないか確認」だった。サブエージェントに公式のドキュメントを当たらせた結果は次のとおり。

| SNS                 | SNS 側で予約できるか                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| YouTube             | できる（`publishAt`）                                                                                                     |
| Instagram（リール） | できない。メディアコンテナに公開時刻の引数が無く、公開の API を呼んだ時点で公開される。コンテナは 24 時間で失効する       |
| X                   | 通常の API v2 ではできない。予約できるのは広告用の Ads API の `scheduled_tweets` だけで、広告アカウントと個別の承認が要る |

結論は ADR の前提とほぼ同じだった。それでも、確かめた意味はあった。もし 3 つとも予約できたなら、「予定時刻に何かが起きて投稿を実行する」仕組みそのものが要らなくなる。公開ゲートの後に 1 回叩けば、全部を SNS 側に予約して終わりになるからだ。そのため、答えが出るまで、実行の起点・二重投稿の防ぎ方・再試行の問いは保留にした。

**複数の外部サービスをまとめて「〜できない」と書いた前提は、サービスごとに確かめる。** 1 つでも例外があれば設計の分岐になる。全部に当てはまれば、仕組みそのものが要らなくなるかもしれない。その答えに依存する問いは、結果が出るまで聞かない。

### 2. 取り消せない外部への操作は、呼ぶ前に「始めた」と書き、結果が無ければ人間に回す

nyaucast は、進捗や状態を表す列を持たない。状態は、追記だけをする事実の行から、読み取り用の層（read model）が導く。この規約を投稿にも当てはめ、事実を 3 種類にした。

- 投稿: カット・アカウント・投稿文・予定時刻。書いたら変えない
- 投稿の試行: SNS の API を呼ぶ**前に**開始を書き、終わったら結果を書く。結果は成功とリモートの ID、一時的な失敗、恒久的な失敗のいずれか
- 投稿の取り消し

試行を独立した事実にすると、「開始はあるのに結果が無い」という行が残りうる。これは、プロセスが落ちたか通信が切れて、SNS に出たかどうかが分からない状態を表す。この試行は自動では再実行せず、「確認待ち」にして人間に回すことにした。再実行して実は出ていたら二重投稿になる。二重投稿は、このプロジェクトがリリースを止める欠陥に数える「誤公開」に当たる。SNS に問い合わせて自動で判定する手もあったが、問い合わせの手段は SNS ごとにまちまちなので、v0.1 では作らない。

投稿の行に `remote_id` や結果の列を足して更新する案も比べた。行は少なくて済む。しかし、「列は公開済みなのに実体は出ていない」という食い違いの余地を作る。状態の列を持たないと決めた理由が、まさにこの余地を作らないことだった。

**取り消せない外部への操作では、呼ぶ前に記録を書くことで「結果が分からない」状態を検知できるようにする。** 分からないものは自動で再試行せず、人間に回す。

### 3. 自動化を後回しにするときは、手で叩くコマンドを自動化と同じ形にしておく

最初のラウンドの推奨は、plist（launchd の定期ジョブの定義）を手で置き、5 分おきに `nyaucast post due` 相当のコマンドを叩かせる形だった。運営者の答えは「定期実行の job はとりあえずは作らない」だった。ADR-0009 の決定 4 には「launchd の定期ジョブが CLI を叩く」と書かれている。そのため、この答えは ADR の改訂を伴う。

改訂の中身は、実行の主体を人間に変えるだけにとどめた。コマンドの形は変えない。予定時刻が来た投稿だけを実行し、遅れが許容時間（既定 60 分）を超えた投稿は確認待ちにする。この形なら、人間が叩くのが遅れても、誤った時刻に投稿が出ることはない。v0.2 で定期実行を足すときは、同じコマンドを叩く役を launchd に渡すだけで済む。

あわせて、投稿の実行は人間のコマンド（CLI）だけに置き、エージェントが呼ぶ MCP tool には開かないことにした。nyaucast は、ゲートの承認を CLI だけが書ける形にしている。エージェントが善意で先へ進む事故を、構造で防ぐためだ。取り消せない外部への公開も、同じ扱いにした。

**自動化を後回しにするときは、人間が手で叩くコマンドを、自動化が叩くものと同じ形・同じ安全装置で作る。** 後から足すコストが、呼び出し役の差し替えだけに減る。

### 4. 承認と実行に時間差がある操作は、実行の直前にも鮮度を検査する

公開ゲート（人間が公開してよいと承認するゲート）には、「承認は、採用したカットと最後のサムネイルの選択より新しくなければならない」という条件がある。この検査をどの tool に置くかが、前のチケットから申し送られていた。投稿を作る tool に置くだけでは足りない。投稿を作った後でも、カットを描き直したり、サムネイルを選び直したりできるからだ。予定時刻が数日先なら、その間に変わりうる。そこで、投稿を作るときと、投稿を実行する直前の両方で検査し、実行時に落ちた投稿は確認待ちにした。作るときの検査は、早めに気づくためのものだ。

**承認したものと出すものの間に時間差がある操作は、承認の時点だけでなく、実行の直前にも検査する。** 時間差の間に変わりうるものを数えると、検査の置き場が決まる。

### 5. 過去の時刻を「即時」と解釈する API は、実行の遅れと組み合わせると誤公開になる

前の調査で、YouTube の `publishAt` には、過去の時刻を入れると即時公開になるという仕様が分かっていた。単体なら親切な仕様だが、「予定時刻に人間がコマンドを叩く」運用と組み合わせると危ない。叩くのが遅れて予定時刻を過ぎたまま upload すると、確認なしに即時公開されてしまう。

そこで YouTube は、公開ゲートの後に最初にコマンドを叩いたときに、予定時刻を `publishAt` にして upload することにした。こうすると、YouTube 側の処理の時間も取れる。予定時刻が既に過去になった YouTube の投稿は upload せず、確認待ちにする。

**過去の値を「今すぐ」と解釈する寛容な API は、遅れて実行されうる処理から呼ぶ前に、値が未来であることを自分で確かめる。** 寛容さは、遅延と組み合わさると、確認なしの公開に変わる。

## 公開のゲートで投稿の下書きを見せて承認させ、投稿を作る口を 1 つに絞った話

公開ゲートで人間が何を確定し、コマンドがどう対話するかを決めたときの学び。nyaucast の解説動画は、人間が承認する 2 つのゲートで区切られる。公開ゲートは、描き上がったカット（書き出した動画ファイル 1 本）を見て「公開する / しない」を決める 2 つ目のゲートだ。承認は `nyaucast video publish <id>` を人間が叩くことそのもので、`approve` のような独立した操作は無い。問いは、投稿の行を誰がいつ作るか、ショート動画の 2 種類のカットからどちらを選ぶか、投稿先のアカウントをどう確かめるか、公開ゲートの後に投稿文や予定時刻をどう直すか、だった。

- 決定の記録: [公開ゲートで確定するものと CLI の対話](https://github.com/daiki-beppu/nyaucast/issues/470)
- ADR の更新: [PR #514](https://github.com/daiki-beppu/nyaucast/pull/514)（ADR-0009 に決定 10 を足し、決定 7・9 を合わせて改訂した。用語集に「投稿案」を足した）

### 1. 前の決定の事前条件を読むと、作る順番が既に決まっていることがある

前のチケット（[投稿の状態を追記型の事実から導いた話](#post-state)）で、投稿を作る処理の事前条件を決めてあった。「公開ゲートの承認が、採用したカットと最後のサムネイルの選択より新しいこと」だ。この条件は、投稿が承認の**後**に作られることを前提にしている。承認の前に作ろうとすると、承認がまだ無いので必ず落ちる。

一方で、用語集は公開ゲートを「投稿の予定時刻もここで確定する」と定義していた。予定時刻は投稿が持つ値だ。投稿は承認の後にしかできないのに、その値を承認の時点で人間に見せる必要がある。2 つの決定を並べると、間に「承認の前に存在し、投稿ではないもの」が要ることになる。これを「投稿案」と名付けた。エージェントがゲートの前に書く投稿の下書きで、投稿文と予定時刻を持つ。

比べた案は 3 つある。

| 案                                                                                 | 結果                                                                                 |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| エージェントが投稿案を書き、ゲートのコマンドがそれを見せて、承認と投稿を同時に書く | 採用。人間が見たものと作られるものが一致する                                         |
| 承認だけを書き、投稿はその後にエージェントが作る                                   | 不採用。人間は投稿文も予定時刻も見ないまま承認することになる                         |
| ゲートの対話で、人間が投稿文と予定時刻を入力する                                   | 不採用。投稿文はエージェントが手順書を読んで書くものと決めてあり、人間の手間も大きい |

2 つ目の案は、nyaucast がゲートを「コマンドの実行 = 承認」にした理由を壊す。承認と実行が時間的に離れると、承認したものと作るものが食い違う事故が生まれる。この事故を消すために、独立した `approve` を作らなかったのだった。

**前の決定の事前条件は、検査の中身だけでなく、何がいつ存在するかの前提として読む。** 新しい決定が満たすべき順番が、そこから決まることがある。

### 2. 下書きのキーから、人間が後で選ぶ軸を外す

解説動画のショートは、見どころ 1 つ（ショートの候補）から 2 種類のカットを作る。長尺の一区間を縦型に切り出した「切り抜きショート」と、縦型のレイアウトで組み直した「専用ショート」だ。どちらを公開するかは、公開ゲートで人間が選ぶ。

投稿案のキーを「カット × アカウント」にすると、エージェントは候補ごとに 2 本分の投稿案を書くことになる。しかも、どちらか一方は必ず捨てられる。キーを「ショートの候補（長尺は長尺）× アカウント」にすれば、どちらのカットを選んでも同じ投稿案を使える。人間の選択と、エージェントが書くものが独立する。

**人間が後で選ぶ軸は、その前に書く下書きのキーに入れない。** 選択の結果で捨てられる下書きを作らずに済み、選び直しても下書きを書き直さなくてよい。

### 3. 他の事実から導けるものは、新しい事実にしない

「切り抜きと専用のどちらを採用したか」を、独立した追記型の事実として記録する案も比べた。採用しなかったカットの投稿を作らせない、という要件を担保するのに使えそうだったからだ。

ただ、投稿を作る経路が公開ゲートだけなら、投稿は採用したカットからしか作られない。採用は「投稿が指しているカット」から導ける。鮮度の検査も、投稿ごとに「最後の承認が、その投稿のカットとサムネイルの選択より新しいか」と書ける。採用を別の事実にすると、「採用したのに投稿が無い」「投稿はあるのに採用されていない」という食い違いの余地を新しく作るだけになる。

**導出できる情報を別に記録すると、記録どうしの食い違いという新しい状態が生まれる。** 書く前に、既存の事実から導けないかを確かめる。

### 4. 作る口を 1 つに絞ると、いろいろな「直したい」が 1 本の経路にまとまる

投稿は書いたら変えない事実なので、直すときは取り消してから作り直す、と前のチケットで決めてあった。残っていたのは、作り直す経路だ。投稿を作る口は公開ゲートのコマンドだけにしたので、次の流れになる。人間が投稿を取り消す → エージェントが投稿案を書き直す → 人間が `video publish` をもう一度叩く。2 回目以降は、生きている投稿（取り消されていない投稿）の無い投稿案だけを表示し、新しい承認とその投稿を書く。

この経路を決めてみると、別々に考えるつもりだった場面がすべて同じ形で扱えた。

- 投稿文や予定時刻を直したい
- ゲートの後でカットを描き直した（投稿は鮮度の検査に落ちて「確認待ち」になる）
- ゲートの後でサムネイルを選び直した（同上）

どれも「取り消して、投稿案を直して、ゲートを叩き直す」で済む。叩き直すたびに新しい承認が積まれるので、鮮度の検査も自然に通る。

**変えない事実を作る口を 1 つに絞ると、修正の経路はその口の再実行に集まる。** 修正の種類ごとに専用の経路を作らずに済む。

### 5. 新しい決定で、前の決定の条件が空振りしていないか確かめる

制作をやめる `video abandon` には、前のチケットで「予約済みの投稿が残る動画はやめられない」という条件が付いていた。ところが今回、投稿は公開ゲートの承認の後にしか存在しないと決めた。`abandon` は承認待ちのゲートに「やめる」を書く操作なので、公開ゲートを承認した後には書く先が無い。したがって、「投稿が残る」と「承認待ちのゲートがある」が同時に成り立つ場面が無くなり、この条件は一度も効かない文になっていた。

そこで条件を「公開ゲートを承認した動画はやめられない。配信を止めるときは投稿単位で取り消す」に書き直した。意味は変えず、今の構造で実際に効く形にした。同じ差分で、ADR の決定 7・9 と用語集の「やめる」の項も直した。

**前提を変える決定を入れたら、その前提の上に書かれた条件を読み直す。** 空振りする条件は害が無いように見えるが、後から読む人に「この場面がありうる」と誤解させる。

### 6. 対話を TTY に限るのは防御ではなく、うっかり通る経路を消すため

エージェントも Bash から `video publish` を叩ける。標準入力が TTY でなければ拒否し、対話を省く `--yes` も作らないことにした。ただし、これは防御にはならない。`script` コマンドなどで疑似端末を作れば回避できる。目的は、エージェントが普通に叩いただけで承認が通る経路を残さないことだ。決定の記録にも、防御ではないとそのまま書いた。

**安全装置の強さは、記録に正直に書く。** 「防げる」と書くと、後の人がそれを前提に別の検査を外してしまう。

### 7. まだマージされていない PR の上に積んだら、squash の後は `rebase --onto` で載せ替える

今回の ADR の改訂は、前のチケットの改訂 PR がまだマージされていない時点で書いた。同じ決定の段落を触るので、その PR のブランチから新しいブランチを切り、base をそのブランチにして PR を出した。前の PR を squash でマージすると、main には元のコミットとは別の 1 コミットができる。そのため、積んだブランチを次の手順で main の上に載せ替えた。

```sh
gh pr merge 512 --squash
gh pr edit 514 --base main
git fetch origin
git rebase --onto origin/main origin/docs/469-post-state docs/470-publish-gate
git push -f origin docs/470-publish-gate
```

`--onto` には、前の PR のブランチ（`origin/docs/469-post-state`）より後のコミットだけを main の上に載せ直させる。こうすると、squash で中身が同じになった前の PR のコミットを、もう一度適用しようとして衝突することがない。

**squash でマージするリポジトリで PR を積むときは、下の PR のマージ後に `rebase --onto <main> <下のブランチ>` で載せ替える。**

## 解説動画の成果物のうち、DB に行を持つものを「外から指されるか・時刻で比べるか」で絞った話

解説動画を作る区間（produce）でできる成果物のうち、どれを DB（local store）に行として持つかを決めたときの学び。local store は、チャンネルごとに置く libSQL の組み込み DB で、進捗や履歴の正本だ。nyaucast は「進捗を表す列を持たず、成果物の行があるかどうかから進捗を導く」と決めている。一方で、作り直せる成果物（データ 4 分類の ③）はキャッシュであり、正本を持たないとも決めている。produce 区間の成果物は大半が作り直せるものなので、この 2 つの決まりがぶつかった。対象の成果物は次のとおり。

- エージェントが書くもの: 台本、図解、ショートの候補
- 決まった手順で作るもの: 段落ごとの音声、ナレーションのトラック、composition（1 枚の HTML で書いた動画）、mp4、プレビュー
- 前のチケットから足されたもの: サムネイルの候補と選択、投稿の下書き（投稿案）

ほかに、公開ゲートの「プレビューできるカットがそろっている」が何を意味するかも決めた。

- 決定の記録: [解説動画の成果物の実体行と、進捗の導出](https://github.com/daiki-beppu/nyaucast/issues/494)
- ADR の更新: [PR #518](https://github.com/daiki-beppu/nyaucast/pull/518)（ADR-0009 に決定 11 を足し、ADR-0005 の「図解は ③」を改めた。用語集に「カットの書き出し」「ショートの候補の版」を足した）

質問は 3 ラウンドで 10 問出し、運営者の返事は 3 回とも「すべて推奨」だった。

### 1. 地図の順番で最初に来る ticket が、既にした決定や地図の範囲とぶつかるなら、着手する前に人間に聞く

wayfinder（大きな計画を、決定 ticket を 1 枚ずつ解いて進める進め方）では、ticket を指定しなければ、着手できる ticket のうち地図で最初のものを取る決まりだ。最初に来たのは「nyaucast を全面 Effect にする試作」だった。ところが、手元の記録には「schema は zod を使い続けると決めた。蒸し返さない」とあった。さらに、地図の到達点は「ドメインと境界まで決める」で、ライブラリの選定はその外にも見えた。

順番どおりに着手すると、決めた本人が蒸し返さないと言った決定を、1 セッションかけて掘り返すことになる。そこで着手する前に、3 択で聞いた。成果物の ticket に進む、試作に進む、試作を地図の範囲外にする、の 3 つだ。運営者は成果物の ticket を選んだ。

**順番の決まりは、機械的に従ってよい場面のためにある。** 既にした決定や、範囲の判断とぶつかるなら、それは人間が決めることなので、着手の前に聞く。

### 2. 「作り直せるか」で分類するなら、エージェントが書いたものは作り直せないものに入る

ADR-0005 は、図解を「作り直せる生成物（③）」に入れていた。図解は composition の材料なので、出力の側に置いたのだろう。しかし ③ の定義は「作り直せるので、キャッシュとして扱う」だ。図解はエージェントが書いた HTML で、消すと LLM をもう一度走らせるしかない。走らせても同じものは出てこない。台本とショートの候補も同じだ。

そこで線を引き直した。エージェントが書く入力は、tool が検証してファイルに書く。中身は DB に入れないが、分類は「消してはいけないもの（②）をファイルに置いたもの」とする。決まった手順で作る出力だけを ③ とする。中身をファイルにしたのは、HTML や台本は DB の行よりファイルのほうが、エージェントも人間も読み書きしやすいからだ。

この線は、地図に残っていた「作り直しの手段（`force` と削除）をいつ使うか」にもそのまま効いた。消してよいのは ③ だけで、② は上書きで直す。

**分類の定義を書いたら、その定義で個々の成果物を判定し直す。** 置き場（ファイルか DB か）と分類（消してよいか）は別の軸なので、ファイルに置いたことを理由に「作り直せる」へ入れない。

### 3. DB に行を持つのは、外から指されるものと、時刻で比べるものだけ

決まった手順で作る出力のうち、行を持たせる範囲には 3 つの案があった。

| 案                                                         | 結果                                                                                             |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| どれも行を持たない。ファイルの有無と、横に置いた鍵から導く | 不採用。投稿はカットを指す識別子を要る。公開ゲートの鮮度の検査は、カットが新しくなった時刻を要る |
| カットの書き出し（とプレビュー）だけ行を持つ               | 採用                                                                                             |
| 段落の音声ごと、トラックごとに、すべて行を持つ             | 不採用。行と実際のファイルが食い違う余地を、段落の数だけ増やす                                   |

基準は 2 つあった。1 つは、他の事実から指されるかどうか。投稿は「カット × アカウント」の事実なので、カットを指せないといけない。もう 1 つは、時刻で比べるかどうか。前のチケットで「公開ゲートの承認は、カットより新しくなければならない」と決めてある。段落の音声は、どちらにも当たらない。キャッシュの鍵で作り直しを判定できれば足りる。

**成果物を DB に載せるかは、「誰かがそれを指すか」「それの時刻を誰かが比べるか」で決める。** どちらにも当たらないものの行は、食い違いの元が増えるだけになる。

### 4. 「作らずに既存を返した」ときに行を積むと、鮮度の検査が壊れる

nyaucast の tool は、どれも冪等だ。既にあれば作らずに返す。再開は専用の仕組みを持たず、エージェントが同じ手順を頭から歩き直し、作ってあるものは tool がすぐに返す。

カットの書き出しを行にすると決めたとき、細かいが決定的な条件が 1 つ要った。**実際に新しく作ったときだけ積み、既存を返したときは積まない。** 逆にすると、再開して歩き直すたびに、カットの最後の書き出しの時刻が新しくなる。その結果、何も描き直していないのに「承認より後にカットが変わった」と判定され、投稿がすべて確認待ちになる。

**時刻を比べる事実は、「何かが変わった」ときだけ積む。** 冪等な操作の呼び出しのたびに積むと、時刻が「変わった時刻」ではなく「最後に呼んだ時刻」になる。

### 5. 下書きが古くなる問題は、版の時刻と比べるだけで、既存の拒否条件に流し込める

投稿案のキーは「ショートの候補 × アカウント」と前のチケットで決めてあった。危ないのは、エージェントが候補 2 の中身（切り抜く範囲や、画面に出す一言）を差し替えたときだ。古い候補 2 向けの投稿文が、そのまま生き残る。

候補を書くたびに、候補ごとに「版」を積むことにした。そして、投稿案はその候補の最後の版より新しいものだけを有効とする。古い投稿案は無いものとして扱われる。公開ゲートには前のチケットで「採用したカットに投稿案が無ければ承認を拒否する」という条件が既にあるので、それがそのまま効く。新しい検査を足さずに、「中身が変わったのに投稿文が古い」事故を止められた。

同じ形を、公開ゲートの承認待ちの条件と、企画ゲートにも使った。

- 公開ゲート: ショートのカットは、その候補の最後の版より新しくなければならない
- 企画ゲート: サムネイルの選択は、企画の最後の更新より新しくなければならない（企画を書き直したら、選び直すまでゲートに進めない）

**下書きの古さは、下書きの元になったものの版の時刻と比べて判定する。** 古い下書きを「無い」扱いにすると、「無ければ拒否」という既存の条件に吸収できる。

### 6. 事実を追記型にすると、削除の tool は要らなくなる

nyaucast の ADR は、すべての tool に「明示的な作り直しの手段（`force` 引数か、行を削除する tool）」を求めていた。今回の事実（カットの書き出し、プレビュー、候補の版、サムネイルの候補・除外・選択）は、すべて追記型だ。最後の行が有効になるので、「消す」は「新しい行が古い行を覆う」で代わりになる。そこで解説動画では、削除の tool を置かず、`force` だけにした。

削除の tool は、リリースを止める 3 種の欠陥のうち「データ破壊」の入口を増やすだけだった。地図の未決の欄にあった「`force` と削除の使い所」も、これで片づいた。残ったのは「失敗したときの戻し方」だけだ。

**追記型の事実なら、作り直しは新しい行を積むことで表せる。** 削除の手段を別に用意する前に、上書きで足りないかを確かめる。

### 7. 後のラウンドに回す質問は、前の答えで形が変わるものを選ぶ

1 ラウンド目には、分類（エージェントの入力をどう扱うか）、行を持つ範囲、サムネイルの行の 3 問だけを出した。ショートの候補を行にするか、カットの新しさを何で測るか、ゲートの承認待ちの条件も、問いとしては最初から見えていた。しかし、どれも「何に行を持つか」の答えで選択肢そのものが変わる。たとえば、カットが行を持たなければ、新しさはファイルの更新時刻で測るしかない。そのため、これらは 2 ラウンド目に回した。

結果として、2 ラウンド目の 5 問は、どれも「1 ラウンド目の決定を前提に、ここまで具体にする」形で書けた。3 ラウンド目は、企画の上書きという端の場面と、決定の書き先の確認だけで済んだ。

**答えが他の問いの選択肢を変える問いを、先に単独で聞く。** 後の問いが具体になり、推奨も前の決定を根拠に書ける。

<a id="ci-paths-guard"></a>

## CI を一部の PR で止めたら、ローカルのマージガードがその PR を永久に通さなくなった話

開発ログ（この `docs/knowledge/`）を追記した PR をマージしようとして止められ、CI の設定を戻したときの学び。nyaucast のリポジトリは private で、GitHub は Free プランで使っている。この組み合わせでは branch protection も rulesets も使えず、GitHub 側で「CI が green でなければマージ不可」を強制できない。そこで、Claude Code のフック（ツールの実行前に走るスクリプト）で `gh pr merge` を見張り、`gh pr checks` のチェックが 1 件以上あり、すべて pass のときだけ通すようにしてある。

- 起票した issue: [ci: docs/knowledge だけの PR でも CI を走らせる（paths-ignore を戻す）](https://github.com/daiki-beppu/nyaucast/issues/520)
- 修正: [PR #521](https://github.com/daiki-beppu/nyaucast/pull/521)（同じ日の朝に入れた [#500](https://github.com/daiki-beppu/nyaucast/issues/500) を戻した）

### 1. 「CI が走らなかった」と「CI がまだ登録されていない」は、チェックの一覧からは区別できない

同じ日の朝、開発ログだけを変える PR では CI を走らせないよう、workflow の `pull_request` に `paths-ignore: ["docs/knowledge/**"]` を付けていた。Markdown 1 ファイルの PR で、install・型検査・テストのフルセットが毎回走るのを省くためだ。

その日の夕方、開発ログの PR を作ってマージしようとすると、フックが次の理由で拒否した。

```text
PR 519 の CI チェックを取得できません（no checks reported on the 'docs/knowledge-494-artifact-facts' branch）。
```

フックが「チェックが 0 件なら拒否」としているのは、PR を作った直後の事故を防ぐためだ。PR を作った直後は、まだチェックが登録されていない。この状態で `gh pr checks --watch` を叩くと、待たずに "no checks reported" で終わる。後ろに `| tail` を付けていると終了コードも消えるので、そのままマージに進んでしまう。実際、このセッションでも PR を作った直後に `--watch` を叩いて、すぐに返ってきた。

一方、`paths-ignore` で CI を飛ばした PR も、チェックは 0 件のままだ。いつまで待っても登録されない。フックから見ると、2 つの状態は同じ「0 件」になる。

**チェックの有無でマージを見張るなら、チェックを意図して出さない PR を作ってはいけない。** 出さない PR があると、見張る側は「まだ」と「出ない」を区別できない。

### 2. 前提を書いた issue は、その前提がどこで崩れたかをすぐに教えてくれる

`paths-ignore` を入れた issue には、前提が 1 行書いてあった。「main に required status check が無いので、スキップされた PR が『チェック待ち』でマージ不能にはならない」。GitHub の設定だけを見れば、この前提は正しい。ところが、ローカルのフックが required check の役を果たしていた。強制する場所がサーバーではなくクライアントにあったので、GitHub の設定を見ても見つからなかった。

この 1 行があったので、原因を探す手間はほとんどかからなかった。「required check が無い」という前提を、「マージの条件を強制しているものが、どこにも無い」と読み替えれば、フックが当てはまる。

**設定を変える issue には、その変更が安全である前提を書いておく。** 崩れたときに、どの前提がどこで崩れたかを特定できる。「強制しているもの」を探すときは、サーバーの設定だけでなく、手元のフックやスクリプトも数える。

### 3. 誤検知を直す前に、見張りを賢くするのと、見張られる側を変えるのとで手間を比べる

最初は、フックを賢くする方向で手を動かし始めていた。チェックが 0 件のとき、PR の変更ファイルと workflow の `paths` / `paths-ignore` を照らし合わせ、どの workflow も起動しないと判定できたときだけ通す案だ。フックを管理するリポジトリに作業用の worktree まで作ったところで、運営者から「このガードいる？」と聞かれた。

聞かれて、案を並べて比べ直した。

| 案                                                              | 手間                 | 欠点                                                                          |
| --------------------------------------------------------------- | -------------------- | ----------------------------------------------------------------------------- |
| CI 側の `paths-ignore` を外し、開発ログの PR でも CI を走らせる | 1 行                 | 開発ログの PR ごとに CI が約 1 分走る                                         |
| フックに paths の判定を足す                                     | Python で 100 行前後 | GitHub の glob の書き方（`?` `+` `!` など）を再現しきれず、保守の対象が増える |
| フックを外す                                                    | 削除だけ             | PR を作った直後にマージする事故を防げなくなる                                 |

`paths-ignore` で節約していたのは、1 回 1 分ほどの CI だった。Free プランの private リポジトリは月 2,000 分あるので、開発ログの PR が毎日数本あっても誤差だ。その節約を守るためにフックへ glob の解釈を持ち込むのは、割に合わない。運営者は 1 つ目の案を選び、フックは変えずに残した。

外れたのは、着手の順番だった。誤検知を見て、すぐに「誤検知を出した側（フック）を直す」と決め、見張られる側を変える案を比べなかった。

**誤検知が出たら、見張りを賢くする案と、見張られる側を見張りに合わせる案を並べてから手を付ける。** 見張りの側は、扱う場面が増えるほど自分の検査が正しいかを確かめにくくなる。

### 4. `pull_request` の CI は、マージ先にある workflow の設定で走る

`paths-ignore` を外した修正を main にマージした後、止まっていた開発ログの PR を main の上に載せ直して push した。

```sh
git fetch origin
git rebase origin/main
git push -f origin HEAD
```

すると、その PR でも CI が起動し、47 秒で green になった。GitHub の `pull_request` の実行は、PR のブランチとマージ先を合わせたマージコミットにある workflow を使う。今回は main の上に載せ直したので、PR のブランチにも新しい設定が入っていた。ただ、GitHub の仕様どおりなら、載せ直さずに push するだけでも、マージ先の新しい設定で走るはずだ（今回は確かめていない）。

**workflow のトリガーを直したら、止まっていた PR は push し直せば新しい設定で走る。** 確実にするなら、main の上に載せ直してから push する。

<a id="effect-adoption"></a>

## コードを全面 Effect 4.0 で書くかを試作で確かめ、推奨とは逆の「採る」に決まった話

nyaucast のコードを、全面的に Effect 4.0 で書くかを決めたときの学び。Effect は TypeScript のライブラリで、失敗の型・依存の注入・並行・リトライ・時刻を 1 つの型（`Effect`）で扱う。この日の[成果物の行のエントリ](#artifact-facts)では、この ticket を後回しにしていた。今回は、そのとき後回しにした ticket の番が来た。

確かめ方は、既存の縦の一本を書き直す試作にした。範囲は、collection を作る MCP tool、状態を読む MCP tool、ゲートを承認する CLI、MCP の stdio サーバーで、ここに X（旧 Twitter）へ動画を投稿するクライアントを 1 本足した。MCP は、エージェントが外部の tool を呼ぶためのプロトコルだ。私の推奨は「v0.1 では採らない」だったが、運営者は「全面採用する」を選んだ。

- 決定の記録: [nyaucast を全面 Effect にする試作](https://github.com/daiki-beppu/nyaucast/issues/475)
- ADR の更新: [PR #523](https://github.com/daiki-beppu/nyaucast/pull/523)（ADR-0001 のエラーと schema の決定を改め、Effect の組み立て方を決定 9 として足した。ADR-0004 の DB 層を Drizzle から `@effect/sql-libsql` に移した）

### 1. ライブラリの全面採用の試作は、「動くか」より「版の穴がどこにあるか」を拾うために回す

試作した部分は、どれも動いた。MCP は、公式 SDK のクライアントから stdio で tool の一覧取得と呼び出しができた。CLI もゲートの承認を書けた。X のクライアントでは、refresh の直列化（`Semaphore`）、処理待ちの polling（`Schedule`）、仮想時間を進めるテスト（`TestClock`）が素直に書けた。

決定に効いたのは、動いたことより、入れてみて初めて見えた版の穴のほうだった。

| 見つかったこと                                                                                       | 決定への影響                                                                                                             |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `effect` 4.0.0 は正式版だが、`effect/ai`（MCP）・`cli`・`http`・`sql` はすべて `@stability unstable` | nyaucast が外とつながる部分は、全部 unstable 側に乗る。exact pin にし、破壊的変更は pin を上げる差分で受け止めると決めた |
| `@effect/sql-drizzle` には 4.x の版が無い（effect 3 向けの 0.51.0 で止まっている）                   | Drizzle を残すなら、Effect で包む層を自前で書くことになる                                                                |
| `@effect/sql-libsql@4.0.0` は libsql 0.18 を要求する（今の pin は 0.17.4）                           | 移るなら libsql も上げる                                                                                                 |
| `@effect/language-service` は TypeScript 7 で動かない                                                | 代わりに tsgo のフォークの `@effect/tsgo` が要る（ネイティブバイナリ 190 MB）                                            |
| tool 名はドットのまま `plan.init` で出る。既定は `additionalProperties: true`                        | Claude API の tool 名はドットを許さないので、`plan_init` の形で名付ける。入力は strict にする                            |

**採用の試作では、パッケージを実際に入れ、周辺の版（DB・テスト・型検査）がそろっているかを数える。** 「書けるか」は API のドキュメントを読めば大体わかる。周辺に版の穴があるかどうかは、入れてみるまでわからない。

### 2. ticket に書かれた前提は、試作のその日に最新版で確かめ直す

ticket の前提には、「`@effect/vitest` は vitest 5 系が必須で、vite-plus 0.3.0 が同梱している vitest 4.1 とは組み合わせられない」とあった。vite-plus は、test・lint・format を 1 つにまとめたツールチェーンだ。私も `@effect/vitest` の peer 依存（`vitest >=5.0.0 <6.0.0`）を見て、この前提を確かめたつもりになった。そのうえで、`TestClock.layer()` を手で provide するテストを書き、vitest 4.1 で 4 本通した。

テストの方針を聞いたとき、運営者の返事は選択肢のどちらでもなく、「vite-plus も確認。1.0 になってどうなってるか」だった。調べると、vite-plus 1.0.0 は 2026-09-28 に出ていて、vitest 5.0.1 を同梱していた。ticket が書かれた 2026-10-01 の時点で、前提はもう古くなっていたことになる。試作の依存を 1.0.0 に上げると、`@effect/vitest` の `it.effect`・`layer()`・`TestClock` がそのまま動き、既存のテスト 133 本も通った。

外れたのは、制約を「相手側（`@effect/vitest`）の要求」だけで確かめたことだ。こちら側（vite-plus）の最新版は見ていなかった。

**「A と B は組み合わせられない」という前提は、A と B の両方の最新版で確かめる。** 片側の要求だけを見ると、もう片側が追いついていることに気づけない。

### 3. 推奨と逆の判断が返ってきたら、その判断の下での細目は試作の事実で既定を埋め、分かれるところだけ聞く

推奨しなかった案が選ばれると、決めることが一気に増える。ADR-0001 の改訂だけでも、エラーの扱い、Layer を組む場所、`runMain` の位置、tool 名、pin の方針、DB 層、テスト、型検査の診断、既存コードの移行の順番がある。

全部を聞くと、運営者に 10 問近く投げることになる。そこで、試作で答えが一つに決まったものは、私の既定として提示するだけにした。たとえば、Layer を組むのと `runMain` を呼ぶのは entry point の 1 か所だけ（Effect 同梱の手引きと同じ形）、tool 名は `plan_init` の形（Claude API の制約）、といったものだ。聞いたのは、代償のある選択の 4 問だけにした。DB 層、診断を検査ゲートに入れるか、テストの書き方、既存コードを移す順番だ。

**判断が逆に転んでも、試作の事実が既定を決めてくれる細目は多い。** 人間に聞くのは、「どちらを選んでも成り立つが、代償が違う」ものだけにする。

### 4. 「シンプルで依存が少ないのはこっち？」と聞かれたら、依存の数とシンプルさを分けて答える

DB 層の質問への返事は、「シンプルで依存が少ないのは 2 という理解で合ってる？」だった。2 は、Drizzle をやめて `@effect/sql-libsql` に移る案だ。

依存が少ないのは事実だった。Drizzle を残す案では、drizzle-orm と drizzle-kit（esbuild と tsx を連れてくる）が残る。移る案では、`@effect/sql-libsql` と libsql だけになる。一方で、シンプルさには代償があった。スキーマの差分から SQL を生成する仕組みが無くなり、マイグレーションを手で書くことになる。`effect/sql` 自体も unstable だ。表にして見せると、運営者は移る案を選んだ。決め手は 2 つだった。今のマイグレーションは 1 本だけしかない。そして、追加型（additive）を原則にしているので、手で書く SQL は短く済む。

**「A のほうが X で Y だよね？」と 2 つの性質をまとめて聞かれたら、性質ごとに答える。** まとめて「はい」と答えると、片方の代償が見えないまま決まってしまう。

### 5. 名前が消えた API は型検査で弾ける。古い API の診断が役に立つのは「直し方」を示すところ

Effect の v3 と v4 では、API の名前が大きく変わった。エージェントは学習データに多い v3 を書きがちだ。実際、試作の途中で私自身が v3 の `Argument.Choice` を書いた（v4 では `Argument.Literals`）。これは素の型検査が「そのプロパティは無い」と弾いた。

v3 の API を混ぜた囮のファイルに、`@effect/tsgo` の `outdatedApi` もかけてみた。`catchAll` / `either` / `zipRight` を検出し、「`catch` に改名」「`result` に改名。Either ではなく Result を返す」のように、直し方まで出した。ただ、検出だけなら型検査で足りていた。

```sh
pnpm exec effect-tsgo diagnostics --project prototype/effect/tsconfig.json
```

この診断を検査ゲートに入れたのは、エージェントが型エラーを直すときに、改名先を推測しなくて済むようにするためだ。全面採用なので unstable API の警告は毎回出る。そのため対象から外した。

**名前が消えた API の混入は、型検査がすでに止めている。** 古い API の診断に期待するのは、止めたあとに正しい名前へ導く情報のほうだ。

### 6. 覆す決定は、その決定の決め手が消えたことと一緒に記録する

この日の朝の時点で、手元の記録には「schema は zod を続けると決めた（2026-08-23）。蒸し返さない」とあった。そのときの決め手は、公式 MCP SDK の `registerTool` が zod 専用だったことだ。zod 以外に移るなら、adapter の境界で JSON Schema への変換を自前で持つことになる。

今回は MCP サーバーごと `effect/ai` に置き換える。そのため、この決め手は前提ごと消える。ADR-0001 の「検討した選択肢」には、「zod と throw を続ける」案を不採用として書いた。そのうえで、なぜ 2026-08-23 の決定が今回は効かないかを、決め手の名前を挙げて残した。手元の記録も同じ内容に書き換えた。

**決定を覆すときは、「前の決定の決め手は何で、それがなぜ今は成り立たないか」を書く。** そうしておくと、次に誰かが「前に zod で決めたはず」と言ったとき、どこで前提が変わったかがすぐにたどれる。

### 7. テストが効いているかは、変異を 1 つ入れて落ちることで確かめる。読み込みの失敗を「落ちた」と数えない

X のクライアントのテストには、「並行に投稿しても refresh は 1 回だけ」があった。X の refresh token は使い捨てで、二重に使うと失効する。このテストが本当に lock を見ているかを確かめるため、lock を外す変異を入れた。

1 回目は、`lock.withPermits(1)(` を `(` に置き換えた。テストファイルは FAIL になった。しかし中身を見ると、置き換えで末尾のカンマが括弧の中に残り、構文エラーでファイルの読み込み自体が失敗していただけだった。テスト本体は 1 本も走っていない。2 回目は、`Semaphore.make(1)` を `make(2)` に変えた。今度は狙ったテストが `expected [ 'POST /2/oauth2/token', …(1) ] to have a length of 1 but got 2` で落ち、戻すと 4 本とも通った。

**変異を入れて落ちたら、落ちたのが狙ったアサーションかを見る。** `FAIL <file> [ <file> ]` のようにファイル単位の失敗しか出ていなければ、それは読み込みの失敗で、テストの強さについては何も言っていない。
