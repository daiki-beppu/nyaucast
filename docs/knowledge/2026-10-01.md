## 古いチケットを捨てて実装計画を地図に描き直したら、初日の調査で設計の前提が崩れた話

v0.1.0 の実装計画を描き直したときの学び。v0.1.0 のゲートは、解説動画のエピソードを 1 本作り、YouTube・TikTok・Instagram・X の 4 つの SNS へ公開するまでを nyaucast だけで完走すること。ツール名が 2 回変わる途中で書かれた古いチケット 38 本をすべて閉じ、wayfinder の地図（決めることを 1 問 1 チケットに分け、依存関係でつないだ親 issue）を一から描いた。地図を描いたその日のうちに調査チケットを並列で走らせ、その結果で地図を 3 回描き直した。

- 決定の記録: [v0.1.0 エピソード lifecycle と 4 SNS 配信の実装計画マップ](https://github.com/daiki-beppu/nyaucast/issues/457)
- 方針の記録: [ADR-0009 制作物に解説動画のエピソードを加え、4 つの SNS へ配信する](../adr/0009-episode-and-multi-sns-distribution.md)、[ADR-0007 collection lifecycle は codec を読んだ agent が駆動し、関門は tool の事前条件が持つ](../adr/0007-collection-lifecycle-execution-model.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)

### 1. 古い仕様を引き継ぐ前に、それが前提にしている実装が本当にあるかを確かめる

古い仕様は「描画の tool `video.render` は既にある。それを長尺とショートで使い分ける」という前提で書かれていた。`video.render` は、HTML で書いた絵コンテを headless Chrome で 1 フレームずつ撮り、動画に書き出す tool である。設計は ADR に決まっていて、仕様の正書（`docs/reference/composition-contract.md`）もある。だから「ある」と思い込みやすい。

実際に確かめると、tool のファイルは 3 本しかなかった。

```sh
$ find src/tools -name '*.ts' ! -name '*.test.ts'
src/tools/collection.status.ts
src/tools/plan.checkTitle.ts
src/tools/plan.init.ts

$ git log --oneline --all -- 'src/tools/benchmark*' 'src/tools/video*' 'src/tools/thumbnail*'
（出力なし）
```

`video.render` だけでなく、競合チャンネルの分析（`benchmark.collect`）もサムネイル生成も、一度も実装されたことがなかった。決まっていたのは設計だけだった。古い仕様のチケット分割をそのまま引き継いでいたら、「描画の基盤を作る」という大きな仕事が丸ごと抜けた計画になっていた。

**設計文書と ADR が揃っているほど、実装済みだと錯覚しやすい。** 古い計画を材料にするときは、その計画が「ある」と書いているものを 1 つずつ git で確かめる。確かめる対象は、ファイルの有無と、履歴に一度でも現れたかの 2 つ。

### 2. 調査は地図を描いたその場で並列に走らせ、その結果で地図を描き直す

地図には、決めるための材料を集める調査チケットを 4 本置いた。YouTube・TikTok・Instagram・X の投稿 API と規約を、一次情報で確かめるものだ。この 4 本を、地図を作った直後にサブエージェントで並列に走らせた。かかった時間は 1 本あたり 3.5〜6 分だった。

結果が返るたびに地図を直した。

| 調査       | 結果を受けて地図に起きたこと                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| TikTok     | 新しい決定チケット「TikTok の配信経路と v0.1.0 ゲートでの扱い」を立て、認証・投稿の実行・公開ゲートの 3 本をその後ろに置いた |
| Instagram  | 「動画を一時的に公開する置き場」を、まだ問いの形にならない論点（地図の「Not yet specified」）に足した                        |
| YouTube・X | 既存のチケットの前提が増えただけで、構造は変わらなかった                                                                     |

調査を「地図が固まってから」に回していたら、TikTok の規約の問題（3 節）を知らないまま、認証や投稿の状態モデルを議論していたことになる。**調査は安く並列化できるので、地図の初日に走らせる。** 結果で地図の形が変わることを前提に、ブロックの関係は後から張り直せる仕組み（GitHub の issue の依存関係）で持つ。

### 3. 「監査なしで使える」は、別の審査を暗黙の前提にしていないかを疑う

ADR-0009 は TikTok について、こう決めていた。「監査なしで公開まで運用できる Upload 方式（TikTok アプリの受信箱へ下書きを送り、最後は人間がアプリで投稿する）から始め、並行して Direct Post（API から直接公開する方式）の監査を申請する」。

調べると、たしかに Upload 方式に Direct Post の監査は要らなかった。ただし Upload 方式で使う `video.upload` の権限は、**アプリ自体の本番審査**を通らないと使えない。そして投稿の開発者ガイドラインには、受け付けない用途がはっきり書かれていた。

> Not acceptable: A utility tool to help upload contents to the account(s) you or your team manages.

アプリ審査の基準にも「Apps must not be for private or personal use.」とある。自分のチャンネルにだけ投稿する nyaucast は、名指しで退けられる用途に当たる。「監査なしで運用できる」は、通らない見込みの高い別の審査を暗黙の前提にしていた。

API のドキュメントは「この方式なら監査が要らない」と書く。その方式を使うためのアプリ審査は、別のページに書かれている。**SNS の API を設計に組み込む前に、API の仕様より先に、開発者規約の「想定する用途」とアプリ審査の基準を読む。** 自分専用のツールを作る場合は、ここで止まることが多い。

### 4. 設計文書に書いた外部の事実には、出典と日付を残す

ADR-0009 には「Instagram の 2026 年 4 月の規約強化を、公開前に一次情報で確かめる」と書かれていた。調べたところ、それらしい変更は一次情報では特定できなかった。Meta の Platform Terms と Developer Policies の最終更新はどちらも 2026-02-03 で、中身は広告関連の変更だった。4 月の変更で見つかったのは、再投稿中心のアカウントをおすすめから外す方針の拡張と、API に指標とラベルを足した changelog だけで、自動投稿を制限するものはなかった。出典が書かれていないので、何を指していたのかを後から辿れない。

逆向きの例もあった。YouTube の upload の quota を「1 回 1,600 units」と覚えていたが、2026-06-01 から upload には専用の枠ができ、既定で 1 日 100 回、1 回で 1 消費に変わっていた。サムネイルの上限も 2026-09-14 に 2MB から 50MB に上がっていた。

外部 API と規約の事実は、数か月単位で変わる。**ADR や仕様に外部の事実を書くときは、出典の URL と確かめた日付を一緒に書く。** 出典のない事実は、後から確かめることも、古くなったと気づくこともできない。

### 5. 料金表と API の制約は、投稿の状態モデルの入力になる

ADR-0009 は X について「従量課金なので、URL を含めずに動画を直接投稿する」と決めていた。2026-04-20 からの単価を確かめると、この判断は数字で裏付けられた。

| 操作                       | 単価               |
| -------------------------- | ------------------ |
| 投稿                       | $0.015             |
| URL を含む投稿             | $0.200             |
| 投稿の取得（公開後の照合） | $0.001〜0.005 / 件 |

URL を含めると約 13 倍になる。一方で、動画を添付すると本文に付く短縮リンクが「URL を含む投稿」に数えられるかは、料金表からは読み取れなかった。これは最初の実走で、請求の明細を見て確かめるしかない。

料金以外の制約も、状態の分け方を直接決めた。

- X のアップロードした動画の ID は 24 時間で失効する。そのため、アップロードは予定時刻の直前に行う。「動画の処理が済んだ」と「投稿した」は別の状態にする
- Instagram の Instagram Login 方式では、動画を分割して送る方式が使えず、公開 URL を渡すしかない。そのため、動画を一時的に公開する置き場が必要になる
- YouTube だけは、SNS 側に予約公開の機能がある。ただし過去の時刻を渡すと即時公開になるので、送る直前に時刻を確かめる

**投稿の状態モデルは、SNS の料金表と制約を並べてから決める。** 状態を先に決めて API に合わせると、「処理済みだが投稿前に ID が失効した」のような状態を取りこぼす。

### 6. 新しいライブラリは「主張」と「実物」を分けて調べ、懸念を実物で 1 つずつ潰せるかを見る

計画の途中で、運営者から「Effect（TypeScript で型付きエラー・再試行・依存の注入を扱うライブラリ）の 4.0 が出たので使いたい」という案が出た。動機は「エージェントとの相性が良いらしい」という評判だった。

Effect 4.0.0 が npm の最新版になったのは、この日（2026-10-01）だった。調べた結果を、主張と実物に分けた。

| 区分               | 内容                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公式の主張         | 「Reliable TypeScript for the AI era」。型付きのエラー情報がエージェントの自己修正を助ける                                                                                                        |
| 実物で確かめた事実 | npm パッケージにエージェント向けの `AGENTS.md` と `ai-docs/` が同梱され、中身は 4.0 の API で書かれている。言語サービスの `outdatedApi` 診断が、3.x の古い API の使用を検出し、CLI でも実行できる |
| 裏付けなし         | 「エージェントとの相性が良い」ことの実測やベンチマーク                                                                                                                                            |

最初の懸念は「エージェントが学習データの多い 3.x の書き方を混ぜる」だった。これは、同梱の文書と、古い API を機械的に弾く診断で潰せる。一方、次の懸念は実物の側に残った。

- `@effect/vitest@4.0.0` は vitest 5 系を要求するが、使っている開発ツール（vite-plus 0.3.0）が同梱するのは vitest 4.1.11 だった
- HTTP クライアントと MCP サーバのモジュールは unstable で、minor のリリースでも壊れうる
- 公式の MCP SDK は、tool の定義に zod を必須にしている

判断は 2 回動いた。最初は「v0.1 では採らず、v0.2 以降で試す」とした。しかし再試行・polling・後片付けが一番効くのは、v0.1 で新しく書く 4 SNS のクライアントだった。v0.2 に回すと、4 本を書いた後に書き直すことになる。そこで「地図の中で試作して、仕様を書く前に決める」に変えた。

途中で一度、言い過ぎた説明もあった。「`@effect/vitest` が使えないので、テストで時間を飛ばす利点は得られない」と言ったが、`TestClock.layer()` を手で注入すれば素の vitest でも書ける。専用のラッパが無いことと、機能が使えないことは別である。

**評判で入ってきたライブラリは、主張・実物・裏付けなしの 3 つに分けて書き出す。** 懸念ごとに「実物で潰せるか」を見ると、採る・採らないではなく「どの範囲なら採れるか」と「いつ決めるべきか」が見えてくる。

### 7. 実行環境の間の引き渡しは、仕組みを作らず、状態を外に置いて「頭から歩き直す」で成り立たせる

運営者から「Cloudflare の R2（ファイル置き場）や D1（データベース）に状態を貯めておけば、クラウドに移っても動く」という案が出た。私は最初、「Chrome も、FFmpeg のネイティブ binding も、Cloudflare Workers の上では動かないので、データだけ移してもクラウドでは動かない」と反論した。

この反論は、クラウドの実行環境を Workers だと思い込んでいた。運営者が想定していたのは、Devin や Claude Code のようなコーディングエージェントのクラウド VM だった。Devin には macOS の VM もあり、Chrome と FFmpeg の実測（どちらも macOS で済ませていた）がそのまま当てはまる見込みがある。そして VM は使い捨てなので、状態を VM の中に置くと消える。データを外に置く理由は、まさにそこにあった。

さらに、運営者の「引き渡しの仕組みを整えておく方がシンプル」という一言で、nyaucast が既に持っている設計とつながった。ADR-0007 は「専用の再開 API を持たない。再開は頭から同じ手順を歩き直し、各 tool が『実体があれば作らず既存を返す』ことで受け止める」と決めている。状態が実行環境の外にあれば、別の環境のエージェントが手順を頭から歩き直すだけで、続きから進む。引き渡し用のコマンドも、状態のエクスポートも要らない。

置き場は、データの性質と使い手で分かれた。

| 置き場の候補 | 何か                                            | nyaucast（Node の CLI と MCP サーバ）からの使いやすさ                                                                                                                              |
| ------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1           | Cloudflare の SQLite。Workers の中から使う前提  | Workers の外からは REST API 越しで、「管理用途向き」とされ、1 ユーザーあたり 5 分で 1,200 リクエストまで。ORM（drizzle）の実行時ドライバが無く、対話的なトランザクションも使えない |
| Turso        | 場所を問わず使える libSQL（今の DB と同じもの） | 接続先を `libsql://` に変えて token を付けるだけで、今の ORM がそのまま動く。トランザクションは 5 秒以内                                                                           |
| R2           | ファイル置き場（S3 互換）                       | 動画などの成果物向け。外向き転送は無料で、署名付き URL は最長 7 日                                                                                                                 |

ただし、状態を共有すると、2 つの環境が同じエピソードを同時に歩き出せてしまう。冪等な tool は「済んだものを作り直さない」ことは守れるが、「2 か所で同時に作り始める」ことは防げない。音声合成の二重課金や、投稿の二重実行がそれに当たる。

**「再開は頭から歩き直す」で設計しておくと、実行環境の間の引き渡しは、状態の置き場を変えるだけで手に入る。** ただし同時実行は別の問題として残るので、ロック（Turso のトランザクションや、R2 の条件付き書き込み）を別に考える。クラウドの DB を選ぶときは、「クラウドにあるか」ではなく「自分のプログラムから使うために作られているか」で選ぶ。

## ナレーションの声を聴き比べずに決めた話

解説動画のナレーションに使う音声合成（TTS）サービスと声を決めたときの学び。地図（[前のエントリ](#v01-map-charting)）には、「ElevenLabs と Gemini TTS で同じ日本語の台本を合成し、人間が聴き比べて決める」という作業チケットを置いていた。結局、聴き比べはしていない。運営者の別のリポジトリに Gemini TTS の本番運用の記録があり、そこから判断の材料がほぼ揃ったからだ。

- 決定の記録: [ElevenLabs と Gemini の日本語ボイスの聴き比べ](https://github.com/daiki-beppu/nyaucast/issues/462)
- 先送りした論点: [[v0.2] ElevenLabs の TTS アダプタを opt-in で加える](https://github.com/daiki-beppu/nyaucast/issues/483)、[[v0.2] チャンネルの語り口のベースを TTP 先から作る](https://github.com/daiki-beppu/nyaucast/issues/482)

### 1. チケットが指定する実験を始める前に、自分の別のプロジェクトで既に測っていないかを探す

チケットに書いた作業は、「台本を 1 本（3〜5 分）用意して両方のサービスで合成し、聴き比べる」だった。そのためには ElevenLabs の有料プランの契約と、2 つの API キーと、台本が要る。

運営者に段取りを聞くと、返ってきたのは「Gemini で進めて OK。台本は life リポジトリを参考に」という答えだった。`life` は運営者の個人のナレッジベースで、その日に読んだ記事を解説動画にして配信する仕組みが既に動いていた。中を読むと、nyaucast が作ろうとしている「台本と図解を AI 音声で解説動画にする」型の先行実装そのものだった。設計の記録には、チケットで調べるつもりだった事実が実測つきで並んでいた。

- 使っているモデルは `gemini-3.8-flash-lite-tts`。上位の Flash ではなく Flash-Lite を選んだ理由は料金で、2027 年の値上げ後も月 $5 の撤退基準に収まる方を採っていた
- 読む速さは 5.5〜7 文字/秒（実測）
- 4 回に 1 回ほど、読み終えた後も意味のない声が続く崩れ方をする（同じ文で実測）

**チケットに書いた実験は、チケットを書いた時点での「分からない」を前提にしている。** 着手する前に、自分や同じ運営者の他のプロジェクトで、同じものを既に測っていないかを探す。今回はそれだけで、契約・キーの発行・合成・試聴の手間がまるごと消えた。

### 2. 後から差し替えられる選択なら、比較より「実績のある既定値＋差し替え口」で決める

聴き比べで決めたかったのは、表向きは「どの声にするか」だった。ただ、チケットにはその結果で決まるものとして、次の 2 つも書いてあった。

- TTS のアダプタ（外部サービスを呼ぶ部品）を 1 本作るか 2 本作るか
- ナレーションと画面の時間合わせをどうするか

運営者の答えは「Gemini を既定にし、ElevenLabs は後から切り替えられるようにアダプタの形にしておく」だった。TTS の呼び出しを境界の後ろに置けば、声やサービスの選択はチャンネルの設定を書き換えるだけで変えられる。後から差し替えられる選択に、今、比較実験のコストを払う理由はない。v0.1 で作るアダプタは Gemini の 1 本だけにした。

**選択が後から安く差し替えられる形になっているなら、比較で最善を探すより、実績のある方を既定値にして差し替え口を残す。** 比較が要るのは、差し替えのコストが高い選択（データの形や外部との契約）の方である。

### 3. TTS を選ぶときは、音質より先に「時刻情報を返すか」を見る

並行して公式ドキュメントを調べ、2 つのサービスを並べた。2026-10-01 時点の数字である。

| 項目                    | Gemini TTS（Flash-Lite）              | ElevenLabs Starter                                                         |
| ----------------------- | ------------------------------------- | -------------------------------------------------------------------------- |
| 日本語 1 分あたりの費用 | 約 $0.009（2027-01-01 から約 $0.018） | 約 $0.06（月 $6 で 30,000 文字、1 文字 1 クレジット、1 分 ≒ 300 字で試算） |
| 出力                    | WAV、24 kHz / mono / 16-bit           | mp3・opus・pcm・wav。Starter で確実なのは 24 kHz まで                      |
| 時刻情報                | 返らない                              | `/with-timestamps` で文字単位の開始・終了時刻                              |

解説動画では、ナレーションを句ごとに字幕で出し、図の変化も字幕の句に合わせる。そのため、どの文字がいつ読まれたかを知る必要がある。Gemini は時刻情報を返さない。`life` は、1 段落を 1 リクエストで合成して段落ごとの実際の長さを測り、段落の中の句の時刻は文字数の比で割り振って推定していた。

**TTS の選択は、字幕と画面の時間合わせの方式を決める。** 時刻情報を返すサービスなら実測、返さないなら段落ごとの合成と推定になる。音質の比較より先に、この違いで設計が分かれることを押さえておく。nyaucast では推定の方式を前提に進め、精度が足りなければ ElevenLabs に切り替える道を残した。

### 4. 1 日前に書いた比較の候補も、既に古いことがある

チケットに書いた ElevenLabs の候補は `eleven_v3` と `eleven_multilingual_v2` だった。調べると、公式ドキュメントでは両方とも「previous generation」の扱いで、現行の主力は `eleven_v4` になっていた。チケットを書いたのは、調べたのと同じ日である。

候補の名前は記憶から書いていた。外部の事実に出典と日付を残す話は[前のエントリの 4 節](#v01-map-charting)にも書いたが、比較の候補を挙げる段階でも同じことが起きる。**比較の候補を書くときも、記憶ではなく公式の一覧から挙げる。** 古い候補どうしを比べて選ぶと、選んだ時点で既に置き換わっている。

### 5. 回答がスコープの外のものを前提にしていたら、今やれる部分と先送りする部分に分ける

台本について、運営者はもう 1 つ要件を出した。「ユーザーごとに語り口が被らないようにしたい。ヒアリングで決めるか、TTP 先からベースを作る設計にしたい」。TTP は「徹底的にパクる」の略で、伸びている他のチャンネルを分析して型を取り入れることを指す。

ところが、TTP 先を集める仕組み（`benchmark.collect`）は、v0.1 の地図で「スコープ外」と決めていた。要件をそのまま受けると、先送りしたはずの大きな基盤が v0.1 に戻ってくる。そこで、要件を 2 つに分けてよいかを運営者に確かめた。

- v0.1: 語り口（声・TTS への演出メモ・台本のトーン）は、チャンネルの立ち上げ時にヒアリングで決め、チャンネルの設定に書く。全チャンネルで共有する既定値は持たない
- v0.2: TTP 先から語り口のベースを作る経路を、`benchmark.collect` と一緒に作る

**新しい要件がスコープの外のものに依存していたら、黙って広げることも、黙って捨てることもしない。** 今の仕組みだけで満たせる部分と、依存先を待つ部分に分けて確かめ、後者は issue にして先送りする。

### 6. Gemini TTS で日本語を読ませるときのはまりどころ

`life` の運用記録にあった、Gemini TTS の実測済みのはまりどころをまとめておく。nyaucast でも同じモデルを使うので、そのまま前提にする。

- **読み方の指示は英語で書き、本文と見出しで分けて渡す。** 「指示: 本文」の形で前に置くと、短い段落ほど指示まで読み上げられる（4 回中 3 回）。日本語で書いた指示は毎回読み上げられた。このモデルは `system_instruction` も受け付けない。`### DIRECTOR'S NOTES` と `### TRANSCRIPT` の見出しで分けると読み上げられなくなった
- **英字はネイティブ寄りの発音で読まれる。** 台本に `{表記|カタカナの読み}` の形で読み仮名を添え、字幕には表記を、TTS には読みを渡す
- **崩れた音声を長さで検出して合成し直す。** 3.5 文字/秒で読んだ長さに 1.5 秒を足しても超える段落は崩れとみなし、その段落だけ合成し直す（4 回で打ち切る）
- **声を変えたら読む速さを測り直す。** 文字/秒が変わり、台本の文字数の上限にも響く
