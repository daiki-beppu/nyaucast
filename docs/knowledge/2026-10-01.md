## 古いチケットを捨てて実装計画を地図に描き直したら、初日の調査で設計の前提が崩れた話

v0.1.0 の実装計画を描き直したときの学び。v0.1.0 のゲートは、解説動画のエピソードを 1 本作り、YouTube・TikTok・Instagram・X の 4 つの SNS へ公開するまでを nyaucast だけで完走すること。ツール名が 2 回変わる途中で書かれた古いチケット 38 本をすべて閉じ、wayfinder の地図（決めることを 1 問 1 チケットに分け、依存関係でつないだ親 issue）を一から描いた。地図を描いたその日のうちに調査チケットを並列で走らせ、その結果で地図を 3 回描き直した。

- 決定の記録: [v0.1.0 エピソード lifecycle と 4 SNS 配信の実装計画マップ](https://github.com/daiki-beppu/nyaucast/issues/457)
- 方針の記録: [ADR-0009 制作物に解説動画のエピソードを加え、4 つの SNS へ配信する](../adr/0009-episode-and-multi-sns-distribution.md)、[ADR-0007 collection lifecycle は codec を読んだ agent が駆動し、関門は tool の事前条件が持つ](../adr/0007-collection-lifecycle-execution-model.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)

### 1. 古い仕様を引き継ぐ前に、それが前提にしている実装が本当にあるかを確かめる

古い仕様は「描画の tool `video.render` は既にある。それを長尺とショートで使い分ける」という前提で書かれていた。`video.render` は、HTML で書いた絵コンテを headless Chrome で 1 フレームずつ撮り、動画に書き出す tool である。設計は ADR に決まっていて、仕様の正書（`docs/reference/composition-contract.md`）もある。だから「ある」と思い込みやすい。

実際に確かめると、tool のファイルは 3 本しかなかった。

```sh
$ find src/tools -name '*.ts' ! -name '*.test.ts'
src/tools/collection.status.ts
src/tools/plan.checkTitle.ts
src/tools/plan.init.ts

$ git log --oneline --all -- 'src/tools/benchmark*' 'src/tools/video*' 'src/tools/thumbnail*'
（出力なし）
```

`video.render` だけでなく、競合チャンネルの分析（`benchmark.collect`）もサムネイル生成も、一度も実装されたことがなかった。決まっていたのは設計だけだった。古い仕様のチケット分割をそのまま引き継いでいたら、「描画の基盤を作る」という大きな仕事が丸ごと抜けた計画になっていた。

**設計文書と ADR が揃っているほど、実装済みだと錯覚しやすい。** 古い計画を材料にするときは、その計画が「ある」と書いているものを 1 つずつ git で確かめる。確かめる対象は、ファイルの有無と、履歴に一度でも現れたかの 2 つ。

### 2. 調査は地図を描いたその場で並列に走らせ、その結果で地図を描き直す

地図には、決めるための材料を集める調査チケットを 4 本置いた。YouTube・TikTok・Instagram・X の投稿 API と規約を、一次情報で確かめるものだ。この 4 本を、地図を作った直後にサブエージェントで並列に走らせた。かかった時間は 1 本あたり 3.5〜6 分だった。

結果が返るたびに地図を直した。

| 調査       | 結果を受けて地図に起きたこと                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| TikTok     | 新しい決定チケット「TikTok の配信経路と v0.1.0 ゲートでの扱い」を立て、認証・投稿の実行・公開ゲートの 3 本をその後ろに置いた |
| Instagram  | 「動画を一時的に公開する置き場」を、まだ問いの形にならない論点（地図の「Not yet specified」）に足した                        |
| YouTube・X | 既存のチケットの前提が増えただけで、構造は変わらなかった                                                                     |

調査を「地図が固まってから」に回していたら、TikTok の規約の問題（3 節）を知らないまま、認証や投稿の状態モデルを議論していたことになる。**調査は安く並列化できるので、地図の初日に走らせる。** 結果で地図の形が変わることを前提に、ブロックの関係は後から張り直せる仕組み（GitHub の issue の依存関係）で持つ。

### 3. 「監査なしで使える」は、別の審査を暗黙の前提にしていないかを疑う

ADR-0009 は TikTok について、こう決めていた。「監査なしで公開まで運用できる Upload 方式（TikTok アプリの受信箱へ下書きを送り、最後は人間がアプリで投稿する）から始め、並行して Direct Post（API から直接公開する方式）の監査を申請する」。

調べると、たしかに Upload 方式に Direct Post の監査は要らなかった。ただし Upload 方式で使う `video.upload` の権限は、**アプリ自体の本番審査**を通らないと使えない。そして投稿の開発者ガイドラインには、受け付けない用途がはっきり書かれていた。

> Not acceptable: A utility tool to help upload contents to the account(s) you or your team manages.

アプリ審査の基準にも「Apps must not be for private or personal use.」とある。自分のチャンネルにだけ投稿する nyaucast は、名指しで退けられる用途に当たる。「監査なしで運用できる」は、通らない見込みの高い別の審査を暗黙の前提にしていた。

API のドキュメントは「この方式なら監査が要らない」と書く。その方式を使うためのアプリ審査は、別のページに書かれている。**SNS の API を設計に組み込む前に、API の仕様より先に、開発者規約の「想定する用途」とアプリ審査の基準を読む。** 自分専用のツールを作る場合は、ここで止まることが多い。

### 4. 設計文書に書いた外部の事実には、出典と日付を残す

ADR-0009 には「Instagram の 2026 年 4 月の規約強化を、公開前に一次情報で確かめる」と書かれていた。調べたところ、それらしい変更は一次情報では特定できなかった。Meta の Platform Terms と Developer Policies の最終更新はどちらも 2026-02-03 で、中身は広告関連の変更だった。4 月の変更で見つかったのは、再投稿中心のアカウントをおすすめから外す方針の拡張と、API に指標とラベルを足した changelog だけで、自動投稿を制限するものはなかった。出典が書かれていないので、何を指していたのかを後から辿れない。

逆向きの例もあった。YouTube の upload の quota を「1 回 1,600 units」と覚えていたが、2026-06-01 から upload には専用の枠ができ、既定で 1 日 100 回、1 回で 1 消費に変わっていた。サムネイルの上限も 2026-09-14 に 2MB から 50MB に上がっていた。

外部 API と規約の事実は、数か月単位で変わる。**ADR や仕様に外部の事実を書くときは、出典の URL と確かめた日付を一緒に書く。** 出典のない事実は、後から確かめることも、古くなったと気づくこともできない。

### 5. 料金表と API の制約は、投稿の状態モデルの入力になる

ADR-0009 は X について「従量課金なので、URL を含めずに動画を直接投稿する」と決めていた。2026-04-20 からの単価を確かめると、この判断は数字で裏付けられた。

| 操作                       | 単価               |
| -------------------------- | ------------------ |
| 投稿                       | $0.015             |
| URL を含む投稿             | $0.200             |
| 投稿の取得（公開後の照合） | $0.001〜0.005 / 件 |

URL を含めると約 13 倍になる。一方で、動画を添付すると本文に付く短縮リンクが「URL を含む投稿」に数えられるかは、料金表からは読み取れなかった。これは最初の実走で、請求の明細を見て確かめるしかない。

料金以外の制約も、状態の分け方を直接決めた。

- X のアップロードした動画の ID は 24 時間で失効する。そのため、アップロードは予定時刻の直前に行う。「動画の処理が済んだ」と「投稿した」は別の状態にする
- Instagram の Instagram Login 方式では、動画を分割して送る方式が使えず、公開 URL を渡すしかない。そのため、動画を一時的に公開する置き場が必要になる
- YouTube だけは、SNS 側に予約公開の機能がある。ただし過去の時刻を渡すと即時公開になるので、送る直前に時刻を確かめる

**投稿の状態モデルは、SNS の料金表と制約を並べてから決める。** 状態を先に決めて API に合わせると、「処理済みだが投稿前に ID が失効した」のような状態を取りこぼす。

### 6. 新しいライブラリは「主張」と「実物」を分けて調べ、懸念を実物で 1 つずつ潰せるかを見る

計画の途中で、運営者から「Effect（TypeScript で型付きエラー・再試行・依存の注入を扱うライブラリ）の 4.0 が出たので使いたい」という案が出た。動機は「エージェントとの相性が良いらしい」という評判だった。

Effect 4.0.0 が npm の最新版になったのは、この日（2026-10-01）だった。調べた結果を、主張と実物に分けた。

| 区分               | 内容                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公式の主張         | 「Reliable TypeScript for the AI era」。型付きのエラー情報がエージェントの自己修正を助ける                                                                                                        |
| 実物で確かめた事実 | npm パッケージにエージェント向けの `AGENTS.md` と `ai-docs/` が同梱され、中身は 4.0 の API で書かれている。言語サービスの `outdatedApi` 診断が、3.x の古い API の使用を検出し、CLI でも実行できる |
| 裏付けなし         | 「エージェントとの相性が良い」ことの実測やベンチマーク                                                                                                                                            |

最初の懸念は「エージェントが学習データの多い 3.x の書き方を混ぜる」だった。これは、同梱の文書と、古い API を機械的に弾く診断で潰せる。一方、次の懸念は実物の側に残った。

- `@effect/vitest@4.0.0` は vitest 5 系を要求するが、使っている開発ツール（vite-plus 0.3.0）が同梱するのは vitest 4.1.11 だった
- HTTP クライアントと MCP サーバのモジュールは unstable で、minor のリリースでも壊れうる
- 公式の MCP SDK は、tool の定義に zod を必須にしている

判断は 2 回動いた。最初は「v0.1 では採らず、v0.2 以降で試す」とした。しかし再試行・polling・後片付けが一番効くのは、v0.1 で新しく書く 4 SNS のクライアントだった。v0.2 に回すと、4 本を書いた後に書き直すことになる。そこで「地図の中で試作して、仕様を書く前に決める」に変えた。

途中で一度、言い過ぎた説明もあった。「`@effect/vitest` が使えないので、テストで時間を飛ばす利点は得られない」と言ったが、`TestClock.layer()` を手で注入すれば素の vitest でも書ける。専用のラッパが無いことと、機能が使えないことは別である。

**評判で入ってきたライブラリは、主張・実物・裏付けなしの 3 つに分けて書き出す。** 懸念ごとに「実物で潰せるか」を見ると、採る・採らないではなく「どの範囲なら採れるか」と「いつ決めるべきか」が見えてくる。

### 7. 実行環境の間の引き渡しは、仕組みを作らず、状態を外に置いて「頭から歩き直す」で成り立たせる

運営者から「Cloudflare の R2（ファイル置き場）や D1（データベース）に状態を貯めておけば、クラウドに移っても動く」という案が出た。私は最初、「Chrome も、FFmpeg のネイティブ binding も、Cloudflare Workers の上では動かないので、データだけ移してもクラウドでは動かない」と反論した。

この反論は、クラウドの実行環境を Workers だと思い込んでいた。運営者が想定していたのは、Devin や Claude Code のようなコーディングエージェントのクラウド VM だった。Devin には macOS の VM もあり、Chrome と FFmpeg の実測（どちらも macOS で済ませていた）がそのまま当てはまる見込みがある。そして VM は使い捨てなので、状態を VM の中に置くと消える。データを外に置く理由は、まさにそこにあった。

さらに、運営者の「引き渡しの仕組みを整えておく方がシンプル」という一言で、nyaucast が既に持っている設計とつながった。ADR-0007 は「専用の再開 API を持たない。再開は頭から同じ手順を歩き直し、各 tool が『実体があれば作らず既存を返す』ことで受け止める」と決めている。状態が実行環境の外にあれば、別の環境のエージェントが手順を頭から歩き直すだけで、続きから進む。引き渡し用のコマンドも、状態のエクスポートも要らない。

置き場は、データの性質と使い手で分かれた。

| 置き場の候補 | 何か                                            | nyaucast（Node の CLI と MCP サーバ）からの使いやすさ                                                                                                                              |
| ------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1           | Cloudflare の SQLite。Workers の中から使う前提  | Workers の外からは REST API 越しで、「管理用途向き」とされ、1 ユーザーあたり 5 分で 1,200 リクエストまで。ORM（drizzle）の実行時ドライバが無く、対話的なトランザクションも使えない |
| Turso        | 場所を問わず使える libSQL（今の DB と同じもの） | 接続先を `libsql://` に変えて token を付けるだけで、今の ORM がそのまま動く。トランザクションは 5 秒以内                                                                           |
| R2           | ファイル置き場（S3 互換）                       | 動画などの成果物向け。外向き転送は無料で、署名付き URL は最長 7 日                                                                                                                 |

ただし、状態を共有すると、2 つの環境が同じエピソードを同時に歩き出せてしまう。冪等な tool は「済んだものを作り直さない」ことは守れるが、「2 か所で同時に作り始める」ことは防げない。音声合成の二重課金や、投稿の二重実行がそれに当たる。

**「再開は頭から歩き直す」で設計しておくと、実行環境の間の引き渡しは、状態の置き場を変えるだけで手に入る。** ただし同時実行は別の問題として残るので、ロック（Turso のトランザクションや、R2 の条件付き書き込み）を別に考える。クラウドの DB を選ぶときは、「クラウドにあるか」ではなく「自分のプログラムから使うために作られているか」で選ぶ。

## ナレーションの声を聴き比べずに決めた話

解説動画のナレーションに使う音声合成（TTS）サービスと声を決めたときの学び。地図（[前のエントリ](#v01-map-charting)）には、「ElevenLabs と Gemini TTS で同じ日本語の台本を合成し、人間が聴き比べて決める」という作業チケットを置いていた。結局、聴き比べはしていない。運営者の別のリポジトリに Gemini TTS の本番運用の記録があり、そこから判断の材料がほぼ揃ったからだ。

- 決定の記録: [ElevenLabs と Gemini の日本語ボイスの聴き比べ](https://github.com/daiki-beppu/nyaucast/issues/462)
- 先送りした論点: [[v0.2] ElevenLabs の TTS アダプタを opt-in で加える](https://github.com/daiki-beppu/nyaucast/issues/483)、[[v0.2] チャンネルの語り口のベースを TTP 先から作る](https://github.com/daiki-beppu/nyaucast/issues/482)

### 1. チケットが指定する実験を始める前に、自分の別のプロジェクトで既に測っていないかを探す

チケットに書いた作業は、「台本を 1 本（3〜5 分）用意して両方のサービスで合成し、聴き比べる」だった。そのためには ElevenLabs の有料プランの契約と、2 つの API キーと、台本が要る。

運営者に段取りを聞くと、返ってきたのは「Gemini で進めて OK。台本は life リポジトリを参考に」という答えだった。`life` は運営者の個人のナレッジベースで、その日に読んだ記事を解説動画にして配信する仕組みが既に動いていた。中を読むと、nyaucast が作ろうとしている「台本と図解を AI 音声で解説動画にする」型の先行実装そのものだった。設計の記録には、チケットで調べるつもりだった事実が実測つきで並んでいた。

- 使っているモデルは `gemini-3.8-flash-lite-tts`。上位の Flash ではなく Flash-Lite を選んだ理由は料金で、2027 年の値上げ後も月 $5 の撤退基準に収まる方を採っていた
- 読む速さは 5.5〜7 文字/秒（実測）
- 4 回に 1 回ほど、読み終えた後も意味のない声が続く崩れ方をする（同じ文で実測）

**チケットに書いた実験は、チケットを書いた時点での「分からない」を前提にしている。** 着手する前に、自分や同じ運営者の他のプロジェクトで、同じものを既に測っていないかを探す。今回はそれだけで、契約・キーの発行・合成・試聴の手間がまるごと消えた。

### 2. 後から差し替えられる選択なら、比較より「実績のある既定値＋差し替え口」で決める

聴き比べで決めたかったのは、表向きは「どの声にするか」だった。ただ、チケットにはその結果で決まるものとして、次の 2 つも書いてあった。

- TTS のアダプタ（外部サービスを呼ぶ部品）を 1 本作るか 2 本作るか
- ナレーションと画面の時間合わせをどうするか

運営者の答えは「Gemini を既定にし、ElevenLabs は後から切り替えられるようにアダプタの形にしておく」だった。TTS の呼び出しを境界の後ろに置けば、声やサービスの選択はチャンネルの設定を書き換えるだけで変えられる。後から差し替えられる選択に、今、比較実験のコストを払う理由はない。v0.1 で作るアダプタは Gemini の 1 本だけにした。

**選択が後から安く差し替えられる形になっているなら、比較で最善を探すより、実績のある方を既定値にして差し替え口を残す。** 比較が要るのは、差し替えのコストが高い選択（データの形や外部との契約）の方である。

### 3. TTS を選ぶときは、音質より先に「時刻情報を返すか」を見る

並行して公式ドキュメントを調べ、2 つのサービスを並べた。2026-10-01 時点の数字である。

| 項目                    | Gemini TTS（Flash-Lite）              | ElevenLabs Starter                                                         |
| ----------------------- | ------------------------------------- | -------------------------------------------------------------------------- |
| 日本語 1 分あたりの費用 | 約 $0.009（2027-01-01 から約 $0.018） | 約 $0.06（月 $6 で 30,000 文字、1 文字 1 クレジット、1 分 ≒ 300 字で試算） |
| 出力                    | WAV、24 kHz / mono / 16-bit           | mp3・opus・pcm・wav。Starter で確実なのは 24 kHz まで                      |
| 時刻情報                | 返らない                              | `/with-timestamps` で文字単位の開始・終了時刻                              |

解説動画では、ナレーションを句ごとに字幕で出し、図の変化も字幕の句に合わせる。そのため、どの文字がいつ読まれたかを知る必要がある。Gemini は時刻情報を返さない。`life` は、1 段落を 1 リクエストで合成して段落ごとの実際の長さを測り、段落の中の句の時刻は文字数の比で割り振って推定していた。

**TTS の選択は、字幕と画面の時間合わせの方式を決める。** 時刻情報を返すサービスなら実測、返さないなら段落ごとの合成と推定になる。音質の比較より先に、この違いで設計が分かれることを押さえておく。nyaucast では推定の方式を前提に進め、精度が足りなければ ElevenLabs に切り替える道を残した。

### 4. その日に書いた比較の候補も、既に古いことがある

チケットに書いた ElevenLabs の候補は `eleven_v3` と `eleven_multilingual_v2` だった。調べると、公式ドキュメントでは両方とも「previous generation」の扱いで、現行の主力は `eleven_v4` になっていた。チケットを書いたのは、調べたのと同じ日である。

候補の名前は記憶から書いていた。外部の事実に出典と日付を残す話は[前のエントリの 4 節](#v01-map-charting)にも書いたが、比較の候補を挙げる段階でも同じことが起きる。**比較の候補を書くときも、記憶ではなく公式の一覧から挙げる。** 古い候補どうしを比べて選ぶと、選んだ時点で既に置き換わっている。

### 5. 回答がスコープの外のものを前提にしていたら、今やれる部分と先送りする部分に分ける

台本について、運営者はもう 1 つ要件を出した。「ユーザーごとに語り口が被らないようにしたい。ヒアリングで決めるか、TTP 先からベースを作る設計にしたい」。TTP は「徹底的にパクる」の略で、伸びている他のチャンネルを分析して型を取り入れることを指す。

ところが、TTP 先を集める仕組み（`benchmark.collect`）は、v0.1 の地図で「スコープ外」と決めていた。要件をそのまま受けると、先送りしたはずの大きな基盤が v0.1 に戻ってくる。そこで、要件を 2 つに分けてよいかを運営者に確かめた。

- v0.1: 語り口（声・TTS への演出メモ・台本のトーン）は、チャンネルの立ち上げ時にヒアリングで決め、チャンネルの設定に書く。全チャンネルで共有する既定値は持たない
- v0.2: TTP 先から語り口のベースを作る経路を、`benchmark.collect` と一緒に作る

**新しい要件がスコープの外のものに依存していたら、黙って広げることも、黙って捨てることもしない。** 今の仕組みだけで満たせる部分と、依存先を待つ部分に分けて確かめ、後者は issue にして先送りする。

### 6. Gemini TTS で日本語を読ませるときのはまりどころ

`life` の運用記録にあった、Gemini TTS の実測済みのはまりどころをまとめておく。nyaucast でも同じモデルを使うので、そのまま前提にする。

- **読み方の指示は英語で書き、本文と見出しで分けて渡す。** 「指示: 本文」の形で前に置くと、短い段落ほど指示まで読み上げられる（4 回中 3 回）。日本語で書いた指示は毎回読み上げられた。このモデルは `system_instruction` も受け付けない。`### DIRECTOR'S NOTES` と `### TRANSCRIPT` の見出しで分けると読み上げられなくなった
- **英字はネイティブ寄りの発音で読まれる。** 台本に `{表記|カタカナの読み}` の形で読み仮名を添え、字幕には表記を、TTS には読みを渡す
- **崩れた音声を長さで検出して合成し直す。** 3.5 文字/秒で読んだ長さに 1.5 秒を足しても超える段落は崩れとみなし、その段落だけ合成し直す（4 回で打ち切る）
- **声を変えたら読む速さを測り直す。** 文字/秒が変わり、台本の文字数の上限にも響く

## コマンド名を決めるつもりが、制作物の名前と上位概念を決め直すことになった話

解説動画の制作フローにある 2 つの人間の判断ポイントを、どう名付け、どう記録するかを決めたときの学び。nyaucast では、AI エージェントが制作を進め、人間が節目で「作る / 作らない」「公開する / しない」を決める。この節目を**ゲート**と呼び、人間がターミナルで CLI を叩いた事実そのものを承認として記録する（エージェントには書き込めない）。問いは「CLI のコマンド名」と「記録の表の持ち方」だった。結論は、制作物の呼び名を「エピソード」から「解説動画」に改め、その上に「動画」という上位概念を置く、という語の決め直しにまで広がった。

- 決定の記録: [エピソードのゲートと区間名、ゲート記録の持ち方](https://github.com/daiki-beppu/nyaucast/issues/463)
- 方針の記録: [ADR-0009 決定 7](../adr/0009-episode-and-multi-sns-distribution.md)、用語集 [`CONTEXT.md`](../../CONTEXT.md) の「動画」「解説動画」「やめる (abandon)」
- 先送りした論点: [collection のゲート CLI に、ゲートの前後関係の強制と abandon をそろえる](https://github.com/daiki-beppu/nyaucast/issues/486)、[[v0.2] collection を BGM 動画として video に統合する](https://github.com/daiki-beppu/nyaucast/issues/487)

### 1. 名前への違和感が出たら、動詞より先に名詞を疑う

質問は 5 つ並べ、それぞれに推奨の答えを付けた。運営者の返事は「全部推奨で OK。1 のコマンド名は要検討」だった。1 は `nyaucast episode produce <id>` / `episode publish <id>` / `episode reject <gate> <id>` という案である。

私は「要検討」を動詞の問題だと受け取った。`publish` は叩いた瞬間に公開されるように読める（実際は予定時刻を確定するだけ）し、`reject` に付けるゲートの引数は冗長だ、と。そこで `schedule` や `go` / `nogo` などの動詞の代案を 4 つ出した。返ってきたのは、こうだった。

> エピソードとかのワードが普段使わない単語なのでイメージがむずい気がする

引っかかっていたのは動詞ではなく、名詞の方だった。「エピソード」は前の日に地図を描いたときに、用語集に入れた語である。連載の 1 回分という意味では正確だが、運営者の頭の中の言葉ではなかった。用語集にある語はすでに決まったものとして扱い、その上にコマンドを組み立てていた。

**用語集の語は、それを日々使う人が普段使う語でなければ定着しない。** コマンド名に違和感が出たら、変える候補は動詞だけではない。名詞が普段の語かどうかも疑う。今回は、コードのどこにもまだ `episode` が出てこなかったので（`grep` で確かめた）、改名は文書の書き換えだけで済んだ。語を変えるなら、コードに入る前がいちばん安い。

### 2. 普段の語は意味が広いので、何を包むのかを決めることになる

候補には「題材」「動画」「ネタ」を出した。私の推奨は「題材」で、運営者が選んだのは「動画が素直かな」だった。

「動画」は普段の語なぶん、意味が広い。まず、既存の名前とぶつかることを洗い出した。ADR に仮の名前として書いた描画の tool `video.render` があり、用語集でも「当たり動画」（伸びている他チャンネルの 1 本）が同じ字面で使われている。そこで「識別子は `video`、用語集では『解説動画』と書く」と提案した。それへの返事が、次の問いだった。

> 解説動画に限った場合 BGM 動画だとどうする？

nyaucast には、もう 1 種類の制作物がある。音楽チャンネルの collection（楽曲群とそれをまとめた 1 本の動画）だ。解説動画だけを `video` と呼ぶと、BGM 動画は動画ではないのか、という説明できない非対称が生まれる。

2 つの制作フローを並べると、ゲートの意味は同じだった。どちらにも「作る / 作らない」と「出す / 出さない」があり、違うのは区間の中身だけだった。そこで、**動画**を上位概念とし、その種類を解説動画と BGM 動画にした。人間が覚えるのは `nyaucast video produce | publish | abandon <id>` の 3 つの動詞だけになり、音楽チャンネルに戻っても増えない。種類で違う部分（制作の手順書や記録の表）にだけ、種類の名前を付ける。

さらに「1 つのチャンネルが作る動画は 1 種類に限り、種類はチャンネルの設定で決まる」とした。これで、CLI が id から種類を判定するために、種類をまたいで id を一意にする、という制約が要らなくなった。

**専門的な語は、その語が指す範囲を狭く固定して、隣の概念との共通点を隠す。** 普段の語を選ぶと、それが何を包むのかを決めざるを得なくなり、そこで共通の構造が見つかる。

### 3. 「却下」に 2 つの意味を持たせない。打ち切りは記録し、差し戻しは記録しない

collection の既存の CLI には `reject`（NO-GO を書く）があり、NO-GO が 1 つでもあれば、その制作物は「打ち切り」として扱われる。解説動画の公開ゲートでは「サムネイルを作り直して」「この字幕を直して」のような差し戻しがよく起きそうだった。これを NO-GO として記録すると、「やめる」と「直して出す」が同じ記録になる。

案は 3 つあった。

| 案                                               | 問題                                                       |
| ------------------------------------------------ | ---------------------------------------------------------- |
| NO-GO を差し戻しと兼用し、打ち切りの判定をやめる | 「やめた」ことが記録から読めなくなる                       |
| 差し戻しを第 3 の記録として足す                  | 差し戻しの後の状態は「まだ承認していない」と何も変わらない |
| NO-GO は「やめる」だけ。差し戻しは何も記録しない | （採用）                                                   |

決め手は、差し戻しを記録しても、その後の判定が何も変わらないことだった。差し戻された動画は承認待ちのままで、エージェントが作り直し、人間がもう一度見る。コマンド名も、ゲートを引数に取る `reject` から、承認待ちのゲートを CLI が判定する `abandon`（やめる）に変えた。名前に「打ち切り」の意味だけが出るようにするためだ。

**状態の記録は、その後の判定を変えるものだけを残す。** 1 つの記録に 2 つの意味が乗りそうなときは、片方を記録しなくて済まないかを先に考える。

### 4. 自動でマイグレーションするローカル DB では、表を一般化せずに、ロジックだけを共有する

collection のゲートの記録は、`approvals(collection_id, gate, approved_at)` と `rejections(...)` の 2 つの表にある。`collection_id` は `NOT NULL` で、collections 表への外部キーを持つ。ゲートの値には CHECK 制約が付いている。

解説動画のゲートを記録する方法として、最初に浮かぶのは「この表を一般化して、制作物の種類と id の列を足す」ことだ。しかし SQLite では、`NOT NULL` を外したり外部キーを付け替えたりするのに、表の作り直しが要る。nyaucast の DB はユーザーの手元にあり、起動時に自動でマイグレーションする。そのため、ADR-0004 で「マイグレーションは列や表の追加だけにする（additive）」という原則を決めている。

そこで、解説動画専用の、同じ形の表を追加することにした。最新の承認と NO-GO を比べて状態を決める判定のロジックだけを、表を引数に取る形にして共有する。

**自動でマイグレーションする DB では、スキーマの重複を嫌って表を一般化するより、表は並べてロジックを共有する方が安全である。** 重複するのは表の定義の数行で、外部キーによる整合性はそのまま残る。

### 5. 新しい規則を決めたら、既存のコードが同じ規則を守っているかを読んで確かめる

「公開ゲートは、企画ゲートの承認を前提にする」と決めた。このとき既存の collection も守っているつもりでいたが、コードを読むと守っていなかった。ゲートを記録する関数は、collection が存在するかの確認と二重記録の防止しかしておらず、企画を承認していなくても `collection publish` が通る。

誤公開は、このプロジェクトがリリースを止める欠陥の筆頭に置いているものだ。それでも、v0.1 のスコープは解説動画なので、collection 側はここでは直さず、issue にした。

**新しい規則を決めたら、既存の似た仕組みが同じ規則を守っているかを、思い込みではなくコードで確かめる。** 守っていなければ、その場で直すのではなく issue にして、今の作業のスコープを守る。

## 題材の取り方を決めていたら、「自分で考える題材もある」の一言で冪等性のキーを決め直した話

解説動画の最初の区間、つまり題材を集めて企画を記録するところの、tool の責務と記録の形を決めたときの学び。nyaucast では、AI エージェントが MCP tool を順に呼んで制作を進める。tool はどれも冪等にする決まりで、同じ呼び出しを 2 回しても、既にあるものは作らずに返す。エージェントは途中で落ちたら頭からやり直すので、それでも二重に作られないようにするためだ。問いは 4 つあった。フィード（はてなブックマークや Hacker News の RSS）から題材の候補をどう取るか、候補を DB に残すか、企画に何を記録するか、記事の著作権の線をどこで守るか。

- 決定の記録: [題材候補の取得元と企画の記録](https://github.com/daiki-beppu/nyaucast/issues/465)
- 用語集の更新: [PR #489](https://github.com/daiki-beppu/nyaucast/pull/489)（「題材」「題材候補」「出典」「当たる型」を足した）

### 1. 回答に但し書きが付いたら、その前提に乗っていた他の質問を洗い直す

最初のラウンドでは、質問を 7 つ並べ、それぞれに推奨の答えを付けた。1 問目は「題材の候補は tool がフィードから取るか、エージェントが自分で読むか」。運営者からの返事は 1 行だった。

> 1は自分で考えるケースもあるのでそこは考慮しておく

1 問目の答え自体は変わらない（tool がフィードから取る）。変わったのは、他の質問の前提だった。私は「題材はフィードから来るもの」と思い込んで、4〜6 問目を組み立てていた。用語集にも、前の日に描いた計画の元になった古い仕様にも「フィードから個別の題材を選ぶ」と書いてあったからだ。その結果、次の 3 つが成り立たなくなった。

| 質問                                         | フィード前提の推奨         | 自分で考えた題材で起きること                     |
| -------------------------------------------- | -------------------------- | ------------------------------------------------ |
| 企画に記録するもの                           | 出典（元記事）は 1 件以上  | 出典の無い題材（経験談など）を記録できない       |
| 同じ題材の重複判定                           | 出典の URL をキーにする    | キーが無い                                       |
| 企画の作り直し（人間の差し戻しを受けた修正） | タイトル案を上書きするだけ | タイトル案がキーになると、上書きで別の題材になる |

そこで、但し書きを推奨に足して済ませるのではなく、影響を受ける 3 問を新しい質問として出し直した。他の質問（設定の形、候補を残すか、投稿文の出典）はフィードの有無に関係しないので、推奨のまま進めると明言した。

**1 つの回答への但し書きは、その質問より、その前提に乗っていた別の質問を壊すことが多い。** 但し書きが付いたら、どの質問が同じ前提に乗っていたかを洗い出し、壊れたものだけを問い直す。用語集に書かれた前提でも、ユーザーの実際の運用と食い違うことがある（今回は用語集の方を直した）。

### 2. 自然なキーが無い入力にも、冪等性のキーは要る。新規作成と作り直しは別の操作に分ける

出典の無い題材には、重複判定をしないという選択肢もあった。しかし冒頭に書いたとおり、エージェントは落ちたら頭からやり直す。重複判定が無いと、やり直すたびに同じ企画が二重に作られる。冪等性は「同じ題材をうっかり 2 回作らない」ためだけでなく、**やり直しを安全にする**ためのものでもある。

キーは 2 段にした。出典があれば、その URL を正規化したもの（`utm_*` などの計測用のパラメータ、`#` 以降、末尾の `/` を落とす）。出典が無ければタイトル案。後者は、音楽チャンネル側の既存の tool がタイトルを一意キーにしているのと同じ形で、エージェントに新しい概念を増やさない。もう 1 つの案は「エージェントが題材ごとに短い slug（識別用の英字の短い名前）を付ける」だった。これは採らなかった。同じ記事に日によって違う slug が付きうるので、フィード由来の題材では URL より弱くなる。

タイトル案がキーになりうると、作り直しでタイトルを変えたときに「キーで探して上書き」が成り立たない。そこで、キーで探すのは新規作成のときだけにした。作り直しは、動画の id を指定して上書きする。

**キーが変わりうる記録では、「キーで探して作る」と「id を指定して直す」を 1 つの操作に混ぜない。** 混ぜると、直すたびに別の記録ができる。

### 3. 「残すかどうか」は、読む人がいるかと、後から復元できるかの 2 軸で決める

同じ回の中で、一見逆の判断を 2 つした。

- フィードから取った題材の候補は、DB に残さない。その場でエージェントに返すだけにする
- 企画には「使った当たる型」を記録する。当たる型は、そのジャンルで再生を集める構成やタイトルの付け方の型で、チャンネルの設定に宣言しておく。v0.1 ではこの記録を読む機能は無い

違いは、後から復元できるかどうかだ。候補は v0.1 で読む機能が無く、必要になれば取り直せる。一方、「この動画はどの型で作ったか」は、記録しておかないと後から分からない。次の版で予定している実績分析（どの型が伸びたか）は、この記録が無いと始められない。記録のコストは、企画に列が 1 つ増えるだけだ。

**読む人がいない記録は持たない。ただし、後から復元できない事実は、読む人がまだいなくても安く残す。**

### 4. 著作権の線は、tool の構造で守る部分と、手順書で守る部分に分ける

解説動画は他人の記事を材料にする。本文を転載せず、要約と独自の図解で解説する、という線をどこで守るかが問いだった。

同じ運営者の別のプロジェクトで、同じ型の動画を作るときに測った数字がある。フィードの RSS に載っている記事の抜粋は短い。2026-09-28 に 889 件を測ったところ、文字数の中央値ははてなで 279 字、HN で 441 字、2000 字以上は 0 件だった。抜粋だけでは解説の材料にならず、本文を読む必要がある。

そこで、守る場所を 2 つに分けた。

| 守るもの                 | 守る場所                  | 方法                                                              |
| ------------------------ | ------------------------- | ----------------------------------------------------------------- |
| 本文を保存しない         | tool の構造               | nyaucast は本文を取得しない。企画の記録に本文を入れる欄を持たない |
| 要約と言い換えで解説する | 手順書（knowledge codec） | エージェントは本文を自分で一時的に読むだけ。引用は短い一句に限る  |

knowledge codec は、エージェントが読む「いつ・どの tool を・どう使うか」の手順書だ。tool の型で縛れるのは「何を受け取るか」までで、「どう書くか」は縛れない。だから、保存しないことは構造で強制し、書き方は手順書に書く。前者は破りようがなく、後者はレビューで見る。

**型で強制できるものと、できないものを分けて、それぞれに守る場所を割り当てる。** 全部を手順書に書くと破れる。全部を型で縛ろうとすると、書き方のように縛れないものが抜け落ちる。

### 5. 料金表は投稿文の規則にまで入ってくる

出典の URL を投稿文に必ず書くか、という問いでは、前に調べた X の API の料金が効いた。投稿 1 件は $0.015 だが、URL を含むと $0.200 と約 13 倍になる。

そこで、出典の明記を必須にするのは、長尺を投稿する YouTube の概要欄だけにした。TikTok・Instagram・X では任意にした。出典の URL は企画の記録が持っているので、どの SNS の投稿文にも書こうと思えば書ける。

**外部 API の料金の差は、状態の設計だけでなく、エージェントに渡す文章の規則まで変える。** 料金表は調査の段階で読み終えておき、規則を決める場面で引けるようにしておく。

## ナレーションと画面の時間合わせを、エージェントに秒数を書かせない形で決めた話

解説動画のナレーション（AI 音声）と、画面の図解・字幕のタイミングをどう合わせるかを決めたときの学び。解説動画の画面は、エージェントが HTML で書く絵コンテ（composition）を headless Chrome で 1 フレームずつ撮って動画にする。ナレーションは Gemini TTS で合成するが、Gemini は「どの文字をいつ読んだか」という時刻情報を返さない（[前のエントリ](#tts-default-voice)の 3 節）。問いは、合成の単位、時刻の出どころ、尺を誰が決めるか、合成のキャッシュの鍵、BGM をどこで混ぜるかの 5 つだった。

- 決定の記録: [ナレーションとシーンの時間合わせ](https://github.com/daiki-beppu/nyaucast/issues/466)
- 用語集の更新: [PR #491](https://github.com/daiki-beppu/nyaucast/pull/491)（「台本」「段落」「句」を足し、「ボイス」に読む速さを持たせた）

質問は 2 ラウンドで 10 問出し、運営者の返事は 2 回とも「すべて推奨」だった。推奨がそのまま通ったのは、同じ運営者の `life` リポジトリ（個人のナレッジベースで、同じ型の解説動画を毎日作って配信している）に、実測つきの先行実装があったからだ。この回の学びは、判断が覆った場面ではなく、その先行実装の何を引き継ぎ、何を引き継がなかったかにある。

### 1. エージェントには、計算で出せる数字を書き写させない。時刻は台本上の位置で指し、秒への変換はコードに任せる

尺の決め方には 3 つの案があった。

| 案                                                                                              | 問題                                                       |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| エージェントが尺を決め、TTS をそれに合わせる（話す速さの調整や無音の挿入）                      | 声の自然さを犠牲にする                                     |
| nyaucast が段落・句ごとの開始と終了の秒を返し、エージェントがそれを見て絵コンテに秒数を書き込む | 写し間違いと、作り直した後に古い秒数のまま書く事故が起きる |
| エージェントは「段落 2 の読み始め」「段落 2 の 3 番目の句」のように台本上の位置で書く（採用）   | —                                                          |

ここで段落はナレーションの 1 回の発話、句は段落を読点・句点で切った字幕 1 枚分の文言を指す。3 つ目の案では、位置から秒への変換を nyaucast が決定的に行う。`life` も最初は等分などの経験則で時刻を決めていて、内容に合わない動きになっていた。今は「秒数は書かず、実測した尺からビルダーが決める」に落ち着いている。

2 つ目の案は一見シンプルだが、エージェントに「計算で出せる値を、別の場所へ手で写す」仕事をさせている。1 段落を直して合成し直すと、それより後ろの秒数がすべてずれる。エージェントが全部を書き直さなければ、絵と声がずれる。

**エージェントが書くのは意図（どこで出すか）だけにして、そこから計算で出せる値（何秒か）は書かせない。** 写させた値は、元が変わったときに古いまま残る。

### 2. 生成のたびに出力が変わる API のキャッシュは、費用より再現性のために置く。鍵には出力を変える入力だけを入れる

Gemini TTS は、同じ入力でも毎回少し違う音声を返す。合成を段落ごとにキャッシュする（同じ入力なら既にある音声を返す）ことにしたが、効いているのは費用ではない。1 分あたり約 $0.009 なので、全部を合成し直しても安い。問題は、1 か所を直しただけで、直していない段落の声の調子まで変わってしまうことだ。

鍵には「TTS に渡す読み・アダプタ・モデル・声・演出メモ・出力形式」のハッシュを使う。ポイントは、台本の本文をそのまま鍵にしないことだ。台本には `{API|エーピーアイ}` のような読み仮名の記法があり、字幕と画面には表記（API）、TTS には読み（エーピーアイ）を渡す。表記だけを直した場合は、読みが同じなので合成し直さない。

句の時刻を推定するときも、同じ区別が効く。段落の実測の長さを、句の文字数の比で割り振る。このとき表記で数えると、「API」は 3 文字、実際の発話は「エーピーアイ」の 6 文字で、字幕がずれる。そこで読みで数えることにした。

**非決定的な生成のキャッシュは、変えていない部分を変えないための仕組みとして設計する。** 鍵には、生成される出力を実際に変える入力だけを入れる。見た目の表記のように出力に関係しない入力まで入れると、無関係な修正のたびに出力が変わる。

### 3. 先行実装の実測は引き継ぎ、ファイルの形式と語は、このリポジトリの規約に照らして決め直す

`life` から引き継いだのは、実測で裏付けられた事実と値だ。

- 1 段落を 1 リクエストで合成し、段落の長さを実測する
- 段落の間合い: 先頭 0.8 秒・段落の間 0.35 秒・シーンの間 0.6 秒・末尾 1.4 秒
- 句の切り方: 6 字未満の句は、28 字を超えない範囲で次の句とつなぐ（参考にした YouTube チャンネルの観察から取った値）
- 崩れた音声（読み終えた後も意味のない声が続く）の検出: 「読む速さで読んだ長さ + 1.5 秒」を超えたら合成し直し、4 回で打ち切る

引き継がなかったものも 2 つある。

- **台本の形式**: `life` は Markdown（`## S1` の見出しと段落）で書いている。nyaucast には「読み書きするファイルはすべて JSON」という規約があるので、シーンの配列 → 段落の配列の JSON にし、スキーマで検証することにした
- **語**: `life` は段落を「セグメント」と呼んでいる。nyaucast では、絵コンテの契約にもう `segments` というキーがある（タイムラインのうち、絵が動かない区間の自己申告）。同じ語を持ち込むと 2 つの意味がぶつかるので、「段落」と呼ぶことにした

**先行実装から引き継ぐのは、実測で裏付けられた事実と値まで。** 形式や語は、その実装のリポジトリの都合で決まっているので、引き継ぐ先の規約と既存の語に照らして決め直す。

### 4. 本物の経路が安いなら、推定の経路を持たない

`life` には、TTS を使わずに「文字数 ÷ 5.7 文字/秒」で尺を推定し、無音のまま画面を確かめるプレビューのモードがある。台本を書くエージェントの自己検査に使っている。

nyaucast では持たないことにした。合成は 1 分あたり約 $0.009 で、段落ごとのキャッシュがあるので、2 回目以降は直した段落の分しかかからない。推定のモードを持つと、時刻を出す経路が 2 本になる。そうなると、プレビューで見た時刻と、本番で使う時刻が食い違うことが起こりうる。

**本物の経路が安く済むなら、速さのための推定の経路は持たない。** 経路が 2 本あると、2 本の結果が食い違ったときにどちらを信じるかという、別の問題が生まれる。

### 5. 重い依存の許可範囲を守れるように、工程の切れ目を置く

nyaucast は ADR（設計判断の記録）で、headless Chrome への依存を「描画」と「プレビュー」の 2 つの tool に限っている。依存の範囲を、工程の名前ではなく tool の名前で列挙して縛っている。

BGM とナレーションを混ぜる場所の候補は 3 つあった。描画の tool の中、描画の後（`life` の方式で、エンコードが 2 回になる）、描画の前だ。描画の前に、Chrome を使わない音声の tool で混ぜることにした。音声の処理は Chrome を必要としないので、描画の tool に入れる理由がない。入れれば、Chrome に依存する tool の仕事が増える。

音声の区間は、さらに 2 つの tool に分けた。

1. ナレーションの合成: 台本 → 段落ごとの音声 → 1 本のナレーショントラックと、段落・句の時刻を書いたタイミング表（JSON）
2. カットの音声トラック: ナレーション + BGM → ラウドネスの正規化 → 最終の音声

こう分けておけば、BGM を差し替えても、ナレーションを合成し直さずに 2 だけを作り直せる。

**重い依存を許す範囲を決めてあるなら、その範囲に依存の要らない仕事が流れ込まないように、工程を切る。** 切れ目は、何を差し替えたときに何を作り直したくないか、で置く。

### 6. 決まったのが「向き」だけなら、置き場は次のチケットに渡す

「秒への変換は nyaucast が行う」とは決めたが、それを描画の tool の中でやるか、別の組み立て用の tool でやるかは、この回では決めなかった。後者は、長尺・切り抜きショート・専用ショートの 3 種類のカットをどう描くかで答えが変わるからだ。切り抜きショートの音声を長尺のどこから切り出すかも、同じ理由で描画方式のチケットに渡した。

渡すときは、そのチケットにコメントで論点を書いた。決定の記録に「下流へ渡すこと」の節を設け、どのチケットで何を決めるかを並べた。

**1 つのチケットで決めるのは、そのチケットの材料で決められることまでにする。** 決められない部分を推測で埋めると、次のチケットの議論が、既成事実を覆すところから始まることになる。
