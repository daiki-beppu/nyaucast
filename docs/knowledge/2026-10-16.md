## トリアージで、issue に残った「どちらにしますか」を実測で決めてから渡した話

v0.1 の範囲で状態のラベルが付いていなかった issue 9 件をトリアージしたときの学び。トリアージは、issue を読んで種別（バグか機能か）と状態（エージェントに渡せるか、人が要るか、閉じるか）を決め、エージェントに渡すものには仕様の要約（agent brief）をコメントで付ける作業。結果は 6 件を実装に回し（#854・#809・#853・#811・#850・#726）、3 件を閉じた（#682・#747・#852）。このリポジトリの issue の書き方の規約には「本文を読んだ実装者が『どちらにしますか』と聞き返せる文が 1 つでもあれば、投入せず書き直す」という検出器がある。今回の作業は、ほぼこの検出器に引っかかる文を潰すことだった。

### 1. issue の「要調査」は、トリアージの中で実行して答えを出す

3 件の issue が、答えを実装者に預けたまま起票されていた。

- #854: Cloudflare の CLI（`cf`）の専用プロファイルに、新しく足したスコープがあるかを判定したい。issue には「`cf auth whoami` の出力にスコープが含まれるかは要調査」とあった。nyaucast が子プロセスに渡すのと同じ環境変数で実行すると、JSON に `"scopes": ["offline_access", "workers-r2.write", "account_api_tokens:create"]` の配列があった。この手元のプロファイルが、まさに新しいスコープ（`workers-r2-bucket-item.write`）を欠いた古いものだった。再現と「要調査」の答えが 1 回の実行で揃った
- #853: 下流のリポジトリで `pnpm add -D nyaucast` が、承認されていない build script（core-js・node-av・workerd）のせいで失敗する。「どれを承認すべきか」を決めるために、`pnpm pack` した tarball を空のリポジトリに入れ、3 つとも `allowBuilds: false` で拒否して試した。インストールは終了コード 0 で通り、CLI も起動し、node-av を使った H.264 のエンコードも動いた。node-av の postinstall は ffmpeg の CLI バイナリを落とすだけで、nyaucast は CLI を使わない（binding は optionalDependencies の別パッケージにある）
- #809: mp4 の `moov` を先頭に置く方式。mediabunny の型定義を読み、`'in-memory'`（10 分の動画で約 600 MB をメモリに持つ）・`'reserve'`（パケット数の上限を先に渡す）・`'fragmented'`（fMP4。Instagram の仕様に合うか不確か）を表にしてから、運営者に `'reserve'` を選んでもらった

どれも数分で答えが出る調べものだった。トリアージで済ませないと、実装者が同じ調べものから始めるか、推測で片方を選ぶ。

### 2. 起票から日が経った issue は、まず前提がまだ生きているかを確かめる

9 件のうち 3 件は、書かれた前提がすでに古かった。

- #682（サムネイルのテストが高負荷で時間切れ）は、起票の 2.5 時間後にマージされた別の PR（#709）で、本文の 3 本がすでに直っていた。残っていたのはコメントで後から足された 1 本だけで、それは同じ種類の #811 に移して閉じた
- #811 は「テストに `.heavy` の接尾辞を付けると決めた」を前提にしていた。その決定は 2 日前に覆り、`.heavy` の層は作らないことになっていた（ADR-0014 決定 1）。前提どおりに渡すと、実装者は廃止された層を作り始める
- #747（描画の撮影が Chrome のフレームの拍に待たされる）は、完了条件の「1080p で測る」「採否を ADR にする」が、決定マップの下のチケットで両方とも済んでいた

確かめ方は、ADR の改訂履歴と、issue 番号で PR を検索することだった。issue の本文は、起票した時点のリポジトリの写しでしかない。

### 3. 遅いテストのボトルネックは、推測で直さずに区間ごとに測る

#811 の due-posts のテストは、X へのチャンクの送信を観測するために、約 10 MB の中身を作り、base64 と JSON を通して組み立て直す。私は base64 の変換と、10 MB の型付き配列を `deepStrictEqual` で比べるところが重いと見ていた。テストの中の処理を切り出して測ると、外れていた。

| 処理                                                   | 所要時間      |
| ------------------------------------------------------ | ------------- |
| `Uint8Array.from({ length: size }, (_, i) => i % 256)` | 210〜1,100 ms |
| base64 と JSON の往復                                  | 13 ms         |
| `assert.deepStrictEqual`                               | 31 ms         |
| `Buffer.equals`                                        | 2 ms          |

重かったのは、要素ごとにコールバックを呼んで中身を作る 1 行だけだった。テスト全体は単独で 1.7 秒、3 ファイルを並べて負荷平均 14 のときに 6.0 秒、報告では負荷平均 50 で 30.2 秒と、負荷にほぼ比例して延びていた。残りの時間は CPU の取り合いで、テストを軽くしても消せない。

そこで受け入れ基準も書き換えた。issue の「負荷平均 30 以上でも落ちない」は、CI でも手元でも再現できず、合否を決められない。代わりに「中身の生成にコールバック付きの `Uint8Array.from` を使っていない」「重さに見合う上限が明示されている」のように、コードを読めば判定できる述語にした。

### 4. 一次情報が曖昧なら、どちらの解釈でも成り立つ値を選ぶ

#726 は、X のメディアアップロードで、1 チャンク 4 MiB の生のバイトを base64 にして JSON で送っている（本文は約 5.6 MB）ことが、X の「5 MB」の上限を超えるおそれがある、という issue だった。X の公式ガイドには「Keep each segment at or below 5 MB (the server maximum is 8 MB).」とある。ただし、上限が生のバイトと要求の本文のどちらに掛かるかは書かれていない。API リファレンスにも上限の記載は無かった。

実機で確かめる機会（X の初回の実機確認）を待つ案もあった。代わりに、チャンクを 3 MiB にした。base64 にすると 4,194,304 文字で、どちらの解釈でも 5 MB（10 進）を下回る。送り方を multipart に変えて膨らみを無くす案は、アダプタとテストの両方を書き換えることになるので退けた。曖昧さが残っても、両方の解釈を満たす値なら実機の答えを待たずに決められる。

### 5. 「表示がおかしい」という報告は、その表示を決めた理由に照らしてから直す

#850 は、認証したばかりの YouTube のアカウントを `nyaucast auth status` が `expiring`（期限が近い）と表示する、というバグ報告だった。Google の OAuth の同意画面が「テスト」のままだと、refresh token の寿命は 7 日になる。`expiring` の窓も 7 日なので、認証した直後から `expiring` になる。

窓を寿命に対する割合にすれば、表示は直る。ところが、コードのコメントに窓の理由が書いてあった。「週に 1 回 status を見る運営者が、次の確認までに切れる前に気づける長さ」。寿命 7 日のトークンは次の週次の確認までに必ず切れるので、この理由に照らせば `expiring` は正しい。割合にすると数日 `valid` に見え、その間の週次の確認で見落とす。

直すべきは判定ではなく、いつ切れるかが見えないことだった。状態はそのままにして、行に期限の日時を出すことにした。もう 1 つ、「同意画面を本番に公開すれば起きない」という見方も外れていた。nyaucast の利用者はそれぞれ自分の Google Cloud のアプリで認証するので、「テスト」の 7 日のトークンを持つ利用者は残る。

### 6. 後から簡単に覆せる決定は、ADR にしない

#852 は、Gemini（サムネイルの生成と TTS）を Gemini Developer API のまま呼ぶか、Vertex AI 経由にするかを決める issue で、本文に「決まったら ADR にする」とあった。調べると、Vertex の express mode（API キーだけで呼べる経路）は画像生成のモデルに対応しているが、TTS は対応のモデルの一覧に無かった。Vertex で TTS を呼ぶには別の認証が要り、実機の確認も経路ごとに増える。v0.1 は Developer API のままにして、Vertex は v0.2 の issue に先送りした。

ADR にはしなかった。経路の差はエンドポイントと認証を持つ 1 つのモジュールに閉じていて、後から足す費用が小さい。ADR を書くのは、後戻りの費用が大きく、文脈が無いと驚かれ、本物のトレードオフがあったときに限る。この決定は 1 つ目を満たさない。決定の理由は issue の resolution のコメントに残した。

## 7 件の修正を Orca のワーカーで並列に回したら、PC が 2 回落ちた話

トリアージで実装に回した 6 件と、途中で見つかった 1 件（#857）を、Orca のワーカーに並列で実装させたときの学び。Orca は git worktree とターミナルを束ねるアプリで、coordinator（今回は私）がタスクを作り、ワーカー（別の Claude Code のセッション）を worktree ごとに起動して、完了の報告やエスカレーションを受け取れる。バグ修正の流れは、テストを先に書く `/tdd`、レビューの `/code-review`、commit、PR 作成と自動マージの予約、CI の監視の順。7 件はすべて CI を通ってマージされた（PR #859〜#865）。

### 1. 並列の本数は、エージェントの数ではなく、内側の並列との掛け算で見積もる

最初は 6 本のワーカーを一斉に起動した。各ワーカーは検査ゲート（`pnpm run check`）を流し、その中の vitest は、既定でコアの数だけワーカーを立てる。描画のテストはそれぞれ headless の Chrome を起動する。10 コア・16 GB のマシンで、負荷平均が 270〜300 まで上がり、Chrome が 30 個以上立って、PC が 2 回落ちた。同じマシンで別のリポジトリの作業をしていた別のセッションからも、本数を絞ってほしいという依頼が届いた。

本数を 2 本に絞り、1 本が終わるたびに次を起動するようにした。vitest のワーカーも絞った。検査ゲートの中身は `package.json` の 1 本の script で決まっていて、引数で `--maxWorkers` を足せない。vitest 5.0.1 の配布物を grep すると、環境変数を読む行があった。

```js
if (process.env.VITEST_MAX_WORKERS)
  resolved.maxWorkers = Number.parseInt(process.env.VITEST_MAX_WORKERS);
```

`VITEST_MAX_WORKERS=4 pnpm run check` も `VITEST_MAX_WORKERS=4 git push`（pre-push フックの検査）も、script を変えずに効く。2 本に絞ってからは、1 度も落ちなかった。

### 2. セッションが落ちても、そこから起こした子プロセスは止まらない

1 度目の再起動の後、6 本を同じ worktree で再開させたところ、また落ちた。調べると、落ちる前のワーカーが起こした `pnpm run check` が、親を失って（ppid 1）動き続けていた。vitest と Chrome だけで約 5.8 GB を使っていた。親のシェルを止めても孫のプロセスが残り、それも ppid 1 に付け替わった。

最後は、プロセスの系統ではなく作業ディレクトリで探した。`lsof -a -p <pid> -d cwd` で各プロセスの cwd を引き、ワーカーのいない worktree の下にあるものだけを止めた。名前で一括して止める `pkill` は、同じマシンの別のセッションの vitest まで巻き込むので使わなかった。止めた後、負荷平均は 300 前後から 114 まで下がった。

私自身の残骸もあった。前のセッションで回していた「報告を待つループ」が生き残り、Orca の Run を待ち続けていた。Orca は 1 つの Run に待ち手を 1 つしか置けないので、新しいループの待機は毎回 `waiter_exists` で即座に返り、回数だけを使い切っていた。

### 3. 中断したワーカーは、worktree の中身を確かめさせてから続きを書かせる

PC の再起動の後、Orca のタスクは失敗ではなく「起動待ち」に戻っていた。失敗したタスクを引き継ぐ `--retry-of` は、`task_not_startable` で拒否された（失敗か停止のタスクにしか使えない）。そこで、同じタスクを同じ worktree の path を指定して起動し直し、次のメッセージを送った。「最初からやり直さず、`git log origin/main..HEAD` と `git status` で残っている commit と変更を確かめて続きから進める。未 commit の変更は途中で切れている可能性があるので、確かめてから使う」。

6 件とも、前のワーカーの commit や stage 済みの変更を検証して引き継いだ。1 から書き直したワーカーは無かった。

### 4. 推移的な依存の公開 1 つで、main から切った PR がすべて同時に赤くなる

最初の PR（#859）の CI が、変更と関係の無い package-smoke のテスト 1 件で落ちた。package-smoke は、`pnpm pack` した tarball を lockfile の無い空のリポジトリに入れ、MCP server を起動する検査で、利用者のインストールを再現している。

原因は前日に公開された `@effect/platform-node-shared@4.0.5` だった。nyaucast は `effect` と `@effect/platform-node` を 4.0.0 で exact pin しているが、`@effect/platform-node@4.0.0` は `@effect/platform-node-shared` を `^4.0.0` で要求する。lockfile の無い環境はこれを 4.0.5 に解決し、4.0.5 は `effect` の 4.0.0 に無い export を import して起動に失敗する。リポジトリの中は lockfile が古い版に固定しているので、普段の検査は通る。exact pin は直接の依存にしか効かない。

直し方は、`effect` と 4.0 系の `@effect/*` をすべて 4.0.5 に揃えて上げることにした。Effect 4 は全パッケージが同じ版番号で出て、それぞれが peer に `effect: ^<自分の版>` を取るので、揃えた組み合わせだけが安定する。リポジトリの中の `overrides` で推移的な依存を固定する案は、利用者のインストールに届かないので退けた。

修正が入るまでの間、ほかのワーカーには、package-smoke だけで落ちるなら pre-push を `--no-verify` で飛ばして PR を作り、自動マージを予約して終えるよう指示した。自動マージは CI が green にならないと実行されないので、main は守られる。修正（#863）が入った後、残りの PR を `gh pr update-branch --rebase` で main に追従させると、5 本が 1 分の間に順にマージされた。

### 5. Orca の待機と zsh の `echo` には、はまりどころがある

- `orca orchestration check --wait --types "worker_done,escalation,question"` は、種類を絞っても、ワーカーの生存通知（heartbeat）が届くと返ってくる。heartbeat だけなら既読にして待ち直すループを、バックグラウンドで回した
- そのループのログに `null` が並んだ。zsh の `echo` は `\"` や `\n` を解釈するので、応答の JSON の中のエスケープされた文字列が壊れ、`jq` が読めなくなっていた。`printf '%s' "$r" | jq` に替えて直った
