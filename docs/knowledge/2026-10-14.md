## 「Effect を導入する」という依頼を、書き方の規約を揃える決定マップに描き直した話

運営者から「effect の導入をする、手本は live-mindmap」と頼まれ、作業の道筋を決定マップに描いたときの学び。Effect は TypeScript で失敗・依存・並行処理を型で扱うライブラリで、live-mindmap は同じ運営者の別のリポジトリ（会議の発言からマインドマップを作る道具）。決定マップは、作業を始める前に決めることを 1 問 1 チケットに分けて並べ、どれを先に決めるかを依存関係で表した issue の束のこと。決定の記録は [マップ #775](https://github.com/daiki-beppu/nyaucast/issues/775) と、その下の決定チケット（#776〜#783）。調査の記録は [#781](https://github.com/daiki-beppu/nyaucast/issues/781) の resolution コメントと、そこからリンクした調査用ブランチのファイルにある。

### 1. 「導入」と頼まれたら、まず導入済みかどうかを数える

依頼の文面どおりなら、Effect をこれから入れる作業になる。ところが調べると、nyaucast は 10 月 2 日の試作（#475）を経て、すでに Effect 4.0 を全面採用していた。`src` の 190 ファイルが `effect` を import し、Effect を import していないのは WAV の読み書きや図の markup のような純粋関数と、DB のマイグレーションだけだった。

依頼は「Effect を入れる」ではなく、「Effect の使い方を手本に寄せる」ことだった。そこで、最初の質問で対象を確かめた。候補は (a) 使い方を手本の流儀に寄せる、(b) Effect を使っていない範囲に広げる、(c) 別のリポジトリに入れる、の 3 つで、運営者は (a) を選んだ。(b) を推さなかったのは、Effect を使っていない箇所が、手本の規約でも「Effect で包まない純粋関数」に当たるからだ。

`grep -rlE 'from "(effect|@effect)' src | wc -l` の 1 行で、質問の中身が「入れるか」から「どう揃えるか」に変わった。

### 2. 手本との差は、ライブラリではなく、文書にされていない判断の基準に出る

両方のリポジトリをサブエージェントに比べさせると、大枠はすでに一致していた。Service の定義（`Context.Service`）、型付きのエラー（`Schema.TaggedError`）、`Schema.Class` を使わないこと、実行の入口を 1 か所にすること、古い API を検出する診断を error にすること、である。

差は、どれも書かれていない基準のほうにあった。いちばん大きいのは defect（自分のコードが約束を破った状態）の扱いで、2 つのリポジトリは正反対だった。

|                                        | live-mindmap                                                    | nyaucast                                           |
| -------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------- |
| defect の書き方                        | `throw`・`!`・`Effect.die` のどれでもよい                       | `throw` は src 全体で 0 か所。テストが禁止している |
| 利用者が編集するファイルの読み取り失敗 | 型付きの失敗にする                                              | `orDie`（defect）にしている                        |
| 失敗の分け方の基準                     | 「普通の関数 / 型付きの失敗 / defect」の 3 分類を文書にしている | 文書が無い                                         |

nyaucast では `orDie` が 49 か所あり、その中に、チャンネル設定や BGM の一覧のように利用者が手で編集するファイルの読み取り失敗が混ざっていた。「`throw` を書かない」という機械的な規則だけがあって、「何を defect とみなすか」の基準が無いと、`throw` で書かれるはずだった失敗がまとめて `orDie` に移る。規則が禁止しているのは書き方なのに、結果として失敗の分類まで変わってしまう。

### 3. テストの層は、ディレクトリではなく、本物の資源に触るかどうかで切る

live-mindmap は、テストの層をファイル名の接尾辞（`.it.test.ts` が軽い結合テスト、`.heavy.test.ts` が重いテスト）で分ける。さらに、unit がファイルシステム・子プロセス・ネットワークを import していないかを、構文木を見る検査で守らせている。nyaucast は `src/**` を unit、`test/**` を contract とディレクトリで分けている。そのため、unit 69 本のうち 24 本が本物のファイルシステムや HTTP クライアントを使っていた。

ここで私の思い込みが 1 つ外れた。調査を頼むときに、層の検査の実装として live-mindmap の `helper/scripts/checkTestLayers.ts` を指定した。名前から TS のテストの検査だと思ったが、実際には Swift で書かれた音声処理のヘルパー用の検査だった。TS 側の検査は `server/scripts/check-test-layers.ts` という別のファイルにあった。サブエージェントが両方を読んで指摘したので、比較の結果を間違えずに済んだ。手本のファイルを指定するときは、名前から推測せず、言語と対象を確かめてから渡す。

### 4. 規約の置き場所は、それを読む道具から逆算する

規約をどこに書くかの候補は、新しく作る `CODING_STANDARDS.md`、設計の決定記録（ADR）、エージェント向けの `AGENTS.md` の 3 つだった。決め手は、どの道具が何を読むかだった。

- バグ修正の経路で品質ゲートを担うレビューの skill（`/code-review`）は、規約の出典として `CODING_STANDARDS.md` を読む
- `AGENTS.md` には「読む前に踏み抜く落とし穴だけを置く」という方針がある
- 機能の実装を担う takt（AI エージェントに実装させるワークフローのツール）は、builtin のテスト方針を持っている

最後の点は調査で確かめた。live-mindmap のテストの基準のうち 3 つ（テストを足す前に根拠をそろえる、内部構造を契約にしない、評価はテストの層ではない）は、takt の `testing.md` とすでに重なっていた。ところが takt の方針が届くのは機能の経路だけで、バグ修正の経路には届かない。重なっている 3 つも、`CODING_STANDARDS.md` に書かなければ、バグ修正では効かない。規約は「どこに書けば正しいか」ではなく、「どの経路のどの道具が読むか」で置き場所を決める。

### 5. 決定は今、移行は後に分けると、移行対象がこれ以上増えない

このリポジトリは v0.1 のリリースに向けて、スコープを広げない約束をしている。既存の約 190 ファイルを揃える作業はリリースの条件と関係が無いので、次の v0.2 に回した。一方で、規約と ADR の決定は今確定させることにした。今も takt が新しいコードを書き続けているので、規約が決まるまでの間に、規約から外れたコードが増え続けるからだ。

揃え方には、機械的に検出できるものを検査ゲートに入れる方式を選んだ。違反を直す issue を軸ごとに切り、違反が 0 になった時点でゲートを有効にする。エージェントに書かせるコードは、文書に書いただけの規約からずれていく。手本の live-mindmap も、テストの層や実行の入口の規則をスクリプトの検査で守らせている。

## 中断した TAKT の依存付き実行を、記録と仕様を確かめて完走させた話

Cloudflare 環境の作成機能を、TAKT（計画・テスト・実装・レビューを順に実行する開発ツール）で進めたときの学び。2026-10-13 から翌14日未明にかけて、一時的に Codex を使い、中断した実行を再開しながら9件をマージした。対象は、動画の受け渡しに使う R2（Cloudflare のファイル置き場）の準備で、認証、アカウントの選択、アクセスキーの保存、利用者向けの説明が依存関係でつながっていた。仕様は [#687](https://github.com/daiki-beppu/nyaucast/issues/687)、認証の改訂は [#700](https://github.com/daiki-beppu/nyaucast/issues/700)、利用者向けの文書は [#705](https://github.com/daiki-beppu/nyaucast/issues/705)。設計の正本は [ADR-0012](../adr/0012-cloudflare-environment.md)、開発の実行経路は [ADR-0008](../adr/0008-takt-dedicated-workflow.md) にある。

### 1. 一時的なモデル変更は、適用する範囲と戻す条件を先に決める

今回の Codex への切替は、このリポジトリの実行に限った。通常の runtime（モデルと provider の割り当て）を残し、リポジトリ側の `.takt/runtime.yaml` に一時設定を置いた。グローバルの設定や、追跡する `.takt/config.yaml` に provider を書き足す方式にはしなかった。

TAKT は runtime と旧来の provider 設定が混在すると、`Mixed provider configuration` で実行前に止まる。起動できるかは `takt workflow doctor default` で確認した。切替先の名前が設定に入ったことと、builtin workflow 全体がその割り当てで成立することは別の確認になる。

復元の条件も「モデルが返答し終えたら」にはしなかった。対象の PR のマージを確認し、動いているタスクがなく、一時 runtime が自分の置いた内容から変わっていないことを確かめて解除した。最終記録は `complete`、`runtimeRestored: true`、`normalRunnerStarted: true`。一時変更を始めるときに、何を保存し、何を観測したら戻せるかまで決めておくと、途中の停止でも通常設定への戻し忘れを防げる。

### 2. 中断からの再開は、同じ clone と失敗位置を引き継ぐ

実行中、別エージェントによるタスクキルで runner が落ちたという報告が入った。ここで新しいタスクとして積み直すと、計画、途中の差分、レビューの報告、どこまで進んだかを示す checkpoint が別々になる。既存の隔離 clone（TAKT がタスクごとに用意する作業用の複製）と記録を残し、失敗タスクの retry 処理を使った。

[#699](https://github.com/daiki-beppu/nyaucast/issues/699) の retry 記録では、表面上の失敗工程は `develop` だったが、`resume-checkpoint` が指した位置は、その内側の `development-core > write_tests` だった。再開後の trace も `write_tests` から始まる。外側の工程名だけで再開位置を決めると、内側で済んだ計画をやり直したり、途中のテスト工程を飛ばしたりする。

今回は `prepareFailedTaskRetry` で保存済み状態を読み、`resolveTaskRetryStartOption` で `resume-checkpoint` を選び、`persistFailedTaskRetry` で再開を登録した。これは当時の TAKT 0.68.0 の内部 API を使った復旧で、版をまたいでそのまま使える公開コマンドではない。`tasks.yaml` を手編集せず、ツール自身に checkpoint と報告の対応を保たせたことが要点だった。

runner の確認にも同じ「対象の同一性」が要る。複数のリポジトリが同じホストで動くため、プロセス名だけでは対象を区別できない。`lsof -a -p <pid> -d cwd` で作業ディレクトリを確かめ、対象リポジトリの `takt watch` を1本にした。最後の復元処理では PID と起動時刻も照合し、同じ runner が終了したことを確認してから通常の runner を起動した。

### 3. 待機状態は、実行がないことと仕事がないことを分けて読む

最初の監視は `SyntaxError: Unterminated string in JSON` で停止した。大きい `takt list --non-interactive --format json` の出力を直接受け取っていたので、ファイルに全量を書いてから JSON として読む方式に変えた。表示された範囲だけで状態を判断すると、監視の入力そのものが欠けていることを見落とす。

入力を直しても、判定には別の穴が残った。実装中のタスクがない時点で、監視が「残りは依存待ち」と判断して終了した。しかし実際には、[#702 の PR](https://github.com/daiki-beppu/nyaucast/pull/769) に競合が残っていた。`ci-wait` は CI の確認が残る状態、`merge-conflict` は競合の解消が残る状態で、どちらも監視対象として動いている仕事だった。

そこで、実行中・投入済み、CI待ち、競合、失敗、依存待ち、マージ済みを分けて追い続けた。#705 は認証の #700、R2 利用可否の #701、キーの保存先を一つに保つ #703 を待つ。前提の実装が終わったという報告だけで進めず、main に入ったことを確認してから説明を書く順番にした。依存待ちを判定する前に、その依存を解除するための仕事がまだ残っていないかを見る。

### 4. 固定版で仕様が成立しなければ、テストを合わせる前に仕様を直す

#700 の元の要求は「専用プロファイルで `cf auth login` を起動する」と「利用者の既定プロファイルを読み書きしない」の両方だった。ところが固定依存 `cf@1.0.0-beta.12` の配布コードでは、`auth login --profile nyaucast` を拒否し、`auth login` の認証先は `default` に固定されていた。計画は配布物の SHA-512 が lockfile の integrity と一致することまで確認し、この衝突を報告して停止した。

偽物の子プロセスだけがこの引数を受け入れるテストなら、成功させられる。しかし本番の固定版は受け入れない。`--profile` を外すだけでも既定プロファイルの保護を破る。実装の都合で片方の要求を捨てず、名前付きプロファイルを作成・再認証できる `auth create <name>` を使うよう、先に issue の本文を改訂した。

確定した認証の引数は、専用名を位置引数、2つのスコープを別々の引数で渡す形だった。

```text
cf auth create nyaucast --scopes workers-r2.write account_api_tokens:create
```

スコープをカンマ区切りの1引数にまとめず、認証操作には `--profile` を付けない。これは nyaucast が内部で起動するコマンドで、利用者の入口は `nyaucast cloudflare` のままだ。

元の run `20261013-070726-implement-using-only-the-files-wkv21o` は計画段階で `Workflow aborted by step transition`、改訂後の run `20261013-145358-implement-using-only-the-files-zpmhdi` は同じ clone の計画位置から再開して完了した。再開時には改訂済み `order.md` を渡し、ADR-0012 の変更も [PR #772](https://github.com/daiki-beppu/nyaucast/pull/772) に含めた。復旧とは、止まった工程を動かすだけでなく、その工程が読んでいる前提を更新することでもある。

### 5. 競合を解くときは、双方の観測可能な動作を並べて残す

#702 は、アクセスキーの保存先が1Passwordかファイルかを、作成後の要約に出す変更だった。#704 は、R2 の環境変数が保存したキーより優先されるときに、変数名だけを標準エラーへ警告する変更だった。同じ CLI の要約付近を触ったため、マージ時に競合した。

片方のファイルをそのまま採用すれば、Git の競合は消えても、保存先の説明か、古い環境変数への警告のどちらかを失う。解消後は、要約の `accessKey` が実際の保存先を示し、その後で環境変数の警告を出す両方の動作を残した。変更なしの再実行でも両方を保ち、警告に秘密の値を出さない条件も維持した。

[PR #769](https://github.com/daiki-beppu/nyaucast/pull/769) と [PR #770](https://github.com/daiki-beppu/nyaucast/pull/770) はともにマージされ、現在の `src/cloudflare/cli.ts` に要約と警告の両経路がある。競合解消の確認単位は行の一致ではなく、それぞれの issue が求めた出力と副作用にする。

### 6. 並行数の制限は、そのホストで確認した運用条件として残す

今回の実行は `TAKT_CONCURRENCY=1`、ローカル検査は `VITEST_MAX_WORKERS=2` を基準に進めた。#699 の実装報告には、最初の timeout を成功扱いせず、worker 数を制限したうえで必要な検査を再実行した記録がある。一方、複雑度の検査で落ちた箇所はコードの変更で直している。検査の失敗をすべてホスト負荷のせいにしてはいけない。

この設定は、共有ホストで負荷を抑えながら完走させた条件として記録する。並行数を比較した性能実験ではないので、「どのホストでも最速」「2 worker なら timeout しない」とは言えない。回復の再現に必要な実行条件と、一般化できる性能の結論を分けて残す。

### 7. 実装完了・マージ・人間の実機確認には、それぞれ別の証拠を置く

#700 の再開 run は10月14日00:51 JSTに完了し、PR #772 は00:55 JSTにマージされた。後続の #705 も、run 完了は01:31 JST、[PR #773](https://github.com/daiki-beppu/nyaucast/pull/773) のマージは01:36 JSTだった。モデルの完了からマージまでは、CI と統合の確認が残っていた。

最終的に #697〜#705 の9件は PR #765〜#773 としてマージされ、最後の2件も `quality` の成功を確認できた。しかし、認証テストは子プロセスの引数、標準入出力の継承、失敗や中断後に先へ進まないことを確かめたもので、実際のブラウザ同意や Cloudflare の資源作成を実証したものではない。

[#706](https://github.com/daiki-beppu/nyaucast/issues/706) の実機確認は未完了のまま残した。実装がテストを通ったこと、変更が main に入ったこと、実サービスで人間が同意して動いたことを、同じ「完了」でまとめない。この区別があるから、開発の一時 runtime は戻せても、利用者の環境が動くとまでは報告せずに済む。

### その後

執筆時点の main では、ADR-0012 の専用プロファイル認証は `auth create` と独立したスコープ引数に改訂済みで、README も #705 により同じ流れを案内している。[10月6日の認証方式の記録](./2026-10-06.md#cloudflare-env-alchemy) にある `cf auth login` は、今回の固定版との照合を経て具体的な操作が変わった。専用プロファイルを守り、人間の同意から資源作成までをつなぐ目的は維持した。9件の実装の統合と通常 runtime への復元は完了し、実サービスでの確認は #706 に残る。

## defect を `throw` で書くかどうかを決めたら、関数を Effect で包むかどうかまで決まった話

1 本目のエントリで描いた決定マップのうち、最初の決定チケット「defect の書き方」を、運営者と質問を往復して決めたときの学び。defect は、外から来たものではなく、自分のコードが自分との約束を破った状態（バグ）を指す。手本の live-mindmap は、関数と失敗を「普通の関数（Effect で包まない）/ 型付きの失敗（`Effect<A, TaggedError>` を返す）/ defect」の 3 つに分けて文書にしている。nyaucast はこの 3 分類を取り込むことにして、defect の書き方も手本に揃えた。ただし 1 点だけ手本と違う決め方をした。決定は [#776 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/776#issuecomment-6158900238) にある。

### 1. 「`throw` を禁止するか」と「純粋関数を Effect で包むか」は、1 つの決定の表と裏になる

nyaucast では、`src` 全体で `throw` という語をテストが禁止している（コメントやテスト用の偽物も含む）。この禁止の副作用が、純粋な関数の形に出ていた。投稿の最後の試行を読み直す `toLastAttemptInput` は、入力を出力に詰め替えるだけの関数だ。ところが「成功したのに remote ID が無い」という、書き込み側の契約違反を表す分岐が 1 つある。`throw` が使えないので、この分岐を `Effect.die` で書くことになり、関数全体が `Effect.Effect<LastAttemptInput>` を返す形になっていた。

手本の規約は、defect を `throw`・`!`・`Effect.die` のどれで書いてもよいとしている。これがあるから「失敗も待ちも依存もない関数は Effect で包まない」という規則が成り立つ。defect の分岐を持つ純粋関数でも、`throw` で書ければ値を返す関数のままでいられる。2 つを別々の質問として扱うと、「包まない」を採用したのに `throw` を禁止したまま、という食い違った組み合わせを選べてしまう。そこで質問を出すときに、2 つが連動していることを説明に書いた。

書き方を変えても意味は変わらない。`Effect.gen` の中で `throw` すると、Effect はそれを die として扱う。effect 4.0.0 で次のように確かめた。

```ts
const exit = Effect.runSyncExit(
  Effect.gen(function* () {
    throw new Error("boom");
  }),
);
// Cause.hasDies(exit.cause) === true, Cause.hasFails(exit.cause) === false
```

### 2. 機械で区別できない規則に移るときは、禁止を外すのと規則を書くのを同じ PR にする

`throw` を認めると、「その `throw` は defect のためか」を機械で確かめる手段がなくなる。予期された失敗を `throw` で逃がしていないかは、レビューで規約と照らし合わせるしかない。そのため、禁止のテストを外す時期を独立した質問にした。候補は、規約の文書（`CODING_STANDARDS.md`）を置く PR で外す、既存コードを移行する v0.2 で外す、の 2 つだった。

前者を選んだ。理由は、どちらか片方だけが main に入っている期間を作らないことにある。文書だけが先に入ると、「`throw` を使ってよい」と書いてあるのに検査が落ちる。禁止だけが先に外れると、規則の無いまま `throw` が書ける。外すのは `throw` の検査の 1 行だけで、同じテストファイルにある zod の不使用や、実行の入口を 1 か所にする検査はそのまま残す。

### 3. 手本から外れる点は 1 つに絞り、その 1 点の理由を残す

手本には例外が 1 つある。同期の helper が `throw` し、呼び出し側が `Effect.try` で型付きの失敗に変えるなら、その `throw` は予期された失敗を運んでいてもよい、というものだ。nyaucast はこれを取り込まなかった。`Effect.try` や `Result.try` で包んでよいのは、外部ライブラリが投げる例外（XML パーサの `parse` など）だけにした。自分のコードの予期された失敗は、最初から `Effect.fail` で書く。

この例外を取り込まない理由は、nyaucast の経緯にある。前身のリポジトリは、検証ライブラリと `throw` で失敗を運んでいて、それを抜け出すために Effect を採用した。手本の例外を受け入れると、`throw` を見ても「バグだ」と言い切れなくなる。手本に「揃える」決定マップでも、全部を写すわけではない。外れる点を 1 つに絞って理由を書いておけば、後から読んだ人が「写し忘れ」と「意図した違い」を区別できる。

### 4. 1 つの規則を、機械で拾える部分と判断の部分に割る

「失敗しない関数は Effect で包まない」は、まるごと機械で検査することはできない。ただ、その一部は拾える。`yield*` を 1 つも持たない `Effect.gen` は、その典型だ。DB の行を記録の形に詰め替える `toPostRecord` は、この形で値を包んでいるだけだった。Effect の言語サービス（`@effect/tsgo`）には、こうした不要な gen を指摘する diagnostic が同梱されている。そこで、この部分は検査ゲートに入れ、違反が 0 になってから有効にすることにした。一方、「本当は失敗しないのに Effect を返している」かどうかの判断は、規約の文書に書いてレビューで見る。

規則を「検査か文書か」の二択で考えると、検査できない部分があるだけで文書に寄せてしまいがちだ。割れる規則は割って、機械で拾える部分を検査に任せる。

### 5. 失敗を値で返すのは出口だけにする

RSS などのフィードを読む `feed-reader.ts` は、取得や解析の失敗を、型付きのエラーではない素のオブジェクト `{ reason: "Timeout" }` などとして `Result` に載せて運び、最後に「失敗したフィード」の値に変えていた。1 本のフィードが壊れていても、他のフィードの結果は返したいからだ。部分的な成功を値で返すこと自体は正しい。

ただし、3 分類で見ると、外から来たフィードが壊れているのは型付きの失敗にあたる。内部では型付きのエラーを Effect の失敗チャネルで運び、関数の出口でだけ値に変えることにした。手本も「`Result` は使わず、呼び出し元がどの失敗も `yield*` で同じように読めるようにする」と書いている。「呼び出し元を失敗させない」という要求は、出口の形で満たせば十分で、内部の書き方まで変える理由にはならない。直すのは v0.2 の移行 issue で行う。

## ファイルと DB の失敗を、型付きにするか defect にするかを「誰が直せるか」で分けた話

決定マップの 2 枚目の決定チケット「ファイル I/O と SQL の失敗を、どこまで型付きの失敗にするかの線引き」を、運営者と決めたときの学び。前のエントリで決めた 3 分類（普通の関数 / 型付きの失敗 / defect）のうち、ファイルの読み書きと、ローカルの SQLite データベース（local.db。nyaucast が動画や投稿の状態を記録する store）の失敗を、どちらに入れるかを決めた。型付きの失敗は、MCP tool（エージェントが呼ぶ道具）が `failure` として宣言し、CLI が 1 行の文面にする失敗のこと。defect は内部のエラーとして扱われ、利用者には原因が伝わらない。決定は [#777 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/777)にある。

### 1. 問いの前提は、コードで数え直すと狭くなる

チケットの前提には、「nyaucast は利用者が編集するファイルの読み取り失敗も `orDie`（失敗を defect に変える）にしている」とあった。1 本目のエントリの比較表にも、同じ趣旨で書いていた。ところが、チャンネル設定を読むコードを開くと、事情はもっと細かかった。

```ts
if (!(yield * fileSystem.exists(configPath).pipe(Effect.orDie))) {
  return yield * new ChannelConfigNotFound({ path: relativePath });
}
return yield * fileSystem.readFileString(configPath).pipe(Effect.orDie);
```

「ファイルが無い」と「中身が壊れている」は、すでに型付きの失敗になっていた（`ChannelConfigNotFound` と `InvalidChannelConfig`）。BGM の一覧も同じだった。`orDie` になっているのは、ファイルはあるのに OS が読ませない場合（権限が無い `EACCES`、ディレクトリだった `EISDIR` など）だけだった。曲ファイルについては、その場合もすでに `BgmSongUnreadable` という型付きの失敗にしていた。

問いは「読み取り失敗を型付きにするか」から、「ファイルが存在した後の OS の I/O 失敗を、どのファイルなら型付きにするか」に縮んだ。調査で比べた結果を 1 行の表にまとめると、その時点で細部が落ちる。決定チケットに取りかかるときは、表の行ではなく、行の元になったコードを読み直してから質問を作る。

### 2. 型付きか defect かは、失敗の種類ではなく、ファイルの持ち主で決める

手本の live-mindmap の規約は、型付きの失敗の例として「ディスクから読むログや正解ファイル」を挙げている。この文だけを読むと、ディスクの読み取りはすべて型付きにするように見える。ところがコードでは、同梱の単語リストを読む箇所や、自分で管理するトークンのファイルを読む箇所を `orDie` にしていた。型付きにしているのは、CLI の引数で受け取ったパスや、利用者が用意する正解ファイルだった。規約の文よりもコードのほうが、本当の基準をよく表していた。

その基準は「誰が直せるか」だ。同じ `EACCES` でも、利用者が編集する設定ファイルで起きたなら、利用者が権限を直せば済む。だから、パスと理由を返す価値がある。nyaucast が自分で書き出した動画ファイルや local.db で起きたなら、利用者に渡しても打つ手が無い。そこで、次のように分けた。

| 持ち主                                   | 例                                                                   | OS の I/O 失敗 |
| ---------------------------------------- | -------------------------------------------------------------------- | -------------- |
| 外（利用者が編集する・置く・引数で渡す） | チャンネル設定、BGM の一覧と曲ファイル、引数で受け取った画像のパス   | 型付きの失敗   |
| nyaucast（自分で作って管理する）         | local.db、書き出した成果物、書き込み途中の一時ファイル、バックアップ | defect         |

引数で受け取った画像のパスを `orDie` で読んでいる箇所が 1 つ見つかった。これは移行のときに型付きの失敗へ直す。この基準はファイルの持ち主の判断なので、機械では見分けられない。`orDie` を許可リストで縛る検査も候補にしたが、新しい成果物のファイルを足すたびにリストを書き足すだけの作業になる。そこで検査は作らず、規約の文書に基準と具体例を書いて、レビューで守らせることにした。

### 3. 型付きの失敗の名前に、どのファイルかを持たせる

外のファイルの I/O 失敗を運ぶ型には、3 つの候補があった。ファイルごとに `ChannelConfigUnreadable { path, reason }` のような失敗を足す、共通の `FileUnreadable` を 1 つ作る、Effect のファイル操作の失敗（`PlatformError`）をそのまま出す、の 3 つだ。

ファイルごとに足す案を選んだ。tool の `failure` の宣言に、何のファイルが読めないのかが型の名前として出るからだ。共通の型にすると宣言は減るが、どのファイルかは文字列の中にしか残らない。`PlatformError` をそのまま出すと、Effect の内部の型が MCP の境界まで漏れる。`BgmSongUnreadable` という前例がすでにあったので、新しい形を発明せずに済んだ。

### 4. ロックの競合は、失敗として宣言する前に、待って解けるかを見る

local.db の SQL の失敗（`SqlError`）は、すべて defect のままにした。local.db は nyaucast 自身の store なので、壊れていたり制約に違反したりするのは自分のバグだ。

迷ったのは、別のプロセスがロックを握っている場合だった。手本の規約は「他のプロセスが握っているロック」を型付きの失敗の例に挙げている。nyaucast でも、CLI と MCP サーバーが同時に local.db へ書き込むことはありうる。そこで接続の設定を見ると、SQLite の `busy_timeout`（ロックが空くまで待つ時間）を設定していなかった。今は競合した瞬間に `SQLITE_BUSY` で失敗し、それが defect として返る。

ロックの競合は、型付きの失敗として宣言するより、待って吸収するほうがよい。宣言すると、SQL を使うすべての tool の `failure` に「混んでいます」が加わる。しかも、利用者に返せる対処は「もう一度やってください」だけで、それは待つのと変わらない。手本がロックを型付きにしているのは、待っても解けない、別のプログラムが持つロックだからだ。設定を足す作業は決定マップの外のバグ修正として切り出した（[#787](https://github.com/daiki-beppu/nyaucast/issues/787)）。待っても取れなければ、そのときは defect にする。

### 5. `exists` してから `read` する 2 段の書き方が、`orDie` の出どころになっていた

上のコードのように、「ある？」と聞いてから読む 2 段の書き方には、失敗の経路が 3 本ある。無い、読めない、そして `exists` 自体の I/O 失敗だ。3 本目には自然な行き先が無いので、`orDie` で片づけられていた。確認と読み取りのあいだにファイルが消える競合（TOCTOU）もある。

読み取りを 1 回だけ行い、その失敗のうち「見つからない」理由のものだけを捕まえる形（Effect 4 の `catchReason("PlatformError", "NotFound", ...)`）にすれば、経路は 2 本になる。「無い → `NotFound`」と「読めない → `Unreadable`」を、それぞれ 1 か所で割り当てられる。手本の live-mindmap もこの形で書いている。規約の文書に書き、既存コードの書き換えは v0.2 の移行で行う。失敗の線引きを決めると、どの書き方ならその線を 1 か所で引けるかまで決まる。

## 描画が遅いという報告を、撮影を速くする手段を選ぶ決定マップに描き直した話

動画の描画が Chrome のフレームの拍に待たされているという報告（[#747](https://github.com/daiki-beppu/nyaucast/issues/747)）から、作業の道筋を決定マップに描いたときの学び。nyaucast の動画は、HTML で書いた composition（時刻 `t` を渡すとその瞬間の絵になる 1 枚のページ）を headless の Chrome で開き、1 フレームずつ seek してスクリーンショットを撮り、それをエンコードして作る。決定の記録は [マップ #789](https://github.com/daiki-beppu/nyaucast/issues/789) と、その下のチケット（#790〜#793）。

### 1. 「このフラグを採るか」という問いは、速さを決める掛け算の 1 項に過ぎない

報告は、320x180 の小さな composition を使った実測だった。1 フレームの撮影に約 51 ms かかっていて、そのほとんどは CPU の仕事ではなく、Chrome の 60 Hz の拍を待っている時間だった。10 分の動画（18,000 フレーム）なら、撮影の待ちだけで約 15 分かかる。Chrome の起動フラグを 2 つ併用すると、1 フレームが約 4 ms まで縮んだ。報告の完了条件は「1080p でこのフラグの効果を測る」になっていた。

ところが描画時間は「撮る枚数 × 1 枚の時間 ÷ 同時に撮る数」で決まる。フラグが縮めるのは 2 項目だけだ。行き先を「フラグの採否」から「撮影を速くする手段の組み合わせを選ぶ」に広げ、比べる手段を 4 つにした。Chrome のフラグ、static 区間（絵が変わらない区間）の省略、タブ並列、撮影の画像形式の 4 つだ。報告者が測ったものを、そのまま問いの範囲にしない。

### 2. 契約が許している最適化が、使われないまま眠っていることがある

composition の契約は、`static: true` と宣言した区間を代表 1 フレームだけ撮り、エンコードのときに引き延ばしてよいと定めていた。ところがコードを読むと、解説動画の composition を作る組み立ての tool は、すべての区間に `static: false` を付けていた。撮影も、1 タブで先頭から全フレームを逐次に撮っていた。初期の試作では 4 タブ並列で 59.8 fps まで線形に伸びていたのに、それも使われていなかった。

解説動画は、図解が切り替わる瞬間以外ほとんど動かない。だから、フラグで 1 枚を速く撮るより、撮る枚数を減らすほうが効く見込みがある。速くする手段を探すときは、新しい仕組みを足す前に、すでに決まっている契約の中で使われていない余地がないかを先に見る。

### 3. 速さの合格ラインより先に、CPU の予算を決める

フラグの併用は撮影を約 12 倍速くした。しかし、何もしていないページでも Chrome が約 3.3 コアを回し続けた。テストを並行に走らせると、負荷平均が 155 まで上がり、timeout が多発した。この問題には「速さ」の基準だけでは答えが出ない。

そこで、予算を「何もしていないときの空回りは禁止、撮影中は使える CPU を使い切ってよい」と決めた。描画は利用者が明示的に起動する一括処理なので、撮影中に CPU を独占しても困らない。予算をこの形にすると、フラグの併用は直ちに不採用にはならない。代わりに「撮影していない間だけ空回りを止められるか」という、調べて答えが出る問いになる。この問いは調査チケット（#791）にした。

合格ラインは「10 分の解説動画 1 本の描画が実時間以内」にした。今のままでも約 15 分で終わるので、v0.1 のリリース作業を止める問題ではない。そこで今は決定だけを進め、実装は v0.2 に回す。

### 4. 小さな解像度での比率を、本番の解像度に持ち越さない

320x180 では、1 フレームの時間のほとんどが拍の待ちだった。1080p では、スクリーンショットを PNG にエンコードする時間の比重が増えるので、フラグの効き方の比率が変わる。最初のチケット（#790）は、4 つの手段を、1080p の実際の composition で、同じ機械を使って測る作業 1 本にまとめた。手段ごとに別のチケットで測ると、機械の負荷や composition が揃わず、数字を並べて比べられなくなる。

### 5. 速くする手段の候補は、決定論の検証の方式で絞られる

nyaucast は、同じ composition から同じ動画が出ることを、同じ時刻へもう一度 seek して撮った絵とバイトを比べて検証している。画像形式を PNG から変えて速くする候補も挙げたが、比べる形式は可逆なもの（ロスレスの WebP など）に限った。非可逆な形式では、バイトの一致が「同じ絵」を意味しなくなり、検証そのものの意味が変わるからだ。

static 区間の宣言方式も同じ理由で、今は決めずに測定の後へ回した（#792）。区間はプレビューで 1 枚ずつ撮る単位も兼ねているので、細かく分けるとプレビューの意味が変わる。宣言を誤ると、再 seek のバイト比較とプレビューのどちらで検出されるかも、方式によって変わる。省略が効くと数字で分かってから、契約を改訂する価値があるかを決める。

## 手本の「core を層に分ける」規約を、理由ごと確かめて持ち込まなかった話

Effect の書き方を live-mindmap に揃える決定マップで、決定チケット「effect 本体だけに依存する core を、物理的な層として作るか」を運営者と決めたときの学び。live-mindmap は、中核のコード（core）を `server/src/core/` に集め、`effect` 本体だけに依存させている。Node の型を外した専用の tsconfig（`types: []`）で型検査して、この境界を守らせている。nyaucast にも同じ層を作るかを問い、作らないと決めた。そのうえで、同じ手本の規約から「外から来るデータは Schema で検証する」と「型の正本は Schema」の 2 つだけを取り込んだ。Schema は Effect の、実行時に値を検証できる型定義のこと。決定は [#778 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/778)にある。

### 1. 手本の規約を持ち込む前に、その規約を立てた理由が自分のリポジトリにもあるかを確かめる

live-mindmap の規約は「中核が依存してよいのは `effect` 本体だけ」と書いている。文面だけを読むと、`effect` パッケージに入っているものなら何でも使ってよいように見える。ところが同じ ADR は、`effect/process` や `effect/socket` を、同じパッケージの中にあっても使わないと決めていた。規約の本当の意味は「実行環境に依存しない部分」で、その根拠は別の ADR の「中核は Node の実行環境に依存しない（ブラウザでも動く）」だった。

nyaucast は Node だけで動き、web もブラウザも無い。層の境界が守る対象が無いので、ディレクトリを作って検査を足しても、v0.2 の移行に「純粋な判定を抜き出す」大きな組み替えを足すだけになる。規約を写すかどうかは、規約の文ではなく、規約が立っている要件で判断する。

### 2. 同じ「core」という語が、2 つのリポジトリで別のものを指していた

nyaucast の ADR と用語集は、core を「MCP tool の handler」と定義している。MCP tool はエージェントが呼ぶ型付きの操作で、nyaucast の業務の中心だ。ところが、tool の定義ファイルは 21 本すべてが `effect/ai` の `Tool` を import している。多くは `SqlClient`（DB）や `node:util` も直接使っている。

つまり、nyaucast の core はつくりの上で、live-mindmap の意味の core（実行環境に依存しない層）になれない。2 つの定義を両立させるには、どちらかの「core」の呼び名を変える必要があった。層を作らないと決めたので、nyaucast の定義をそのまま残した。手本と語をそろえる作業では、同じ語が同じものを指しているかを、import を数えて確かめる。

### 3. 「今は作らない」には、問い直す条件を 1 行添える

v0.2 には、Cloudflare Workers の上に何かを置く案が 2 つある。R2 に投稿の知識を貯めてリモートの MCP で公開する案と、local store と成果物を実行環境の外に置く案だ。どちらかが nyaucast 本体の tool を Workers で動かすと決めたら、Node に依存しない core が初めて要る。

ただ、何を Workers に載せるかが決まらないうちに層の形を決めても、外れる見込みが高い。そこで「本体の tool を Workers で動かすと決めたら、core の範囲を問い直す」と ADR の Consequences に 1 行書くことにした。不採用の判断に、それが変わる条件を添えておくと、後から読む人が「なぜ無いのか」と「いつ要るのか」を同時に知ることができる。

### 4. 検証の規約は、違反 0 件で入れられる入口だけをゲートにする

「外から来るデータを Schema で検証したか」は、機械では直接検出できない。代わりに、検証を飛ばすいちばんよくある入口である `JSON.parse` を lint で禁止し、JSON は Schema を通して読むことにした。

grep で `JSON.parse` が 1 件見つかったときは、移行の対象かと思った。開いてみると、それは HTML テンプレートの文字列の中に書かれた、ブラウザで実行されるコードだった。TypeScript の AST の上では文字列リテラルなので、lint の対象にならない。実際の違反は 0 件で、ゲートはすぐ有効にできる。

型の断定（`as`）の禁止も候補にしたが、採らなかった。`as const` などの正当な使い方を除外する調整が要るうえ、`as` の多くは外のデータの検証とは関係がないからだ。誤検出を調整する費用が大きい検査より、違反 0 件のまま入れられる狭い検査を先に置く。

### 5. 型と Schema の二重定義は、DB の行を写す箇所に集まっていた

「型の正本は Schema」を規約にする前に、二重定義の実数をサブエージェントに数えさせた。

| 項目                                                  | 件数 |
| ----------------------------------------------------- | ---- |
| export している `interface` と `type`                 | 123  |
| うち手書きのオブジェクト形                            | 58   |
| Schema から型を導いている箇所（`typeof S.Type` など） | 63   |
| 同じ形を interface と Schema で二重に書いているもの   | 7    |

7 件のうち完全な重複は 2 件だけだった。残りの 5 件は、DB の snake_case の行の Schema を、手書きの camelCase の interface へ変換関数で 1 対 1 に写す形だった。列を足したときに片方だけ直してずれるのは、この写しだ。そこで規約の対象を「境界を越えるデータと、それを写した業務の型」とし、写しも Schema の変換で書くことにした。関数のオプションや内部の計算結果（58 件の大半）は interface のままでよいとした。すべての型を Schema にする案は、検証も直列化もしない値にまで Schema を強いることになるので採らなかった。手本の live-mindmap も、Schema を正本にする対象を外とやり取りするデータに限っている。二重定義は機械では見分けにくいので、ゲートは作らず、コードレビューで守らせる。

## 描画の撮影を 1080p で測ったら、効く手段がフラグから並列と省略に入れ替わった話

[描画が遅いという報告を、撮影を速くする手段を選ぶ決定マップに描き直した話](#render-capture-map)で作ったチケットのうち、最初の測定（[#790](https://github.com/daiki-beppu/nyaucast/issues/790)）を片付けたときの学び。比べたのは 4 つの手段で、Chrome の起動フラグ、static 区間（絵が変わらない区間）の省略、並列、撮影の画像形式。1080p の解説動画 1 本を使い、どれがどれだけ撮影を速くするかを同じ機械で測った。測定の記録は [#790 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/790)と、そこからリンクした調査用ブランチの `docs/research/capture-speed-bench.md` にある。機械は Apple M4（10 コア）、Chrome は chrome-headless-shell 154。

### 1. 測る対象の composition が無ければ、本物の tool で作る

dogfood のチャンネル（運営者が自分で回している本番相当のチャンネル）には、まだ 1080p の解説動画の composition が 1 本も無かった。手で HTML を書いて代用すると、字幕の帯、埋め込みフォント、図解の動きの runtime が本物と食い違う。そこで、テスト用の部品（一時ディレクトリのチャンネル、偽の外部 API）を流用し、本物の tool を lifecycle の順に呼んで作った。順番は、台本を書く → 図解を書く → 音声を合成する → 組み立てる、だ。偽物にしたのは音声合成の API の応答だけだった。

できたのは 1920x1080・30 fps・621 秒の composition だ。15 シーンで、字幕は 135 句、図解の動きは 105 個ある。フォントには日本語の Noto Sans JP（9.6 MB）を埋め込んだので、ファイルは 12.9 MB になった。

動きの密度だけは決めて書くしかなかった。そこで「ほぼ句ごとに 1 つ動く」という多めの側に置き、記録にもそう書いた。§4 の static 区間の割合はこの密度で決まるので、仮定を書かずに数字だけを残すと、後で読む人が数字を一般化してしまう。

### 2. 待ちに縛られた処理には、速くするより並べるほうが効く

| 手段（10 分の動画 = 18,000 フレームに換算） | 撮影の時間  | 撮影中の Chrome の CPU                   |
| ------------------------------------------- | ----------- | ---------------------------------------- |
| 現行（フラグなし・1 タブ・PNG）             | 24〜25 分   | 0.3 コア                                 |
| `--disable-frame-rate-limit`                | 15.5〜16 分 | 0.56 コア                                |
| フラグ 2 つを併用                           | 11.1 分     | 3.5 コア（何もしていなくても 3.35 コア） |
| Chrome 8 本 × 1 タブ                        | 3.1〜3.5 分 | 2.5〜3.7 コア                            |
| static 区間の省略                           | 約 2.6 分   | 0.3 コア                                 |

現行の撮影は 1 フレームに 80 ms かかる。その間、Chrome は 0.3 コアしか使っていなかった。時間の大半は計算ではなく、フレームの拍とスクリーンショットの完了を待つ時間だった。そのため並列は、2 → 4 → 8 とほぼ線形に効いた。8 並列では、1 つの Chrome に 8 タブを開く（5.3 分）より、Chrome を 8 本立てる（3.1〜3.5 分）ほうが速かった。

フラグは「1 枚を速く撮る」手段で、最大でも 2.2 倍にとどまった。1 本の処理が CPU を使っていないと分かったら、その 1 本を削る前に、何本並べられるかを見る。

### 3. 小さな解像度で見えた倍率は、本番の解像度で縮んだ

報告の実測は 320x180 で、フラグの併用は撮影を約 12 倍速くしていた。1080p では 2.2 倍だった。1 フレームの内訳を分けると理由が分かる。

| フラグ | seek と settle | スクリーンショット（PNG） |
| ------ | -------------- | ------------------------- |
| なし   | 21〜29 ms      | 52〜56 ms                 |
| 併用   | 1.2〜1.5 ms    | 40〜47 ms                 |

フラグが縮めるのは seek と settle（seek 後の描画が落ち着くまでの待ち）だけだ。1080p ではスクリーンショットの PNG の作成が大半を占めるので、全体の倍率は小さくなる。前のエントリで「小さな解像度での比率を本番に持ち越さない」と書いた予想は当たった。倍率だけを測らず、内訳を段ごとに分けて測っておくと、倍率が変わった理由まで説明できる。

### 4. 1 つずつは効く手段が、組み合わせると壊れる

フラグの併用は、単独では 3 番目に速い手段だった。ところが並列と組み合わせると壊れた。

- 1 つの Chrome に 2 タブを開くと、どちらのタブでも撮影が返らなくなった（5 秒で打ち切った）
- Chrome を 4 本並べると、空回り（フラグの併用で起きる、仕事が無くても CPU を回し続ける現象）が CPU を食い尽くし、1 フレーム 465 ms になった。現行の 80 ms より遅い

`--disable-frame-rate-limit` 単独の利得も、並列にすると消えた。Chrome 8 本で速い PNG（§6）を使うと、フラグなしが 1.9〜2.1 分、フラグありが 2.7〜2.9 分で、フラグありのほうが遅く、CPU は約 2 倍使った。CPU が飽和すると、1 本あたりの CPU を増やす手段は全体を遅くする。手段ごとの単独の数字だけを並べると、組み合わせの採否を誤る。最初から、組み合わせの格子（フラグ 4 種 × 並列の形 × 画像形式）で測った。

格子の測定は 1 本ずつ別の Node プロセスで走らせ、結果を 1 行の JSON で追記する形にした。途中で 1 つの組み合わせが止まっても、それまでの結果は残る。実際に、併用で 2 タブを開く組み合わせで 10 分以上止まり、そこから先だけを測り直した。

### 5. 省略してよいかは、危険な向きの誤りが 0 件かで確かめる

static 区間を省くには、どのフレームが前のフレームと同じ絵かを知る必要がある。composition が埋め込んでいるデータ（字幕の時刻、各動きの開始と長さ）から、各フレームの状態を、runtime の `seek` と同じ式で計算した。前のフレームと同じ状態が続く区間を数えると、全フレームの 90.3% が static で、区間ごとに 1 枚撮れば 10.7% の枚数で済む。

この予測は 20 秒分（600 フレーム）を実際に撮って確かめた。隣り合う 599 組のうち、15 組で予測とバイトが食い違った。食い違いは 2 つの向きに分けて数えた。

- 安全な向き: 「状態は変わるのに PNG は同じ」。動きの終わり際の、画素に出ない差だった。省けるのに撮るだけなので、無駄にはなるが壊れない
- 危険な向き: 「状態は同じなのに PNG が違う」。省くと絵が欠ける。これは 0 件だった

一致率（584/599）だけを報告すると、残りの 15 件が危険かどうかが分からない。省略やキャッシュのように「同じとみなして飛ばす」判定は、誤りを向きで分けて数える。

### 6. 「可逆な形式か」は、仕様ではなく画素を比べて確かめる

画像形式の候補は、可逆なものに限っていた。nyaucast は、同じ時刻へもう一度 seek して撮った絵とバイトを比べて、描画の決定論（同じ入力から同じ動画が出ること）を検証しているからだ。各形式で撮った画像を sharp で RGBA に戻し、PNG の画素と完全に一致するかを見た。

| 形式（CDP の引数）             | スクリーンショット | サイズ | PNG と画素が一致 |
| ------------------------------ | ------------------ | ------ | ---------------- |
| PNG（現行）                    | 40〜56 ms          | 67 KB  | 9/9              |
| PNG + `optimizeForSpeed: true` | 33〜47 ms          | 103 KB | 9/9              |
| WebP `quality: 100`            | 73〜86 ms          | 226 KB | 9/9              |
| WebP（既定）                   | 100〜121 ms        | 27 KB  | 0/9              |

既定の WebP は、同じ時刻を撮り直すとバイトは一致した。決定論の検査だけなら通ってしまう。それでも画素は PNG と一致しなかった（非可逆だった）。バイトの再現性と可逆性は別の性質なので、両方を確かめる。

効いたのは、最初は候補に挙げていなかった PNG の `optimizeForSpeed` だった。圧縮を軽くするだけなので可逆のまま、1 タブで 30〜35% 速くなった（ファイルは 1.5 倍）。報告の 320x180 では「効果なし」とされていた引数で、ここでも解像度で結論が変わった。

### 7. パイプラインの 1 段だけを測ったら、すべての数字にその段の名前を付ける

描画は、1 フレームごとに 3 段を通る。Chrome で PNG を撮る → sharp で PNG を RGBA に戻す → mediabunny（TypeScript の動画エンコードのライブラリ）でエンコードして mp4 に書く、の 3 段だ。今回測ったのは 1 段目だけだった。記録の「測っていないこと」の節にも、エンコードを含む描画全体の時間は測っていないと書いていた。

ところが要約には「static 区間の省略でも、Chrome 8 本の並列でも、単独で合格ラインに入る」と書いた。合格ラインは「10 分の動画の描画全体が実時間以内」なので、この一文は描画全体が速くなったように読める。運営者からは「mediabunny を使ってこれってことだよね？」と聞かれ、続けて「25 分が 13 秒で終わるのは激アツ」という反応が来た。13 秒は、3 つの手段（省略・並列・速い PNG）をすべて組み合わせたときの撮影だけの時間だ。デコードとエンコードは 1 ms も測っていない。

撮影が速くなるほど、残りの 2 段が描画の大半を占める。しかもエンコーダーにはフレームを順に流すので、撮影の並列はエンコードを速くしない。static 区間を省いても、エンコーダーに全フレーム分を渡すなら、その分の時間は残る。そこで、採否を決めるチケットの前に「PNG のデコードとエンコードの時間を測る」チケット（[#797](https://github.com/daiki-beppu/nyaucast/issues/797)）を足した。地図の要約は「撮影の時間は合格ラインの内側に入る（PNG のデコードとエンコードは未計測）」に直し、測定のチケットにも補足のコメントを残した。注記を本文の末尾に書いても、要約の一文だけが引用されて広まる。数字を出すたびに、それがどの段の数字かを同じ文の中に書く。

### 8. 並行に足し上げるときは、`await` を済ませてから足す

並列の測定では、画像の平均サイズが、並列度を上げるほど小さく出た（1 本で 67 KB、8 本で 9.5 KB）。並列で画像が小さくなるはずはない。原因は集計のコードだった。

```ts
bytes += (await captureAt(tab, index / fps, format)).length;
```

`bytes += await x` は、`bytes` の値を先に読んでから `await` で止まる。止まっている間に別のタブが `bytes` に足しても、再開したこのタブは古い値に足して書き戻すので、別のタブの分が消える。シングルスレッドの JavaScript でも、`await` をまたぐ読み・書きは競合する。`const shot = await ...; bytes += shot.length;` と、`await` を済ませてから足すように直した。時間の測定には影響しなかったが、1 回目の格子の平均サイズの列は使わず、測り直した値を使った。

<a id="test-layers-by-time"></a>

## テストの層を、手本の「本物の資源に触るか」ではなく所要時間で切った話

Effect の書き方を live-mindmap に揃える決定マップで、決定チケット「テストの層を接尾辞で分け、unit が本物の資源に触れないことを検査するか」を運営者と決めたときの学び。live-mindmap は、テストをファイル名の接尾辞で 3 つの層に分けている（`*.test.ts` が unit、`*.it.test.ts` が軽い結合テスト、`*.heavy.test.ts` が重いテスト）。そのうえで、unit がファイルシステム・子プロセス・ネットワークを import していないかを、構文木を見るスクリプトで検査している。nyaucast は層を接尾辞で分けることだけを取り込んだ。層の境界は「資源に触るか」ではなく「記録した所要時間が 7 秒を超えるか」で引き、`.it` の層は作らなかった。決定は [#779 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/779)にある。

### 1. 層の境界は、層を分けて走らせる目的と同じものさしで引く

まず、層を分けて何をしたいのかを数え直した。nyaucast で一部のテストだけを走らせたい場面は 2 つある。1 つは Stryker（コードを少しずつ壊して、テストが気づくかを確かめる mutation テストの道具）で、dry run を 1 プロセスで直列に流すので、重いテストが入ると時間の上限を超える。もう 1 つは、手元で速く回したいときだ。どちらも気にしているのは時間で、遅い原因はどうでもいい。

最初は、境界を「外部のプログラム（ffmpeg・Chrome・音声合成）を起動するかどうか」に置くことを勧めた。遅いテストを見ると描画や音声のものが並んでいたからだ。運営者もこの案を採り、遅さは記録した所要時間で検出することも決めた。ところが、検出の仕組みを詰めるために遅いテストの中身を開くと、外部のプログラムを起動していないのに遅いテストが 3 本見つかった。

| テスト               | 所要時間 | 遅い理由                                                              |
| -------------------- | -------- | --------------------------------------------------------------------- |
| `publish-gate`       | 15.5 秒  | CLI を通したケースが多く、ファイルと SQLite の本物の I/O が積み重なる |
| `generateThumbnails` | 13.5 秒  | 画像の JPEG 変換で CPU を使い、実際の時間でも待つ                     |
| `due-posts`          | 10.4 秒  | テスト用の時計を 10 秒ずつ進めて、ポーリングの待ちを解放する          |

定義は「外部のプログラム」、検出は「時間」になっていて、2 つが別のものを見ていた。この 3 本は、定義の上では unit なのに、検出の上では重いテストになる。そこで定義のほうを時間に寄せ、heavy を「記録した所要時間がしきい値を超えるテスト」とした。外部のプログラムの起動は、遅くなる代表的な原因として書くだけにした。定義と検出が同じものさしを見ていれば、食い違いはそもそも起きない。

### 2. 手本の層の境界は、手本が守りたい要件から来ていた

live-mindmap が unit で `fs` を禁じているのは、中核のコードがブラウザでも動く、という要件のためだ。unit が Node の資源に触れないことを確かめれば、その要件がテストの側からも守られる。同じ決定マップの前のチケットで、nyaucast にはこの要件が無いことを確かめ、中核を層として分けないと決めていた（[手本の「core を層に分ける」規約を、理由ごと確かめて持ち込まなかった話](#no-physical-core)）。境界の根拠になる要件が無いので、境界の引き方も手本に合わせる理由が無い。

数字もこれを裏づけた。src の unit 69 本のうち 61 本が、`test/` の helper を通して、一時ディレクトリと SQLite を本物で使っている。それでも 1 本あたり 0.1 秒前後で終わり、全テストの合計は約 199 秒だった。時間の大半は 7 本に集まっている（描画の 44.2 秒を筆頭に、29.1 / 20.6 / 15.5 / 13.5 / 11.1 / 10.4 秒）。手本の検査をそのまま入れると、61 本を書き換えることになるが、速さはほとんど変わらない。

### 3. 中に入るテストが無い層は置かない

`.it` を置かないと勧めたとき、運営者から「なぜそうなるのかわからない。`.it` はあってもいいと思う」と返ってきた。決定を急がず、なぜ `.it` が空になるのかを説明し直した。

手本の層は「何に触るか」で分かれている。unit は資源に触れず、`.it` は触れるが軽く、`.heavy` は触れて重い。unit で一時ディレクトリや SQLite に触れてよいと決めた時点で、`.it` に入るはずのテストは unit に吸収され、重いものは `.heavy` に入る。`.it` に入る条件を満たすテストが残らない。

`.it` を残すなら、入る条件を決め直す必要がある。現実的な候補は「ファイルや SQLite に触れるもの」で、その場合は約 53 本の名前を変え、unit には純粋なテストが 8 本ほど残るだけになる。得られるのは、手本と同じ 3 層の形と、unit が `node:fs` を直接 import していないかの検査だ。ただ、どちらの層も 1 本 0.1 秒前後なので、分けて走らせても手元の時間は縮まない。helper を通した間接的な利用も、import の検査では見えない。この比較を表で見せると、運営者は `.it` を置かない案を選んだ。層は、そのテストだけを走らせたい場面があるときに初めて意味を持つ。

### 4. 手書きの除外一覧は、すでに実態とずれていた

Stryker の設定には、重いテストの除外一覧が手書きで 4 本載っていた。所要時間の記録で 10 秒を超えるテストは 7 本あり、`publish-gate`・`generateThumbnails`・`due-posts` の 3 本は一覧から漏れていた。重いテストを足した人が、別のファイルにある一覧を直さなかった結果だ。

除外は、手書きの一覧をやめて `**/*.heavy.test.ts` の glob から導くことにした。ファイル名が分類の唯一の置き場所になり、一覧を直し忘れることが起きなくなる。ただし、除外されたテストは mutation の監査からも外れる。`due-posts` は予約投稿の中心のロジックなので、監査では `STRYKER_TESTS` に名前を挙げて個別に流す運用にした。

### 5. しきい値は分布の隙間に置き、検査は片方向にする

接尾辞を付け忘れていないかは、所要時間の記録（`vitest.shard-weights.json`、CI の shard の分け方に使っている、ファイルごとの秒数）と照合して、check の中で検査する。記録はリポジトリに入っているので、照合の結果はチェックアウトだけで決まる。

しきい値は 7 秒にした。記録を並べると、10.4 秒（`due-posts`）の次は 4.1 秒（`writeDiagram`）で、その間が空いている。記録はローカルで測った値なので、CI では揺れる。隙間の真ん中に置けば、どちらに揺れても誤検出しにくい。

検査は片方向にした。`.heavy` が付いていないのに 7 秒を超えるものだけを失敗にし、`.heavy` が付いているのに 7 秒を下回るものは見逃す。両方向にすると、記録を測り直すたびに、しきい値の近くのテストで `.heavy` を付けたり外したりする改名が起きる。ファイル名を変えると履歴をたどりにくくなるので、揺れを吸収する遊びを片側に持たせた。CLI やパッケージを外側から確かめる contract の層（`test/**`）は、プロセスを起動するのが当たり前なので、検査の対象から外した。今の違反は 7 本で、名前を変えるだけで 0 にでき、ゲートはすぐ有効にできる。

### 6. 前の見立ては、helper を通した利用まで数えたら外れた

同じ日の朝、決定マップを描いたときには、テストの層を「本物の資源に触るかどうかで切る」と書いていた（[「Effect を導入する」という依頼を、書き方の規約を揃える決定マップに描き直した話](#effect-conventions-map)）。そのとき数えた「本物の資源を使う unit」は 24 本だった。これは、テストのファイルが `node:fs` などを直接 import しているかを数えた結果だった。

このチケットで数え直すと、61 本のテストが `test/` の helper を import していて、その helper が一時ディレクトリと SQLite を作っていた。直接の import だけを数えると、資源の利用は半分以下に見える。この数え違いに気づいて、「資源に触るかで切る」という方針は、1 本 0.1 秒のテストをほぼ全部書き換える話だとわかった。依存を数えるときは、テストのファイルだけでなく、それが import する helper まで追う。

### その後

この日の最後の決定チケット「check のゲートを有効にする順番」で、Stryker を廃止すると決め、heavy 層もやめた。`.heavy` の接尾辞を読むのは Stryker の除外一覧だけで、ほかに読むものが無かったからだ。テストの層は unit と contract の 2 つになり、7 秒のしきい値と照合の検査は作らない。1 節の「層を分けて走らせる目的」は、その目的の片方が消えたことで成り立たなくなった。経緯は[検査ゲートの順番を、違反を数えてから決めたら、Stryker と heavy 層ごと消えた話](#gate-order)にある。

<a id="static-holds"></a>

## 変わらない区間の宣言を、区間を細かく切らずに別のキーで足すと決めた話

[描画が遅いという報告を、撮影を速くする手段を選ぶ決定マップに描き直した話](#render-capture-map)で後回しにした、static 区間（絵が変わらない区間）をどう宣言するかを決めたときの学び。[1080p の測定](#capture-speed-bench)で、解説動画の全フレームの 9 割は省いて撮らずに済むと分かった。この省略を使うには、composition（時刻 `t` を渡すとその瞬間の絵になる 1 枚のページ）が、どこが変わらないかを capturer に申告する必要がある。決定の記録は [#792 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/792)。

### 1. 区間を細かく切る前に、その区間が他に何の単位を兼ねているかを数える

composition 契約では、タイムラインを segment という区間の並びで覆い、segment ごとに `static: true` を申告できる。解説動画の composition を作る組み立ての tool（図解・字幕・テーマから composition を作る、ブラウザを使わない tool）は、segment をシーン単位で作り、すべてに `static: false` を付けていた。素直に考えると、変わる区間と変わらない区間ごとに segment を切り直せば、契約を変えずに省略が使える。

コードを読むと、segment は省略の単位のほかに 3 つの役目を兼ねていた。

- プレビュー（人とエージェントが絵を確かめるための静止画）は segment 1 つにつき 1 枚撮る。番号は「シーン N」を指していて、エージェントは「シーン 3 の図解を直す」の手がかりに使っている
- 描画の決定論の検証は、各 segment の終わる直前のフレームを撮り直してバイトを比べる
- composition の中の runtime は、シーンを表示するかどうかを、segment から作った `data.scenes` で判定していた

10 分の動画は字幕が 135 句、動きが 105 個なので、細かく切ると segment は 200〜400 個になる。プレビューも 200〜400 枚になり、番号はシーンを指さなくなる。そこで segment はシーン単位のまま残し、変わらない区間は新しい任意キー `holds: [{ start, duration }]` で宣言すると決めた。追加だけの改訂なので、BGM 動画の composition（agent が全体を書く）は `holds` を書かなければ何も変わらない。

### 2. 宣言は、描画が読むのと同じデータから導く

変わらない区間は、タイミング表（音声合成が返す、句ごとの秒の表）からも計算できる。しかし、そうすると、seek が絵を描くときに読む値と、宣言を作る値が別々になり、片方だけを直したときにずれる。

そこで、runtime の `seek` が読むのと同じ `data` から導くことにした。使う値は、動きの区間（各動きの開始と長さ）、字幕の切り替わり、シーンの境目の 3 つだ。変わる時刻をすべて集め、その補集合のうち 2 フレーム以上続く区間を hold にする。こうすると、宣言と描画がずれるのは組み立ての tool のバグだけになる。そのバグは「hold がどの動きの区間とも、どの字幕の切り替わりとも重ならない」という性質のテストで、ブラウザを立てずに止められる。

### 3. 同じ時刻への撮り直しでは、宣言の誤りは見えない

契約書は、static の申告の誤りは「再 seek のバイト比較でも不一致として表面化する」と書いていた。ところが実装の検証（`reseekMismatches`）は、一度撮ったフレームと同じ時刻へもう一度 seek して比べている。これが確かめるのは「同じ `t` から同じ絵が出るか」という純関数性で、「区間の中で絵が変わらないか」ではない。宣言を誤っていても、同じ `t` を 2 回撮れば同じ絵が出る。プレビューもシーンの最後のフレームしか撮らないので、シーンの途中にある hold の誤りは写らない。この食い違いには、宣言の方式を決めた後、この記事を書くために検証のコードを読み直して気づいた。

誤りを見るには、hold の中の違う 2 つの時刻を比べる必要がある。そこで、描画の検証で各 hold の最初と最後のフレームを撮り、バイトが違えば throw することにした。代表フレームは最初のフレームを流用するので、追加の撮影は hold 1 つにつき 1 枚で済む。

### 4. 両端の 2 枚で足りるのは、動きが単調だからだ

区間の両端が同じ絵でも、途中で一度変わって元に戻っていれば誤りを見逃す。解説動画の動きは、登場（enter）・強調（beat）・暗転（dim）の 3 種類しかない。どれも進み具合を 0〜1 に clamp した単調な値で動かしていて、元の絵に戻る動きはない。だから、途中で絵が変われば最後のフレームは必ず違う絵になる。

この前提は、点滅や揺れのような往復する演出を語彙に足すと崩れる。その日が来たら、両端の比較では足りなくなる。決定の記録には、この前提も書いておいた。

### 5. 採るかどうかが決まっていない手段は、形だけ決めて契約にはまだ書かない

省略を採るかどうかは、別のチケット（手段の組み合わせの採否）が、エンコードの時間の測定を待って決める。このチケットで契約に `holds` を書き足すと、採らないと決まったときに取り消す手間が生じる。そこでこのチケットでは「採るなら、この形で宣言する」という条件付きの答えだけを resolution コメントに残し、契約と ADR の改訂は採否の PR でまとめて行うことにした。

用語も増やさなかった。契約書がすでに使っている「static 区間」を、「`static: true` の segment か hold が覆う区間」の総称に広げる。キー名には、アニメの「止め」と同じ意味の `holds` を選んだ。`static` という語と混ざらないからだ。

## 構造の検査をテストから外し、lint と検査スクリプトに振り分けた話

Effect の書き方を live-mindmap に揃える決定マップで、決定チケット「構造の検査を、テストで持つか check のスクリプトで持つか」を運営者と決めたときの学び。ここでいう構造の検査とは、振る舞いではなくコードの形を見る検査のことで、たとえば「ある import を使っていない」「Effect の実行関数（`runMain` など）を入口の 1 ファイルでしか呼んでいない」「tool 1 本ごとにテストが 1 本ある」といったものを指す。nyaucast はこれを vitest のテスト 1 本（`test/effect-migration.test.ts`）に集めていた。live-mindmap は同じ役を、型検査の一部として走らせる `scripts/check-*.ts` に置いている。決めた結果は次のとおり。lint で書けるものは lint に、lint で書けないものだけを検査スクリプトに置き、テストには置かない。テストのファイルは振り分けたうえで削除する。決定は [#780 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/780)にある。

### 1. 置き場所を決める前に、すでに動いている検査を数える

テスト 1 本の中身を開くと、検査は 3 種類に分かれていた。ソースの禁止パターン、ファイルの置き方、`package.json` の方針（依存を消したこと、版を固定したこと）の 3 つだ。問いは「テストかスクリプトか」の 2 択として立てていたが、check（コミット前に通す検査のまとめ）の中身を読むと、3 つ目の置き場所がすでにあった。未使用の依存やコードの重複を見つける fallow というツールだ。fallow は、未使用の依存、本番コードで dev 依存を使っていないか、ディレクトリ間で import してよい向き（`boundaries`）をすでに検査していた。

そのため、テストにあった「zod と Drizzle を依存から消した」「実行時の依存と開発用の依存を正しく置き分けている」という確認は、置き場所を移すまでもなく重複していた。依存を消したことは、lint で import を禁じれば再び入ってこなくなり、fallow が未使用の依存を拾い、`lockfile:check` が lockfile と manifest のずれを拾う。2 択で問いを立てると、どちらにも移さずに捨てる、という第 3 の答えが見えにくい。

### 2. lint で書けるかどうかは、ルールを実際に動かして確かめる

lint に寄せる案を出す前に、Vite+ に同梱されている oxlint が、どの制限ルールに対応しているかを確かめた。設定ファイルに書いて 1 行のファイルにかけるだけで分かる。

```json
{
  "rules": {
    "no-restricted-syntax": ["error", "CallExpression"],
    "no-restricted-properties": ["error", { "object": "Date", "property": "now" }]
  }
}
```

結果は `Rule 'no-restricted-syntax' not found in plugin 'eslint'` だった。`no-restricted-syntax` を外して `no-restricted-properties` だけにすると、`Date.now` と `JSON.parse` の呼び出しを正しく指摘した。この違いで、lint とスクリプトの線が引けた。`Date.now`・`process.argv`・`process.exit`・`Effect.runPromise` のような「オブジェクトのメンバーを呼ぶ」禁止は lint で書ける。特定のファイルだけで許すもの（libSQL の client を開くのは local store だけ、`runMain` を呼ぶのは入口だけ）も、ファイルごとの override で書ける。一方、「引数の無い `new Date()`」は構文の形でしか見分けられないので、スクリプトに残る。ESLint では当たり前に使える `no-restricted-syntax` が無い、ということは、動かすまで分からなかった。

lint に寄せる理由は、エディタの上ですぐに赤くなり、行番号付きで指摘され、テストの shard（CI でテストを分けて並行に走らせる単位）をまたがないことだ。テストの assert は「違反したファイルの一覧」を出すだけで、どの行かまでは示さない。

### 3. 移行が済んだ時点を固める assert は、規則と分けて捨てる

残りを振り分けるとき、「規則」と「移行が済んだ時点の確認」を分けた。たとえば、tool の配置の検査は、tool の名前 16 本と 3 本を一覧で持っていた。「定義 1 本ごとにテストが 1 本ある」は規則だが、名前の一覧は、tool を足すたびに書き換える必要がある写しだ。規則だけをスクリプトに移し、一覧は捨てた。

ほかに、「vite-plus を 1.0 に固定している」「check に `@effect/tsgo` の検査が入っている」も捨てた。前者は移行が済んだ時点の版の確認で、後者は check の中身を別の場所に写したものだ。このリポジトリでは、check に何が入っているかを決めるのは `package.json` の script だけで、他のどこにも書き写さないと決めている。テストがその中身を確かめていると、その決まりを自分で破ることになる。移行のときに書いた検査は、終わった後も「ずっと守る規則」と「移行を確かめた跡」が混ざったまま残りやすい。

### 4. 検査器そのものには、振る舞いのテストを付ける

live-mindmap は「内部構造を契約にしない」というテストの基準を持っている。それなのに、検査スクリプトには `test/checkEntrypoints.test.ts` のようなテストを付けている。一見すると矛盾しているように見えるが、そうではない。検査器のテストが確かめているのは、ソースの構造ではなく「違反を入れたら検査器が見つける」という検査器の振る舞いだ。テストが無いと、正規表現が壊れて何も検出しなくなっても、check は黙って通り続ける。

nyaucast もこの形に揃えた。違反を探す処理は純粋な関数として export し、実行の部分は薄くする。置き場所だけは手本と変えた。手本はこのテストを `test/` に置いているが、nyaucast は前のチケットで `test/**` を「CLI やパッケージを外側から叩く contract の層」と決めていた（[テストの層を、手本の「本物の資源に触るか」ではなく所要時間で切った話](#test-layers-by-time)）。純粋な関数のテストは unit なので、`scripts/*.test.ts` に置き、unit の対象に加える。層の定義を決めた直後に、それと矛盾する置き方を手本からそのまま写しかけていた。

### 5. 手本の検査は、それが守っている事情ごと持ち込むかを決める

live-mindmap の入口の検査は 3 つある。`process.exit` を呼ばない、`runMain` の終了処理に `exitNaturally` を渡す、`runSync` を呼んでよい場所を許可リストで縛る、の 3 つだ。このうち持ち込んだのは `process.exit` の禁止だけで、nyaucast の違反は 0 件だった。`exitNaturally` は持ち込まなかった。nyaucast の CLI は終了処理を自前の `cliTeardown` で組み、そこで終了コードを決めている。その振る舞いは、CLI のテストが終了コードを見て確かめている。手本の検査は、手本の入口の書き方を前提にしている。前提が違うリポジトリにそのまま写すと、正しいコードを違反として指摘する検査になる。

### 6. 「違反 0 件の見込み」は、数えるまでは見込みとして書く

チケットを閉じるとき、決定マップに「lint への移し替えは既存の検査を移すだけなので、違反 0 件で入れられる見込み」と書いた。直後に運営者から「検証器は通った？」と聞かれ、何も走らせていないことに気づいた。コードは 1 行も変えておらず、実際に動かしたのは前の節の oxlint の 2 つのルールだけだ。

「見込み」と書いた根拠は、元のテストが通っているから、lint に移しても違反は出ないはずだ、という推論だった。しかしこの推論は、移した後のルールが元の正規表現と同じ範囲を見ているときにしか成り立たない。たとえば `fetch` の禁止は、元のテストでは `src/youtube/client.ts` の 1 ファイルだけを見ていた。lint で `src/` 全体に広げれば、別のファイルの `fetch` が違反として出てくるかもしれない。決定の記録には、確かめた事実と推論を区別して書き、推論のほうは実装の issue で数えるところから始める。

<a id="test-criteria"></a>

## テストの判断基準を、重なるレビュー方針があっても書くと決めた話

Effect の書き方を live-mindmap に揃える決定マップで、決定チケット「live-mindmap のテストの判断基準のうち、どれを持ち込むか」を運営者と決めたときの学び。live-mindmap の規約ファイル（`CODING_STANDARDS.md`）には、テストを書くときの判断基準が 8 項目ある。テストを足してよい条件（Evidence gate）、内部構造を契約にしないこと、層の選び方、待ちの補助関数の形などだ。このうちいくつかは、nyaucast が feature の実装に使う takt（AI エージェントに実装・レビューを順に回させるワークフローのツール）の組み込みのテスト方針と中身が重なる。重なる項目を書くかどうかと、手本のどの項目を採るかを決めた。重なりの調査は前のチケット（[#781](https://github.com/daiki-beppu/nyaucast/issues/781)）で済んでおり、決定は [#782 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/782)にある。

### 1. 重なる規則を書くかどうかは、その規則がすべての経路に届いているかで決める

Evidence gate は、テストを足す前に 5 つの根拠（足す義務、正本から取った契約、実際の経路での失敗、既存のテストが拾わない理由、いちばん小さい層）を示せ、という基準だ。live-mindmap 自身が takt の `testing.md` を出典として書いており、中身はほぼ一対一で一致する。チケットの問いには「takt がすでに課しているものを重ねて書くと二重管理になる」という前提が書かれていた。この前提に従えば、書かないことになる。

ところが、nyaucast でコードが main に入る経路は 2 つある。feature は takt で実装し、fix は takt を使わず、別のスキル（`/implement`。テスト先行で実装し、`/code-review` でレビューする）で実装する。takt の方針が届くのは feature の経路だけだ。`/code-review` は、リポジトリの `CODING_STANDARDS.md` を規約の出典として読むが、nyaucast にはこのファイルがまだ無い。書かなければ、fix の経路では Evidence gate がまったく効かない。

そこで、全文は写さず、1 行の要旨と「出典: takt の `testing.md`（ここには写さない）」というリンクだけを書くことにした。中身の正本は takt に残るので二重管理にはならず、fix の経路のレビューからも参照できる。「重なっているから書かない」という判断は、重なっている相手がすべての経路を覆っているときにしか成り立たない。

### 2. プロジェクトの方針に「禁止」と書くかどうかで、レビューの強さが変わる

層の規則は「契約を持てるいちばん小さい層に置き、同じ失敗を別の層で検査し直さない」というものだ。これも takt と重なって見える。しかし、takt の `testing.md` を読むと、上位の層での重複は、既定では「警告」にとどまる。REJECT（差し戻し）にするのは、プロジェクトのテスト方針が明示的に禁止している場合だけだ。

つまり、takt の方針は、プロジェクトの方針を入力として受け取るように書かれている。nyaucast が重複の禁止を明示的に書けば、feature の経路の takt のレビューも重複を差し戻すようになる。書かなければ警告が出るだけだ。同じ規則でも、書くことでレビューの判定そのものが変わる。重なりを比べるときは、項目の有無だけでなく、相手の規則が自分の方針を参照して強さを変えていないかまで読む。

### 3. 手本の失敗例は、自分のリポジトリにもあるか grep してから採る

live-mindmap は「待ちの補助関数は壁時計の締め切りで動き、時間切れになったら待った条件の名前を付けて失敗する」と定めている。きっかけは、200 回ポーリングしたあと何も言わずに return する補助関数が、takt のレビューを通ってしまった実例だ。この形は、速い機械では通り、CI に負荷がかかったときだけ、待ちの後ろの検査が分かりにくい理由で落ちる。

採るかどうかを問う前に `waitUntil` と `poll` で grep すると、nyaucast にもまったく同じ形があった。

```ts
const waitUntil = (condition: () => boolean) =>
  Effect.gen(function* () {
    for (let attempt = 0; attempt < 200 && !condition(); attempt += 1) yield* realDelay(10);
  });
```

手本の例と一致する実物が手元にあると、規則を採る理由を説明し直す必要がない。この補助関数は、規則を採ったうえで、決定マップの外の fix として起票した（[#802](https://github.com/daiki-beppu/nyaucast/issues/802)）。

反対の例も、同じ日に目にしていた。作業を始める前に、不要になったブランチをリモートから消そうとしたところ、push の前に走る検査（テスト全件）が落ちた。落ちたのは、MCP サーバーを子プロセスとして起動して JSON-RPC で話すテストの 3 本で、失敗のメッセージは `timed out waiting for JSON-RPC response 1` だった。こちらの補助関数は 25 秒の締め切りを持ち、何を待っていたかを名前で言う。並行して他の作業が走っていて負荷が高かったので、時間切れになったとみている（原因はまだ調べていない）。それでも、どの待ちが時間切れになったのかは 1 行で分かった。

### 4. Effect のテストでは、締め切りを「どの時計で」測るかまで書く

手本の規則をそのまま写すと、Effect では落とし穴になる。Effect のテストは、時計を止めたテスト用の時計（`TestClock`）の下で動き、時刻はテストが明示的に進めたときにしか進まない。この下で `Effect.timeout` を使って締め切りを書くと、止まった時計で測られるので、締め切りがいつまでも来ない。上の `waitUntil` も、この事情を知っていて、`setTimeout` を包んだ実時間の遅延（`realDelay`）でポーリングしている。間隔は実時間で取れていても、止める条件が回数になっていた。

そこで規則に「締め切りは実時間（`Date.now()` など）で測る。`TestClock` の下では `Effect.timeout`・`Effect.sleep` は締め切りとして働かない」という注意を書き足すことにした。fix の issue では、締め切りの既定値を 3 秒にした。unit のテストのタイムアウト（vitest の既定の 5 秒）より短くしておけば、テストランナーのタイムアウトより先に、条件名の付いた失敗が出る。

### 5. 外部の API を呼んで確かめる規則には、呼べないときの逃げ道を書く

live-mindmap には「レビューで未検証のまま先送りした指摘が、外部 SDK・API の挙動に依存するなら、マージ前に最小の実呼び出しで確かめ、PR に記録する」という規則がある。nyaucast は YouTube・Instagram・X・R2 などを呼ぶので、採る理由は十分にある。

ただし、nyaucast の外部 API の多くは投稿系で、呼ぶと実際に公開されるか、認証の資格情報が要る。エージェントは資格情報を持たない。規則をそのまま書くと、守れない場面が必ず出て、守れない規則は黙って無視されるようになる。そこで「実呼び出しができない API は、できなかったことと、確かめていない範囲を PR に書けばよい」という逃げ道を、規則の中に明記した。逃げ道を書いておけば、守れなかったことが記録として残る。

### 6. 2 つの経路で基準が食い違うなら、強い側に揃える

既存のテストの扱いは、手本と takt で方向が違った。live-mindmap は「規則は新しいテストにだけ適用し、内部構造を固定する既存のテストを一度に掃除しない」。takt は「今回の変更の契約に触れる既存のテストが内部構造を固定していれば、消す。関係のないテストまでは広げない」。

feature の経路では、nyaucast が何を書いても takt の基準が効く。fix の経路に手本の基準を書けば、同じ既存テストを、feature では消し、fix では残すことになる。経路によって結果が変わらないよう、takt の基準に揃えた。「一度に掃除しない」という点は両者で共通なので、失うものはない。

### 7. 対象の無い規則は持ち込まず、決まっていないことを規則にしない

残りの 3 項目は持ち込まなかった。E2E のテストを locator の `expect` だけで判定する規則と、Evals（モデルの出力の品質を測る評価）はテストの層ではないという規則は、nyaucast に Playwright の E2E も Evals も無いので、守る対象が無い。

Fakes（外部サービスの偽物の実装）は事情が違う。nyaucast にも Instagram・R2・X・YouTube の fake があるが、その形を決めた記録は無い。live-mindmap の規則は「fake の形は #446 の決定に従う」で、中身は手本の別の決定にある。nyaucast には参照できる決定が無いので、規則として書けることが無い。決める必要が出てきたら、そのときに決定として起票する。

運営者は、ここまでの 7 問すべてに推奨どおりと答えた。

<a id="render-encode-bench"></a>

## 撮影を速くしたら、描画の律速がエンコードへ移った話

[描画の撮影を 1080p で測ったら、効く手段がフラグから並列と省略に入れ替わった話](#capture-speed-bench)で「撮影だけを測った数字を、描画全体の数字のように書いてしまった」と書いた。その穴を埋めるチケット（[#797](https://github.com/daiki-beppu/nyaucast/issues/797)）で、残りの 2 段を測ったときの学び。描画は 1 フレームごとに、Chrome で PNG を撮る → sharp で PNG を RGBA に戻す → mediabunny で H.264 にエンコードして mp4 に書く、の 3 段を通る。同じ機械（Apple M4・10 コア）で、同じ 10 分・1080p の composition（描画の元になる HTML 1 枚）を使った。測定の記録は [#797 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/797)と、調査用ブランチの `docs/research/render-encode-bench.md` にある。

### 1. 1 段を速くしたら、次の段を同じ機械で測り直す

10 分の動画 1 本の描画全体（3 段すべて）の時間はこうなった。合格ラインは 10 分。

| 形                                                             | 描画全体    | 遅い段                      |
| -------------------------------------------------------------- | ----------- | --------------------------- |
| 現行（Chrome 1 タブで 1 枚ずつ）                               | 25.1 分     | 撮影（79 ms/フレーム、95%） |
| Chrome 8 本で並列に撮る                                        | 3.8〜5.3 分 | 撮影とエンコードが釣り合う  |
| static 区間の省略 + Chrome 8 本、同じ絵を枚数分エンコード      | 2.5〜3.1 分 | エンコード                  |
| static 区間の省略 + Chrome 8 本、長い `duration` の 1 枚で覆う | 0.8〜1.2 分 | 映像が音声の進みを待つ      |

static 区間は、演出も字幕も変わらず、絵が同じまま続く区間のこと。

現行では、撮影の 79 ms に対し、デコードは 3.5 ms、エンコードは 1 ms だった。撮影を除いた 2 段を単独で回すと、10 分の動画で 1.6〜2.4 分しかかからない。ここまでは「後ろの 2 段は小さい」という予想どおりだった。

予想と違ったのは並列のときだ。Chrome 8 本の撮影だけなら、前のチケットで 1.9〜2.1 分だった。エンコードをつなぐと 3.8〜5.3 分になった。エンコーダーへの 1 枚の受け渡しは、単独では 4 ms だったのに、8 本の Chrome と同じ CPU を取り合うと 6〜17 ms に伸びた。エンコーダーにはフレームを順に流すしかないので、撮影を何本に増やしてもここで頭打ちになる。段ごとに測った時間を足し合わせても、描画全体の時間は出ない。CPU を取り合う段は、つないだ状態で測り直す。

### 2. 非同期の段は、直列に流すと「待ち」しか測れない

エンコーダーは、mediabunny のサーバー向け拡張（`@mediabunny/server`。FFmpeg のバインディングの node-av を使う）が既定で選ぶ。既定ではハードウェアのエンコーダーが優先され、この Mac では `h264_videotoolbox` が選ばれていた。選ばれたエンコーダーは、node-av の `HardwareContext.auto()` に H.264 のエンコーダー名を尋ねて確かめた。

VideoToolbox は非同期に動く。現行の作りのように「1 枚デコードしたら 1 枚渡す」と直列に流すと、エンコーダーが手すきのまま次の 1 枚を待つので、受け渡し（`VideoSampleSource.add`）は約 1 ms で返る。この 1 ms はエンコーダーの処理量ではない。デコードを 4 枚先に進めておき、エンコーダーが追いつけない速さで渡すと、受け渡しは 4〜5 ms に伸びた。これが処理量（約 200〜250 fps）で、全フレームを渡す限りの床になる。非同期の段の速さを知りたいときは、その段が詰まるまで入力を先に送り込んでから測る。

### 3. 省いた区間を出力でどう表すかで、mp4 の性質が変わる

static 区間を省いて撮ると、デコードも区間ごとに 1 回で済む。エンコーダーへの渡し方は 2 通りあり、出力の性質が違った。

- **同じ RGBA を、区間のフレーム数だけ渡す。** 出力は、全フレームを撮って渡したときと**バイト単位で同じ mp4** になった（18,633 フレーム・固定 30 fps）。省略が絵を変えていないことを、これ以上ないほど強く確かめられる。ただしエンコードの回数は減らないので、2.5〜3.1 分にとどまる
- **長い `duration` を持つ `VideoSample`（mediabunny でエンコーダーへ渡す 1 フレーム分の映像）を 1 枚だけ渡す。** 渡すのは 1,986 枚で済み、描画全体は 0.8〜1.2 分まで縮んだ。再生時間（621.1 秒）は正しく、全体に散らした 24 時刻で出力と元の PNG を比べた PSNR（2 つの画像がどれだけ近いかの指標）も、全フレームを渡したときと同じ最低 41.4 dB だった。ただし出力は、1,986 枚のパケットで 621 秒を覆う**可変フレームレートの mp4** になった

出力の確かめ方は 3 つ用意した。映像のパケット数、映像と音声の再生時間、散らした時刻での PSNR だ。どれか 1 つだけだと、可変フレームレートになったことか、絵が正しいことか、どちらかを見落とす。

可変フレームレートの mp4 を、配布先の YouTube・Instagram・X がそのまま受け付けるかは分からない。採否を決めるチケットに入れずに、調査のチケットとして切り出し、採否のチケットの前提につないだ。運営者は 1.2 分という数字に「やばいね激アツ」と反応した。そこで返答では、1.2 分の形は可変フレームレートになること、固定フレームレートを保つ形なら 1.4〜2.5 分になることを、同じ段落で伝えた。前のエントリの教訓（数字を出すたびに、それがどの段の数字かを同じ文に書く）を、条件付きの数字にも当てはめた形だ。

### 4. ファイルが大きい形式のほうが、デコードは速かった

PNG の `optimizeForSpeed`（Chrome のスクリーンショットの引数。圧縮を軽くする）で撮った画像は、通常の PNG より 1.5 倍大きい。デコードは遅くなると思っていたが、逆だった。通常の PNG が 6.2 ms/フレーム、速い PNG が 2.8 ms/フレームで、半分以下になった。圧縮が軽いぶん、展開も軽い。2 つの形式は画素が同じなので、エンコード後の mp4 もバイト単位で同じだった。撮影で 30〜35% 速い引数が、デコードの段でも得になる。

### 5. ベンチが黙って白紙を撮っていたのを、前回の記録の数字で見つけた

最初に全フレームを撮ってディスクに書いたとき、PNG の平均サイズが 8.5 KB だった。前のチケットの記録では、同じ composition で 67 KB だ。開いてみると真っ白だった。

原因は、composition のパスを相対パスのまま `file://` に付けて Chrome に渡したことだった。ページは読み込まれず、seek を呼ぶ `Runtime.evaluate` は例外を結果の中に返すだけで、呼び出し側は失敗しない。前のチケットのスクリプトは絶対パスに直してから渡していたが、新しく書いたスクリプトはそれを引き継いでいなかった。18,633 枚・約 2 分の撮影は、何のエラーも出さずに終わった。

気づけたのは、前回の記録に平均サイズの列があったからだ。測定を作り直したら、前回の記録と同じ条件の値を 1 つ出して、一致するかを先に見る。今回は直したあと 66 KB になり、前回の 67 KB とそろった。

同じときに、30 フレームだけの試運転が 65 秒かかった。映像は 30 フレームなのに、音声は 621 秒分をすべて AAC にエンコードしていたからだ。短く測るときは、音声も同じ長さに切る。

### 6. 負荷の高い機械では、揺れても変わらない結論だけを言う

測定のあいだ、同じ機械でほかの作業も重く動いていた（負荷平均 5〜40）。同じ組み合わせを 2 回測ると、Chrome 8 本で 3.8 分と 5.3 分、省略との併用で 0.8 分と 1.2 分のように、最大 1.4 倍開いた。

負荷の無い時間を待つ代わりに、結論のほうを揺れに強い形にした。「どの組み合わせが合格ライン（10 分）の内側に入るか」と「どの段が遅いか」は、2 回のどちらで見ても変わらない。値は 2 回分を幅で書き、生の結果を 1 回目と 2 回目で別のファイルに残した。負荷の無い機械での再測定は、「測っていないこと」の節に書いた。

<a id="cli-failure-table"></a>

## CLI の失敗の文面を、型で網羅する表にしなかった話

Effect の書き方を live-mindmap に揃える決定マップで、最後の決定チケット「CLI の失敗の文面を、タグの漏れが型エラーになる表にするか」を運営者と決めたときの学び。nyaucast の CLI は、コマンドが失敗すると、その失敗を標準エラーに 1 行で出す。失敗はどれも、種類を表すタグ（`_tag`）と、何が起きたかを表す値の field を持つ型付きのエラー（Effect の `Schema.TaggedError`）だ。手本の live-mindmap は、この 1 行をタグごとの表で作り、タグを扱い漏らすと型エラーになると聞いていた。nyaucast も同じ形にするかを決めた。決定は [#783 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/783)にある。

### 1. 「型で網羅している」と聞いたら、何に対して網羅しているかを読む

チケットの前提には「live-mindmap は、タグを漏れなく扱わないと型エラーになる表を持つ」と書いてあった。問いを運営者に出す前に手本のコードを読むと、表は次の形だった。

```ts
const CLI_FAILURES = [ServerUnreachable, ServerFailed, NoSession /* …全 10 クラス */] as const;
type CliFailure = InstanceType<(typeof CLI_FAILURES)[number]>;

const failureLine = (failure: CliFailure): string => {
  switch (failure._tag) {
    case "ServerUnreachable":
      return "サーバーにつながりません（pnpm dev で起動）";
    // …
  }
};
```

`switch` が網羅しているのは、手で並べた配列 `CLI_FAILURES` の 10 クラスだけだ。プログラムが実際に出しうる失敗の全体ではない。配列に入れ忘れた失敗は型エラーにならず、入口で汎用の表示（`describe(failure)`）に落ちる。型エラーになるのは「配列には入れたが、`case` を書き忘れた」場合だけだった。

前提のとおりに受け取っていれば、「型で漏れを防げる表を、nyaucast では採るか」という問いになっていた。実際の守りの範囲は狭いので、問いは「手で列挙した一覧に対する網羅に、手間に見合う価値があるか」に変わった。

### 2. 網羅の価値は、漏れたときに出る文面の質で決まる

live-mindmap の表は、失敗ごとに日本語の文面を手で書く。この方式では、表に無い失敗は利用者に読めない形で出るので、網羅に意味がある。

nyaucast は方式が違う。共通の関数 `describeFailure` が、どの失敗でも「タグ + field の JSON」を 1 行にする。

```
CollectionNotFound {"collectionId":"01JMISSING"}
```

`message` も stack も出さず、事実だけを出す。nyaucast には型付きのエラーが 54 個あるが、どれを足しても、追加の作業なしに読める 1 行が出る。表に載せ忘れても、困るのは「次に何をすればよいか」の一言が出ないことだけだ。今それが必要な失敗は 4 つしかない（1Password へのサインイン、Cloudflare R2 の checkout、Cloudflare のアカウント作成、`--yes` を付けた再実行）。この 4 つには、`cli.ts` で補足の文を足している。

同じ「表で網羅する」でも、漏れたときに読めない文面が出る設計では価値が大きく、漏れても読める文面が出る設計では価値が小さい。

### 3. 本当に網羅させる案は、費用を数えてから捨てる

手本より強く、プログラムの失敗の型そのものから表を作る案も検討した。コマンドを実行する関数の失敗の型から `_tag` の union を取り、`Record<タグ, 文面>` で受ければ、新しい失敗が増えた時点で型エラーになる。

費用を数えると見合わなかった。54 個以上のタグに 1 件ずつ書くことになり、ほとんどは `describeFailure` と同じ文面だ。さらに、nyaucast の CLI は、各サブコマンドに渡す依存（Effect の Layer）を外から型引数で受け取っており、その Layer が出す失敗の型も型引数になっている。タグを型として取り出すには、この型引数も解く必要がある。

補足の要る失敗が増えたときに書き忘れるおそれは残る。これには、その失敗を起こす PR のテストで文面を確かめることで対応し、`pnpm run check` のゲートは作らなかった。運営者は、推奨どおり「表にしない」を選んだ。

### 4. 手本から持ち込まなかった流儀こそ、規約に 1 行書く

表にしないなら、何も書かなくても今のコードのままでよい。それでも、規約ファイル（`CODING_STANDARDS.md`）に次の 1 行を書くことにした。

> CLI の失敗は `describeFailure` がタグと事実で 1 行にする。`message` は出さない。利用者が次に何をすればよいかを伝える必要がある失敗だけ、`cli.ts` で補足を足す。

このマップの目的は「手本に揃える」ことなので、後でレビューする人やエージェントは、手本と見比べて「表になっていない」と指摘しやすい。揃えなかった点と、その理由になった nyaucast 側の設計を規約に書いておけば、その指摘に規約の側から答えられる。

### 5. 決定チケットが尽きたら、保留していた論点を問いの形に書き直す

このチケットで、マップの決定チケットはすべて閉じた。マップには、まだ問いの形にできない論点を置く「Not yet specified」の節があり、3 つが残っていた。規約ファイルと ADR の構成、`pnpm run check` に検査を入れる順番、v0.2 の移行 issue の切り方だ。どれも「決定チケットがひととおり閉じた後で問いにする」と書いて保留していた。

閉じた決定を前提にすると、3 つとも「何を決めるか」を箇条書きにできたので、新しいチケットにした（[#806](https://github.com/daiki-beppu/nyaucast/issues/806)・[#807](https://github.com/daiki-beppu/nyaucast/issues/807)・[#808](https://github.com/daiki-beppu/nyaucast/issues/808)）。移行の切り方は、どのゲートが違反 0 件で先に入るかに左右されるので、ゲートの順番のチケットの後にしか着手できないよう依存を張った。「Not yet specified」は空になった。

## 規約の文書と ADR を、「何が変わったら書き直すか」で分けた話

Effect の書き方を live-mindmap に揃える決定マップで、チケット「`CODING_STANDARDS.md` と ADR の構成」を運営者と決めたときの学び。それまでの 7 枚の決定チケットで、失敗の分け方・テストの層・構造の検査などの中身は決まっていた。残っていたのは、それをどの文書にどう書き分けるかだ。`CODING_STANDARDS.md` は、レビューの skill（`/code-review`）が「このリポジトリのコーディング規約」として読むファイルで、ADR（Architecture Decision Record）は、設計の決定とその理由を 1 件ずつ残す文書である。決定は [#806 の resolution コメント](https://github.com/daiki-beppu/nyaucast/issues/806)にある。

### 1. ADR を分ける単位は、「何が変わったら書き直すか」で決める

候補は 3 つあった。既存の ADR-0001 を改訂して済ませる、新しい ADR を 1 本作ってマップの決定をまとめる、軸ごとに 2 本作る、である。

ADR-0001 は「1 MCP tool = 実装 1 ファイル + テスト 1 ファイル」という薄いアーキテクチャの規約で、すでに 9 項目の決定を抱えていた。失敗の書き方は、その決定 3（エラーを型付きの失敗として持つ）を細かくしたものなので、ここに足すのは自然に見える。けれども、テストの層や構造の検査の置き場所まで入れると、「薄いアーキテクチャ」という主題がぼやける。

1 本にまとめる案と 2 本に分ける案は、書き直すきっかけで比べた。テストの層の境界は「記録上 7 秒を超えるテスト」というしきい値で引いているので、テストの所要時間の分布が変われば見直すことになる。その見直しは、失敗を型付きにするか defect にするかの規約には触れない。変わる理由が別々なので、2 本に分けた。

- ADR-0013「失敗と境界のデータ」: 関数と失敗の 3 分類、ファイルの持ち主による線引き、core を物理的な層にしないこと、境界を越える型の正本を Schema にすること
- ADR-0014「テストの層と構造の検査」: テストの 3 層と 7 秒のしきい値、lint と検査スクリプトの 2 段、テストの判断基準を規約に書く理由

2 本には「v0.2 で tool を Cloudflare Workers で動かすと決めたら問い直す」という同じ条件が付く。その条件だけを理由に 1 本にはせず、両方の Consequences に 1 行ずつ書くことにした。ADR-0001 には、決定 3 と決定 9 に新しい ADR への参照を 1 行ずつ足すだけにした。

### 2. 機械で守らせる規則は、規約の文書に書かない

書き分けの原則は次の 3 つにした。

- ADR: 理由、採らなかった案、問い直す条件
- `CODING_STANDARDS.md`: 機械では見分けられない判断の規則と、その例（`throw` は defect のときだけ使う、利用者が直せるファイルの失敗だけを型付きにする、など）
- lint や検査スクリプトで守らせる規則（`JSON.parse` の禁止、`process.exit` の禁止、`.heavy` の付いていない遅いテストの検出など）: `CODING_STANDARDS.md` には書かず、理由は lint のメッセージとスクリプトのエラー文に書く

機械で守らせる規則を文書にも書くと、設定を変えたときに文書との食い違いが生まれる。違反すれば検査が止めるので、文書に書く意味は薄い。nyaucast の `AGENTS.md` にはもともと「検査ゲートが何を実行するかは `package.json` の `check` script だけが定義し、どこにも書き写さない」という規則があり、手本の live-mindmap の `CODING_STANDARDS.md` も冒頭で「機械的な規則は check が持ち、このファイルは判断だけを持つ」と書いていた。2 つの規則は同じ考え方なので、そのまま揃えられた。

境目になったのはテストの層の定義だ。手本は層の名前と接尾辞を別のファイル（`docs/agents/checks.md`）に分けている。nyaucast では、層の定義は `CODING_STANDARDS.md` のテストの節の冒頭に置き、しきい値の「7 秒」という数値は検査スクリプトにだけ置くことにした。どの層にテストを置くかは判断なので、その前提になる定義は判断の近くに置く。数値は機械が使う値なので、機械の側に置く。別のファイルを作ると、check の中身を書き写す場所が 1 つ増える。

### 3. 短い返答が前の決定を覆しそうなら、範囲を確かめてから記録する

1 回目の質問で「`CODING_STANDARDS.md` は日本語で書く」を推し、運営者は「すべて推奨どおり」と答えた。ADR・`AGENTS.md`・用語集と言語を揃えるのが、推した理由だった。

2 回目の質問で章立ての案を出すと、「07 は英語でいい」と返ってきた。この 1 行は 2 通りに読めた。章立ての見出しだけを英語にする（手本と見出しを揃える）か、本文まで英語にして 1 回目の決定を覆すかだ。前者だと思い込んで記録していれば、1 つ前の回答と矛盾しない形には収まるが、運営者の意図とずれていたかもしれない。確認の質問を 1 つ出すと、答えは「本文まで英語」で、1 回目の決定が覆った。

推奨どおりの回答が続くと、短い返答も推奨に沿った意味で読みたくなる。けれども、その返答が直前に決めたことを覆す読み方を許すなら、どちらの意味かを聞いてから記録する。往復は 1 回増えるが、決定チケットに誤った決定を残して後で直すより安い。

### 4. 実装と同じ PR にすると決まっている文書は、決定チケットでは書かない

このチケットの成果物を、構成を決めるところまでにするか、ADR と `CODING_STANDARDS.md` の PR まで作るかも問いにした。前に閉じた決定チケットで、「`throw` を禁止しているテストは、`CODING_STANDARDS.md` を置くのと同じ PR で外す」と決めていた。規則が文書に書かれていないまま、禁止だけが解かれる期間を作らないためだ。

このチケットで文書を書くと、その約束を守るためにテストの変更まで含めることになる。決定マップは「決めるだけで、実装はしない」という運用なので、文書を書く作業は、テストを外す作業と 1 つの PR にまとめて、最初の実装 issue に回した。その PR を検査ゲートの順番のどこに置くかは、次の決定チケット「check のゲートを有効にする順番」で決める。前の決定が後のチケットの成果物の形を縛ることがあるので、チケットの範囲は前の決定と照らし合わせて決める。

### その後

1 節で ADR-0014 に入れるとした「テストの 3 層と 7 秒のしきい値」は、次の決定チケットで heavy 層ごとやめた。ADR-0014 には、代わりに heavy 層を作らない理由（Stryker の廃止）を書く。経緯は[検査ゲートの順番を、違反を数えてから決めたら、Stryker と heavy 層ごと消えた話](#gate-order)にある。

## 検査ゲートの順番を、違反を数えてから決めたら、Stryker と heavy 層ごと消えた話

Effect の書き方を live-mindmap に揃える決定マップで、決定チケット「check のゲートを有効にする順番」を運営者と決めたときの学び。検査ゲートは、`pnpm run check` の 1 コマンドで走らせる検査（lint・型検査・テスト・検査スクリプトなど）のことで、CI と push 前のフックも同じコマンドを呼ぶ。それまでのチケットで「機械で検出できる規約はゲートに入れ、違反が 0 になってから有効にする」と決めていた。このチケットでは、そのゲートをどの順番で、どう issue に分けて入れるかを決めた。決定は [#807 の resolution コメントと追記](https://github.com/daiki-beppu/nyaucast/issues/807)にある。

### 1. 「直す issue と有効にする issue をどう分けるか」は、違反を数えると問いごと消えることがある

チケットの問いは、違反が残るゲートについて「違反を直す issue」と「ゲートを有効にする issue」をどう分けるか、どれを v0.1 に入れてどれを v0.2 に回すか、だった（v0.1 は今のリリースで、スコープを広げない約束がある）。問いを立てたときは、違反が多く残るゲートがあると見込んでいた。

grilling の質問を出す前に、候補のゲートごとに今の違反を数えた。

| ゲート                                                                   | 今の違反                      |
| ------------------------------------------------------------------------ | ----------------------------- |
| lint で `JSON.parse` を禁止する                                          | src の本体で 0 件             |
| lint で `process.exit` を禁止する                                        | 0 件                          |
| 既存の構造テスト（`effect-migration.test.ts`）を lint とスクリプトに移す | 移すだけなので 0 件           |
| `.heavy` の付いていない遅いテストを検出する                              | 7 本（改名だけで 0 件になる） |
| tsgo の diagnostic を error に上げる                                     | 15 件（どれも機械的に直せる） |

いちばん多くても 15 件で、どれも 1 本の issue の中で直してから有効にできる。直す issue と有効にする issue を分ける理由が無くなった。

v0.1 と v0.2 の線引きも同じように消えた。v0.2 に回した移行の対象（失敗を値で返している箇所、Schema と型の二重定義など）には、前のチケットでどれも「ゲートを作らない」と決めていた。どのゲートも v0.2 の移行を待たないので、すべて v0.1 の期間に入れてよい。問いの形のまま運営者に聞いていたら、存在しない選択肢を選ばせることになっていた。

### 2. 違反の数は、検査を一時的に強くして実際に数える

tsgo の diagnostic（Effect の言語サービスが TypeScript の型検査に足す警告）は、設定ファイルを書き換えなくても、ルールの重さを上書きして走らせられる。

```sh
effect-tsgo diagnostics --project tsconfig.json --format json \
  --lspconfig '{"name":"@effect/language-service","diagnosticSeverity":{"outdatedApi":"error","unstableApiUsage":"off","unnecessaryEffectGen":"error","effectSucceedWithVoid":"error","unnecessaryFailYieldableError":"error"}}'
```

結果を `jq` でルールごとに数えると、`unnecessaryEffectGen`（`yield*` の無い `Effect.gen`）が 9 件、`unnecessaryFailYieldableError` が 5 件、`effectSucceedWithVoid` が 1 件だった。`unnecessaryEffectGen` の 9 件はすべてテストのコードにあった。設定を変えずに数えられるので、ゲートを入れる前の見積もりを、決める前の会話の中で済ませられる。同じ出力には、ゲートの対象外の warning（`multipleEffectProvide`）も 71 件あった。どのルールを上げるかを決めずに「diagnostic を error にする」とだけ書くと、この 71 件まで巻き込む。

### 3. 「違反 0 件」は、どこに禁止をかけるかを決めるまでは 0 件ではない

前のチケットでは「`JSON.parse` の禁止は違反 0 件」と書いていた。grep で数え直すと、2 つのことが分かった。

- src の本体で見つかった 1 件は、ブラウザに埋め込む JavaScript の文字列の中だった。lint は文字列の中を見ないので、違反にはならない。grep の件数と lint の件数は一致しない
- テストでは 9 ファイルが `JSON.parse` を使っていた。テスト対象に出力させた JSON を読み戻している

「0 件」は、禁止を src の本体だけにかけた場合の数だった。テストにもかけると 9 ファイルを直すことになる。これは事実ではなく決定なので、運営者に問いとして出した。禁止の趣旨は「外から来るデータを Schema で検証する」ことで、テストが自分で出力させた JSON は外から来たデータに当たらない。そのため、テストは対象から外した。

### 4. 出典を指すゲートは、出典の後に入れる

順番の先頭には、ADR と規約の文書（`CODING_STANDARDS.md`）を書く PR を置いた。lint のメッセージやスクリプトのエラー文には、規則の理由を ADR へのリンクで書くと決めていた。ゲートが先に main に入ると、エラー文が指す ADR がまだ存在しない期間ができる。参照する側を、参照される側の後に入れる。依存の向きは、どちらが相手を指しているかで決まる。

違反が 0 件のゲートを規約の PR に同梱する案は採らなかった。このリポジトリでは、文書の修正は fix として人と一緒に進める経路（`/implement`）で書き、設定やスクリプトを足す作業は feature としてエージェントの takt に渡す。経路が違う作業を 1 つの PR に入れると、どちらの経路でも扱いにくくなる。

### 5. 道具を捨てると、その道具のためにあった層も捨てられる

決定を記録して閉じた直後に、運営者から「ついでに Stryker は廃止で」と届いた。Stryker は、コードを少しずつ壊して、テストが気づくかを確かめる mutation testing の道具で、このリポジトリでは CI に入れず、人が節目に回す監査として置いていた。

廃止そのものは 1 行の指示だが、波及を追うと、同じ日の午前に決めたテストの層に届いた。重いテストに `.heavy` を付ける層は、2 つの目的のために作っていた。Stryker の時間の上限から重いテストを外すことと、手元で速く回すことだ。`.heavy` を読む場所を探すと、Stryker の除外一覧の 1 か所しかなかった。check も push 前のフックもすべてのテストを走らせ、手元で重いテストを除くための script も無い。Stryker が消えると、読む側のいない接尾辞と、それを付け忘れていないか確かめるゲートだけが残る。

そこで、heavy 層もやめるかを問いにした。運営者はやめる案を選び、テストの層は unit と contract の 2 つになった。ゲートの候補から `.heavy` の検査が消え、ゲートの issue も 4 本から 3 本になった。その検査のために作るはずだったスクリプト層の土台（検査スクリプトのテストを unit に含める設定など）は、構造の検査をスクリプトへ移す issue が引き取る。

記録を書いている途中で、運営者から「heavy 層は今後出てこない？ 重い it だよね？」と聞かれた。手本の live-mindmap では、`.heavy` は本物の外部プロセスに触る重い統合テストで、「重い it」と呼んでよい。けれども nyaucast では、unit に fs や SQLite を許したので `.it` を作らず、heavy は「記録上 7 秒を超える」という時間だけの定義だった。外部プロセスを起動しないのに遅いテストも heavy に入る。同じ名前を手本から借りると、中身も手本と同じだと読まれやすい。違いを説明すると、運営者は 2 層のままにする案を選んだ。手元で遅いテストを除いて走らせたくなったら、そのときに入れ直す。

ある仕組みを捨てるときは、その仕組みの入力を作っているものを探す。入力を読む側が他にいなければ、作る側も一緒に捨てられる。

### 6. 閉じた決定を改めるときは、書き換えずに追記し、影響を受けたチケットにも知らせる

Stryker の廃止は、閉じたばかりのこのチケットの決定（ゲートの issue の 1 本目が `.heavy` の検査だった）と、その前に閉じた 2 枚のチケット（テストの層、構造の検査の置き場所）を改める。

resolution コメントは書き換えず、「追記」のコメントで改めた。どの決定を、なぜ、どう改めたかを残し、改めた後の順番の表を付けた。閉じた 2 枚のチケットにも、改めたことと追記へのリンクをコメントした。決定マップの索引には、それぞれの要約の末尾に「後に heavy 層とともにやめた」と添えた。

書き換えてしまうと、閉じたチケットを根拠に動いている別のセッションが、根拠の変わったことに気づけない。決定マップは複数のセッションが並行して読むので、変わったという事実そのものを、読む人が通る場所に置く。

廃止の理由は、運営者に選択肢を示して聞いた。理由は ADR に残すので、記録する側が推測で書くわけにはいかない。示した推測（監査を実際には回しておらず維持の手間に見合わない、テストの質は別の規則で担保する）を運営者がそのまま採ったので、それを理由として記録した。

## 撮影を速くする手段を、速さではなく「どこで効かなくなるか」で組み合わせた話

描画の撮影を速くする決定マップ（[#789](https://github.com/daiki-beppu/nyaucast/issues/789)）で、測定と調査が出そろった後に、どの手段を組み合わせて採るかを決めたときの学び。候補は 4 つあった。Chrome の起動フラグ、static 区間（絵が変わらない区間）の撮影の省略、撮影の並列、撮影の画像形式だ。合格ラインは「10 分の解説動画 1 本の描画が実時間以内」で、現行は約 25 分かかる。決定は [#793](https://github.com/daiki-beppu/nyaucast/issues/793) と、メディア処理基盤の ADR（判断の記録）である ADR-0005 の決定 16 にある（[PR #831](https://github.com/daiki-beppu/nyaucast/pull/831)）。

### 1. 手段を採るかどうかを先に決めると、その手段にぶら下がる問いが消える

チケットには、決めることが 4 つ並んでいた。採る手段と採らない手段。フラグを採るなら、seek の後の settle（描画が落ち着くまで待つ手順。double rAF と 50 ms の race）の契約と矛盾しないか。CPU の予算（何もしていないときの空回りは禁止、撮影中は使い切ってよい）を守れる形か。撤退のトリガを足すか。

この 4 つは同じ高さの問いではない。settle の問いも CPU の予算の問いも、フラグを採ったときにしか生じない。そこで 1 回目の質問では、4 つの手段について、それぞれ採るかどうかだけを聞いた。運営者の返答は「推奨」の一言で、フラグは採らないと決まった。この時点で、settle は変えなくてよくなり、CPU の予算も自動的に守られた。下流の問いに答えるまでもなく、問いそのものが消えた。

チケットの「決めること」の箇条書きは、書いた人が思いついた順に並んでいる。答える前に、どの問いがどの問いの答えを前提にしているかを並べ替える。

### 2. どちらか 1 つで足りる 2 つの手段は、効かなくなる条件が重なるかで採否を決める

測定では、static 区間の省略だけで描画全体は 2.7 分、Chrome 8 本の並列だけで 3.8〜5.3 分になった（10 分の動画 1 本に換算）。どちらか 1 つで合格ラインに届く。速さだけで比べれば、省略 1 つを採って終わりにできた。

それでも両方を採ったのは、効かなくなる条件が違うからだ。省略の利得は内容で決まる。測った解説動画は全フレームの 9 割が static 区間だったが、動きが詰まった動画ではほとんど効かない。並列の利得はコア数で決まる。測ったのは 10 コアの Apple M4 で、コアの少ない機械では伸びない。条件が重ならないので、両方を採れば、どちらかが効かない動画や機械でも合格ラインに残れる。さらに、契約を変えずに collection（BGM 動画。こちらはエージェントが composition を書く）まで速くできるのは並列だけだった。

候補が合格ラインをすでに越えているときは、速さの比べ合いに意味はない。それぞれが**どの条件で効かなくなるか**を並べて、その条件が重ならない組み合わせを選ぶ。

### 3. 合格ラインに余裕があるなら、出力を変えない遅い形を選ぶ

省いた区間をエンコーダーへ渡す形は 2 つあった。長い `duration` の 1 枚で区間を覆うと、両方を採った描画全体は 0.8〜1.2 分になる。同じ画像を枚数分流すと 2.5〜3.1 分になる。

採ったのは遅いほうだ。前者は出力が可変フレームレートの mp4 になり、平均は約 3 fps まで落ちる。Instagram の仕様にある「23〜60 FPS」を平均で判定されると下限を割る。受け付けられるかは、実物を上げてみないと分からなかった。後者なら、出力は全フレームを撮ったときと**バイト単位で同じ mp4** になる。省略は、出力をまったく変えない最適化になる。そのため、決定論の検証も配布先での受け入れも、新しく確かめる必要がない。遅いほうでも合格ラインの 3 倍以上内側にある。

速い形の利得は合格ラインの内側での上積みにすぎず、代わりに確かめることが 1 つ増える。余裕があるうちは、下流に何も持ち込まない形を選び、速い形は Out of scope に記録しておく。

### 4. 契約の「してよい」は、実装されていなくても誰かを罠へ導く

composition 契約（描画の元になる HTML が満たす `window.__hf` の取り決め）には、もともと次の一文があった。「capturer は static 区間の capture を代表 1 フレームに省略し、エンコード側で引き延ばしてよい（mediabunny `CanvasSource.add(timestamp, duration)`）」。

実装を見ると、今の撮影は static 区間も含めて全フレームを撮っていた。この許可は一度も使われていない。ところが書かれている手段は、前節で採らなかった「長い `duration` で覆う」形そのものだ。この一文に従って誰かが省略を実装すれば、気づかないまま可変フレームレートの mp4 を出していた。

使われていない許可は害が無いように見えるが、後から来た実装者にとっては設計の指示になる。決定に合わせて契約を書き換えるときは、新しく足す規則だけでなく、既存の「してよい」が決定と矛盾していないかも読む。

### 5. 検証の文面が何を確かめているかは、検証のコードで確かめる

契約には「申告の誤りは、static 区間内の再 seek バイト比較でも不一致として表面化する」とも書かれていた。しかし検証のコード（`reseekMismatches`）は、控えておいたフレームと**同じ時刻**へ seek し直して撮り比べている。確かめているのは「同じ時刻なら同じ絵になる」という純関数性だけだ。「この区間は変わらない」という申告が誤っていても、同じ時刻を 2 回撮れば一致してしまう。

この食い違いは、前のチケット（[変わらない区間の宣言を、区間を細かく切らずに別のキーで足すと決めた話](#static-holds)）で見つけていた。そのチケットでは、採るかどうかが決まるまで契約は書き換えないことにしていた。今回、省略を採ると決まったので、この一文を消した。代わりに、申告の誤りは各 hold（変わらない区間の宣言 1 つ）の最初と最後のフレームを比べて検出する、と書いた。

検証について書かれた文は、検証が実際に何と何を比べているかを読むまで信用しない。文の主張と、比較している 2 つの値が合っているかを見る。

### 6. 検証の失敗は、誰の不具合かで扱いを分ける

ADR-0005 には撤退のトリガが列挙されている。その 1 つが「決定論の破れ（Chrome を更新した後、再 seek のバイト比較が恒常的に失敗する）」で、このときは Chrome での描画をやめ、静止画のパスへ戻る。今回の決定で、新しい不一致が 2 種類生まれる。並列のとき、別の Chrome で撮り直して比べた不一致。そして、hold の両端の不一致だ。

前者は Chrome の振る舞いの問題なので、既存のトリガに含まれると明記するだけにした。並列にすると、プロセスごとに状態が違うという種類の非決定論が新しく入り込みうる。そのため、撮り直しは元のフレームを撮ったのとは別の Chrome で行うと決めた。後者は Chrome の問題ではない。hold を導いた組み立ての tool（図解から composition を作る tool）の不具合で、撤退ではなく修正の対象になる。どちらも render を throw で止める点は同じだが、その後に取る行動が違う。

失敗を 1 つの「検証失敗」にまとめると、ツールの不具合を基盤の撤退の判断に混ぜてしまう。検証を足すときは、それが失敗したら誰が何を直すのかまで決めておく。

### 7. CI のジョブが 0 秒・ステップなしで落ちたら、まず再実行する

ADR と契約の改訂の PR で、CI のテストのシャード 4 本がすべて 0 秒で失敗した。ステップは 1 つも動いておらず、注釈もログも無かった。直前の main の run は成功していた。変更はドキュメントだけなので、コードが原因とは考えにくい。runner が割り当てられなかった失敗とみて `gh run rerun <run-id> --failed` を実行すると、4 本とも通った。ステップが 1 つも動いていない失敗は、差分を疑う前に再実行で切り分ける。
