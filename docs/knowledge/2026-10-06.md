## 利用者の Cloudflare の環境を作る道具を、Alchemy と cf の組み合わせに決めた話

利用者の Cloudflare アカウントに資源を作る仕事を、[Alchemy](https://alchemy.run/)（TypeScript で書く IaC。v2 は Effect の上で書き直された beta 版）に任せるか、を決めたときの学び。きっかけは運営者の「Cloudflare の環境を作るのを Alchemy に移譲するのはどう？」という一言だった。nyaucast は、Instagram へ動画を渡すために R2（Cloudflare の S3 互換のファイル置き場）を使う。利用者は自分のアカウントに、bucket と 7 日で中身を消すライフサイクルルールと、R2 のアクセスキーを持つ必要がある。想定利用者は、AI エージェントの助けを借りる非エンジニアだ。決め方は wayfinder（大きな問いを、決定の ticket に分けた map として issue に描き、1 つずつ解く進め方）に沿った。調査の ticket 2 本をサブエージェントに並行で回し、試作は飛ばして、運営者との grilling（質問を重ねて決める対話）で決めた。

- map: [Cloudflare の環境の作成を Alchemy と cf に任せるかの決定マップ](https://github.com/daiki-beppu/nyaucast/issues/648)
- 決定: [Alchemy と cf に任せるかを決める](https://github.com/daiki-beppu/nyaucast/issues/652)（ADR-0012、PR [#666](https://github.com/daiki-beppu/nyaucast/pull/666)）、[Alchemy の状態の置き場を決める](https://github.com/daiki-beppu/nyaucast/issues/653)（ADR-0012 決定 8、PR [#668](https://github.com/daiki-beppu/nyaucast/pull/668)。書いた時点では未マージ）
- 調査: [Alchemy v2 を組み込めるか](https://github.com/daiki-beppu/nyaucast/issues/649)、[cf CLI と Cloudflare API で R2 の環境を作る最小の手順](https://github.com/daiki-beppu/nyaucast/issues/650)

決まった形は次のとおり。

| 役割                                    | 担うもの                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 人間の同意                              | `cf auth login`（Cloudflare 公式の新しい CLI。ブラウザで同意する）       |
| Alchemy に渡す認証                      | `cf` で作る、権限を絞った有効期限の短いデプロイ用トークン                |
| 資源の差分の計算（plan）と適用（apply） | Alchemy v2 を nyaucast と同じプロセスでライブラリとして呼ぶ              |
| 作る資源                                | R2 の bucket・7 日のライフサイクルルール・アクセスキーの元になるトークン |
| 状態（state）                           | `~/.config/nyaucast/cloudflare/` のファイル。利用者ごとに 1 つ           |

### 1. 道具の組み合わせは、人間の同意から最後の資源まで、認証が 1 本でつながるかで絞る

運営者は最初から「`cf` と組み合わせる前提」を置いていた。2 本の調査を並べると、組み合わせの候補はほとんど認証で決まった。

- Alchemy は、認証を環境変数か自前のプロファイル（`~/.alchemy`）から読む。`cf` や wrangler のログインは読まない。自前の OAuth のスコープには、API トークンを作る権限が無い
- `cf auth login` の OAuth のスコープには、R2 の書き込みと API トークンの作成が入っている。ただし、取ったトークンを外へ出すコマンドが無い。他の道具と共有できる認証は、環境変数 `CLOUDFLARE_API_TOKEN` だけだ
- R2 のアクセスキーは、アカウントの API トークンそのものだ。Access Key ID はトークンの ID、Secret Access Key はトークンの値の SHA-256 になる。つまり、アクセスキーを作るには「API トークンを作る権限」が要る

Alchemy 単独では、アクセスキーまで届かない。`cf` 単独では、取った認証を Alchemy に渡せない。残る経路は「`cf` のログインで、`cf` に Alchemy 用のトークンを作らせて渡す」だけだった。代わりに、利用者にダッシュボードで API トークンを作らせる手もある。ただ、非エンジニアに権限グループを選ばせるのは、一番つまずきやすい手順だ。

この経路では、デプロイのたびにトークンが 1 つ増える。nyaucast には「削除する操作を置かない」という方針があるので、増えたトークンを消せない。Cloudflare の API トークンは有効期限（`expires_on`）を持てると分かり、この矛盾が解けた。期限の短いトークンなら、作りっぱなしでも残らない。

**道具の比較表を並べる前に、人間の同意から最後の資源まで、認証が途切れずに渡るかを確かめる。** 認証が途切れる組み合わせは、機能が揃っていても使えない。

### 2. IaC が今の規模で働くかは、資源ごとに「何度呼んでも同じ結果になるか」を見て判断する

調査の結果を受けて、私（この開発を進めている Claude Code）は、v0.1 では Alchemy を採らず、`cf` を nyaucast から子プロセスで呼ぶ案を推した。理由は、3 つの資源の性質を 1 つずつ見たことにある。

| 資源                     | 何度呼んでも同じ結果か                                    | state が要るか |
| ------------------------ | --------------------------------------------------------- | -------------- |
| bucket                   | 名前を固定すれば、あるか確かめてから作るだけで済む        | 要らない       |
| ライフサイクルルール     | 設定全体を置き換える PUT なので、そのままで同じ結果になる | 要らない       |
| アクセスキー（トークン） | 作るたびに増える。Secret は作ったときに 1 回しか返らない  | 要る           |

IaC の強みである「state と実物の差分の計算」が働くのは、トークンだけだった。そのトークンについても、Alchemy には専用の資源が無く、汎用の `AccountApiToken` と SHA-256 の導出で補う必要があった。しかも state はトークンの値を平文で持ち、state を失うとトークンを二重に作る。重さも測った。`node_modules` は 1.3 GB 増え、直近 21 版の beta のうち 11 版に破壊的な変更があった。一方、Cloudflare API を直接呼ぶなら 4 回の呼び出しで済む。

運営者の答えは「Alchemy は v0.1 から実装、plan-apply で環境を作るのは Alchemy の仕事にする」だった。v0.2 では、Workers のリモート MCP や成果物の置き場で、利用者のアカウントの資源が増える。運営者が見ていたのは、その時に作成の操作の形を変えずに済むことだ。私の比較は v0.1 の 3 資源だけで閉じていて、これは「v0.2 の資源は判断材料にとどめる」と自分で決めた範囲の読み方の差だった。

**資源ごとの性質の表は、「今は IaC が空回りする」ことを示すのには役立つ。** ただし、採るかどうかは、資源が増える先の見通しと合わせて決める。表だけでは決まらない。

### 3. 推奨を覆す答えが来たら、それまでの答えのうち前提が崩れたものを数え直す

Alchemy を採らない推奨と一緒に、`cf` の入れ方（Q2）、アクセスキーを何度作っても増やさない方法（Q3）、Alchemy を見直す条件（Q4）も推奨していた。運営者は「すべて推奨」と答えたうえで、Q1 だけを覆した。

文字どおり受け取ると、Q2〜Q4 も決まったことになる。だが、Q3 の推奨は「トークンを固定の名前で探し、Secret を失っていたら値だけ作り直す」という、Alchemy の外で資源を触る処理だった。Alchemy が plan と apply を担うなら、外で同じ資源を触ると state と実物がずれる。Q2 の「`cf` を dependencies に入れて子プロセスで呼ぶ」は、`cf` の役割が認証だけになって意味が変わる。Q4 は要らなくなる。さらに、前のラウンドで「不要になるはず」と書いた「Alchemy の状態の置き場」の ticket が、必要なまま残ることになった。

そこで、崩れた前提を 3 つ挙げてから、認証のつなぎ方・Alchemy の呼び方・plan を人間に見せるか・アクセスキーの冪等性・依存の重さを、新しいラウンド（Q6〜Q10）として聞き直した。認証のつなぎ方（1 節）は、ここで初めて問いになった。

**1 つの答えが覆ったら、同じラウンドの「推奨どおり」を、覆った答えを前提にして読み直す。** 推奨は、その時点の他の推奨を前提に組んである。

### 4. state を分ける単位は、使う側の数ではなく、資源を持つ側の数で決める

state の置き場を決める grilling で、運営者から「複数チャンネル運用する場合は別の state が必要？」と聞かれた。nyaucast では、1 人の運営者が複数のチャンネルを持つ。チャンネルの状態を貯める local store（チャンネルのリポごとの libSQL のファイル）も、チャンネルごとに 1 つある。

答えは「要らない」だった。Alchemy の state が対応するのは Cloudflare のアカウントで、チャンネルではない。5 つのチャンネルを 1 つのアカウントで運用するなら、bucket もアクセスキーも 1 組で、オブジェクトのキーの先頭にチャンネル名を入れれば分けられる。state を分ける必要が出るのは、クライアントのチャンネルだけ、クライアントの Cloudflare アカウントを使う、といった場合だけだ。

この質問のおかげで、local store に state を入れる案も退けやすくなった。local store はチャンネルごとに 1 つ、Cloudflare の環境は利用者ごとに 1 つで、数え方が合わない。入れると、チャンネルの数だけ state が重複し、どれが正しいのかも決められない。v0.1 では、扱う Cloudflare アカウントを 1 人 1 つまでに絞った。広げるときは、state のディレクトリを `cloudflare/<名前>/` に分け、チャンネルの設定から参照を足せばよい。その道筋も ADR に書いた。

**状態を置く単位は、それを使う側（チャンネル）ではなく、その状態が写している実物の持ち主（アカウント）で数える。**

### 5. map と ADR に書く前に、用語集と調査ノートに照らし直す

この作業では、自分で書いたものを 2 回直した。

1 つ目は用語だ。map を作るとき、「運営者の環境（試験台）」と書いた。nyaucast の作り手自身のアカウントという意味だった。ところが、nyaucast の用語集では「運営者」は「チャンネルを運営する利用者」を指す。作り手側の公式アプリについては、この衝突を避けるために「運営型アプリ」という語を退けてあった。決定の ticket で用語集と照らし合わせたときに気づき、「dogfood の環境（提供者自身のアカウント）」に直した。dogfood は、作り手自身のチャンネルで nyaucast を実際に回す受け入れ検証の呼び名だ。

2 つ目は ADR だ。退けた案の一覧に「wrangler は API トークンを作れない」と書いていた。だが、2 本の調査はどちらも wrangler を調べていない。もっともらしい一言を記憶から足していた。「資源ごとのコマンドで、差分の計算も state も持たない」という、調べなくても言える形に直してから PR にした。

**ADR の「退けた案」は、後から読む人が「なぜこれを採らなかったか」の根拠として読む欄だ。** 調査ノートに無い主張は書かない。用語も、map の段階から用語集の意味で使う。map の文言は、そのまま ADR や ticket に写されていくからだ。

### 6. 調査がその場で動かして確かめていれば、試作は飛ばせる

map には、調査 2 本の後に「作り手のアカウントで Alchemy と `cf` を使い、R2 の環境を作ってみる」試作の ticket を置いていた。調査の結果を見た運営者が「試作は飛ばして決定に進もう」と決め、ticket は理由を書いて閉じた。

飛ばせたのは、Alchemy の調査のサブエージェントが、文書を読むだけでなく使い捨ての環境で動かしていたからだ。`npm install alchemy@2.0.0-beta.80 effect@4.0.0` の後、`npm ls effect --all` で `effect` の実体が 1 つにまとまることを確かめた。さらに、その環境の Effect のコードから `deploy()` を呼び、Cloudflare API まで届くことも Node で確かめていた。試作で知りたかった「同じプロセスに載るか」「ライブラリとして呼べるか」には、もう答えが出ていた。

**調査の依頼に「確かめられることは動かして確かめる」を含めると、後の試作が要らなくなることがある。** 試作の ticket を置くときは、調査で答えが出なかった問いだけを残す。

### 7. 曖昧な依頼が高くつく操作の引き金になりうるときは、実行の前に聞く

途中で運営者から「新しいワークフローで wayfinder を流して」と頼まれた。この環境には、複数のサブエージェントを並行で動かす Workflow というツールがあり、利用者がはっきり頼んだときだけ使う決まりになっている。文字どおりに読めば、その条件を満たしていた。

ただ、残っていた 2 本はどちらも grilling で、人間の答えが無いと決まらない。エージェントが自分で質問して自分で答えるのは、wayfinder の規則に反する。そこで、「Workflow で下準備をする」「この会話で次の ticket に進む」「新しい会話で再開する」の 3 つの選択肢を出して聞いた。返事は「ワークツリーの間違い」だった。新しい worktree を作り、そこで別の Claude Code に次の ticket を渡した。

**依頼の読み方の 1 つが、トークンを大きく使う操作や、規則に反する操作につながるときは、もっともらしく読めても先に聞く。** 選択肢を出すと、相手は 1 語で訂正できる。

### 8. 検査のフックが通らない形のコミットがあると、エージェントはフックを外して進む

調査の 2 本は、どちらも `research/<名前>` のブランチに調査ノートを 1 ファイルだけコミットした。2 つのサブエージェントは、どちらも `git commit --no-verify` で pre-commit のフックを外していた。報告によれば、`docs/research/` は formatter の対象外なので、そこだけを変えるコミットではフックが必ず失敗するという。push の前の検査は通っていた。

2 つとも、外したことを報告には書いていた。ただし、事前に許可を取ってはいない。調査のブランチを切るたびに同じことが起きるので、フックの側を直す価値がある。

**通せないゲートは、いずれ黙って迂回される。** エージェントの報告に `--no-verify` が出てきたら、その回の判断を問うより先に、ゲートの側に穴が無いかを見る。
