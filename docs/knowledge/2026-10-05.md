## 投稿の実行を takt で回し直し、レビューが同じ論点を狭め続けたところで打ち切った話

時刻が来た投稿を SNS へ出す CLI と、その最初のアダプタである YouTube の予約（#553）を、takt で回し直したときの学び。takt は、計画 → テスト → 実装 → 6 観点のレビュー → 裁定 → 修正 → 修正の検証、を自動で回す実装用のワークフローツールだ。1 回目の run は 6.5 時間かかり、修正の検証で 2 回差し戻されたところで運営者の判断で止めていた。2 回目は 8 時間 10 分の時点で私（この開発を進めている Claude Code）が止め、差分を引き取って PR にした。

- 実装した issue と PR: [#553](https://github.com/daiki-beppu/nyaucast/issues/553)（[#658](https://github.com/daiki-beppu/nyaucast/pull/658)）
- 切り出した issue: [投稿に保存したアカウントとの照合](https://github.com/daiki-beppu/nyaucast/issues/656)、[検査から送信までの隙間](https://github.com/daiki-beppu/nyaucast/issues/657)、[ショートの予約の実機確認](https://github.com/daiki-beppu/nyaucast/issues/655)

| 段                   | 1 回目                                                 | 2 回目                                                                   |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| 実装の段             | 約 120 分                                              | 約 88 分                                                                 |
| 修正の検証の差し戻し | 2 回（並行実行のテストが無い・予定時刻の再確認の漏れ） | 1 周目は 1 回（狭い経路 1 件）                                           |
| 結果                 | 運営者が停止                                           | 3 周目のレビューの後に私が停止し、PR にした（26 ファイル、+1098 / −116） |

### 1. 回し直すときは、前回の裁定と検証の論点を、issue の本文に書き写してから渡す

takt は、issue の本文だけを仕様として読む。前回の run の報告書もコメントも読まない。そこで、1 回目の裁定（9 件の問題）と修正の検証の差し戻しの理由を、本文の「決定」と「受け入れ条件」に書き足してから起動した。足したのは、試行の開始を投稿ごとに原子的に取ること、2 つの実行を本当に競わせる並行実行のテスト、upload の直前の予定時刻の再確認など 11 項目だ。受け入れ条件には「逐次の 2 回の実行や、獲得関数の単体テストで代えない」とまで書いた。1 回目は、並行実行のテストを逐次のテストで代えて差し戻されていたからだ。

2 回目の計画は、11 項目をすべて要件として拾った。試行の開始は `INSERT … SELECT … WHERE <最後の試行の条件> … RETURNING id` の 1 文で取る方針になった。最初のレビューで、並行実行のテストの不足は指摘されなかった。予定時刻の再確認は、入ってはいたが、確かめる位置が早いと指摘された（2 節）。

**前回の run で分かったことは、次の run の入力に書き写さない限り引き継がれない。** 報告書を読むのは人間とその場のエージェントだけで、次の run は読まない。

### 2. レビューが同じ論点を毎周狭い位置で指摘し始めたら、打ち切りの合図にする

予定時刻の再確認は、周を追うごとに位置を下げて指摘された。

| 周           | 指摘された隙間                                                            |
| ------------ | ------------------------------------------------------------------------- |
| 1 周目       | 予定時刻を確かめた後、upload までの間にファイルの準備と試行の獲得が挟まる |
| 2 周目       | 確かめてから送るまでの間に、OAuth のトークンの更新という通信が挟まる      |
| 2 周目の検証 | 試行を取る SQL が終わるまでの間に時刻を過ぎうる                           |
| 3 周目       | 401 を受けてトークンを更新し、送り直す間に時刻を過ぎうる                  |

鮮度の検査（承認の後にカットやサムネイルが変わっていないか）も、同じ形で「検査した後、送るまでの間に変わりうる」と指摘され続けた。確かめてから外部 API を呼ぶまでの隙間は、どこまで下げても残る。直す範囲は回るたびに狭くなるのに、終わりは来ない。

3 周目のレビューが、こうした隙間の指摘と、すでに 2 回退けられた指摘だけになった時点で、run を止めた。差分は `pnpm run check`（このリポジトリの検査ゲート）が通る状態だった。残った隙間は「許容するか、401 の後の再送だけ直すか」を決める issue（#657）にした。予定時刻を過ぎて送ると即時に公開されてしまうので、私の推奨は後者だ。

**自動のレビューは、指摘が尽きるまで止まらない。** 「新しい不具合が出ているか、同じ論点が狭くなっているだけか」で、人が打ち切りを決める。

### 3. 「ADR の文面に無い」で退けた指摘は、ADR の目的に照らして読み直す

3 周とも、2 つの観点が同じ指摘を出した。承認の後に、宣言（そのチャンネルが使う SNS のアカウント）とトークンを両方とも別のアカウントへ替えると、承認した投稿が新しいアカウントへ出てしまう、というものだ。投稿には承認したときのアカウントの ID が残っているのに、実行の直前の照合は「トークンの ID と宣言の ID」しか比べていなかった。

裁定役は 3 回とも、これを根拠なしとした。ADR-0009（設計の判断の記録）の決定 6 が「投稿の直前には、トークンに記録した ID と宣言とを比べる」と書いていて、実装はその文面どおりだからだ。途中で実装役がこの照合を自分の判断で足したが、修正の検証が「計画に無い変更」として差し戻し、次の段で消された。

決定 6 の目的は「投稿先の取り違え」を防ぐことで、同じ ADR の決定 9 は投稿を「アカウントを含め、書いたら変えない事実」としている。文面どおりの照合では、その目的を果たせない。PR の後に、照合を足す fix と決定 6 の改訂を同じ差分で入れた（#656、PR #662）。

**裁定役は、ADR の文面に無いことを「必要以上の拡張」として退けやすい。** 複数の観点が周をまたいで同じ指摘を出し続けるときは、文面ではなく、その決定が何を防ぐためにあるかで読み直す。

### 4. 並行実行のテストは、本当に競わせているかを自分で読む

二重 upload を防ぐ排他は、テストが逐次の実行になっていると、壊れていても通る。PR にする前に、該当のテストを読んだ。2 つの `runDuePosts` を fiber で同時に起動し、どちらも期限到来の判定と再検査を終えた時点で `Latch`（待ち合わせの仕組み）で止め、そろってから試行を取りに行かせていた。そのうえで、upload の呼び出しと試行の行がちょうど 1 つずつになることを確かめている。1 回目に足りなかった、先に一時的な失敗の試行がある状態で競わせるテストもあった。

**並行の排他のテストは、名前や報告書ではなく、待ち合わせの位置を読んで確かめる。**

## takt の長い run を見張り、「止まっている」を CPU 時間で確かめた話

#553 と #554（投稿単位の 3 つの CLI と YouTube の公開の確認）の takt を、それぞれ数時間見張ったときの運用の学び。#553 の 1 回目は、見張りの上限で通知が来なくなっていた。

### 1. takt はエージェントの background に載せず、端末のタブで動かし、終了をファイルで知る

Claude Code の background のコマンドには 2 時間の上限がある。takt をその子として動かすと、上限で見張りが切れるか、takt ごと止まる。#553 の 1 回目は 6.5 時間かかり、見張りが途中で切れた。

2 回目からは、Orca（ターミナルと worktree の管理ツール）の新しいタブで takt を起動した。

```sh
orca terminal create --worktree active --title "takt 553 v2" --json \
  --command "cd <worktree> && script -q <log> takt --pipeline --auto-pr -b <branch> -w default -i 553; echo \$? > <exit-file>"
```

takt はタブのシェルの子なので、エージェント側の上限で止まらない。`script` は TTY を保ったままログを取るので、運営者はタブで進み具合を見られる。エージェントは「終了コードのファイルが出るか、40 分が経つまで待つ」ループを background で回し、起きるたびに進んだ段と報告書を読んだ。

**長い処理は、エージェントの寿命から切り離して起動し、終了は副作用のファイルで検知する。**

### 2. 「止まって見える」は、プロセスの木と CPU 時間で確かめる

#554 の実装の段で、運営者から「全然進んでなくない？」「絶対止まってるて」と言われた。差分は 40 分で 736 行から 790 行にしか増えていなかった。最初の私の返事は、ファイルの更新時刻とログの書き込みだけを根拠に「止まっていない」と言うもので、確かめ方として弱かった。

プロセスの木をたどると、次のことが分かった。

1. takt → エージェント（Claude Agent SDK）→ シェル → `pnpm run check` → `vp test run` → テストのワーカー、とつながっていた
2. テストのワーカーは 1 本だけ残り、CPU を 100% 使って 2 分以上、出力を出していなかった
3. 実装の段で足された・変えられたテストのファイル 13 本を 1 本ずつ流すと、どれも 0〜3 秒で通った
4. その間に `pnpm run check` が終わった。68 ファイル、1,731 件が通り、173 秒かかっていた

固まっていたのではなく、重いテストのファイルが最後に残り、出力をファイルにまとめて書いていただけだった。実装の段の中で、この 3 分の検査を何度も流し直していたので、外からは何も起きていないように見えた。

エージェントの直近の操作は、そのセッションのログ（`~/.claude/projects/<worktree>/*.jsonl`）の末尾でも読める。今どのコマンドを実行しているかが分かる。

**「動いている」は、ファイルの更新時刻ではなく、どのプロセスが CPU を使っているか、出力が伸びているかで言う。**

### 3. pipeline で起動した run には、途中で指示を足せない

takt には、実行中の run に次の段の境界で指示を届ける口（`takt_tell_run`）がある。#553 の裁定に指示を足そうとして `takt_list_tasks` を引くと、空だった。`--pipeline` で直接起動した run は、タスクのキュー（`tasks.yaml`）に載らないので、この口が届かない。

その結果、軌道修正の手段は「そのまま回す」か「止めて引き取る」の 2 つだけになった。#554 では、この学びを先に issue の本文へ入れた（[3 つ目のエントリ](#takeover-and-small-fixes)の 4 節）。

**途中で舵を切りたい run は、キュー経由で起動する。pipeline で起動するなら、入力の issue で先に縛る。**

### 4. 調べ物のつもりのコマンドでも、他の作業が使う checkout を動かさない

#554 の本文を直す前に、#553 の後のコードの構成を確かめようとして、メインの checkout で `git checkout --detach origin/main` を実行してしまった。メインの checkout は、並行する他の作業が使う場所だ。すぐに元のブランチへ戻し、未コミットの変更が無いことも確かめた。

その後は、checkout を動かさずに読める `git show origin/main:<path>` を使った。

**読むだけなら、`git show <ref>:<path>` で読む。checkout を動かすのは、自分の worktree の中だけにする。**

## 止めた run の差分を引き取って仕上げ、小さな fix と mutation testing の実測を片付けた話

#554 の takt をレート制限のために止め、差分を引き取って PR にしたときの学び。あわせて、小さな fix を 3 本（#656・#645・#644）と、mutation testing の道具の確認（#562）を片付けた。

- 実装した issue と PR: [#554](https://github.com/daiki-beppu/nyaucast/issues/554)（[#661](https://github.com/daiki-beppu/nyaucast/pull/661)）、[#656](https://github.com/daiki-beppu/nyaucast/issues/656)（[#662](https://github.com/daiki-beppu/nyaucast/pull/662)）、[#645](https://github.com/daiki-beppu/nyaucast/issues/645)（[#663](https://github.com/daiki-beppu/nyaucast/pull/663)）、[#644](https://github.com/daiki-beppu/nyaucast/issues/644)（[#664](https://github.com/daiki-beppu/nyaucast/pull/664)）
- 実測を書いた issue: [#562](https://github.com/daiki-beppu/nyaucast/issues/562)

### 1. 途中で止めた run は、一から回し直すより、差分を引き取って仕上げる方が安い

#554 の takt は、裁定が直すと決めた 2 件の修正を終え、修正の再計画に入ったところで止めた。運営者から「レート制限もあるので一旦止めて」と言われたからだ。止める前に、途中の差分をローカルの WIP コミットに残し、報告書を写した。

再開のとき、takt で一から回し直すのではなく、差分を引き取った。修正の報告書を読むと、直すと決めた 2 件のうち、今すぐ実行の予定時刻の扱いは直してテストも済み、もう 1 件は CONTEXT.md（用語集）の定めと食い違うとして、段の中で元に戻されていた。その判断は筋が通っていたので採った。`pnpm run check` を通し、次の 2 節の 2 点を足して PR にした。

**止めた run の差分は、報告書で「どこまで済んだか」を確かめれば、そのまま土台にできる。** 一から回し直すと、計画と実装の数時間をもう一度払うことになる。

### 2. 裁定が「範囲外」にしても、1 件の失敗が全体を止める作りは直す

`post run` は、同じ実行の中で、予約済みの YouTube の投稿の公開を `videos.list` で確かめてから、時刻が来た投稿を実行する。レビューは、公開の確認の照会が 1 件でも失敗すると、その実行の upload まで全部止まると指摘した。裁定は「issue の決定にも受け入れ条件にも無い」として範囲外にした。

`videos.list` が 1 回 5xx を返すだけで、その実行の投稿が全部出なくなる。運用で困るのは明らかなので、照会の失敗を投稿ごとの `check_failed` の 1 行に閉じ、事実は積まずに残りへ進む形にした。テストを先に書いた。1 件目に 503 を返し、2 件目に `public` を返す偽の HTTP で、2 件目が確認され、1 件目は予約済みのまま残ることを確かめている。

**裁定の「issue に書いていない」は、直さなくてよい理由にはならない。** 1 件の失敗が無関係な処理まで止める作りは、仕様に書いていなくても不具合として扱う。

### 3. ADR の読み方を決めたら、その読み方を ADR に書く

#554 の計画は、ADR-0009 決定 13 の「public でない結果は事実として積まない」を、「公開の確認」という事実に対する制約と読んだ。そのうえで、YouTube が upload を拒否・失敗と返した結果は、別の事実として積む設計にした。read model（積んだ事実から状態を導く読み口）は外部に問い合わせないので、事実が無ければ「拒否された」という確認待ちの理由を返せないからだ。裁定もこの読み方を妥当とした。

ただ、この読み方は計画の報告書にしか書かれておらず、ADR は元の文面のままだった。このリポジトリには「ADR から黙って逸脱しない。逸脱するなら同じ差分で ADR を改訂する」という規約がある。決定 13 に「この 2 つは upload の拒否・失敗という別の事実として積む」と書き足し、決定 9 の事実の種類の列挙にも 5 種目として加えた。

**解釈で済ませた判断は、次に読む人には「ADR と違うコード」に見える。** 読み方を決めたら、その読み方を正本に書く。

### 4. 回し直す issue には「隙間はここまで確かめれば足りる」と書いて、終わりの無い指摘を先に封じる

#553 の学び（[1 つ目のエントリ](#post-execution-retry)の 2 節）を受けて、#554 の本文に次の一文を入れてから takt に渡した。「検査から外部 API の呼び出しまでの隙間は #657 で扱いを決める。この issue では #553 と同じ位置で確かめれば足り、隙間をさらに狭める変更をしない」。

#554 の最初のレビューでは、隙間を追う指摘は 1 件も出なかった。出た指摘は、今すぐ実行が予定時刻の検査まで外していた、許容時間の後だと公開の確認を取りに行かない、など本物の不具合だった。

**止まらないレビューへの対処は、run の途中ではなく、入力の issue に書いておく。** pipeline の run は途中で指示を足せないので（[2 つ目のエントリ](#takt-watching)の 3 節）、なおさら先に縛る。

### 5. テストの上限は、単独の所要時間を測ってから決める

負荷が高いときに落ちたテスト（#644）の上限を、単独で流して測ってから決めた。

| テスト                                                     | 単独の所要                        | 上限                                                         |
| ---------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------ |
| `mixAudioTrack` の、ちょうど 60 秒のショートの 2 本        | 約 12 秒（他のテストは 3 秒前後） | 120 秒 → 300 秒                                              |
| `assembleComposition` の、60 秒の上限の 3 本               | 61〜142 ms                        | 既定の 5 秒 → 300 秒（同じファイルの描画のテストに合わせた） |
| MCP サーバーを子プロセスで起動する契約テストの、応答の待ち | —                                 | 10 秒 → 25 秒（契約テストの上限 30 秒の内側）                |

`mixAudioTrack` の 2 本は、60 秒分の音声の合成とラウドネスの正規化に時間を使っていた。60 秒ちょうどという境界を確かめるテストなので、入力は短くできない。落ちたときは、ディスクの空きが数百 MB まで減っていて、単独の 10 倍の 120 秒を超えていた。300 秒なら 25 倍まで耐える。

**上限は「落ちたから倍にする」ではなく、単独の所要時間と、何に時間を使っているかを測ってから決める。** 入力を短くできるなら、そちらが先だ。

### 6. mutation testing は、dry run が 1 つのプロセスで全件を流す前提で範囲を決める

Stryker（テストが変異を見抜けるかを測る mutation testing の道具）が、テストの基盤を上げた後も動くかを確かめた（#562）。`pnpm exec stryker run --dryRunOnly` を 3 回流した。

| 回  | dry run の上限 | 結果                                                                          |
| --- | -------------- | ----------------------------------------------------------------------------- |
| 1   | 既定の 5 分    | 時間切れ                                                                      |
| 2   | 30 分          | 25 分で最後まで流れた。落ちたのは、テストに渡している 120 秒を超えた 1 件だけ |
| 3   | 40 分          | 時間切れ                                                                      |

Stryker は、テストごとのカバレッジを取るために、最初のテストの実行を 1 つのプロセスで流す。テストのプロセスを 9 個作っても、動いているのは 1 個だけで、CPU を 100% 使っていた。ゲートで並列に約 140 秒かかる unit テストが、直列で 25〜40 分以上かかり、所要時間もぶれる。変異は 183 ファイルで 27,073 個あり、全件を流す本番の実行は現実的でない。

道具そのものは動くので、設定は直さなかった。代わりに、監査のたびにマージした issue が触ったファイルだけを対象にし、重い音声・描画のテストを対象から外す、という方針の案を #562 に書いた。

**mutation testing を導入するときは、「動くか」と同時に「全件の dry run が何分かかるか」を測り、その数字から対象の範囲を決める。**
