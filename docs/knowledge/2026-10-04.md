## コアのライセンスを Apache-2.0 に決め、参考に挙がったサービスに「どこまで寄せるか」を段階に分けて比べた話

配布モデルの地図に残っていた「コアの OSS ライセンスを MIT / Apache-2.0 / GPLv3 から選ぶ」を、人間と詰めて決めたときの学び。地図は、GitHub の issue 1 本に目的地と決めたことの索引を書き、論点を子 issue（ticket）として並べたものだ。前日の決定（[配布モデルの決定](./2026-10-03.md#distribution-model-decision)）で、配布モデルは「コアは OSS、課金するのは YouTube の公式アプリ（提供者が持ち、YouTube の監査を通した API プロジェクト）の利用量だけ」に決まっていた。ただし、具体的なライセンスは先送りしていた。進め方は grilling で、前提が揃った問いを 1 ラウンドにまとめ、推奨の答えを付けて聞いた。途中で運営者（このツールの作者）が、参考にしたいサービスとして html2pptx.app を挙げた。結論は Apache-2.0 で、新しい ADR は起こさず、前日の ADR（決定の記録）を改訂して書き足した。

- 決定の ticket: [コアの OSS ライセンスを MIT / Apache-2.0 / GPLv3 から選ぶ](https://github.com/daiki-beppu/nyaucast/issues/586)
- ADR: [配布モデルは OSS のコアと、YouTube の公式アプリの利用量への課金にする](https://github.com/daiki-beppu/nyaucast/blob/main/docs/adr/0011-distribution-model.md)（改訂の PR [#599](https://github.com/daiki-beppu/nyaucast/pull/599)）
- 地図: [nyaucast の配布モデル決定マップ（OSS / オープンコア / FSL）](https://github.com/daiki-beppu/nyaucast/issues/574)

### 1. 課金点がコードの外にあるなら、copyleft には守るものが無く、コストだけが残る

最初のラウンドでは、MIT と Apache-2.0 の比較より先に「copyleft（改変を配るならソースの開示を求める GPLv3 / AGPL）か、permissive（MIT / Apache-2.0）か」を聞いた。この 2 つは、何を守りたいかで決まる。

copyleft が守るのは「閉じたフォークを作らせないこと」だ。しかし前日の決定で、課金点は監査済みの公式アプリというサービスに置いた。YouTube の開発者ポリシーは API の認証情報を OSS に埋め込むことを禁じているので、同じサービスを出したい競合は自分で監査を通すしかない。コードを閉じられても、提供者は何も失わない。

一方で、copyleft のコストは残る。1 つは、組織の法務レビューで止まりやすいこと。もう 1 つは見落としやすい。著作権者は自分のライセンスに縛られないが、外部の貢献を取り込むと、その部分については縛られる。提供者が非公開で始めるトークンブローカー（client secret を持ち、認可と利用量の計量だけを受け持つサーバ）へコアのコードを流用したくなったとき、GPLv3 なら配る形態で、AGPL ならネットワーク越しの提供でも、開示の義務がかかり得る。避けるには CLA（貢献者から権利の許諾を集める契約）が要る。permissive ならこの問題が消えるので、貢献の受け入れ条件は何も置かないことにした。

MIT と Apache-2.0 の比較では、Apache-2.0 を選んだ。組織が気にする特許の許諾（§3）が明示されていること、§5（受け取った貢献は同じライセンスで出されたものとみなす）があるので CLA なしでも貢献の扱いが定まること、の 2 点が決め手だった。

**ライセンスを選ぶ前に、ライセンスで守りたいものが何かを書き出す。** それがコードでないなら、copyleft の利点は効かず、コストだけを払うことになる。

### 2. 「ライセンスは Apache-2.0、実行時は実質 GPLv3」は矛盾ではなく二層で、ライセンスの選び方では消せない

このツールはメディア処理に node-av（FFmpeg の GPLv3 ビルド）を使い、同じプロセスで読み込む。そのため、コアをどのライセンスにしても、実行時の全体は実質 GPLv3 になる。

ライセンスの選択で変わるのは、ソースを単位にした自由度だけだ。node-av 抜きで codec や MCP tool のソースを取り出す人は、Apache-2.0 の条件だけで使える。nyaucast をそのまま配る人は、GPLv3 の義務も負う。この二層はどのライセンスでも変わらないので、ライセンスの選択ではなく告知（LICENSE・NOTICE・README）の問題として、次の ticket に回した。

この区別が効いたのは、運営者が html2pptx.app と比べて「イメージ的には、html2pptx よりオープンでクリーンだよって感じ？」と聞いたときだ。オープンさは正しい。html2pptx.app は本体がクローズドで（ライセンスページは「All rights reserved」）、nyaucast はコアのソースを公開する。しかし「クリーン」は、ライセンスの見え方については逆だった。html2pptx.app の依存はすべて MIT なので、表記はあちらのほうが単純だ。nyaucast がクリーンだと言えるのは課金の構造（個人が使う機能に料金所が無い）であって、ライセンスの単純さではない、と分けて答えた。

**依存の copyleft が実行時の全体を決めるとき、本体のライセンスで「クリーンさ」を語らない。** 本体のライセンスと実行時の義務は、別々に説明する。

### 3. 参考に挙がったサービスは、「どこまで寄せるか」を段階に分けると、取り入れられる部分と決定を覆す部分が分かれる

html2pptx.app は、HTML を編集できる PowerPoint に変換するサービスだ。調べると、構成は次のとおりだった。

- 本体はクローズドの SaaS で、MIT の OSS（dom-to-pptx・PptxGenJS）の上に作られている
- ローカルの HTML 編集は無償で、サーバに送るのは明示的に Export したときだけ。課金はエクスポートの回数で、無償枠は月 10 回、有償は $7 / 300 回から $59 / 20,000 回までの段階制
- 入口は Web アプリ・REST API・MCP・Skills（AI エージェント向けの手順書）で、利用者ごとの API キーで数える

運営者が「html2pptx に寄せるとどう変わる？」と聞いたので、寄せる度合いを 3 段階に分けて答えた。

| 寄せ方                                                                                 | 変わること                                                           | 判断       |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ---------- |
| ① API キーでの認証、1 アクション単位の計量、無償枠と段階制の有償枠を取り入れる         | 何も覆らない。ブローカーの設計と価格設定（どちらも後続）の参考になる | 取り入れる |
| ② 自前アプリ（利用者が自分で作る開発者アプリ）の経路を無くし、払わないと止まる形にする | 前日の ADR の「OSS 単体で全機能が動く」を覆す                        | 採らない   |
| ③ 描画やエンコードをサーバで行う                                                       | ローカルで動く前提を作り直す。原価が利用量に比例する                 | 採らない   |

③を退けた理由は原価の構造だ。html2pptx.app がサーバ型で成り立つのは、HTML から PPTX への変換 1 回が軽いからだ。動画は 1 本あたりの計算量と転送量が桁違いで、同じ価格帯の段階制をサーバ処理で組むと利益が出にくい。nyaucast のブローカーが「認可と計量だけ」を受け持ち、upload はローカルから YouTube へ直接行う設計は、この原価の問題への答えでもあった。

①は ADR の Consequences に参照として残した。ブローカーの設計と価格設定は、この地図の範囲の外として後続へ引き渡し済みなので、ここでは決めない。

**「あのサービスみたいにしたい」と言われたら、寄せる度合いを段階に分け、それぞれが既存の決定のどれを覆すかを並べる。** 覆さない段階だけを取り入れれば、参考事例を決定のやり直しにせずに使える。

### 4. 無償の経路を塞いでも、想定利用者がもともとその経路を使えないなら、収益はほとんど増えない

②について、運営者は「収益に差が出ると思う？」と聞いた。私の答えは「差は小さい」で、ただし比べられる実績データは無く推論だ、と断った。根拠は 2 つある。

1 つ目に、想定利用者（AI エージェントの助けを借りる非エンジニアのクリエイター）は、今の設計でも YouTube には公式アプリで乗るしかない。自前アプリでは、監査を通っていない API プロジェクトから上げた動画が private に固定され、個人が監査を通す前提は置けないからだ。自前アプリの経路を最後まで使えるのは、自分で監査を通せるエンジニアだけで、この層はもともと払わない可能性が高い。塞いでも、有償枠に移る人はあまり増えない。

2 つ目に、コアが Apache-2.0 なら、誰でもフォークして経路を戻せる。経路を塞ぐ案は、コアを閉じない限り実効性が無い。

html2pptx.app で「払わないと止まる」が収益になるのは、サーバ側の変換に代わる手段が利用者に無いからだ。nyaucast では、その「代わりが無い」状態を YouTube の監査が作っている。設計でわざわざ作る必要が無い。収益を左右するのは、YouTube に公開する利用者の数と、無償枠の大きさのほうだ。

**無償の経路を塞ぐ案を比べるときは、誰がその経路を実際に使えるかを先に数える。** 想定利用者が使えない経路は、塞いでも転換を生まない。

### 5. 参考にしたい点を選択肢で聞くなら、まだ調べていない面も選択肢に入れる

html2pptx.app が挙がった直後、私は料金ページとライセンスページだけを読んで、「何を参考にしますか」と選択肢で聞いた。選択肢は「(a) 第三者 OSS のライセンス告知ページの形」「(b) 利用量の段階制と無償枠」「(c) その他」だった。

返ってきた答えは「収益構造とツールの配布方法」だった。配布方法（MCP / Skills / API キーでの入口）は、まだ調べていなかったので選択肢に無かった。ページを読み直して初めて、入口が AI エージェント向けで、利用者ごとの API キーで数える構成だと分かった。これは、エージェント経由で使わせる nyaucast にとって、料金表より近い参考だった。

選択肢は、自分が見た範囲から作られる。見ていない面は、相手が「その他」に書いてくれない限り落ちる。

**相手が挙げた参考事例について選択肢で聞く前に、その事例の構成（何を、どこで、どう配り、何に課金しているか）を一通り調べる。** 調べた面だけで選択肢を作ると、相手の関心がそこに無かったときに一往復を失う。

### 6. 先送りした穴を埋める決定は、新しい ADR ではなく、先送りした ADR の改訂に書く

前日の ADR は「ライセンスは GPLv3 互換のものに限る。具体的にどれにするかは、別の決定に回す」と書いていた。この穴を埋める決定を新しい ADR にすると、配布モデルの決定が 2 本に割れる。読み手は「OSS にする理由」と「Apache-2.0 にする理由」を別々に探すことになる。

そこで、前日の ADR の決定 1 を「具体的には Apache-2.0 にする」に書き換え、決定 8（ライセンス）と決定 9（貢献の受け入れ条件）を足した。Why と Considered Options には、MIT・GPLv3・AGPL と、html2pptx.app に寄せる 2 案（②・③）を退けた理由を足した。Status には改訂の日付と ticket を書いた。このリポジトリでは、先送りした決定を後で埋めるときに改訂の行を積む書き方をしているので、それに合わせた。

ライセンスの付与そのもの（LICENSE ファイルと `package.json` の `license`）は、リポジトリを公開するときに行う。それまで npm パッケージは `UNLICENSED` のままにする。名前と商標は、地図の「まだ問いにできないもの」に残した。Apache-2.0 §6 は商標の使用を許諾しないので、フォークに名前を使わせるかは、ライセンスとは別に決まる。

**ADR が明示的に先送りした穴は、その ADR の改訂で埋める。** 1 つの決定の理由が複数の ADR に散らないようにする。

## takt を 2 本並行で回し、偽の CLI が引数の解析を写していないことと、ADR の中の読みの食い違いを拾った話

解説動画の制作の流れのうち、次の 2 本の issue を takt（AI エージェントに issue を渡して実装させるツール）で同時に走らせ、PR にしたときの学び。1 本目は企画ゲートの CLI だ。企画ゲートは「この企画とサムネイルで作るか」を運営者が判断する関門で、`nyaucast video produce <id>` の実行そのものを承認とみなす。`nyaucast video abandon <id>` で動画をやめることもできる。2 本目は、サムネイルの画像を作る provider（画像生成の呼び出し先）に、OpenAI の codex CLI を足す作業だ。前日に Gemini の provider を入れていて、codex CLI を子プロセスとして起動し、組み込みの画像生成で 1 枚ずつ作らせる。

- 実装した issue: [企画ゲートの CLI（`video produce` / `video abandon`）](https://github.com/daiki-beppu/nyaucast/issues/545)（PR [#603](https://github.com/daiki-beppu/nyaucast/pull/603)）、[サムネイルの codex provider](https://github.com/daiki-beppu/nyaucast/issues/544)（PR [#605](https://github.com/daiki-beppu/nyaucast/pull/605)）
- 起票した issue: [ADR-0009 決定 7 の「承認待ちのゲート」を、video abandon の対象として一通りに読めるようにする](https://github.com/daiki-beppu/nyaucast/issues/604)

|             | 企画ゲートの CLI            | codex provider                               |
| ----------- | --------------------------- | -------------------------------------------- |
| takt の所要 | 約 29 分                    | 約 63 分                                     |
| 工程        | 7（1 回目のレビューで通過） | 13（修正を 1 周。修正の検証で 1 回差し戻し） |
| 差分        | 10 ファイル（+706 / −37）   | 9 ファイル（+1253 / −17）                    |
| 最終判定    | APPROVE                     | APPROVE                                      |

2 本とも同じ時刻に、最新の main から切った detached の worktree で、takt の pipeline モード（issue を 1 本渡すと、計画からレビュー、PR の作成までを 1 回で走らせる）を起動した。進め方は前日（[3 本並行の話](./2026-10-03.md#three-takt-merge)）と同じだ。

### 1. 偽の CLI は引数の解析を写していないので、外部 CLI との境界の不具合はテストでは見つからない

codex provider は、参照画像があるときに `codex exec --image <画像> <プロンプト>` の形で起動していた。テストでは、子プロセスの起動を差し替えた偽の codex を使う。偽の codex は渡された引数を記録し、決めた画像を書き出すだけなので、テストはすべて通っていた。

1 回目のレビューで、AI が書いたコードにありがちな誤りを見る観点のレビュー役が、手元の codex CLI 0.157.0 で同じ引数の並びを実行してみた。結果は `Reading prompt from stdin... No prompt provided via stdin.` と表示して終了コード 1 だった。`--image` は複数の値を取るので、直後のプロンプトも画像のパスとして読まれ、プロンプトが無いことになる。実装は stdin を閉じて起動するので、参照画像を設定したチャンネルでは、候補が 1 枚も作れない。

修正は、`--image` の値とプロンプトの間に `--` を挟むことだった。ところが、修正を検証する段階（fix-verifier）が 1 回差し戻した。理由は、修正を外したときの反例を実行していないことだった。偽の codex は、区切りの無い引数を受け取ると、プロンプトの文字列を画像のパスとしてファイルを読みにいき、例外で落ちる。本物の codex のように「プロンプトが無い」として終了コード 1 を返すわけではない。そのため、`--` を外しても、テストは本物と違う理由で落ちる。2 回目の修正で、偽の codex にも本物と同じ失敗の仕方（終了コード 1）を写し、区切りを外すと型付きの失敗 `CodexExecFailed` になって、候補の行が 0 件になることを確かめた。

前日のエントリでは、外部 API の偽物の前提を「実機で 1 回通す」issue にした。今回の引数の並びは、画像の生成まで行わなくても、手元の CLI に引数を渡すだけで確かめられる。生成には費用がかかるが、引数の解析は無料で試せる。

**外部 CLI を偽物でテストするなら、引数の解析だけは本物の CLI に通して確かめる。** 偽物を直すときは、本物の成功の仕方だけでなく、失敗の仕方まで写す。

### 2. 同じ ADR の中で語が狭く定義されていると、後の決定が広い読みを求めていても気づきにくい

企画ゲートの CLI のレビューで、構成を見るレビュー役が「ADR-0009 の決定 7 と決定 14 が食い違っている」と指摘した。ADR（Architecture Decision Record。決定とその理由の記録）の決定 7 は、「`video abandon` は承認待ちのゲートに NO-GO を書く」と書く。NO-GO は「やめる」の意味だけを持つ記録だ。同じ決定 7 の中で、read model（事実から状態を導出する読み口）が返す「承認待ちのゲート」は、公開ゲートについて「プレビューできるカットがそろっていること」を条件に導出する、狭い意味で使われている。

一方で決定 14 は、「produce 区間に入った後で企画を変えたいときは、動画をやめて新しい動画を作る」と書く。produce 区間に入ったばかりで、カットがまだそろっていない動画には、狭い意味の「承認待ちのゲート」が無い。決定 7 を狭く読むと、決定 14 が求める操作ができない。

takt の実装は、決定 14 に合わせて「まだ承認されていない最初のゲート」に NO-GO を書いていた。企画ゲートが未承認なら企画ゲートに、承認済みなら公開ゲートに書く。裁定役（指摘ごとに直すかどうかを判定する役）は、これを「ADR 側の前提が未確定なので持ち越し」と判定し、マージを止める問題にはしなかった。

前日のエントリでは、裁定役が根拠の文書を読まずに指摘を退けていたので、今回も ADR の該当箇所を自分で読み直した。今回は裁定役の見立てが正しく、食い違いは実在した。そのうえで、決定 7 の文言を実装の読みに合わせて直すかどうかを決める issue を起票した。公開ゲートに積んだ NO-GO からの再開を、公開ゲートの CLI の issue で扱うことも、その issue の「決めること」に入れた。

**1 つの ADR に決定を積み増していくと、前の決定で使った語の意味が、後の決定の要求と合わなくなることがある。** 実装はすべての決定を満たす読みを選び、文言の確定は別の issue にする。読み直すのは、裁定を覆すためだけではない。正しかったと確かめるためにも読む。

### 3. 構造を変える PR を先に入れておくと、次の並行では衝突しない。合わせた形は、最初のマージの前に一時 worktree で検査する

引き継ぎのメモには「2 本とも CLI の組み立て（`src/cli.ts`）か entry point（`src/index.ts`）に触る可能性があるので、衝突に気をつける」と書いていた。実際には、2 本の変更したファイルは 1 つも重ならなかった。企画ゲートの CLI は、前日のサムネイルの PR が作った `video` サブコマンドのファイルにだけ足した。codex provider は、チャンネル設定と MCP の配線とサムネイルの生成に足した。前日に CLI の組み立てを `src/cli.ts` に切り出し、サブコマンドはそれぞれのファイルで作って `src/cli.ts` が組み込むだけ、という形にしていた。既存のサブコマンドに動詞を足す変更は、そのサブコマンドのファイルの中で閉じる。

それでも、ファイルが重ならないことは、型が合うことの証拠にならない（前日の 2 節）。そこで最初の PR をマージする前に、main から一時の worktree を切り、2 本のブランチを順にマージして、検査ゲートの `pnpm run check` を通した。

ここで 1 つ、はまりかけた。最初は `pnpm run check 2>&1 | tail -15` で実行した。出力の最後には、検査ツール fallow の健全性の要約（`✗ 0 above threshold · 1840 analyzed · maintainability 91.8 (good)`）が出ていた。しかし、パイプの終了コードは最後の `tail` のものなので、ゲート全体が成功したかどうかは分からない。行頭の `✗` も紛らわしかった。出力を捨てて `pnpm run check >/dev/null 2>&1; echo "exit=$?"` で実行し直し、`exit=0` を確かめた。

**並行の PR は、最初の 1 本をマージする前に、全部を合わせた形を一時 worktree で検査する。** 検査の成否は出力の見た目ではなく、終了コードで見る。

### 4. 「起きないこと」を時間で待って確かめるテストは、不安定には落ちないが、見逃すことはある

codex provider は、候補を 1 枚ずつ順に作る。そのテストは、1 本目の codex の終了を保留した状態で実時間で 100 ms 待ち、2 本目が起動していないことを確かめる。保留を解くと、3 本すべてが起動する。

レビューでは、この 100 ms の待ちが持ち越し事項に挙がった。このテストは、実装が正しければ、CI がどれだけ遅くても落ちない。待ちが短すぎて困るのは、実装が並行に起動するように壊れたときに、2 本目が 100 ms 以内に起動せず、テストが壊れたことを見逃す場合だけだ。つまり、壊れ方は偽陰性の側にしか出ない。今の実装は逐次で、並行に変える予定も無いので、今のままにした。

**「起きないこと」を時間で確かめるテストは、不安定さではなく、検出力の弱さとして評価する。** 待ち時間を延ばすべきかは、その不具合が起きる見込みで決める。

## docs と実態のずれを洗い出し、動いていなかった git hook を「消す」から「全 worktree で動かす」に直した話

issue の仕分け（triage）の途中で、運営者（このツールの作者）から「issue-direct はもう使っていない。どこの情報？」と聞かれたのが始まりだった。issue-direct は、バグ修正を Claude Code が直接実装するための自作 skill の名前だ。今は Matt Pocock の `/implement` skill を使っていて、issue-direct 自体はもう残っていない。それなのに、agent 向けの指示書（`AGENTS.md`、当時は `CLAUDE.md`）、ADR（決定の記録）、運用 docs の 5 か所に古い名前が残っていた。そこから、docs 全体を実装と運用の実態と突き合わせた。最後は、リポを public にしてライセンスを付けるところまで進んだ。

- docs と開発設定を実態に合わせた PR: [#607](https://github.com/daiki-beppu/nyaucast/pull/607)（issue [#606](https://github.com/daiki-beppu/nyaucast/issues/606)）
- ライセンスを付けた PR: [#611](https://github.com/daiki-beppu/nyaucast/pull/611)（issue [#610](https://github.com/daiki-beppu/nyaucast/issues/610)）
- 実装側を直すと決めて既存 issue に追記したもの: [collection のゲート CLI](https://github.com/daiki-beppu/nyaucast/issues/486)、[collection を video に統合する](https://github.com/daiki-beppu/nyaucast/issues/487)

突き合わせは、サブエージェント 2 体に並行で任せた。1 体は agent 運用の docs（指示書、`docs/agents/`、takt の設定、CI、ラベル）を、もう 1 体は ADR と用語集 `CONTEXT.md` をコードと照合した。takt は、issue を渡すと計画からレビュー、PR の作成までを AI エージェントに走らせるツールだ。結果は、運用側で 9 件、ADR と用語集側で 18 件のずれだった。

### 1. 「存在しない名前」は機械で拾えるが、「使わなくなった手順」はファイルからは拾えない

調査を始める前に、運営者から「さっきみたいなずれはそれで拾える？」と聞かれた。答えは「半分」だった。issue-direct のずれには、性質の違う 2 つの面がある。

| ずれの面                    | 機械で拾えるか                                                           |
| --------------------------- | ------------------------------------------------------------------------ |
| 書かれた skill が存在しない | 拾える。`~/.claude/skills/<名前>/` があるかを見ればよい                  |
| 運用が別の手順に変わった    | ほぼ拾えない。skill が残っていても、使っていないことはファイルに現れない |

実際、名前の検査では大きな当たりが出た。PR のレビューに使うと書いてあった takt の builtin workflow `review-fix-default` は、`takt workflow inspect review-fix-default` を実行すると `Workflow not found` が返った。takt 0.61 で `review-fix` に改名されていた。

一方、運用の変化は merged PR の履歴からもほとんど読めなかった。バグ修正の PR の本文やブランチ名には、どの skill で実装したかが残っていないからだ。そこで、docs が「こう運用している」と主張している点を短い一覧にして、運営者に「今もそう / 違う」で答えてもらう形にした。

**docs の監査は、名前の実在は機械に任せ、運用の主張は持ち主に確かめる一覧にする。** 後者を確かめられるのは、運用を知っている人だけだ。

### 2. 参照先を差し替えるときは、新しい参照先の中身を読んでから書く

issue-direct を `/implement` に置き換えるとき、私は「`/implement`（worktree → `/tdd` → `/code-review` → PR 作成 → CI green まで監視）」と書いた。issue-direct の説明をそのまま新しい名前に付け替えた形だ。これは監査のサブエージェントに誤りだと指摘された。`/implement` の SKILL.md に書かれているのは、`/tdd`、型検査とテスト、`/code-review`、「Commit your work to the current branch」だけで、worktree の作成、PR の作成、CI の見届けは含まれていなかった。

この書き方のままだと、実害も出る。当時の指示書には「worktree 作成時に `-b` を付けない」という規約もあった。2 つを組み合わせると、バグ修正のコミットがブランチの無い detached HEAD に積まれる。正しくは「worktree とブランチを作り、`/implement` で commit まで進め、その後 PR を作って CI を見届ける」で、手順の前後は呼び出し側の責任になる。

**名前を差し替えるときは、古い説明を新しい名前に付け替えず、新しい参照先の本文を読んで書き直す。**

### 3. 監査を任せたサブエージェントは、セッションの開始時に読み込まれた古い指示を見ていることがある

ADR 側のサブエージェントは、最初の指摘として「`CLAUDE.md` は issue-direct と書いているが、ADR-0008 は `/implement` と書いていて食い違う」を挙げた。これは誤検知だった。監査の対象にした worktree の `CLAUDE.md` は、すでに直してあった。サブエージェントが見ていたのは、セッションの開始時にコンテキストへ読み込まれた修正前の指示書だった。`git grep` で、worktree に issue-direct が残っていないことを確かめてから、この指摘を外した。

**サブエージェントに作業中の差分を監査させるときは、ファイルを読む場所を明示し、指摘はファイルから裏を取ってから採る。**

### 4. worktree の間で共有される git 設定に 1 つの worktree の場所を書くと、全 worktree の hook が黙って止まる

運用側の監査で、git hook がどの worktree でも動いていないことが分かった。このリポは Vite+（`vp` CLI）の hook を使っている。`vp hooks enable` は hook の振り分け役（dispatcher）を `.vite-hooks/_/` に生成し、`git config core.hooksPath` をそこに向ける。この設定には 2 つの落とし穴があった。

- `core.hooksPath` は、すべての worktree で共有される `.git/config` に書かれる。値はメインチェックアウトの絶対パスを指していたが、その場所に `.vite-hooks/_` は無かった。存在しない場所を指す hook は、git が黙って飛ばす
- dispatcher は gitignore されていて、`vp install` の `prepare` を実行した worktree にしか生成されない。依存が揃っている worktree で `vp install` を実行しても `prepare` は走らず、dispatcher は作られなかった

私は最初、「hook はどうせ動いていないので消す」を提案し、運営者も「hooks は削除でいい」と答えた。ところが、別の worktree でコミットすると pre-commit の整形が走った。新しい worktree で依存を install したときに `prepare` が走り、共有の `core.hooksPath` をその worktree に向け直したからだ。それを見た運営者の答えは「それ自体はなんら問題ない。逆にワークツリーでもちゃんと動くようにしないと」だった。hook が要らないのではなく、hook が届いていないことが問題だった。

直し方は 2 つの組み合わせにした。

1. dispatcher の `.vite-hooks/_/` を git で追跡する。どの作り方の worktree でも、checkout した時点で dispatcher が入る
2. `core.hooksPath` は相対パスの `.vite-hooks/_` にする。今の `vp hooks enable` はこの形で書く。相対パスは各 worktree のルートから解決されるので、各 worktree が自分の dispatcher を使う

依存を入れていない新しい worktree で試すと、hook は黙って通らず、`Cannot find package 'vite-plus'` でコミットが失敗した。`vp install` の後にもう一度コミットすると、整形が走ってから通った。pre-push の `pnpm run check` も戻し、push のたびに検査が走ることを確かめた。

`.env` などを worktree にコピーする `.worktreeinclude` で dispatcher を運ぶ案も、運営者から出た。ただ、`.worktreeinclude` が効くのは、Claude Code や Codex のデスクトップアプリ自身が worktree を作るときだけで、手動の `git worktree add` や takt、Orca（worktree と端末を束ねて管理するアプリ）には効かない。追跡する方式なら、作り方に関係なく届く。

**「動いていない仕組み」を見つけたら、要らないのか、届いていないのかを先に分ける。** worktree の間で共有される設定には、特定の worktree の絶対パスを書かない。

### 5. ADR と実装がずれたとき、どちらに合わせるかは「後から意図して決めた記録があるか」で分ける

運営者の方針は「ADR と用語集は今の実装に準拠させる」だった。ただ、「どちらかに準拠させたほうがいい内容があれば教えて」とも添えられていた。ずれを 1 件ずつ見ると、合わせる向きは 1 本の問いで分かれた。「ずれの後に、意図して決め直した記録があるか」だ。

| ずれ                                                        | 後から決め直した記録                                         | 合わせる向き          |
| ----------------------------------------------------------- | ------------------------------------------------------------ | --------------------- |
| 解説動画の表名が「実装 ticket で決める」のまま              | なし（実装で決まった）                                       | ADR を実装に合わせる  |
| YouTube の OAuth が、外部 HTTP の共通クライアントを通らない | なし（公式 SDK に任せた結果）                                | ADR に例外として書く  |
| collection の CLI が「次に取る行動」の文章を出す            | あり（前日に「CLI は次の行動の文章を持たない」と決め直した） | 実装を ADR に合わせる |
| npm パッケージに `license` が無い                           | あり（ライセンスの付与を決めた）                             | 実装を ADR に合わせる |

実装側を直すものも、新しい issue は立てなかった。CLI の文章は、collection の CLI を解説動画の規則にそろえる既存の issue に、tool の名前の規則違反は、collection を video に統合する既存の issue に、それぞれ要件として追記した。ADR には「v0.1 では collection の CLI は変えない」とあるので、別 issue にすると、その決定とぶつかる作業が宙に浮く。

**実装の結果として自然に決まったものは ADR を書き直し、ずれの後に意図して決め直したものは実装を直す。**

### 6. 課金で止まった CI は、リポを public にすると標準の runner で回る。公開の前に「公開と同時に」の決定と履歴の走査を済ませる

PR の CI が、テストの失敗ではなく `The job was not started because recent account payments have failed or your spending limit needs to be increased.` で止まった。運営者から「このリポジトリはオープンにするので、それをやれば回るのでは？」と聞かれた。GitHub は、public リポで標準の GitHub-hosted runner を使う Actions を無料にしている。ただし、エラーは「支払いの失敗」だったので、アカウント単位で止められていれば public でも動かない可能性がある、と前置きした。結果は、public にして re-run すると 2 本とも success になった。

公開の前に、次の 3 つを済ませた。

- 前日の ADR は「`LICENSE`・`license`・著作権表示は、リポの公開と同時に付ける」と決めていた。Apache-2.0 の全文（apache.org の原文と SHA-256 が一致）、著作権表示だけの `NOTICE`、`package.json` の `license` を入れた。npm の tarball に 3 ファイルが入ることも、契約テストで固定した
- 公開までの暫定措置として出していた「`UNLICENSED` を明記する」PR は、意味がなくなったので閉じた
- `nix run nixpkgs#gitleaks -- git` で全履歴（278 コミット）を走査し、秘密情報が無いことを確かめた

同じ流れで、agent 向けの指示も `AGENTS.md` の 1 本にした。それまでは `CLAUDE.md` を実体とし、`AGENTS.md` をそこへの symlink にしていた。Claude Code は v2.1.277 以降、`CLAUDE.md` が無いときに `AGENTS.md` を読む（手元は 2.1.288）。

**CI の課金エラーは、公開予定のリポなら公開で解けることがある。ただし公開は戻しにくいので、その前に「公開と同時に」と決めた作業と、全履歴の秘密情報の走査を先に終える。**

### 1. 複数の観点が独立に同じ点を挙げたら、裁定の「要求に書かれていない」を自分で読み直す

ショートの run（#550）では、構成・CQRS・業務ルール・AI のアンチパターンの 4 観点が、独立に同じ点を指摘した。重大度を「高」とした観点が 2 つあった。裁定役は 4 件を 1 つにまとめ、「書き出しの時点で composition・音声の鮮度を検証して型付きの失敗にする契約は、issue・ADR・既存の利用側のどれにもありません」として退けた。

マージの前に指摘の中身を読むと、公開の安全を崩す不具合だった。ショートの候補（フックの文言や切り抜く範囲）を書き直したあと、composition を組み立て直さずに描画すると、古い内容の mp4 に、新しい時刻の書き出しの記録が積まれる。公開ゲート（運営者が投稿を承認する関門）の承認待ちの条件は「最後の書き出しが、候補の最後の版より新しい」なので、古いカットがこの条件を満たしてしまう。皮肉なことに、実装の途中で「書き出しの時刻を版の時刻より必ず後にする」処理を足していて、これが古い書き出しでも条件を確実に満たすように働いていた。

修正（[#635](https://github.com/daiki-beppu/nyaucast/pull/635)）では、ショートの composition に候補の版を `<meta name="nyaucast-short-version">` として書き、描画のときに版がずれていれば `CompositionStale` という型付きの失敗で止めるようにした。既存のテストの 1 本（「候補を書き直した後、ファイルが変わらなくても描画し直す」）は、まさにこの不具合の挙動を固定していたので書き換えた。

裁定役の「要求に無い」は、字面としては正しかった。鮮度の検証は、どの文書にも書かれていない。ただし、要求に書かれていたのは「承認待ちの条件」という上位の安全の性質で、鮮度の検証はそれを成り立たせるための前提だった。4 観点が別々の道筋で同じ点に着いたことが、そのしるしだった。

**裁定の「要求に書かれていない」は、上位の性質を成り立たせる前提が抜けている、という指摘を退けてしまうことがある。** 複数の観点が独立に同じ点を挙げたら、裁定を覆すかどうかは別にして、指摘の中身を自分で読む。

### 2. 指摘の失敗シナリオが現実の入力で起きるなら、「要求に無い」は直さない理由にならない

同じ形の退け方は、他の run にもあった。

| run  | 退けられた指摘                                      | 退けた理由                         | 現実に起きること                                                      |
| ---- | --------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| #540 | フィードの取得がリダイレクトに追従しない            | 要求のどこにも追従は書かれていない | http から https への 301 だけで、そのフィードの候補が毎回取れなくなる |
| #543 | 検査に落ちたサムネイルの回を記録しない              | 必要以上の拡張                     | 再実行のたびに同じ番号で再び課金される                                |
| #548 | 図解の CSS の `image-set()` の中の URL を検査しない | 契約は `url(...)` の検査だけ       | 描画の環境から、指定した外部の URL へ GET が飛ぶ                      |

どれも、指摘には具体的な失敗シナリオが付いていた。リダイレクトは、RSS を http で公開しているサイトなら普通に起きる。図解の契約の冒頭には「外部を参照しない」とあり、`url(` の直後だけを検査するのは、その目的の実装の 1 つにすぎなかった。修正はそれぞれ小さく、リダイレクトは上限 5 回まで追従し（[#622](https://github.com/daiki-beppu/nyaucast/pull/622)、+83 / −10）、`image-set()` は括弧の深さ 1 にある文字列も検査した（[#629](https://github.com/daiki-beppu/nyaucast/pull/629)、+59 / −3）。

一方で、退けられたまま今も直していない指摘もある。別のプロセスどうしが同時に書いたときの排他や、負の長さの区間の扱いだ。これらは、今の使い方（運営者が 1 人で、MCP サーバーを 1 つ動かす）では起きない。

**退けられた指摘を読み直す基準は、失敗シナリオの入力が今の運用で現実に来るかどうか。** 来るなら、要求に書かれていなくても直す。来ないなら、退けたままでよい。

### 3. 弱いテストを消す指摘を採るなら、守っていた決定を別の仕組みで守り直す

描画の run（#549）では、テストの観点が「ソース文字列を走査するテストを消すべき」と指摘した。そのテストは、tool のファイル名とソースの文字列を照らして、headless Chrome を使う tool を確かめていた。指摘の理由は「別の tool が共有関数を経由して Chrome を使っても検出できない」で、裁定役はこれを採り、テストは消えた。

指摘そのものは正しかった。ただ、そのテストは「Chrome を使ってよいのは描画と確認用の書き出しの 2 つの tool だけ」という ADR の決定を、機械的に守る唯一の仕組みだった。テストを消すと、決定を守るものが何も無くなる。マージの前の確認でこれに気づき、別の issue（#631）にした。

修正（[#632](https://github.com/daiki-beppu/nyaucast/pull/632)）では、静的解析ツール fallow の `boundaries`（どのディレクトリがどこを import してよいかの規則）で、Chrome の供給を import できる場所を限った。共有関数を経由しても import の連鎖で検出できるので、消したテストの弱点もふさがる。設定は契約テストで固定し、抜け道を 5 通り仕込んで、どれもこの契約テストだけが落ちることを確かめた。あわせて描画のページで外部への要求を止めた。ループバックのテストサーバーに届いた要求は、止める前が 3 回、止めた後が 0 回だった。

**テストの削除は、そのテストが守っていた決定を、より強い仕組みで守り直すところまでで 1 つの変更にする。** 「弱いから消す」だけを採ると、決定が無防備になる。

### 4. テストのファイルの末尾に双方がブロックを足した衝突は、片方を土台にして、もう片方を足し直す

本線の PR を順にマージすると、main を取り込むたびに衝突が出た。#548 と #550 では、どちらもテストのファイルの末尾に、両方のブランチが `describe` のブロックを足した形だった。

最初は「両方残す」を機械的に当てた。ところが git は、2 つのブロックに共通する閉じ括弧（`});`）で区切りを合わせるので、片方のブロックの閉じ括弧がもう片方に吸われる。結果は括弧が 1 組足りないファイルで、整形の段で `Expected } but found EOF` で落ちた。

片方のファイル（HEAD）を土台にして、もう片方のブロックを、コメントの見出しを目印に末尾へ足し直すと通った。

**末尾への追記どうしの衝突は、区切りを信じずに、片方を土台にしてブロック単位で足し直す。**

### 5. 画素で確かめるテストは、システムのフォントに依存しているかもしれない

ショートの PR は、手元（macOS）では通ったのに、CI（Ubuntu）で 1 本だけ落ちた。切り抜きのカットの配置（図解は中央の 16:9 の枠、フックは上の帯、字幕は下の帯）を、描画した画素の色で確かめるテストだ。

テストのテーマに入れたフォントは偽のバイト列なので、文字は実際にはシステムのフォントで描かれる。Ubuntu のランナーには日本語のフォントが無く、字幕の帯の画素が期待と変わった。CI に `fonts-noto-cjk` を入れる手順を足して通った（約 12 秒かかる）。

**画素を確かめるテストを書いたら、文字がどのフォントで描かれているかを確かめる。** 偽のフォントを渡していても、描画はシステムのフォントに落ちていることがある。

<a id="takt-push-failures"></a>

## takt の自動の push が pre-push の検査で落ち、原因を時刻で照合し直した話

投稿案と公開ゲートの承認待ち（#551）、codec の配布（#557）、BGM 動画のゲートの CLI の統合（#487）を takt で回したときの、運用の学び。codec は、どの順で tool を呼ぶかという手順の知識を、AI エージェント向けの skill のファイルとして配るものだ。3 本とも PR になったが、2 本は takt の最後の push が失敗し、PR は私（この開発を進めている Claude Code）が作った。

- 実装した issue と PR: [#551](https://github.com/daiki-beppu/nyaucast/issues/551)（[#641](https://github.com/daiki-beppu/nyaucast/pull/641)）、[#557](https://github.com/daiki-beppu/nyaucast/issues/557)（[#636](https://github.com/daiki-beppu/nyaucast/pull/636)）、[#487](https://github.com/daiki-beppu/nyaucast/issues/487)（[#642](https://github.com/daiki-beppu/nyaucast/pull/642)）
- 起票した issue: [テストのタイムアウト](https://github.com/daiki-beppu/nyaucast/issues/644)、[codec の配布の実機確認](https://github.com/daiki-beppu/nyaucast/issues/640)

| issue | takt の所要 | 差分                       | push |
| ----- | ----------- | -------------------------- | ---- |
| #557  | 約 87 分    | 14 ファイル（+910 / −9）   | 成功 |
| #551  | 約 80 分    | 26 ファイル（+2094 / −57） | 失敗 |
| #487  | 約 37 分    | 19 ファイル（+714 / −455） | 失敗 |

### 1. 自動の push は、pre-push の検査が重いと落ちる。落ちたら PR が無いことに気づける場所を見る

このリポジトリは、push の前に検査ゲートの全体（型検査、lint、テスト約 1,500 件）を pre-push フックで走らせる。takt の最後の手順はブランチの push と PR の作成なので、ここでテストが 1 本でも落ちると、作業は全部終わっているのに PR ができない。

#487 では、MCP サーバーを子プロセスで起動する契約テストが 3 本、`timed out waiting for JSON-RPC response 1` で落ちた。サーバーの最初の応答を 10 秒待つ作りだ。#551 では、ショートの 60 秒の上限を確かめるテストが `Test timed out in 120000ms.` で落ちた。どちらも、takt のログの末尾近くに `failed to push some refs` が出ていた。どちらの worktree でも、main を取り込んで `pnpm run check` を手元で回すと通ったので、私が push して PR を作った。

takt の終了コードと最後の表示だけを見ていると、この失敗は見落とす。終了を待つ見張りには、ログの末尾の `PR created:` の有無まで確かめさせた。

**自動の push を最後に置く仕組みでは、「PR ができたか」を完了の条件にする。** 検査が落ちて push されなくても、実装そのものは使えることが多い。

### 2. 失敗の原因は、思いついた説明で書かず、ログの時刻で照合する

私は最初、2 件とも「takt を 2 本並行で回した負荷」が原因だと考え、引き継ぎのメモにも issue（#644）にもそう書いた。#487 の失敗の時刻（05:25 UTC）には、別の takt（#623）が動いていたからだ。

開発ログの素材を集めるために 3 本の run の時刻を並べると、#551 には当てはまらなかった。#551 の push は 03:00 UTC 頃で、並行していた #557 の run は 02:46 に終わっていた。この時間帯には、ディスクの空きが 261 MB まで減っていた（運営者が空けて解消した）。PR #641 の本文にも、ディスクの不足と書いてあった。さらに、どちらの失敗にも直前に `Connection to github.com closed by remote host.` が出ていた。pre-push の検査が長引く間に、push の SSH 接続が切られた可能性もある。#644 は、この内容に書き直した。

同じ日に、もう 1 つ同じ形の誤りをしていた。メモには「`assembleComposition` の 60 秒の上限のテストが落ちる」と書いていたが、ログで落ちていたのは `mixAudioTrack` の同名のテストだった。`assembleComposition` の方は、タイムアウトが既定の 5 秒のままで落ちうる、という別の事実だった。

**「並行のせい」「負荷のせい」は、もっともらしいので確かめずに書いてしまう。** 失敗の時刻と、そのとき動いていたものを並べてから書く。

### 3. 自動で作られた PR のタイトルは、そのまま main のコミットの件名になる

takt が作る PR のタイトルは `[#550] ショートの候補と、切り抜き・専用のカット` の形だ。このリポジトリのコミットの規約は、日本語の Conventional Commits で、末尾に `(#<issue>)` を付ける。squash マージは既定で PR のタイトルを件名にするので、規約に合わない件名が main に 1 つ入った（`4c333c7`）。main の履歴は書き換えないので、これは直せない。

それ以降は、マージのときに件名を明示した。

```sh
gh pr merge 636 --squash --delete-branch --subject 'feat: explainer-lifecycle codec と codec の配布 (#557) (#636)'
```

**自動で PR を作る仕組みを使うなら、件名はマージの側で決める。** PR のタイトルを直すより、マージのコマンドに件名を持たせる方が漏れない。

### 4. 人が実機で確かめる受け入れ条件は、takt では閉じないので、マージの前に別の issue にする

codec の配布（#557）には、「下流のリポジトリで、symlink の解決と、install 前の Claude Code / Codex の振る舞いを確かめる」という受け入れ条件があった。裁定役はこれを「判定不能（持ち越し）。人間が実機で行う作業」とした。静的な検査は通っていて、実装の判定は APPROVE だった。

この条件を残したまま issue を閉じると、確かめていないことが記録から消える。PR のマージの前に、実機確認だけを別の issue（#640）に切り出した。

**エージェントが閉じられない受け入れ条件は、マージの前に issue に切り出してから閉じる。**

<a id="video-tool-names"></a>

## MCP tool の名前をすべて `video.*` にそろえ、チャンネルの種類の tool だけを公開した話

nyaucast は、解説動画のチャンネルと BGM 動画（collection）のチャンネルという 2 種類のチャンネルを扱う。それまでの MCP サーバーは、18 個の tool を種類に関係なく全部公開していて、名前の先頭もばらばらだった（`plan.init`、`collection.status`、`explainer.renderCut`、`video.status` など）。これを、すべて `video.*` にそろえ、起動したチャンネルの種類の tool だけを公開する形に変えたときの学び。

- 実装した issue: [MCP tool の名前を video.* に統一し、チャンネルの種類の tool だけを公開する](https://github.com/daiki-beppu/nyaucast/issues/623)（PR [#643](https://github.com/daiki-beppu/nyaucast/pull/643)、61 ファイル、+1533 / −1351）
- 起票した issue: [MCP の instructions を、チャンネルの種類ごとに選ぶ](https://github.com/daiki-beppu/nyaucast/issues/645)

### 1. 公開する名前は、起票の後に増えた分まで対応表にして、人に選んでもらう

この issue は前日に別のセッションで起票されていた。takt に渡す前に読み直すと、起票の後に解説動画の tool が 10 個増えていて、それらの新しい名前は本文に無かった。ADR には「カットやファイル単位の操作は `video.` を名乗らない」という決定も残っていて、`explainer.renderCut` のような名前を残す読み方もできた。

tool の名前は、AI エージェントが MCP 越しに呼ぶ公開の API で、codec の手順書にも書かれる。エージェントの側で既定の答えを決めて進めてよい範囲を超えると判断し、運営者に「すべて `video.*` にする / カット単位は種類の名前を残す」の 2 択で聞いた。答えは「全部 video.* にする」だった。そのうえで、増えた 10 個を含む対応表と、名前が波及する先（2 つの ADR、静的解析の境界の設定、codec の tool 名）を issue の本文に書き足してから takt に渡した。

**公開の名前を決める issue は、起票の後に増えた対象まで対応表にして、人に選んでもらってから実装に渡す。** 実装役は本文に無い名前を推測で決めるので、表が無いと、決めていない名前が API になる。

### 2. 種類の違う tool は、中で失敗させるより、そもそも見せない

それまでは、BGM 動画のチャンネルにいるエージェントにも解説動画の tool が見えていて、呼ぶと tool の中で `NotExplainerChannel` という失敗が返った。変更前の tool の実装には、この失敗を扱う行が 43 行あった。

新しい形では、MCP サーバーが起動時にチャンネルの設定から種類を 1 回だけ読み、解説動画なら 15 個、BGM 動画なら 3 個の tool を公開する。公開していない tool は呼べないので、tool の中の種類の判定と `NotExplainerChannel` は消えた。issue では、1 つの tool の中で種類を見て振り分けることと、入力の schema を種類の union にすることを禁じた。その結果、`video.writePlan` や `video.status` は、同じ名前で種類ごとに別の実装を持つ。

その代わり、チャンネルの設定が無いと、MCP サーバーは tool の一覧に答える前に起動が失敗するようになった。以前は設定が無くても起動できたので、挙動の変更になる。

**呼んではいけない tool は、中で失敗させるより、一覧から外す。** エージェントは見えている tool を呼ぶので、見せなければ間違えようがない。

### 3. 名前を変える PR と、同じ範囲に触る PR を並行させると、レビューが名前の古さを指摘し合う

BGM 動画のゲートを `video` の CLI に統合する #487 は、#623 と並行で走らせた。#487 のレビューでは 3 観点が「BGM 動画の MCP tool が旧名のまま」と指摘し、裁定役は「改名先が一意に決まらず、受け入れ基準にも無い」として止めなかった。改名は #623 の範囲だったので、この裁定は結果として正しかった。

マージは #487 を先にした。#623 に main を取り込むと、チャンネルの設定の読み口、BGM 動画の状態の tool のテスト、codec の検査の補助の 3 ファイルで衝突した。#623 の側を土台にし、#487 で入った変更（動画をやめる操作の関数名、使われなくなった補助の削除）を足し直して、検査を通してからマージした。

並べて気づいたこともある。種類ごとに tool を出し分けたのに、MCP サーバーの `instructions`（エージェントに codec への道案内をする文）は種類によらず同じ文面のままだった。BGM 動画のチャンネルでも、解説動画の codec を読むよう案内する。takt の実装役はこれに気づいて範囲の外に回していたが、issue は立っていなかったので、#645 として起票した。

**出し分けを入れたら、一覧以外にエージェントへ渡しているもの（説明文、道案内）も同じ軸で出し分けるかを確かめる。**
