## 検査の品質を落とさずに、CI を約 5 分から約 80 秒まで縮めた話

PR ごとに走る CI（GitHub Actions の `quality` job）を縮めたときの学び。運営者の条件は「検査の品質を落とさない」の 1 つだけで、OSS なので並列にして CI の分数を使うことは気にしなくてよい、とも言われた。途中で「無駄なテスト、flaky なテストは消すのも視野に入れていい」と許可も出たが、実際に消したのは、ほかのテストと同じ内容を実描画で繰り返していた 2 件だけだった。CI の中身は `pnpm run check` の 1 コマンドで、lockfile・書式と lint・Effect の診断・workflow の lint・テスト（Vitest）・dead code の検査が順に走る。テストには、ヘッドレスの Chrome で動画を実際に描画するもの（`video.renderCut` など）や、音声を合成して loudness を測るもの（`video.mixAudioTrack`）が含まれる。

- 2 日がかりの経過: 約 5 分 15 秒 → 2 分 17 秒 →（テストが増えて 2 分 40 秒に戻る）→ 1 分 49 秒 → 同時刻の比較で平均 82 秒
- 主な PR: shard 化 [#716](https://github.com/daiki-beppu/nyaucast/pull/716)、true peak の高速化 [#724](https://github.com/daiki-beppu/nyaucast/pull/724)、flaky の修正 [#736](https://github.com/daiki-beppu/nyaucast/pull/736)、メモリのテストの並行化 [#740](https://github.com/daiki-beppu/nyaucast/pull/740)、pnpm の用意の 1 step 化 [#741](https://github.com/daiki-beppu/nyaucast/pull/741)、所要時間の記録で shard を分ける [#743](https://github.com/daiki-beppu/nyaucast/pull/743)、静的ゲートの並行化 [#749](https://github.com/daiki-beppu/nyaucast/pull/749)
- 見送った案の記録: [描画の撮影が Chrome のフレームの拍に待たされる](https://github.com/daiki-beppu/nyaucast/issues/747)

### 1. 速さの比較は、同じ時刻に並べて走らせた組で行う

GitHub の runner は、同じコードでも 1 回ごとに ±20〜25 秒揺れた（同じコミットで 113〜163 秒を観測した）。runner の割り当て待ちだけで 30 秒以上遅れる回もある。1 回ずつ走らせて比べると、10 秒の改善は揺れに埋もれる。

そこで、比べたい変更を合わせた検証用のブランチを draft PR にし、main の run と同時に `gh run rerun` する組を 3 つ作った。1 回目は cache の状態が違うので捨てる。待ちと rerun はスクリプトにして裏で回した（`gh run watch` や長い sleep のループは、API の一時的な 500 で止まりやすい）。最後の比較はこうなった。

| 構成                            | 3 組の全体の時間   | 平均   |
| ------------------------------- | ------------------ | ------ |
| main                            | 108 / 104 / 102 秒 | 105 秒 |
| 静的ゲート以外の 3 本 + 4 shard | 80 / 82 / 77 秒    | 80 秒  |
| 4 本すべて                      | 81 / 74 / 90 秒    | 82 秒  |

最後の「静的ゲートの並行化」は、全体の時間では揺れに埋もれて見えなかった。ログで「Check の開始からテストの開始まで」だけを切り出すと、平均 9.9 秒から 7.6 秒に縮んでいた。小さな改善は、全体ではなく、変えた区間の時刻を直接比べる。

### 2. 律速は、shard → ファイル → テストの順に、時刻の並びで分解して探す

全体の時間を見ても、どこを削ればよいかは分からない。step ごとの開始と終了（`gh api .../jobs` の `steps[]`）、shard ごとのファイルの所要時間、ファイルの中のテストの開始と終了、と順に細かくした。テストの開始と終了は、Vitest の reporter を 5 行で書けば出る。

```ts
const t0 = Date.now();
export default class {
  onTestCaseReady(t: { name: string }) {
    console.log(`+${((Date.now() - t0) / 1000).toFixed(1)} start ${t.name}`);
  }
  onTestCaseResult(t: { name: string }) {
    console.log(`+${((Date.now() - t0) / 1000).toFixed(1)} end   ${t.name}`);
  }
}
```

`vp test run <file> --reporter=./order-reporter.ts` で動画の描画のテストを見ると、「並行のまとまり 12 秒 → 10 分の音声でメモリを測るテスト 1 件だけ 27 秒 → 並行のまとまり 4 秒」と直列に並んでいた。Vitest は、隣り合う `describe.concurrent` をまとめて並行に走らせるが、並行でない `describe` が 1 つあると、そこで並行のまとまりが区切られる。メモリのテストは「プロセス全体の arrayBuffers を測るので並走させない」という理由で並行でない `describe` に置かれていて、ファイル全体がこの 1 件を単独で待っていた。

### 3. 「並走させない」理由は、測る量が並走でどちらに動くかで見直す

メモリのテストが測るのは、10 分の音声を描画する間の arrayBuffers の伸びで、閾値は 150 MB。音声全体を持ってしまう実装なら約 345 MB 伸びる。並走するほかのテストは 1 秒の音声しか扱わない。並走による上乗せは伸びを増やす向きにしか働かないので、退行を見逃す向きには効かない。危険は誤検知だけで、実測は単独で約 21 MB、並走させて 12〜24 MB だった。

並行のまとまりに入れ、最も長いテストとして先頭に置いた。ところが CI では、このテストそのものが 17 秒から 44 秒に延びた。音声のエンコード（node-av を使う `@mediabunny/server`）が、AAC の 1 フレーム（1024 サンプル）ごとに非同期の往復を約 4 回する作りで、600 秒の音声では約 11 万回になる。並走する描画の画像のデコードや映像のエンコードと、libuv のスレッドプールを取り合って、1 回ごとの待ちが延びた。CPU プロファイルでは、このテストの間、メインスレッドは 13.9 秒のうち 10.3 秒アイドルだった。ファイル全体は 53 秒から 44 秒に縮んだが、律速が入れ替わっただけでもあった。並行にすると、並走で延びる区間が次の律速になる。

### 4. ファイルの大きさは、テストの所要時間の目安にならない

shard（テストを N 本の job に分けて並行に走らせる仕組み）の分け方は、最初はファイルの大きさを重みにした LPT（重い順に、そのときいちばん軽い shard へ詰める）だった。分解してみると、大きさと時間はほぼ無関係だった。

| ファイル                 | 大きさ         | CI の所要時間     |
| ------------------------ | -------------- | ----------------- |
| 投稿の実行のテスト       | 128 KB（最大） | 7〜10 秒          |
| 動画の描画のテスト       | 37 KB          | 44〜53 秒（最長） |
| プレビューの描画のテスト | 28 KB          | 13〜21 秒         |

そのため、最も重い描画のテストが、同じく Chrome を使うプレビューのテストなどと同じ shard に入り、4 vCPU を取り合っていた。

所要時間の cache（Vitest が前回の実行の時間を残すもの）を重みにする案は、最初に退けていた。shard の job ごとに読む cache が違うと、job ごとに分け方が食い違い、どの job も成功したまま、どこでも走らないテストが出る。答えは、所要時間を JSON に記録してリポジトリに含めることだった。チェックアウトが同じなら、どの job も同じ分け方になる。記録が古くなっても崩れるのは均衡だけで、テストの漏れは起きない。記録に無い新しいファイルは 1 秒として扱う。これで描画のテストが軽いファイルだけの shard に入り、4 本にした最も遅い shard の job は約 100 秒から約 75 秒になった。

### 5. 記録を作り直す道具は、一部だけを走らせた結果を読めない形にする

記録の作り直しは、最初は Vitest の cache（`node_modules/.vite/vitest/*/results.json`）を読む形で書いた。直後に、自分で `-t` で 1 件も当たらない絞り込みをして shard の振り分けを確かめた結果、cache の所要時間がすべて 0 で上書きされ、作り直した記録が壊れた。レビューのサブエージェントも同じ穴を指摘した。

cache を読むのをやめ、作り直しのコマンドの中で全件を JSON の reporter で走らせ、その出力だけを読む形にした（`vp test run --reporter=json --outputFile=... && node scripts/update-shard-weights.ts ...`）。全件の結果しか入らないので、古い記録との合成も、消えたファイルを捨てる処理も要らなくなった。

### 6. 速くなる設定は、何もしていないときの CPU も測ってから採る

描画の撮影は、1 フレーム約 51 ms かかっていた。測ると、seek が約 1 周期、スクリーンショットが約 2 周期と、60 Hz の描画周期の倍数に揃っていた。CPU ではなく、Chrome のフレームの拍に待たされている。chrome-headless-shell の起動フラグを試した（320x180・30 フレーム）。

| 追加したフラグ                            | 30 フレームの撮影 | 何もしていない 3 秒間の Chrome の CPU |
| ----------------------------------------- | ----------------- | ------------------------------------- |
| なし                                      | 約 1550 ms        | 0.00 秒                               |
| `--disable-frame-rate-limit`              | 約 1010 ms        | 0.00〜0.03 秒                         |
| `--run-all-compositor-stages-before-draw` | 約 2630 ms        | 測っていない                          |
| 上の 2 つを併用                           | 123〜199 ms       | 9.7〜9.9 秒                           |

併用すると撮影が約 12 倍速くなり、PNG のバイト列は 30 フレームとも元と一致した。ここで採りかけたが、関係するテストを丸ごと走らせると、ローカルの負荷平均が 155 まで上がり、別のテストが次々に timeout した。何もしていないページでも Chrome が約 3 コアを回し続けていた。並行する描画やエンコードと CPU を奪い合うので、製品でも CI でも使えない。正攻法の BeginFrame 制御（フレームを要求したときだけ 1 枚描く）は、macOS 版では `BeginFrameControl is not supported on MacOS yet` を返した。運営者は Mac で描画するので外した。結論を出さずに、測った表を issue に残した。

### 7. 負荷でだけ落ちる flaky は、遅延を注入して再現してから直す

投稿の実行のテストが、負荷の高い CI でだけ timeout した。テストは、仮想時計（Effect の `TestClock`）を進めて polling の sleep を解放していたが、時計を進める回数に 200 回の上限があった。本物の I/O が進む間に空回りした回数が上限を食いつぶしていた。上限を外すと、今度は CI でだけ、時計が許容幅の 60 分を越えてから期日の判定が走り、`scheduled_in_past` で失敗した（ローカルでは通る）。

最初の修正はレビューを通っていたが、この 2 つ目の失敗の形を見逃していた。テストの中に本物の遅延を差し込んで再現させると、初めて見えた。直し方は、polling の最初の要求が出るまで時計を進めずに待ち、そこから時計を進める、だった。同じ形の潜在的なリスクが別の 2 件のテストにもあり、issue にした。

### 8. JS のホットループは、プロファイルで見つけ、出力のビット一致を保って直す

loudness の true peak（4 倍オーバーサンプリングでサンプルの間の山を補間する計算）が、音声のテストの CPU の大半を使っていた。Vitest の worker は `NODE_OPTIONS=--cpu-prof` では取れなかった。`node:inspector/promises` で `Profiler.start` / `stop` する小さなファイルを、テストファイルの先頭で一時的に import して取った。

直すときの縛りは、出力をビット単位で変えないことにした。足し算の順を保てば、浮動小数点の結果は変わらない。

- 1 回の読み込みで 2 点ぶんの和を取ると速くなった
- 3 点を 1 つのループにまとめると、リポジトリの複雑度の上限（`?? 0` も分岐に数える）を超えた
- タプルや subarray を `for...of` で回すと、約 4 倍遅くなった

2 点と 1 点の 2 つの関数に分けて、約 700 ms が約 240 ms になった。テストの音声データを作る関数も、配列のメソッドの連鎖を素の for ループと `DataView` に替え、出力のバイト列を変えずに速くした。

### 9. 検査の並べ方を変えたら、壊し方を入れて契約テストが落ちるかを確かめる

CI の構成には、契約テスト（`test/platform-contracts.test.ts` など。shard がすべてのファイルを 1 回ずつ覆うこと、`quality` の check 名が残ることなどを固定する）がある。変更のたびに、わざと壊して契約テストが落ちるかを見た。

- 記録を読まない sequencer は、つなぎのテストで落ちる
- `require-lockfile` を外すと落ちる。pnpm/setup は既定では lockfile が無くても install して成功する
- 静的ゲートを直列に戻すと落ちる

最後のものは、最初は契約が無かった。静的ゲートの並行化は、pnpm の正規表現による script の実行（`pnpm run '/^(vp|effect|actions):check$/'`）で書いた。pnpm は 1 つが失敗した時点で残りを止め、終了コードを返す。これを確かめたのは手元の実験だけで、`&&` の直列に戻しても全テストが通る状態だった。Spec の軸のレビューがそれを指摘した。使い捨ての package.json で本物の pnpm を走らせ、「20 秒の遅い script を待たずに失敗し、後ろへ進まない」ことを確かめる契約を足した。ゲートの一覧はどこにも書き写さず、「テストの直前のゲートが、2 つ以上の script に当たる正規表現である」という形だけを固定した。
