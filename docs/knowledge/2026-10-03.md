## 地図に残った最後の ticket を範囲の外と判定し、close せずに次のリリースの issue へ付け替えた話

v0.1.0 の実装計画の地図で、残っていた最後の ticket を片づけたときの学び。地図は、GitHub の issue 1 本に「目的地（Destination）」「決めたことの索引」「まだ問いにできない論点（Not yet specified）」「範囲の外（Out of scope）」を書き、論点を子 issue（ticket）として並べたものだ。目的地は「v0.1.0 のリリースゲートに必要な決定がすべて済んだ状態」になっている。ticket は 1 セッションで 1 つずつ解決する。ほかの ticket を待たずに着手できるものの集まりを frontier と呼ぶ。

このセッションの時点で、open の ticket は「Devin の VM で nyaucast を動かす検証」の 1 本だけだった。Devin はクラウドで動くコーディングエージェントで、この ticket は、その VM の中で nyaucast が動くかを人間が手で確かめる task だ。結論として、この ticket を地図から外し、v0.2 の issue の配下に open のまま移した。まだ問いにできない論点として残っていた 3 件は、ticket に起こした。

- 地図: [v0.1.0 解説動画 lifecycle と 3 SNS 配信の実装計画マップ](https://github.com/daiki-beppu/nyaucast/issues/457)
- 付け替えた ticket: [[v0.2] Devin の VM で nyaucast を動かす検証](https://github.com/daiki-beppu/nyaucast/issues/506)（移した先: [[v0.2] 実行環境の間で引き渡せるように、local store と成果物を実行環境の外に置く](https://github.com/daiki-beppu/nyaucast/issues/505)）
- 起こした ticket: [BGM プールの曲の調達元（権利）とダッキングの規則](https://github.com/daiki-beppu/nyaucast/issues/525)、[公開後運用の v0.1 での範囲](https://github.com/daiki-beppu/nyaucast/issues/526)、[dogfood 実走で区間が失敗したときの戻し方](https://github.com/daiki-beppu/nyaucast/issues/527)
- この ticket を地図に足した経緯: [「Devin の VM でも動かしたい」を、決めることと確かめることに分け、v0.1 は Mac に残した話](./2026-10-02.md#state-placement)

### 1. ticket の本文に「結果は今回の要件にしない」と書いてあれば、それは目的地の外にある

検証の ticket は、前日に「状態を実行環境の外に置くか」を決めたときに地図へ足したものだ。その決定は「v0.1 は Mac だけで動かし、引き渡しは v0.2 に回す」だった。それでも、Devin の VM で動くかという不安は事実として確かめておきたかったので、検証の task にした。ticket の本文にはこう書いてある。

> 結果は v0.1 の要件にはせず、「[v0.2] 実行環境の間で引き渡せるように、local store と成果物を実行環境の外に置く」（#505）の方向を決める事実として使う

地図の目的地は「v0.1.0 のゲートに必要な決定」だ。結果が v0.1 のどの決定にも効かない ticket は、どれだけ解いても目的地に近づかない。frontier がこの 1 本だけになって初めて、そのことがはっきりした。足したときにも同じ文を書いていたのに、そのときは気づかなかった。検証を「v0.1 の地図のついで」として足していたからだ。

**ticket を足すときは、その答えが目的地のどの決定に効くかを 1 文で言えるか確かめる。** 言えずに「別の決定の材料」と書くことになるなら、その ticket は、別の決定を持つ issue の側に置く。

### 2. 範囲の外に出すときの close は手段にすぎない。下流が「その完了」を待っているなら付け替える

wayfinder（この地図を運用する手順）は、範囲の外と判定した ticket を close するよう定めている。close しておけば、frontier から確実に外れるからだ。私は運営者に「Out of scope にする（推奨）」を示し、選択肢の説明にも「close して map の Out of scope に移す」と書いた。運営者はこれを選んだ。

ところが、作業の前に移し先の v0.2 の issue を読むと、本文に次の節があった。

> ## 着手の条件
>
> - 「Devin の VM で nyaucast を動かす検証」（#457 の子 task）の結果が出ていること

検証はまだ誰も回していない。ここで close すると、v0.2 の issue は「何を待っているか」を失う。人間が後で issue の一覧を見ても、検証は済んだように見える。

close が担っていた目的は「この地図の frontier から外すこと」だけだった。GitHub の sub-issue（親子関係）を付け替えても、地図の子ではなくなるので、同じ目的を果たせる。そこで、推奨として示した手順から次のように変えた。変えたことは、完了の報告で運営者に伝えた。

- 地図から外し、v0.2 の issue の sub-issue にする
- GitHub の issue の依存関係で、v0.2 の issue を「検証の issue に blocked」にする。検証が終わるまで、v0.2 の issue は UI の上でも着手できない状態に見える
- タイトルの先頭に `[v0.2]` を付け、付け替えた理由をコメントに残す
- 地図の Out of scope には、ほかの先送りと同じ形で 1 行を足す

**手順書の「close する」は、何のための close かに戻って読む。** ほかの issue がその完了を前提にしているなら、close せずに、前提にしている側へ移す。

### 3. GitHub の sub-issue は親を 1 つしか持てないので、付け替えは「外す → 付ける」の 2 手で行う

付け替えには、REST API を次の順で呼んだ。`<id>` は issue の番号ではなく、データベースの id（`gh api repos/<owner>/<repo>/issues/<n> --jq .id`）だ。

```sh
gh api --method DELETE repos/<owner>/<repo>/issues/<旧い親>/sub_issue -F sub_issue_id=<id>
gh api --method POST   repos/<owner>/<repo>/issues/<新しい親>/sub_issues -F sub_issue_id=<id>
gh api --method POST   repos/<owner>/<repo>/issues/<待つ側>/dependencies/blocked_by -F issue_id=<id>
```

これらとタイトルの変更、コメントの投稿を、1 つのシェルで `&&` でつないで実行した。ところが、最後のコメントの投稿だけが `unknown flag: --jq` で落ちた。`gh issue comment` には `--jq` が無い。それより前の付け替えは成功していたので、状態は半分だけ書き換わった形になった。末尾に `;` でつないでおいた依存関係の集計の読み出し（`issue_dependencies_summary` の `blocked_by: 1`）は、失敗しても走った。それを見て、付け替えが終わっていることを確かめてから、コメントだけを投げ直した。

**外部の状態を書き換えるコマンドを `&&` でつなぐと、途中で落ちたときに半分だけ書き換わる。** つないだ後に、最終の状態を読む 1 行を `;` で必ず付けておくと、どこまで進んだかがすぐに分かる。

### 4. 問いにできなかった論点は、frontier が空になったときに、分かっている前提ごと ticket にする

地図の「まだ問いにできない論点」には、次の 3 件が残っていた。

- BGM プールの曲の調達元（権利）と、ダッキングの規則。ダッキングは、ナレーションが鳴っている間だけ BGM の音量を下げる処理
- 公開後運用（投稿した後の区間）を v0.1 でどこまでやるか
- dogfood（自分のチャンネルで実際に 1 周させること）の途中で失敗したときの戻し方

frontier が空になるのは、これらを問いにできるだけの決定がそろったという合図だ。3 件とも、今は問いを 1 文で言える。そこで grilling（人間と対話して決める）の ticket に起こした。

本文には、問いと一緒に「分かっている前提」の節を置いた。ADR と用語集を grep して、関係する決定を書き写した。たとえば次の 2 つだ。

- BGM は描画の前に、Chrome を使わない音声の tool でミックスする
- 成果物を削除する tool は置かず、作り直しは `force` だけで行う

次のセッションはこの ticket から始まるので、前提を探し直さずに問いへ入れる。

依存は 1 本だけ張った。「失敗したときの戻し方」を「公開後運用の範囲」に blocked にした。公開後運用で投稿の照合までするなら、照合で見つかった食い違いをどう戻すかも、戻し方の問いに入ってくるからだ。BGM の問いは、ほかの 2 つと独立している。

**論点を ticket に起こすときは、答えの形を変えうる前提だけを依存として張る。** 関連があるというだけでは張らない。依存が多すぎると、frontier が細って並行で進められなくなる。

## 解説動画の BGM の権利とダッキングを、先行実装の実測から決め直した話

解説動画の BGM について、曲をどこから調達するか（権利）と、ナレーションに対して BGM をどう下げるか（ダッキング）を決めたときの学び。解説動画は、日本語の TTS（音声合成）のナレーションに図解と BGM を重ねた動画で、YouTube・Instagram・X の 3 つの SNS に投稿する。BGM は、チャンネルごとに用意したループ再生できるインスト曲の集まり（BGM プール）から選ぶ。ここでは、別のリポジトリ `life` に、同じ型の動画を毎日自動で配送している先行実装がある。そこには、ダッキングと音量について実測した結果が残っていた。

- 決めた ticket: [BGM プールの曲の調達元（権利）とダッキングの規則](https://github.com/daiki-beppu/nyaucast/issues/525)
- 決定の正本: [PR #529](https://github.com/daiki-beppu/nyaucast/pull/529)（ADR-0009 決定 12、ADR-0005 決定 14・15、用語集の「BGM プール」「ダッキング」）

### 1. 音がどこにあるかを既に知っているなら、音を検知して BGM を下げない

`life` は、ナレーションの音量を検知して BGM を圧縮する方式（ffmpeg の `sidechaincompress`）でダッキングしている。最初の設定（ratio 10・release 600ms）では、語りの切れ目ごとに BGM が 16〜21 dB 戻り、BGM が膨らんだり沈んだりした（ポンピング）。ratio を 2 に下げ、release を段落の間より長く取り、沈む量を 6 dB 前後に留めて抑えた。

nyaucast は、段落ごとに TTS で合成した音声を決まった間合いでつなぎ、各段落が何秒から何秒まで鳴るかを「タイミング表」として持っている。図解の演出と字幕の時刻を決めるために、別の決定で作ったものだ。つまり、ナレーションが鳴っている区間は、音を聞かなくても分かっている。

そこで、タイミング表から BGM のゲインの変化（いつ、どれだけ下げ、いつ戻すか）を計算し、BGM に掛け算する方式にした。

- 段落の間合い（1 秒弱）では沈めたまま保ち、しきい値（1.5 秒）を超える無音でだけ戻す。`life` が ratio と release の調整で間接的に得た「切れ目で膨らまない」を、規則として直接書ける
- 純 TS で決定的に動くので、「段落の間で膨らまない」をテストで検査できる
- nyaucast は ffmpeg CLI を使わず、mediabunny と node-av でデコード・エンコードする。検知の方式なら node-av の filter graph に頼ることになるが、計算する方式ならその依存が要らない

**先行実装の方式をそのまま持ち込む前に、その方式が何の情報の欠けを補っていたかを確かめる。** `life` の検知は、ナレーションの位置を知らないことを補う手段だった。位置を知っている nyaucast には、その手段が要らない。

### 2. 権利の申し立てを防ぐ条件は、照合の DB に載っているかどうかで決まる。その条件を、生成した時点のプランとしてスキーマで検証する

最初は、`life` が Suno（AI の音楽生成サービス）の曲を使っていることから、Suno の有料プランで生成する案だけを推奨にしていた。比べた調達元は、サブエージェントに各社の規約とヘルプを一次情報で調べさせて絞った。

| 調達元                         | 3 SNS に出せるか                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| YouTube Audio Library          | 申し立てを受けない約束は YouTube の Content ID についてだけ。YouTube の外で使えるかは公式ヘルプが答えていない                            |
| Pixabay                        | 投稿者が同じ曲を Content ID に登録していて申し立てを受けうることを、公式 FAQ が認めている                                                |
| 自分の音楽チャンネルの曲の流用 | 配信代行で Content ID に登録した曲は、解説動画のほうが申し立てられる。配信代行の許可リストは動画単位で、申し立てを受けた後にしか使えない |
| AI 音楽生成の有料プラン        | 有料プランなら権利が利用者に移る。照合されるのは、誰かが登録した参照ファイルとの一致だけ                                                 |

表から分かるのは、問題が「どこから取るか」ではなく「誰かが照合の DB に登録しているか」だということだ。これで、「プールの曲は配信代行に出さず、どの SNS の照合にも登録しない。音楽チャンネルの曲と兼用しない」という規則を、調達元とは別に立てた。

運営者は、生成元の候補に ElevenLabs Music と Google の Lyria を足した。これを受けて、2 つのサービスについても規約を調べ直した。分かったのは次の 2 点だ。

- ElevenLabs は、無料プランの商用利用について、利用規約（非商用に限る）とモデル別規約の表（商用可）が食い違っている
- Lyria は、Gemini API に無料枠が無い。一方、Gemini アプリで作った曲は、商用で使えるかを明記した公式文書が見つからなかった

食い違いには厳しいほうを採り、ElevenLabs の無料プランと Gemini アプリの曲は入れないことにした。どのサービスでも、権利は曲を生成した時点のプランで決まる。そこで、プールの記録（git で管理する JSON）には、曲ごとに「サービス・生成時のプランか経路・モデル・生成日」を書かせることにした。条件に合わない組み合わせはスキーマが拒否する。無料プランの曲が混じることを、人の注意ではなく構造で防げる。

ただし、申し立てはこれでもゼロにならない。どの生成元も「似た曲を他のユーザーにも生成しうる」と規約に書いている。Meta は、登録者の参照ファイルに加えて、Audible Magic という第三者のデータベースでも照合する。申し立てを受けたときの扱いは、公開後の運用を決める別の ticket に申し送った。

**権利の扱いは、ゼロを保証できる調達元を探すのをやめて、申し立ての仕組み（何と照合されるか）から条件を立てる。** そして、その条件を機械で検証できる形で記録する。

### 3. 既存の決定を新しい種類の素材に広げるときは、その決定の前提が何の素材についてのものだったかを読む

ラウドネス（音の大きさ）は、音楽の collection のために決めた ADR-0005 決定 2 がすでにあった。「-14 LUFS に正規化し、true peak の上限 -1 dBTP は増幅のときだけ効かせる」。理由には「音楽ミックスは通常 -14 LUFS より大きく、減衰方向が支配的」と書いてある。

この前提は、ナレーションでは成り立たない。`life` では、日替わりで声が替わると音量が 3 LU 以上揺れ、ピークが 0 dBTP を超えた。AAC に変換すると、ピークがさらに上振れした。`life` は対策として、ナレーションを目標に寄せてから BGM を敷き、常に -2 dBTP に抑える手順をとっている。nyaucast の解説動画もこの手順にそろえた。決定 2 は collection に限ると改訂した。

決定 2 は、「全部の音声に効く規則」として読めてしまう書き方だった。理由の節まで読んで、初めて音楽ミックスの前提が見えた。

**既存の決定を別の種類の素材に当てはめるときは、決定の本文だけでなく、理由の節に書かれた前提を読む。** 前提が崩れるなら、黙って流用せず、適用範囲を改訂として書く。

### 4. 欠けたまま続けるか止めるかは、欠けたものが誰の目にも触れずに先へ進むかで決める

`life` は、BGM の素材が無い・ループ素材が作れないときに、BGM なしで配送を続ける。無人で毎日配送するので、1 本のために止めるより、BGM なしで届けるほうがよいからだ。

nyaucast では、チャンネル設定で BGM が有効なのに使えないとき、型付きの失敗にして区間を止める。BGM を使わないチャンネルは、設定で無効にして明示する。nyaucast は、公開の前に人間がゲートで承認する。黙って BGM が欠けた動画をゲートに回すと、人間は欠けた理由を知らされないまま判断することになる。区間で止まれば、何が欠けたかがエラーとして残る。

同じ理由で、チャンネル設定で上書きできる値は「BGM の音量（ナレーション比）」と「下げ幅」の 2 つに絞った。立ち上がり・戻り・しきい値はコードの定数にした。チャンネルの雰囲気で変えたくなるのは BGM の大きさだけで、時間の値まで設定に出しても、検証する組み合わせが増えるだけだ。

**縮退して続けるのが正しいのは、縮退したことを後から誰も判断しない場合に限る。** 人間が判断する工程が後ろにあるなら、縮退を黙らせずに止める。

## 公開後運用の範囲を、SNS に照会して見えるものと見えないものから決めた話

解説動画の制作フロー（lifecycle）の最後の区間「公開後運用」で、v0.1 に何をするかを決めたときの学び。v0.1.0 のリリースゲートは、解説動画を 1 本作り、YouTube・Instagram・X の 3 つの SNS へ公開するまでを nyaucast だけで実走させることだ。投稿の状態は、「投稿」「投稿の試行」「取り消し」という追記だけの事実（append-only の行）から計算で導出し、状態の列は持たない。YouTube は `publishAt` で SNS 側に予約できる。Instagram と X には予約が無いので、予定時刻に人間が CLI を叩いて即時に投稿する。結論は、v0.1 の公開後運用を「YouTube の予約が実際に公開されたかの確認」だけにし、権利の申し立ては検知しない、というものになった。

- 決めた ticket: [公開後運用の v0.1 での範囲](https://github.com/daiki-beppu/nyaucast/issues/526)
- 決定の正本: [PR #533](https://github.com/daiki-beppu/nyaucast/pull/533)（ADR-0009 決定 13 の追加と決定 9 の改訂、用語集の「公開の確認」「確認待ち」「解説動画 lifecycle」）
- 範囲の外にして v0.2 へ回した issue: [公開済みの投稿が受けた権利の申し立てを検知する](https://github.com/daiki-beppu/nyaucast/issues/531)、[公開後に投稿の中身を変える運用（固定コメント・概要欄・相互リンク）](https://github.com/daiki-beppu/nyaucast/issues/532)

### 1. 外部のサービスが後で起こす状態の変化は、API の成功の応答では確定させない

すでに決まっていた状態の一覧には、「SNS 側で予約済み」と「公開済み」の両方があった。しかし、YouTube の投稿がその間をどう移るかは、どこにも書かれていなかった。Instagram と X は、API が成功を返した時点で投稿が公開されている。一方、YouTube の成功の応答が意味するのは「private の動画を上げ、予約した」までで、公開は予定時刻に YouTube の側で起きる。nyaucast からは、その瞬間が見えない。

最も簡単なのは、予定時刻が過ぎたら公開済みとみなす導出だ。これを採らなかったのは、公開されない経路が分かっていたからだ。以前の調査で、Google の監査を通っていない API プロジェクトから上げた動画は、強制的に private になると分かっていた。処理に失敗した動画も公開されない。時刻だけで導出すると、どちらも「公開済み」と表示される。

そこで、時刻が来た投稿を実行する CLI が、同じ実行の中で `videos.list` を読むことにした。`privacyStatus` が `public` なら、「公開の確認」という 4 種目の事実を積む。

ただ、調べ直してみると、予定時刻を過ぎると `privacyStatus` が `public` に変わることは、公式の文書に書かれていなかった。文書が書いているのは、「`publishAt` を過去の時刻にすると、private を public に変えたのと同じ効果になる」ということだけだ。この照合は、予約が過ぎれば public になるという、確かめていない前提の上に立っていたことになる。前提は消せないので、YouTube の投稿を実装する ticket の受け入れ条件に「実際の動画で確かめる」と書き込んだ。

**状態の一覧に「予約済み」と「完了」が並んでいたら、その間を誰が何を根拠に移すかを確かめる。** 外部が移すなら、読みに行く手段を持つ。読む値の意味が文書で保証されていなければ、実装の受け入れ条件に実地の確認を入れる。

### 2. 一部の SNS しか検知できないなら、検知しないほうが誤りが少ない

BGM の権利を決めた前の ticket から、「申し立てを受けたときの扱い」が申し送られていた。申し立てとは、YouTube の Content ID の claim、Meta の BLOCK / MUTE、X の著作権による非表示のことだ。API で何が見えるかを、サブエージェントに公式の文書で調べさせた。

| SNS       | 自分の投稿への申し立てを API で取れるか                                                                                                                         |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| YouTube   | 取れない。Content ID API はパートナー専用。`rejectionReason=claim` は upload の拒否の値で、公開後の申し立ては表さない。`regionRestriction` は国だけで理由が無い |
| Instagram | `copyright_check_information` に一致の有無と措置が出る。ただし Instagram Login 方式で返るかは未確認                                                             |
| X         | 投稿の `withheld.copyright` で分かる                                                                                                                            |

Instagram と X だけでも検知する案はあった。採らなかった理由は 2 つある。

- 3 つの SNS のうち、主戦場の YouTube が見えない。一部だけ検知すると、画面に何も出ていないことが「申し立てが無い」のか「見ていない」のかを区別できない
- 時期が合わない。申し立ては公開の数日後に届くことがある。一方、1 の照合は公開を確かめた時点で終わる。申し立てを拾うには、公開後も繰り返し照会し続ける仕組みが要る。v0.1 は定期実行を持たないので、作れない

v0.1 では、人間が各 SNS の通知で気づき、各 SNS の画面で対応する。異議を出すときの根拠（BGM プールの曲の出所と許諾）と手順は、agent が読む知識パッケージ（codec）に書く。

**監視を部分的にしか作れないときは、「検知していないこと」と「何も起きていないこと」を取り違えさせない設計を先に考える。** それができないなら、作らずに人間の運用に残し、残したことを明記する。

### 3. 「起きなかった」は事実として積まず、時刻から導出する

照合して public でなかったときの扱いも決めた。「未公開だった」という結果を事実として積む案もあったが、採らなかった。予定時刻から許容時間（既定 60 分）を過ぎても公開の確認が無ければ、その時刻から「確認待ち」（人間の判断を待つ状態）を導出する。`uploadStatus` が `rejected` か `failed` のときだけは、時間を待たずに確認待ちにする。

否定の結果を積むと、照合を何度走らせても行が増える。また、「最後の照合では未公開だった」という行が、実体（今は公開されているかもしれない）とずれる余地が生まれる。このプロジェクトは別の決定で、「行と実体のずれ」を増やさないことを原則にしている。肯定の事実だけを積み、否定は時刻で表せば、照合は何度でも同じ結果を返す。

ここで、既存の ADR と矛盾していないかを確かめた。投稿の状態の決定は、却下した案に「結果の無い試行を、SNS に照会して自動で判定する」を挙げていたからだ。読み直すと、却下の理由は 2 つだった。照会の結果で投稿を再実行すると二重投稿になりうること、そして SNS ごとに照会の手段がまちまちなことだ。今回の照合は読むだけで何も投稿せず、対象も YouTube の予約だけなので、どちらの理由にも当たらない。この違いは、ADR の却下した案の節に書き足した。

**過去に却下した案と似た案を採るときは、却下の結論ではなく理由に照らす。** 理由が当たらないなら採ってよいが、その違いを同じ記録に書いておく。後から読む人には、2 つの決定が矛盾して見えるからだ。

### 4. 区間の終点を状態の集合で定義したら、その状態から戻る経路が無いかを確かめる

「lifecycle が 1 周した」と言える終点は、「その動画のすべての投稿が、公開済み・取り消し済み・失敗のいずれかになったとき」とした。終点の事実は積まず、投稿の状態から導出する。公開ゲートの承認を終点にする案は、承認した後で投稿が 1 本も出なくても完走したことになるので採らなかった。

推奨を出した時点では、3 つを「終端の状態」と呼んでいた。決定をまとめ直しているときに、失敗が終端ではないことに気づいた。人間は「今すぐ実行」の CLI で、失敗した投稿をもう一度出せる。つまり失敗は、終点に数えられる状態でありながら、そこから戻る経路も持っている。終わったことを事実として積んでいたら、「終わった」と書いた後で投稿が出直す、という矛盾が残るところだった。導出なので、失敗した投稿を出し直せば lifecycle は自然に再び開く。この振る舞いは ADR に明記した。権利の申し立ては投稿の状態に現れないので、受けても lifecycle は戻らない。これも書いた。

**終わりを表す集合に入れた状態ごとに、その状態から出る操作が無いかを確かめる。** 出る操作があるなら、終わりを事実として固定せず、導出にしておく。

## 失敗したときの戻し方を、出力を読むのが agent だという前提で決め直した話

v0.1.0 の実装計画の地図で、最後に残った ticket「dogfood の実走で区間が失敗したときの戻し方」を決めたときの学び。dogfood は、自分の解説動画チャンネルで制作から 3 つの SNS への公開までを nyaucast だけで 1 周させる受け入れ検証のことだ。nyaucast では、AI エージェント（agent）が知識パッケージ（codec）を読み、MCP tool を順に呼んで制作の区間（plan / produce / publish）を歩く。区間の間には、人間が CLI を叩いて越えるゲートがある。既に決まっていたのは、再開は頭から歩き直して冪等な tool がすぐ返す形で行うこと、作り直しは `force` だけで行うことだった。ここに「何を足せば失敗から戻れるか」を決めた。

- 決めた ticket: [dogfood 実走で区間が失敗したときの戻し方](https://github.com/daiki-beppu/nyaucast/issues/527)
- 決定の正本: [PR #535](https://github.com/daiki-beppu/nyaucast/pull/535)（ADR-0009 決定 14 の追加、決定 4・9 と ADR-0007 の Consequences の改訂、用語集の「確認待ち」「企画ゲート」）

### 1. 戻し方の仕組みを足す前に、既存の部品で失敗の場面を 1 つずつ書いてみる

最初にしたのは、新しい仕組みを考えることではなかった。区間ごとに落ちうる場面を並べ、既にある部品（頭から歩き直す・`force`・やめる・投稿単位の取り消しなどの CLI）で書けるかを 1 つずつ試した。

- 音声合成が途中で落ちた: 段落ごとのキャッシュがあるので、歩き直せば払い直しなく続きから作れる
- サムネイルの画像を 3 枚作る途中で落ちた: 1 回で 3 枚作る tool だと、歩き直したときに 3 枚分を払い直すかが決まっていなかった。「課金される呼び出しは 1 回ごとに成果物と事実を書く」を規約にして埋めた
- Instagram のメディアコンテナ、X の `media_id`、一時置き場の R2 のオブジェクトが残った: 前の 2 つは 24 時間、R2 は 7 日のライフサイクルルールで消えるので、片づけない
- YouTube への upload が成功した直後、結果を書く前に落ちた: SNS 側に private の動画が残るのに、手元にはリモートの ID が無い。取り消しの CLI はこの動画を消せない

最後の場面だけは、既存の部品で書けなかった。nyaucast が自分のチャンネルの最近の upload を探して消す案は、「それらしい動画」を推測で選ぶことになる。別の動画を消すと取り返しがつかないので採らず、取り消しの CLI が「SNS 側に残っているかもしれない」と知らせ、人間が YouTube Studio で確かめて消すことにした。

結果として、resume や rollback の API、「前のゲートに戻す」コマンドは足さなかった。足したのは、上の規約のような小さな約束だけだ。

**戻し方を設計するときは、仕組みから考えず、失敗の場面を列挙して既存の部品で書けるかを試す。** 書けない場面だけが、足すべきものの候補になる。

### 2. 「次に取る行動」を出力に書くかどうかは、その出力を誰が読むかで決まる

既存の ADR には、「利用者は非エンジニアなので、CLI は次に取る行動を日本語で示す」という責務が書かれていた。私はこれを前提に、「人間向けの手順は CLI の表示に、agent 向けの手順は codec に置く」と提案した。

これに対して、運営者からこう返ってきた。

> 5はAIエージェントが使う前提なので考え直す必要があるかな

CLI と read model（local store の読み口）の出力を読むのは、実際には agent だ。agent はその結果を人間に伝える。人間が CLI の出力を直接読んで判断するのは、公開ゲートの対話の 1 か所しか残っていなかった。読み手が agent なら、CLI の文章と codec に同じ手順を書くことになり、知識が二重になる。

そこで、CLI と tool は失敗を安定した識別子（Effect の型付きの失敗のタグ）と事実だけで返し、「識別子 → 手順」の対応表を codec にだけ置くことにした。確認待ち（自動では投稿せず人間の判断を待つ状態）も、read model が理由を 5 種類に分けて返すが、次に叩くコマンドは返さない。ADR-0007 の Consequences にあった CLI の責務は、この決定で書き換えた。

代わりに生まれた制約が 1 つある。失敗のタグと確認待ちの理由の名前は、codec が参照する契約になる。名前を変えるときは codec を同じ差分で直す、と ADR に書いた。

**人間向けの文章をどこに置くかは、ペルソナの設定ではなく、その出力を実際に読む主体で決める。** 読むのが agent なら、出力は機械が分岐できる識別子にし、手順は agent の知識の側に 1 か所だけ置く。

### 3. 誰がコマンドを叩いてよいかは、そのコマンドの中身が「判断」か「実行」かで分ける

agent が CLI を使う前提にすると、それまで「人間だけが叩く」としていた投稿まわりの 4 つの CLI を、誰が叩くかも決め直すことになった。

| CLI                  | 中身                                               | 叩く主体   |
| -------------------- | -------------------------------------------------- | ---------- |
| 時刻が来た投稿の実行 | 公開ゲートで人間が承認したものを、決めた時刻に流す | agent も可 |
| 取り消し             | 配信を止める判断                                   | 人間だけ   |
| 今すぐ実行           | 許容時間を超えても出す判断                         | 人間だけ   |
| 公開済みの記録       | SNS で自分の目で確かめたという申告                 | 人間だけ   |

時刻が来た投稿の実行は、遅れ・鮮度・投稿先のアカウントの照合をすべて tool の事前条件が持っているので、誰が叩いても安全側に倒れる。残りの 3 つは、中身が人間の判断そのものだ。agent が代行すれば、確認待ちという「人間を待つ状態」を作った意味がなくなる。agent は Bash から CLI を叩けるので物理的には止められないが、codec に「この 3 つは叩かずにコマンドを人間に渡す」と書いた。

**「機械に任せてよい操作」の線は、事前条件で安全が保証される実行と、人間の判断を記録する操作の間に引く。** 後で定期実行を足すときも、同じ線で機械に任せる範囲が決まる。

## 地図の決定を仕様と実装 issue に起こし、途中で DB の置き場を一次情報で比べ直した話

地図が完成したので、決定の群れを 1 本の仕様にまとめ、実装の単位に分けて起票したときの学び。nyaucast の実装は takt（AI エージェントに issue を渡して実装させるツール）に任せるので、各 issue は地図を読まなくても着手できる内容にする必要がある。仕様をまとめる途中で、運営者から「Turso が Supabase に買収された。このまま選定して大丈夫か」という確認が入り、local store の置き場の比較を一次情報で取り直した。

- 仕様（親 issue）: [[spec] 解説動画 lifecycle と 3 SNS への配信（v0.1.0）](https://github.com/daiki-beppu/nyaucast/issues/536)
- 実装 issue: [全面 Effect 4.0 への一括移行](https://github.com/daiki-beppu/nyaucast/issues/538) ほか 21 本（親の sub-issue）
- 申し送り: [[v0.2] 実行環境の間で引き渡せるように、local store と成果物を実行環境の外に置く](https://github.com/daiki-beppu/nyaucast/issues/505)

### 1. 仕様を書く前に、決定と今のコードの距離を測る

地図の決定は、ADR と用語集にすべて書かれている。それだけを読んで仕様を書くこともできた。それでも先にサブエージェントにコードの現状を調べさせると、大きな食い違いが 1 つ見つかった。前日に「コードを全面 Effect 4.0 で書く」と決めていたのに、`src/` はまだ zod・drizzle・公式の MCP SDK・素の throw のままだった。

ADR の Consequences には「v0.1 の実装の最初にまとめて移し、zod と throw が混在する期間を作らない」とある。そのため、移行を 1 本目の issue にし、残りの 20 本すべてをこれに blocked させた。決定だけを見て分けていたら、各 issue が「Effect で書く」前提で始まり、最初に着手した 1 本が移行を抱え込むところだった。

**決定の記録だけから実装の分割を作らない。** 決定と今のコードの距離を測り、その距離自体を最初の issue にする。

### 2. テストの継ぎ目は「本番で使うものと同じか」で選び、CI に既にあるものに引きずられない

仕様にはテストの継ぎ目（どこで差し替えて試すか）を書いた。MCP tool を、テスト用の Layer（一時ディレクトリの DB・仮想の時計・偽装した HTTP クライアント）で呼ぶのを主にした。外部の SNS には CI で当てず、実機で確かめる項目は各 issue の受け入れ条件に回した。

動画の描画のテストでは、HTML を Chrome で 1 フレームずつ撮る。ここで運営者から「GitHub Actions には Chrome が最初から入っているのでは」と聞かれた。ランナーに Chrome（stable）が入っているのは事実だ。ただ、nyaucast は決定論を守るために、版を pin した chrome-headless-shell を `@puppeteer/browsers` でダウンロードすると決めている。ランナーの Chrome はイメージの更新で版が変わるので、それで試すと、本番の Mac が使うのとは別の Chrome を試すことになる。pin した版を鍵に `actions/cache` で保存すれば、ダウンロードが走るのは pin を上げたときだけで済む。

続けて「`@puppeteer/browsers` を外すとどうなるか」「Playwright ではないのか」とも聞かれた。代わりの手段を並べると、版を pin して Mac と CI で同じ経路で取ってこられるのは、Chrome for Testing の配布元を直接叩くか、`@puppeteer/browsers` を使うかの 2 つだけだった。Playwright で入れると、Chrome の版が Playwright の版に縛られる。

**CI に既に入っている道具を使うかどうかは、本番と同じものを試せるかで決める。** 手間を省きたいなら、道具を替えるより、本番と同じものを cache する。

### 3. 記憶から書いた比較は、一次情報で裏を取ると決め手が変わる

Turso は、nyaucast の local store が使う libSQL（SQLite のフォーク）を作った会社だ。買収の話を受けて、私は最初、記憶だけで答えた。v0.1 は Turso のクラウドを使わず、Mac の上の libSQL のファイルを開くだけなので影響しない、という答えだ。そのうえで「drizzle をやめたなら D1（Cloudflare の SQLite）でいいのでは」という問いに、D1 の前に API 用の Worker を立てる構成のメリットとデメリットを並べた。運営者の返事は「リサーチしてから再度比較を頂戴」だった。

サブエージェントに公式の文書とライブラリのソースを読ませると、比較の中身が 3 か所変わった。

| 項目                        | 記憶から書いた比較         | 一次情報で確かめた結果                                                                                                  |
| --------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| D1 のトランザクション       | 往復をまたげないと推測     | 裏が取れた。原子的なのは 1 回の `batch()` だけ                                                                          |
| D1 での自動マイグレーション | 「道が変わる」とだけ書いた | `@effect/sql-d1` はトランザクションを呼ぶと die する。Migrator は全体をトランザクションで包むので、そのままでは動かない |
| Turso のリモートの制約      | 書いていなかった           | トランザクションは 5 秒以内に終える必要があり、Migrator も全体がこの制限にかかる                                        |

買収の発表についても、両社とも「既存のユーザーには何も変わらない」と書いている一方で、libSQL という語は本文に一度も出てこないと分かった。libSQL の README は「保守は続けるが、新機能は Rust で書き直した Turso Database で作る」としている。

決め手は、ドライバの有無ではなくトランザクションの形だった。nyaucast の安全装置（冪等の判定、ゲートの承認と投稿を 1 トランザクションで書くこと）は、どれも「読んで事前条件を確かめてから書く」形に乗っている。往復をまたぐトランザクションが無い DB では、この判定を DB の手前の Worker に移すしかなく、業務ロジックが 2 か所に分かれる。v0.1 の選定は変えず、外部化の issue に「推奨は Turso のリモート。ただし `file:` に戻す逃げ道の手順と、5 秒の制限の実測を差分に含める」と申し送った。

**選定の比較を出すときは、記憶から書いた行と、一次情報で確かめた行を分ける。** 確かめると、推測で書いた行の裏が取れるだけでなく、書いていなかった制約が見つかる。

### 4. issue を一括で起票するスクリプトでは、本文の相互参照を起票の後で実番号に置き換える

21 本の issue は、Python のスクリプトで本文を組み立て、`gh issue create` で順に起票した。ここで 2 つ失敗した。

1 つ目は、本文の中で他の ticket を「#4 で作った基盤」のように、分割案の通し番号で参照していたことだ。GitHub はこれをリポジトリの #4（まったく別の古い PR）へのリンクとして表示する。起票した後で全 issue の本文を読み直し、21 以下の番号だけを実番号に置き換えた。`#505` のような実在の issue への参照は残す必要があるので、置き換えは「通し番号の範囲に入る番号だけ」に絞った。

2 つ目は、sub-issue と blocking を張るループで、依存の表から 1 番の項目が抜けていて途中で止まったことだ。1 本目の sub-issue だけが張られた状態で止まったので、再実行するときに 1 本目の sub-issue の追加を飛ばした。張った結果は親から sub-issue の一覧を取り直し、各 issue の開いている blocker の数が分割案と一致することで確かめた。

**一括の起票は、本文の作成・相互参照の解決・関係の配線の 3 段に分け、各段を再実行しても二重にならない形にしておく。** 番号は起票するまで決まらないので、本文の中の参照は仮の記法で書き、最後にまとめて解決する。

## 既存のコードを Effect 4.0 へ一括で移す実装を takt に任せ、検証の手薄な所を確かめた話

起票した 21 本のうち最初の 1 本、「全面 Effect 4.0 への一括移行」を takt（AI エージェントに issue を渡して実装させるツール）で実装し、マージしたときの学び。この issue は、既存のコード（zod の schema、drizzle の DB アクセス、公式の MCP SDK、素の `throw`）を振る舞いを変えずに Effect 4.0 へ移す。DB のマイグレーションは drizzle の管理表から `@effect/sql-libsql` の Migrator へ引き継ぎ、ツールチェーン（`vite-plus` 1.0、`@effect/vitest`、`@effect/tsgo` の診断）も同じ差分で上げる。混在する期間を作らないため、段階に分けない。takt の builtin の workflow `default` は 49 分 43 秒で終わり、51 ファイル（+4665 / −4345）の PR になった。

- 実装した issue: [全面 Effect 4.0 への一括移行](https://github.com/daiki-beppu/nyaucast/issues/538)
- PR: [#560](https://github.com/daiki-beppu/nyaucast/pull/560)
- スコープの外として起票した issue: [CLI のテストを effect/cli の in-process 実行に移す](https://github.com/daiki-beppu/nyaucast/issues/561)、[mutation 監査（Stryker）が vite-plus 1.0 と @effect/vitest で動くか確かめる](https://github.com/daiki-beppu/nyaucast/issues/562)

| 工程（`default`）                    | 所要       |
| ------------------------------------ | ---------- |
| plan（計画）                         | 約 10 分   |
| write_tests（先にテストを書く）      | 約 11 分   |
| implement（実装）                    | 約 14 分   |
| review（6 観点の並列レビューと裁定） | 約 5 分    |
| PR の CI（`pnpm run check`）         | 1 分 10 秒 |

### 1. 新しい版の書き方を守らせるには、古い API を「わざと書いて落ちる」ことまでゲートの検証に含める

takt が走っている途中で、運営者から「4.0 の書き方になってるかは検証させるようになってる？」と聞かれた。Effect 4.0 は v3 と API が大きく違い、AI エージェントは学習データの多い v3 の書き方で書きがちだ。型検査だけでは防げない。v3 から名前だけ残った API や、別の型で通ってしまう書き方があるからだ。

issue の受け入れ条件には「`check` に `@effect/tsgo` の診断（v3 の API を見つける `outdatedApi` を含む）が入っている」と書いてあった。ただ、私はこの時点で 2 つの穴を心配していた。1 つは、診断を入れるのがこの差分自身なので、ゲートが「ある」ことと「効く」ことが別だという点。もう 1 つは、builtin の workflow のレビューには Effect の知識が無く、issue 本文と `node_modules/effect/AGENTS.md` に頼るしかないという点だ。

報告書を読むと、1 つ目は takt の計画の段階で埋まっていた。テストの計画が「ゲートの存在は静的に検査できるが、診断の挙動は `effect` を入れた後でないと確かめられない」と書き分け、実装の工程で次のように確かめていた。

1. `outdatedApi` を warning ではなく error に設定する（warning のままでは `check` が落ちない）
2. 一時ファイルに v3 の `Effect.catchAll` を書いて `pnpm run effect:check` を実行し、終了コード 1 を確認する
3. 一時ファイルを消して、終了コード 0 を確認する

加えて、`src/` に `throw`・zod・drizzle・`fetch`・`process.argv`・`Date.now()` が残っていないことを、grep 相当の静的検査としてテストに入れていた。マージの前に私も grep で探し、残っていた `async` の 2 か所が、外部ライブラリの Promise を Effect に包む境界だけであることを確かめた。

**「ゲートを入れる」を受け入れ条件にするときは、そのゲートが違反を実際に落とすことの確認まで条件に含める。** 違反をわざと 1 つ入れて落ち、外して通る、の 2 回の実行が最小の証拠になる。

### 2. 定型の多いライブラリに移ると、コピペ検出の閾値が定型そのものを重複として拾う

実装の工程は、重複コードの検出（fallow、`semantic` モード）の閾値 `duplicates.minTokens` を 10 から 50（fallow の既定値）に上げていた。検査ゲートを緩める変更なので、マージの前に根拠を確かめた。

Effect では、失敗の型の宣言（`Schema.TaggedError`）や `Effect.gen` の書き出しが、どのファイルでもほぼ同じ形になる。10 トークンのままでは、この定型が重複と判定され、16 ファイルの 75% が重複扱いになった。1 グループでも重複があればゲートは落ちる。実装の工程は閾値を変えて結果を比べていた。

| `minTokens` | 重複と判定されたもの |
| ----------- | -------------------- |
| 30 以下     | 多数                 |
| 40          | 3 ファイル（4.4%）   |
| 45          | 0 件                 |
| 50          | 0 件                 |

45 まで絞る余地はあったが、既定値の 50 のままマージした。

**ライブラリを移したときに検出のゲートが落ちたら、まず「何が重複と判定されたか」を見る。** 新しいライブラリの定型が拾われているなら、閾値の調整は正当だ。そのときは候補の値を並べた比較を決定の記録に残し、レビューする人が緩めすぎていないかを判断できるようにする。

### 3. 決定どうしが衝突して見えたら、それぞれの決定が何を対象にしているかで裁く

6 観点の並列レビューのうち、テストのレビューだけが差し戻した。指摘は、ゲートを越える CLI の成功時の出力「…を実行してください」が、同じ日に決めた「CLI と tool は次に取る行動の文章を持たない」という決定（この日の [失敗したときの戻し方の話](#recovery) の 2 節）に反する、というものだった。

一方、issue の受け入れ条件は「既存の CLI が移行前と同じ入出力で動く」ことを求めており、別の決定も「collection の CLI は変えない」としている。文字どおりに読むと、2 つの決定が衝突する。

takt の裁定の工程は、「次に取る行動を持たない」という決定が定めているのは**失敗の返し方**であり、成功時の出力には及ばないと読んで、指摘を誤検知として退けた。この読みは決定の本文と合っている。ただ、レビューの工程が誤読したということは、決定の本文が適用範囲を明示していなかったということでもある。

**決定を書くときは、その決定が何を対象にするか（失敗の出力か、出力全体か）を本文に書く。** 範囲が書かれていない決定は、後から別の決定と衝突して見え、レビューのたびに同じ裁きを繰り返すことになる。

もう 1 つの指摘（CLI のテストが子プロセスを起動しており、仕様が定めた in-process の実行になっていない）は、受け入れ条件に含まれないとして「スコープの外、後続の issue で扱う」と裁かれた。ただし takt は issue を起票しない。「後続で扱う」という文言は、報告書に残るだけで消えてしまう。マージの前に、計画の段階で「未確認」とされていた mutation 監査と合わせて 2 本を起票した。

**AI のレビューが「スコープの外」と裁いた指摘は、人間が起票するまでどこにも残らない。** マージの前の確認に、報告書の「スコープの外」と「未確認範囲」を読んで issue にする手順を入れる。

### 4. 起動が失敗に見えても、起動し直す前に、プロセスと起動の副作用を確かめる

takt は、Orca（ターミナルを並べる作業環境）の別の pane で走らせて、進み具合を見えるようにする手順にしていた。ところが pane の分割コマンドが「Timed out waiting for split pane handle」で失敗し、数秒後にプロセスを探しても takt は見つからなかった。そこで、ターミナルから切り離して takt を起動し直した。

数分後、運営者から「動いてなさそうよ」と言われた。調べると、次のことが起きていた。

1. pane の分割は失敗扱いになったが、実際には遅れて開き、takt を起動していた
2. 先に走り出していた切り離した側の takt が、作業用のブランチを作っていた
3. 遅れて開いた pane の takt は「branch already exists」で即座に失敗した
4. 失敗した側は、同じログファイルを `tee` で上書きし、終了の印のファイルも作った

本体は正常に走っていたのに、ログの上では「ブランチ作成で失敗して終わった」ように見えていた。終了の印を待っていた見張りも、そこで止まっていた。

見張りは、終了の印のファイルではなく、takt のプロセス ID が生きているかで見るように張り直した。進み具合は、pipeline の実行ではタスクの一覧（`tasks.yaml`）に載らないので、状態を返すスクリプトは「該当タスクなし」を返す。代わりに、run のログ（`.takt/runs/<run>/logs/*.jsonl`）から `step_start` と `step_complete` の記録を拾って工程を追った。

**起動が失敗に見えたときは、再起動の前に、プロセスの有無だけでなく、起動が残す副作用（ブランチ、ログ、終了の印）も確かめる。** 再起動するなら、ログと終了の印のファイル名を起動ごとに変えて、2 つの起動が同じファイルを奪い合わないようにする。

### 5. takt の報告書は、マージする前に作業ツリーの外へ写しておく

開発ログを書くために、takt の worktree に残した報告書（計画、テストの計画、実装の決定のログ、各レビュー、裁定）を読みに戻ると、worktree ごと無くなっていた。PR は `gh pr merge --squash --delete-branch` でマージしていた。その後、worktree のディレクトリも、ローカルのブランチも、`git worktree list` の登録も消えていた。原因は確かめていない。

このエントリは、takt の実行中とマージの前にこのセッションで読んでいた報告書の抜粋から書いた。読んでいなかった部分（各工程の全文、ログの詳細）は失われた。

**takt の報告書を後で読むつもりなら、マージする前に作業ツリーの外へ写しておく。** 報告書は、作業ツリーの中の gitignore された場所にあるので、作業ツリーを消す操作に巻き込まれる。
