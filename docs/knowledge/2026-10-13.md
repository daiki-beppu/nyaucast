## Cloudflare 環境づくりの 9 件を TAKT で回し、差し戻しの無い run の中から学びを拾った話

`nyaucast cloudflare`（利用者の Cloudflare アカウントに、Instagram へ動画を渡すための R2 の bucket とアクセスキーを作るコマンド）の実装 9 件を、TAKT で回したときの学び。R2 は Cloudflare の S3 互換のファイル置き場。TAKT は、issue を受け取って計画（plan）→ テストを先に書く（write_tests）→ 実装（implement）→ 5 観点の並列レビュー → 裁定 → 最終確認（final-gate）の段を自動で進め、PR まで作る開発ツールだ。仕様は [#687](https://github.com/daiki-beppu/nyaucast/issues/687)、実装は [#697](https://github.com/daiki-beppu/nyaucast/issues/697)〜[#705](https://github.com/daiki-beppu/nyaucast/issues/705)、PR は [#765](https://github.com/daiki-beppu/nyaucast/pull/765)〜[#773](https://github.com/daiki-beppu/nyaucast/pull/773)、設計の正本は [ADR-0012](../adr/0012-cloudflare-environment.md)。

止まった run の再開、監視の作り方、固定版の `cf` と仕様の衝突、#702 と #704 の競合の解き方は、[翌日のエントリ](./2026-10-14.md#takt-evidence-led-recovery)に書いた。ここでは、各 run の記録（段ごとの報告・レビュー・裁定）を読み直して、その外に出ていなかったことを拾う。

9 件の run は次のとおりだった。時刻は UTC で、run の開始から final-gate の終了まで。

レビューの差し戻しは #702 の 1 件だけで、CI もすべて 1 回で通った。それでも、段の中では実装者の自己修正がほぼ毎回起き、レビューは「指摘にしない懸念」を表に残していた。学びの多くはそこにあった。

### 1. 同じファイルを触る issue の列は、前の PR がマージされてから次の run を始める

9 件は `src/cloudflare/provision.ts`・`cli.ts`・`test/cloudflare-cli.test.ts` をほぼ全員が触る。それでも、前の PR のマージを待たずに次の run を始めた場面が 2 回あった。

- #701 の run は 09:01 に #698 の上で始まり、その 2 分後に #699 の PR がマージされた。PR #768 には、手で書いた統合のコミット（「main のアカウント検証と R2 の利用可否確認を統合」、テスト +68 行）が要った
- #702 の run は #699 の上で始まり、実行中の 10:23 に #701 がマージされた。PR #769 には、9 ファイル・テスト +225 行の統合コミットが要った。#704 との競合は、これとは別にもう 1 回あった

TAKT の run は、始まった時点の main で計画を立て、テストを書き、5 観点のレビューを通す。後から統合コミットを手で足すと、その部分だけはレビューを通っていない。統合が CI を 1 回で通ったのは結果であって、保証ではなかった。

**依存の順に並べた issue の列は、依存関係が無くても同じ行を書き換えるなら、前の PR のマージを待って次の run を始める。** 並列で始めて時間を稼ぐなら、統合のコミットをレビューの外で書くことになる、と見積もりに入れておく。

### 2. 同じ ADR を読む issue は、計画の段が隣の issue の範囲まで先取りする

#698（アカウントの選択）の計画は、ADR-0012 の決定 10 を読んで、issue に書かれていない要件を 2 つ自分で足した。「再実行のときは記録したアカウント ID を使う」と「それと違う `--account` は拒否する」だ。これはそっくり次の #699 の範囲だった。AI 由来の誤りを見るレビュー（ai-antipattern）はスコープ外ではないかを確かめたが、「ADR に書いてあるので範囲内」と判断して通した。

その結果、#699 の計画は要件 5 つのうち 3 つを「不要」とし、残った仕事は順番の修正とテストだけになった。それでも価値はあった。#698 の実装は、アカウント一覧を取って空かどうかを確かめた**後に**記録を読んでいたので、記録との食い違いが「アカウントが無い」や一覧の取得失敗に隠れることがあった。#699 で、記録を先に読んで食い違いを先に拒否する順に直し、一覧を呼ばないことまでテストで確かめた。

**ADR の決定を複数の issue に分けたら、どの決定をどの issue で実装するかを issue の本文に書く。** 書かなければ、計画の段は ADR を正書として読み、手前の issue で全部を実装しようとする。先取りが起きたら、後ろの issue は「残りは何か」を数え直してから回す。

### 3. 受け入れ条件に無い「条件付きの確認」を計画に入れると、届かない確認のために段が回る

#702 は 13 段かかった。差し戻しの中身を見ると、コードの問題で回ったのはレビューの 1 件だけで、残りは確認の段取りの問題だった。

1. 計画が「実行環境があれば mutation の監査をする」という条件付きの確認を入れた。実装の段の判定は「その環境が使えるかが不明」として、再実装の段に回した
2. 再実装の段（11:00〜11:18）は、本番のコードを 1 行も変えなかった。やったのは事前確認で、`op whoami` は終了コード 1、`cf` の専用プロファイルは未認証だった。判定は「実連携の確認は認証の前提が成り立たず、mutation の監査は正書の休止の指示で未完了」として、計画のやり直しに回した
3. 計画のやり直し（11:18〜11:24）が、明示の受け入れ条件はすでに満たしていて、実連携の確認と mutation の監査は要らないと判断し、レビューに進めた

この往復で約 25 分を使った。issue の受け入れ条件は、実サービスでの確認を最初から [#706](https://github.com/daiki-beppu/nyaucast/issues/706)（人間の実機確認）へ回していた。条件付きの確認を足したのは、計画の段だった。

**計画には、受け入れ条件と、その run の中で必ず実行できる確認だけを置く。** 「〜があれば確かめる」という条件付きの確認は、条件が満たせないときに、判定の段が「未完了」として差し戻す理由になる。

### 4. テストの規約を一律に当てはめると、受け渡しそのものが約束である値の検証まで消える

#702 で唯一の差し戻しは、ai-antipattern のレビューが出した AI-001（重大度: 中）だった。テストを先に書く段が、既存の CLI のテストから「plan が返したハンドルが、そのまま apply に渡る」という検証を消していた。理由は「方針が禁じる参照の同一性の assertion を除いた」だった。

このハンドルは中身の見えない値で、「人間が確認した plan を、そのまま適用する」という約束を運ぶものだ。同一性こそが検証の対象だった。検証を消したテストの偽物は apply の入力を見ずに固定の成功を返すので、別の plan を渡す退行が起きても、呼び出し回数や保存結果の assertion では気づけない。直しの段は、偽物が受け取った入力を記録する形に戻し、TTY で承認する経路・TTY 無しで `--yes` を付ける経路・作成から保存と読み戻しまでの経路の 3 つで、同じハンドルが渡ることを確かめた。「行の中身は同じでも、別のハンドルなら失敗する」反例も残した。

5 観点のレビューのうち、これを見つけたのは ai-antipattern だけだった。テストの観点のレビューも近い懸念を書いていたが、指摘にはしていなかった。

**「〜を assertion しない」という規約は、何を守るための規約かとセットで当てはめる。** 値の受け渡しそのものが約束なら、偽物は入力を記録し、テストはそれを確かめる。

### 5. テストを先に書くときは、空の値の扱いを実装の土台に合わせてから書く

#704 は、`R2_ACCESS_KEY_ID` などの環境変数が保存したキーより優先されるときに、変数名だけを標準エラーに警告する変更だった。テストを先に書く段は、「環境変数に空文字が入っているときも警告する」というケースを 2 つ書いた。実装の段でそれが落ちた。Effect 4 の既定の `ConfigProvider` は、空文字を未設定として扱う。キーを解決する既存の処理も同じ判定を使っているので、空の変数はそもそも保存したキーより優先されない。警告する理由が無かった。

実装者は `ConfigProvider` を変えず、テストの期待を「警告しない」に直した。警告と秘密の解決が同じ判定を使うことの方が大事だったからだ。

**テストを先に書く段と実装の段が別々に動くときは、境界の値（空文字、未設定、0）の扱いを、実装の土台が決めている規則から先に確かめる。** 規則を知らずに書いた期待は、実装の段で書き直しになる。

### 6. 「参照を消して再実行」のような手順は、変更が無ければ何もしない規則と突き合わせる

#703 の issue には、1Password をやめてファイルに戻したい利用者への案内として「`secrets.json` から R2 の参照を消して再実行する」と書かれていた。実装者がこれをたどると、動かなかった。Cloudflare 上の資源に変更が無い再実行は、apply も保存も省く（それ自体が #703 の約束の 1 つだった）。参照を消しても、キーはファイルに戻らない。

実装者は自動の移し替えを足さずに、README の手順の先頭に「参照を消す前に、1Password の `nyaucast R2` から 2 つのキーを `environment.json` の秘密のブロックへ手で写す」を足した。逆向きの自動の移し替えは、元の要件が禁じていたからだ。後の [#705](https://github.com/daiki-beppu/nyaucast/issues/705)（README）の issue の本文は短い手順のままだったが、その計画は「参照を消すだけでキーが保存される説明に変えない」と明記して、#703 の手順を守った。

同じ #703 で、反対向き（ファイルから 1Password へ）の移し替えは、資源に変更が無くても確認を出して apply する形にした。ADR-0012 の決定 10 の「すべて変更なしなら確認しない」に「かつ、移し替えが無いとき」を足す改訂も、同じ PR に入れた。

**冪等な再実行（何度叩いても同じ結果になる実行）を案内に使うときは、その再実行が「変更なし」と判定されて何もしない場合を先に考える。** 変更なしの判定に、資源の差分以外の状態変化が入っているかを確かめる。

### 7. 外部 CLI の挙動は固定版の配布コードで確かめ、文書に無い値は CLI 自身に聞く

#701 の issue は、未購入の R2 を「Cloudflare のエラーを文書で確かめて」検出する、とだけ書いていた。計画の段は、R2 の公式のエラーコード表で `10042`（NotEntitled）を見つけたうえで、固定版の `cf@1.0.0-beta.12` の配布コードを読んだ。`cf r2 buckets list` がどの API を呼び、アカウントをどこから取り、API のエラーを標準エラーに `[10042] メッセージ` の形で出すかを確かめた。HTTP 403 や「R2」という文字列で判定する案は、権限不足を未購入と取り違えるので退けた。テストは、`[100420]` は一致しない、標準出力に出た 10042 は見ない、トークン作成のときの 10042 は一般の失敗のまま、という境界まで押さえた。

#702 では、issue の「既定の vault（1Password の保管庫）に保存する」が引っかかった。`op` には既定の vault の名前を素直に読む手段が無い。計画は「推測した vault 名や成功の応答を証拠にしない」と未確認のまま残し、実装者は `op item create - --dry-run --format json` の応答から `vault.id` を取ってくる形にした。dry-run なので item は保存されず、`op` 自身が選ぶ vault がわかる。この ID で `item list`・`get`・`edit` を絞った。`item list` は `--vault` を付けないと全部の vault を探すので、別の vault の同名の item を拾いうる。

ただし、どちらも偽物の子プロセスで確かめただけで、実際の `op` の応答は見ていない。実物での確認は #706 に残っている。

**外部 CLI の振る舞いは、固定した版の配布物で確かめ、出典と版をコードの注釈に残す。** 文書から読めない値は、副作用の無いモード（dry-run など）で CLI 自身に答えさせる。

### 8. 最初の検査で落ちるのはテストではなく静的検査なので、実装者は先に単独で流す

9 件のうち 7 件で、実装の段の最初の `pnpm run check` が fallow（未使用・重複・複雑度を見る静的検査）で落ちた。テストは毎回すべて通っていた。

| 落ち方                                    | issue                        |
| ----------------------------------------- | ---------------------------- |
| 分岐を足した関数の複雑度・CRAP スコア超過 | #697・#699・#701・#702・#703 |
| 古い分岐を消して残った未使用の export     | #700・#698（複雑度と同時）   |

形もほぼ決まっていた。`prepareProvisioning` のような処理を束ねる関数に分岐を 1 つ足すと、循環的複雑度 6・CRAP 42 のように閾値を越える。どれも閾値や抑制には手を付けず、関数を分ける・`Option.exists` で条件を書き直すといったコードの変更で通した。ただ、全体の check は 1 回 4〜5 分かかる。

別の落ち方もあった。#701 と #702 の実装者は、`pnpm run check` と `vp test` を同時に流し、`test/mcp-cli.test.ts` の JSON-RPC の応答待ちや、5 秒の上限のテストが時間切れになった。順に流し直すと通った。根本原因は確定していない。

**実装者は、全体の check の前に fallow を単独で流し、check とテスト全件を同時に流さない。** 分岐を足す変更や、分岐を消す変更の後は、それだけで落ちると思っておく。

### 9. 差し戻しの無いレビューにも、「指摘にしない懸念」の表に穴が残る

9 件のレビューは、指摘にしなかった懸念を表にして残していた。大半は「実サービスでは未確認」の持ち越しだが、仕様の解釈で残った穴も混じっていた。

- #698: アカウントが 1 件しかないとき、`--account` に別の ID を渡しても、照合せずにその 1 件を使う。計画が「1 件ならそれを使う」を文字どおりに読んだためで、執筆時点の main でもこの形のまま
- #699: 記録があるときも、アカウント一覧は取りに行く。issue の「一覧から選ばずに」を、選び直しの禁止と読み、一覧の取得の禁止とは読まなかった。ID がまだあるかの確認と名前の表示に使っている
- #703: 1Password への保存が途中で失敗すると、ファイルの秘密のブロックが残る。レビュー 3 観点が同じ懸念を書き、保存の順番と、変更なしの再実行で移し替えが完了することから受け入れた

どれも差し戻しの判定には入らないので、run の報告を開かない限り誰の目にも触れない。PR の本文は issue の写しと完了の一文だけで、この表は載らなかった。

**差し戻しが無い run でも、レビューの「指摘にしない懸念」の表は読み、受け入れない項目は issue にする。** 「レビューを通った」は、レビューが気づいたことが無い、という意味ではない。
