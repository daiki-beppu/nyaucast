# 配布モデルは OSS のコアと、YouTube の公式アプリの利用量への課金にする

## Status

accepted (2026-10-03)

## Context

nyaucast は有償で公開する意向がある。一方で評価軸は **採用 > 収益** で、想定利用者は「AI エージェントの助けを借りる非エンジニアのクリエイター」である。比べた型は OSS・オープンコア・source-available（FSL 等）の 3 つ。プロプライエタリは採用優先に反するので、最初から外した。一度 OSS で出した版は撤回できず、閉じたものを開くのはいつでもできる。

決める材料として 4 本を調べた（詳細は各 issue の解決コメント）。

- **GPL**（#575）: node-av のプレビルドは libx264 入りの GPLv3 ビルドである。MIT・Apache-2.0・GPLv3 の OSS なら、node-av を同じプロセスで読み込む今の形のまま両立する（全体は実質 GPLv3）。同じプロセスで動く有償部分はプロプライエタリにできない。FSL / BSL も同じプロセスでの結合とは両立せず、両立させるにはメディア処理を GPL の別プロセスのワーカーに分ける必要がある
- **事例**（#576）: 締める方向の変更は反発を招き（Terraform・Redis）、開く方向の変更は歓迎される（Mastra・Langfuse）。課金点はホスティング・組織向け機能・規模や用途での線引きに収束しており、個人が日常的に使う機能への課金は撤回された例がある。共有 OAuth アプリを有償にしている前例もある（Composio）
- **非エンジニアのセットアップ**（#577）: 自前アプリだけでは完走できない。完走できないのは YouTube だけである。監査を通っていない API プロジェクトの `videos.insert` は private 固定で、個人の監査通過は前提にできない。Instagram（自アカウント・Standard Access）と X（Native App・従量課金）は自前アプリで完走できる
- **公式アプリの要件**（#578）: YouTube は監査を 1 回通せば、そのプロジェクトに全利用者が乗れる。ただし開発者ポリシーが、API の認証情報を OSS に埋め込むことを禁じている。Instagram で他人のアカウントへ投稿するには、App Review・Business Verification と、app secret を守るサーバが要る。X は審査が無い代わりに、投稿ごとの費用がアプリの持ち主に請求される

dogfood のために、YouTube の API プロジェクトの監査はどのみち受ける（ADR-0009）。

## Decision

1. **コアは OSS で出し、第三者が競合する商用サービスを出すことも許す。** ライセンスは GPLv3 互換のものに限る（GPLv2-only は不可）。具体的にどのライセンスにするかは、別の決定に回す
2. **node-av は同じプロセスのまま使い、別プロセス化しない。** ADR-0005 決定 4 で先送りしていた「結合著作物」の論点は、コアを GPLv3 互換の OSS にすることで解消する。利用者には「実行には GPLv3 の node-av が要り、実行時の全体は実質 GPLv3 になる」と明示する
3. **提供者が YouTube の公式アプリを運営する。** 監査済みの API プロジェクトに、利用者は認可だけで乗れる
4. **課金点は YouTube の公式アプリの利用量だけにする。** 無償枠と有償枠に分ける。ローカルで動く機能（MCP tool・codec・自前アプリの経路）はすべて無償にする。枠の数値と価格はここでは決めない
5. **公式アプリはトークンブローカーを通して渡す。** client secret はブローカーだけが持ち、利用者のローカルの nyaucast はブローカー経由で token を取得・更新する。ブローカーが利用者ごとの利用量を数え、無償枠を超えた利用を止める。動画の upload はローカルから YouTube へ直接行い、ブローカーは認可と計量だけを受け持つ。ブローカーのソースは非公開で始める
6. **コアは 3 SNS すべてで自前アプリの経路を持ち続ける。** OSS 単体で全機能が動き、公式アプリは監査の手間と quota を肩代わりする追加の選択肢にとどめる
7. **X と Instagram の公式アプリは今は出さない。** 需要が出たら、有償でだけ足す。無償では出さない

## Why

- **守る対象がコードではない。** 有償の価値は、監査済みの公式アプリと、それを維持する提供者にある。YouTube の認証情報は OSS に埋め込めないので、同じことをしたい第三者は自分で監査を通す必要があり、それ自体が参入障壁になる。ライセンスで競合を止める必要がない
- **入口を塞がずに、共有資源にだけ課金できる。** 想定利用者が YouTube まで完走できる経路は公式アプリしかないので、そこを最初から有償にすると採用の入口に料金所を置くことになる。一方で、公式アプリの quota は全利用者で共有するので、無償のまま開けば先に尽きる。利用量で枠を分ければ、両方の問題が一度に解ける
- **個人の機能に課金しない。** 事例では、個人が日常的に使う機能への課金は撤回されている。課金点を、提供者に実費や運営の手間がかかるもの（監査の維持・quota）に限った
- **GPL の扱いが今の設計のまま済む。** OSS なら node-av を同じプロセスで使い続けられ、メディア処理を別プロセスに分ける工事が要らない。ブローカーは node-av を読み込まず頒布もしないので、GPL と関わらない
- **ブローカーが要るのは計量のためである。** デスクトップ用の client を配るだけなら、サーバは要らない（#577）。ただし、誰が何本上げたかを数えられないので、無償枠と有償枠を分けられない
- **X の公式アプリだけは費用が利用に比例する。** 無償で出すと、利用が増えるほど提供者の負担が増える。自前アプリで完走できるので、今出す理由が無い

## Considered Options

- **FSL（2 年後に OSS へ自動転換）**: 採らない。閉じた側から出発できる安全さはある。ただし、メディア処理を GPL の別プロセスのワーカーに分ける必要が生じ、ADR-0005 が退けた spawn に近い形へ戻る。組織導入とコントリビュータ参加も阻害される。課金点をサービスに置くなら、コードを守る理由が無い
- **有償部分をプロプライエタリのコードにするオープンコア**: 採らない。有償部分が node-av と同じプロセスで動くならプロプライエタリにできず、FSL と同じく別プロセス化が要る。個人が使う機能を有償側に置くことにもなる
- **公式アプリを無償だけで出す**: 採らない。共有の quota が利用者の増加で尽き、提供者の運営の手間にも見返りが無い
- **公式アプリを有償だけで出す**: 採らない。想定利用者が全員、最初の 1 本から払うことになり、採用優先に反する
- **デスクトップ用の client を OSS の外で配る（サーバ無し）**: 採らない。計量ができず決定 4 と両立しない。漏れた client を止める手段も、client ごとの失効しかない
- **YouTube は公式アプリ経由に限る**: 採らない。OSS 単体では YouTube に公開できなくなり、決定 1 の OSS の性格と食い違う
- **公式アプリを運営しない（全員が自前アプリ）**: 採らない。利用者がそれぞれ YouTube の監査を受けることになり、想定利用者が完走できない

## Consequences

- コアの具体的なライセンスを選ぶ必要がある（MIT / Apache-2.0 / GPLv3 などの GPLv3 互換の中から）。暫定措置として、それまで npm パッケージは `UNLICENSED` のままにする（#573）
- リポを公開するので、ADR-0010 の「リポは private」を前提にした記述を改める必要がある
- ブローカーという常設のサーバが初めて生まれる。認証方式・計量の単位・自前経路との切り替えの設計は、後続の実装で決める
- 公式アプリの提供者は、YouTube の監査の維持と、100 ユーザーを超えたときの OAuth 検証の義務を負う
- ADR-0005 決定 4 を改訂した
- CONTEXT.md に **配布モデル**・**公式アプリ**・**自前アプリ** を加えた
