# 制作物に解説動画を加え、複数の SNS へ配信する。v0.1.0 のゲートは解説動画の 1 周に差し替える

## Context

nyaucast はこれまで、音楽チャンネルの collection を YouTube へ出すことだけを対象にしてきた。運営者の次の目的は、`life` リポジトリの「動画ダイジェスト」と同じ型の動画を、非属人チャンネル向けに作ることにある。型は「台本と SVG 図解の HTML を AI 音声で解説動画にする」ものである。作った動画は YouTube・TikTok・Instagram・X へ AI エージェントが投稿する。

調べた範囲では、`nyaucast`・`life`・`youtube-automation` のどれも YouTube 以外への投稿を持たない。一方で、nyaucast がすでに決めている基盤はこの目的にそのまま使える。

- ADR-0005 の HTML composition 方式は、`life` のシーン（`window.__hf` 互換）を受け入れられる
- ADR-0007 の「codec を読んだ agent が区間を歩き、人間のゲートで区切る」実行モデルも使える

## Decision

1. **制作物を 2 種類にする。** 音楽の collection に、解説動画を並べる。解説動画は長尺・切り抜きショート・専用ショートのカットを持つ。lifecycle は `explainer-lifecycle` codec に書く。ゲートは企画ゲートと公開ゲートの 2 つとし、承認の方式は ADR-0007 と同じく CLI の実行そのものとする。
2. **配信先を複数の SNS にする。** v0.1 の配信先は YouTube・Instagram・X の 3 つとし、投稿の状態モデルと SNS ごとの API アダプタの境界は、SNS を後から足せる形にする（改訂 2026-10-02 / #472）。投稿は「1 カット × 1 アカウント」を単位とし、状態を持つ。投稿文・投稿時刻・AI 生成の開示は agent が判断し、`distribution` codec に書く。実行は決定的な API クライアントの primitive tool が担う（ADR-0002 のとおり、core は LLM を呼ばない）。ブラウザ操作による投稿はしない。
3. **SNS ごとの初期方針**
   - YouTube: 監査済みの API プロジェクトを使う。
   - TikTok: v0.1 では配信しない（改訂 2026-10-02 / #472）。投稿ガイドラインは自分やチームが管理するアカウントへのアップロードツールを不可とし、アプリ審査も私的利用のアプリを退ける。このため、Upload（受信箱への下書き）方式でも `video.upload` スコープの本番審査に通らない見込みが高い。API で投稿できない SNS に、手動投稿やブラウザ操作の経路は作らない。本番審査と Direct Post の監査は、有償配布の形が決まってから v0.2 以降で扱う（#502）。
   - Instagram: Instagram Login 方式（Facebook ページ不要）を使う。Instagram Login では resumable upload が使えず、公開 URL が必須になる。動画は R2 に置き、期限付きの署名付き URL（最長 7 日）で渡す（改訂 2026-10-02 / #473）。Meta がクエリ文字列付きの URL を受け付けないときは、推測できないキーで一時的に公開する。どちらでも、投稿が完了したら tool が R2 のオブジェクトを消し、失敗や中断で残ったものは R2 のライフサイクルルール（7 日）が消す。一時オブジェクトはデータ 4 分類の ③ に当たる。
   - X: 従量課金なので、URL を含めず動画を直接投稿する。
   - AI 生成であることは全 SNS で常に開示する。
4. **すべてローカルの Mac で実行する。** 投稿の予定時刻は local store に持つ。SNS 側で予約できるのは YouTube（`publishAt`）だけで、Instagram と X は予定時刻に nyaucast が即時に投稿する。v0.1 は定期実行を作らず、人間が CLI を叩いて、時刻が来た投稿を実行する。launchd の定期ジョブは v0.2 以降で扱う（#511。改訂 2026-10-02 / #469）。予定時刻から大きく遅れた投稿は自動では実行せず、人間の確認に回す（詳細は決定 9）。
   - 実行環境（Mac と Devin の VM など）の間の引き渡しは v0.2 以降で扱う（#505。改訂 2026-10-02 / #473）。そのときに local store と成果物を実行環境の外へ移せるよう、v0.1 では次の 2 つを守る
     - DB を開く口は 1 か所にし、接続先の URL を差し替えられるようにする
     - 成果物は、チャンネルルートからの相対キーで記録する
5. **v0.1.0 のゲートを差し替える。** 新しいゲートは、解説動画チャンネルで解説動画を 1 周させ、YouTube・Instagram・X の 3 つの SNS に公開することとする（改訂 2026-10-02 / #472。当初は TikTok を含む 4 つ）。音楽チャンネルでの collection の 1 周は v0.2 以降に回す。
6. **認証情報の置き場所を分ける**（改訂 2026-10-02 / #464）。
   - 静的なシークレット（各 SNS のクライアントのシークレット、Gemini の API キー、R2 のアクセスキー）は 1Password に置く。チャンネルをまたぐ設定（`~/.config/nyaucast/` の JSON）に、シークレットごとの 1Password の参照を書き、`op read` で解決する。同じ名前の環境変数があれば、そちらを優先する。`client_secrets.json` などのファイルには置かない
   - 更新されるトークンは `~/.config/nyaucast/credentials/<channel>/<platform>.json` に置き、権限は 0600 とする。v0.1 では、1 つのチャンネルが 1 つの SNS に持つアカウントは 1 つまでとする。トークンの読み書きと更新は、SNS をまたぐ 1 つの口にまとめ、アダプタはファイルの場所を知らない（共有の local store へ移せるようにするため。#505）。更新で受け取ったトークンは、すぐに atomic に保存する
   - アカウントはチャンネル設定に、SNS の不変の ID（YouTube のチャンネル ID、Instagram と X の user id）で宣言する。表示用の handle も併記する。宣言は SNS ごとに任意で、宣言していない SNS への投稿はアダプタより前で拒む
   - 投稿先の取り違え（critical regression ①）は、照合で防ぐ。`nyaucast auth` は、取得したトークンで自分の ID を問い合わせ、宣言と違えば保存しない。投稿の直前には、トークンに記録した ID と宣言とを比べ、違えば投稿しない
   - CLI は `nyaucast auth <channel> <platform>` で認証し、`nyaucast auth status [<channel>]` で、宣言されたアカウントごとに「未認証・有効・期限が近い・更新に失敗」を表示する
   - トークンの更新は使うときに行う。失敗したら、再認証のコマンドを示すエラーで止める。Instagram の長期トークンは、使うときに発行から一定の日数を過ぎていれば先に更新する。v0.1 では通知の仕組みを作らない
   - codex CLI のログイン状態は nyaucast が管理せず、codex 自身のログインを使う。provider を実行する前にログインを確かめ、未ログインならエラーにする
7. **「動画」を上位概念とし、解説動画のゲートを次のように持つ**（改訂 2026-10-01 / #463）。
   - 動画（`video`）は「1 つの企画から作り、企画ゲートと公開ゲートを経て投稿する制作物一式」であり、種類は解説動画と BGM 動画（collection）の 2 つ。1 つのチャンネルが作る動画は 1 種類に限り、種類はチャンネルの設定で決まる。旧語「エピソード」は使わない
   - 区間名は `plan` / `produce` / `publish` で、種類をまたいで共通。ゲートの承認は ADR-0007 決定 3 のとおり次の区間名を動詞にした CLI の実行そのもので、解説動画は `nyaucast video produce <id>` / `nyaucast video publish <id>`。打ち切りは `nyaucast video abandon <id>` で、承認待ちのゲートに NO-GO を書く。v0.1 の `video` コマンドは解説動画チャンネルでだけ動き、collection の CLI は変えない
   - NO-GO は「やめる」の意味だけを持つ。差し戻しは記録を書かず、承認待ちのまま作り直す。やめた動画を再開するときは、NO-GO より後に承認を積む。投稿は公開ゲートの承認の後にしか存在しない（決定 10）ので、公開ゲートを承認した動画はやめられない。配信を止めるときは、投稿単位で取り消す（改訂 2026-10-02 / #470）
   - `video publish` は企画ゲートの承認を事前条件とし、満たさなければ throw する
   - ゲート記録は collection と同形の append-only な承認・NO-GO の表を、解説動画専用に additive に足す（ADR-0001 決定 8・ADR-0004）。判定のロジックは collection と共有する
   - read model が返す承認待ちのゲートは、ゲートの事実に加え、publish については「プレビューできるカットがそろっていること」を条件に導出する。条件の具体は決定 11 による
   - 公開ゲートの承認は、採用したカットと最後のサムネイルの選択のどれよりも新しくなければならない（collection のサムネ鮮度と同じ考え方。サムネイルについては決定 8）。この検査は、投稿を作る公開ゲートの CLI と投稿を実行する処理の両方の事前条件に置く（決定 9・10）。採用したカットは独立した事実として持たず、投稿が指すカットから導出するので、検査は投稿ごとに「最後の承認が、その投稿のカットと最後のサムネイルの選択より新しいこと」として行う
   - tool のドメイン名は、`video.*` を種類に依存しない動画全体の操作に、`explainer.*` / `collection.*` を種類に固有の操作に使う。カットやファイル単位の操作は `video.` を名乗らない。本 ADR と ADR-0005・0007 に書かれた `video.render` などの名前は決定前の仮称であり、実際の名前は実装 ticket で決める

8. **長尺のサムネイルは plan 区間で作り、企画ゲートで判断する**（改訂 2026-10-02 / #468）。サムネイルが再生の大半を左右するので、台本・音声・描画に費用をかける前に「このサムネイルで勝てるか」を見る。
   - 区間は「題材収集 → 企画 → サムネイル →[企画ゲート]」になる。企画ゲートの承認は、サムネイルの選択があることを前提とする。公開ゲートでは作り直しと差し替えによる選び直しだけを受け、企画ゲートはやり直さない
   - サムネイルの文言も画像生成に描かせる。agent が渡すのは、サムネイルの文言（動画のタイトルとは別）と背景の描写だけで、画風・お手本の参照画像・禁止語・文字の指示・provider・候補の枚数はチャンネル設定の「サムネイルの型」に人間が宣言する。版権を避ける句と禁止語の検査は tool が保証する
   - 1 回の生成で候補を N 枚（既定 3）作る。provider は Gemini の画像生成 API と codex CLI の 2 本を v0.1 で実装し、チャンネル設定で必ず選ぶ（既定値なし、自動の切り替えなし）。codex CLI の扱いは ADR-0002 の改訂による
   - tool が決定的に検査するのは、16:9・1280x720 以上・2 MB 以下の 3 つだけとする。縮小して読めるか、文字が文言どおりか（誤字）は、agent が codec の手順で判断して候補を落とし、最後は人間がゲートで見る
   - 候補から 1 枚を選ぶのは CLI の実行で、append-only の「サムネイルの選択」として記録する。人間が用意した画像は、同じ検査を通して候補に足し、同時に選ぶ。ゲート記録の表の形は変えない
   - ショートは専用の画像を作らず、カットの中のフレームを表紙にする

9. **投稿の状態と予定時刻の実行**（改訂 2026-10-02 / #469）。
   - 投稿は状態の列を持たず（ADR-0007 決定 2）、append-only の 3 種の事実から read model が状態を導出する。3 種は、投稿（カット・アカウント・投稿文・予定時刻。書いたら変えない）、投稿の試行（外部 API を呼ぶ前に開始を書き、終わったら結果を書く。結果は成功とリモートの ID、一時的な失敗、恒久的な失敗のいずれか）、投稿の取り消しである。YouTube の予約済みの投稿には、4 種目の事実として公開の確認を積む（決定 13。改訂 2026-10-03 / #526）。導出する状態は、予定・期限到来・実行中・SNS 側で予約済み・公開済み・失敗・確認待ち・取り消し済み
   - 予定時刻や投稿文を直すときは、投稿を取り消して作り直す
   - 投稿の実行は人間の CLI だけが行い、MCP に開かない（ADR-0007 決定 6 の非対称を、投稿の実行にも広げる）。予定時刻が来た投稿をまとめて実行する CLI は、定期実行からもそのまま叩ける形にする
   - 予定時刻からの遅れが許容時間を超えた投稿は、自動では実行せず確認待ちにする。許容時間の既定は 60 分で、チャンネル設定の配信の設定に置く。SNS ごとには分けない
   - YouTube は、公開ゲートの後に最初に実行したときに、`publishAt` を予定時刻にして private で upload する。予定時刻が過去になった YouTube の投稿は、即時公開になるので upload せず、確認待ちにする
   - 開始だけが書かれて結果の無い試行は、自動では再実行せず確認待ちにする。SNS に出たかどうかが分からないまま再実行すると、二重投稿（critical regression ①）になるため
   - アダプタはエラーを 2 つに分ける。一時的なエラー（通信の失敗・5xx・429・quota 切れ）は、投稿を期限到来のまま残し、次の実行で許容時間内なら再び試す。同じ実行の中では再試行しない。恒久的なエラー（入力の検証・認証・権限）は失敗にし、自動では再試行しない。認証の失敗が出たら、その実行ではそのアカウントの残りの投稿を試さない
   - 公開ゲートの鮮度の検査（決定 7）は、投稿を作る公開ゲートの CLI（決定 10）と投稿を実行する処理の両方に置く。投稿を作った後にカットを描き直したり、サムネイルを選び直したりできるからである。実行時の検査に落ちた投稿は、確認待ちにする
   - 人間が投稿単位で使う CLI を 3 つ置く。どれも動かす前に、投稿先のアカウントとカットを表示する
     - 取り消し: 取り消しの事実を積む。YouTube で SNS 側に予約済みのときは、リモートの private の動画を消してから積む。公開ゲートを承認した動画はやめられないので（決定 7）、配信を止めるときもこれを使う
     - 今すぐ実行: 確認待ちか失敗の投稿を、許容時間を無視して実行する。鮮度の検査は外さない
     - 公開済みの記録: 結果の無い試行について、人間が SNS で公開を確かめたときに、リモートの URL とともに公開済みとして記録する。公開の確認が取れずに確認待ちになった YouTube の投稿（決定 13）にも使う
   - 投稿文の形式の検査は、投稿案を書く tool と、投稿を作る公開ゲートの CLI の両方が持つ（ADR-0007 決定 5。決定 10）。検査は、空でないこと、SNS ごとの文字数の上限（YouTube はタイトルの 100 字を含む）、X の投稿文に URL を含まないことの 3 つ。AI 生成の開示は投稿文に頼らず、アダプタが API のフラグを常に立て、agent からは外せない
   - Instagram は、1 回の試行の中で「R2 に上げる → メディアコンテナを作る → 処理の完了を待つ → 公開する」を行い、試行の終わりに成功でも失敗でも R2 のオブジェクトを消す（決定 3）。コンテナは 24 時間で失効するので、作り置きしない。X の `media_id` も 24 時間で失効するので、試行の中で上げてすぐ投稿する

10. **投稿は公開ゲートの CLI が投稿案から作る**（改訂 2026-10-02 / #470）。承認したものと作るものを一致させる（ADR-0007 決定 3）。

- agent は公開ゲートの前に、MCP の tool で投稿案を書く。投稿案は「ショートの候補（長尺は長尺）× アカウント」をキーに、投稿文と予定時刻を持つ。YouTube の投稿文はタイトルと説明からなり、タグは v0.1 では持たない。投稿案は append-only で、同じキーの最後の投稿案が有効になる。キーにカットを含めないので、切り抜きショートと専用ショートのどちらを採用しても同じ投稿案を使える
- 投稿を作る口は `nyaucast video publish <id>` だけとし、MCP に開かない。ゲートの承認と投稿は 1 つのトランザクションで書く
- `video publish` は stdin が TTY のときだけ動く。対話を省くフラグは作らない。agent が Bash から承認を代行する経路を、普通に叩いて通る形にはしない
- `video publish` が表示するもの: カット・プレビュー・最後に選んだサムネイルのパス、投稿案の一覧（アカウント・投稿文・予定時刻）。ファイルは CLI から開かない。ショートの候補ごとに「切り抜き / 専用 / どちらも出さない」を対話で選ばせ、agent の推奨を既定値にする。最後に「承認する / やめずに終える」を選ばせ、やめずに終えたときは何も書かない（差し戻し。決定 7）
- 投稿先のアカウントは、`nyaucast auth status` と同じ形（SNS・handle・不変の ID・認証の状態）で表示する（critical regression ①）
- 次のいずれかに当たれば、承認を拒否して何も書かない
  - 投稿先のアカウントが宣言されていない、認証されていない、またはトークンに記録した ID が宣言と違う
  - 予定時刻が過去の投稿案がある
  - 採用したカットに投稿案が 1 件も無い（アカウントに投稿案が無いことは許す。どの SNS に出すかは `distribution` codec の判断である）
  - 投稿文が形式の検査（決定 9）に落ちる
- 採用しなかったカットには投稿案から投稿を作らないので、採用しなかったカットの投稿は構造上できない
- 公開ゲートの後に投稿文・予定時刻を直すとき、カットを描き直したとき、サムネイルを選び直したときは、同じ経路で作り直す。人間が投稿を取り消し、agent が投稿案を書き直し、人間が `video publish` をもう一度叩く。2 回目以降は、生きている投稿（取り消されていない投稿）を持たない投稿案だけを表示し、新しい承認とその投稿を書く。切り抜きか専用かの選び直しは、生きている投稿が 1 件も無いショートの候補に限って受ける

11. **解説動画の成果物は、外から指されるものと時刻で比べられるものだけを local store の事実にする**（改訂 2026-10-02 / #494）。進捗は ADR-0007 決定 2 のとおり実体行から導出し、事実はすべて append-only とする。
    - 成果物を性質で 2 つに分ける。agent が書く入力（台本・図解・ショートの候補）は、tool が検証して動画のディレクトリにファイルで書く。決定的には作り直せないので、データ 4 分類の ② の内容をファイルに置いたものとして扱い、消してはいけない。決定的な出力（段落の WAV、ナレーショントラックとタイミング表、最終の音声トラック、composition、mp4、preview）は ③ とする
    - 決定的な出力のうち、local store に行を持つのは「カットの書き出し」と「プレビュー」だけとする。カットの書き出しは、render が実際に mp4 を新しく作ったときだけ積み、カットの名前・相対キー・composition の鍵・render の鍵・作成時刻を持つ。プレビューは、preview の tool が実際に撮ったときだけ積み、カットの名前・composition の鍵・作成時刻を持つ。冪等で既存を返したときはどちらも積まない。段落の WAV、トラック、composition は行を持たず、各 tool の鍵（ADR-0005 決定 9）で冪等にする
    - カットの新しさは、そのカットの最後の書き出しの作成時刻で測る（決定 7 の鮮度の検査）。投稿はカットを名前（長尺・各ショートの候補の切り抜き・専用）で指す。描き直すと最後の書き出しが新しくなるので、承認より後に描き直したカットの投稿は確認待ちになる。投稿を実行する直前には、最後の書き出しの相対キーにファイルがあることも確かめ、無ければ確認待ちにする。mp4 のハッシュの取り直しはしない（手での差し替えは ADR-0007 決定 5 の「迂回は封じない」の範囲）
    - ショートの候補は、候補を書く tool が中身を検証し、候補ごとに append-only の「ショートの候補の版」を積む。版は、番号・切り抜きの段落の範囲・フック・専用ショートの台本の相対キー・作成時刻を持つ。候補を減らすときは取り下げを積む。投稿案は、同じ番号の最後の版より新しいものだけを有効とする。古い投稿案は無いものとして扱われ、公開ゲートは投稿案の欠けとして承認を拒否する（決定 10）
    - サムネイルの候補は、動画・生成の回・番号・相対キー・出所（生成か人間の差し替えか）・作成時刻の行で持つ。agent が候補を落としたときは、理由つきの「候補の除外」を積む。除外した候補は選べない。サムネイルの選択（決定 8）は、候補の行を指す
    - 企画ゲートの承認待ちは、企画があり、最後のサムネイルの選択が企画の最後の更新より新しいときに導出する。`video produce` も同じ条件を事前条件とする
    - 公開ゲートの承認待ちは、企画ゲートの承認に加えて、次の 3 つがすべて成り立つときに導出する（決定 7）
      - 長尺と、取り下げていない各ショートの候補の 2 カット（切り抜き・専用）に、最後の書き出しがある
      - それぞれの最後の書き出しと同じ composition の鍵のプレビューがある
      - ショートの候補の 2 カットの最後の書き出しは、その候補の最後の版より新しい
    - ショートの候補は 0 件でもよい。どの SNS に何を出すかは `distribution` codec が判断する
    - read model は、事実とそこから決定的に導出できる状態だけを返す（ADR-0007 決定 6）。返すのは、企画、サムネイルの候補・除外・最後の選択、ゲート記録、取り下げていないショートの候補、カットごとの最後の書き出しとプレビュー、投稿の状態、承認待ちのゲート、やめたかどうか。台本・ナレーション・図解の途中経過は返さない。agent は頭から歩き直し、冪等な tool がすぐに返す（ADR-0007 決定 4）
    - 解説動画では、成果物を削除する tool を置かない（ADR-0007 決定 4 の明示的な再生成手段は `force` だけにする）。決定的な出力は各 tool の `force` で作り直し、作り直すと新しい行が積まれる。agent が書く入力は、新しい版の上書きで直す。append-only の行は消さない
12. **BGM プールの曲は、商用利用できるプランで自分で生成し、どの SNS の照合にも登録しない**（改訂 2026-10-03 / #525）。3 つの SNS に出して権利の申し立てを受けないための条件である。
    - 生成元は Suno（Pro / Premier）・ElevenLabs Music（Starter 以上の有料プラン）・Lyria（Gemini API / Vertex AI）の 3 つとする。権利は曲を生成した時点のプランで決まる。無料プラン（Suno の Basic・ElevenLabs の Free）と Gemini アプリで作った曲は入れない
    - プールの曲は配信代行に出さず、Content ID にも Meta の照合にも登録しない。音楽チャンネルの曲と兼用しない
    - プールはチャンネルリポの git 管理 JSON（データ 4 分類の ①）に、曲ごとにファイル・出所・許諾の根拠・ループ点（任意）を書き、スキーマで検証する。出所は `generated`（サービス・生成時のプランか経路・モデル・生成日）と `licensed`（ライセンスの URL）の 2 種とし、上の生成元と条件に合わない `generated` はスキーマが拒否する
    - プールへの曲の投入は人間が手で行う。ミックスの規則は ADR-0005 決定 14・15 が定める

13. **公開後運用は、YouTube の公開の確認だけにする**（改訂 2026-10-03 / #526）。v0.1.0 のゲートは「公開するまで」なので、公開後に投稿へ手を入れる運用は持たない。

- 解説動画 lifecycle は、その動画のすべての投稿が公開済み・取り消し済み・失敗のいずれかになったときに 1 周したとする。投稿の事実から導出し、終わったことを表す事実は積まない。確認待ちの投稿が残る間は閉じない。失敗した投稿を今すぐ実行すれば、導出の結果として再び開く
- Instagram と X は、試行が成功したことをもって公開済みとする。YouTube は `publishAt` で予約し、公開は SNS 側で起きるので、試行の成功は「SNS 側で予約済み」にとどまる
- 予定時刻を過ぎた YouTube の予約済みの投稿は、時刻が来た投稿を実行する CLI が同じ実行の中で照合する。`videos.list` を読み、`privacyStatus` が `public` なら、公開の確認（投稿・確認した時刻）を積んで公開済みとする。照合は投稿の実行と同じく MCP に開かない（決定 9）
- public でない結果は事実として積まない。予定時刻から許容時間を過ぎても公開の確認が無い投稿は、時刻から確認待ちと導出する。`uploadStatus` が `rejected` か `failed` のときは、許容時間を待たずに確認待ちにする。失敗にはしない。人間が Studio で確かめ、公開済みの記録で記録するか、取り消して作り直す
- 予定時刻を過ぎると `privacyStatus` が `public` に変わることは、公式の文書に明記されていない。YouTube の投稿を実装する ticket の受け入れ条件に、実際の動画での確認を入れる
- 権利の申し立ては nyaucast では検知しない。個人のチャンネルでは YouTube の Content ID の申し立てを API で取れず、一部の SNS だけを検知すると「検知していない」を「申し立てが無い」と取り違える。人間が各 SNS の通知で気づいて各 SNS の画面で対応し、その手順（BGM プールの出所と許諾を根拠に異議を出す、など。決定 12）は `distribution` codec に書く。申し立てを受けても、lifecycle が 1 周したことは戻らない
- 固定コメント・概要欄の更新・他の SNS への相互リンクなど、公開後に投稿の中身を変える操作は持たない。投稿は書いたら変えない事実だからである

## Why

- 目的に直結するのは解説動画と複数 SNS への配信で、v0.1 で作る基盤はどちらの lifecycle にも共通である。基盤とは `video.render`、アップロード、ゲート、認証を指す。順番を入れ替えても手戻りはほとんど出ない。
- `youtube-automation` の ADR-0021 追記で TS 版への移行計画は撤回されている。そのため、音楽の dogfood を先に済ませる外部要因は弱い。
- ゲートとローカルの local store という既存の設計に、何も手を入れずに載る。

## Considered Options

- **生成を GitHub Actions で行う（`life` の方式）**: 採らない。Actions のランナーからは Mac 上の `local.db` が見えず、「人間が CLI を叩いた事実が承認」という ADR-0007 のモデルと両立しない。Mac を常時起動できなくなったときは、Turso のリモート DB（または埋め込みレプリカ）による同期を再検討する。
- **v0.1 から状態を実行環境の外に置き、Devin の VM などでも動かす**（#473）: 採らない。v0.1.0 のゲートは Mac だけで完走できる。外に置くと、次の 4 つがまとめて v0.1 に乗る。
  - オフラインで動かない
  - ADR-0004 の `cp` によるバックアップの作り直し
  - 同時実行の排他
  - VM での secret の扱い

  さらに、VM で node-av と headless Chrome が動くかは確かめていない。この検証は「Devin の VM で nyaucast を動かす検証」（#506）で先に行い、移行は #505 で扱う。置き場の候補は、local store が Turso のリモート DB、成果物が R2 である。D1 は Workers の外で使う drizzle の実行時ドライバが無く、ADR-0004 の起動時 `migrate()` を保てないので、候補から外れる。

- **Instagram に渡す動画を GCS の署名付き URL で渡す**（決定 3 の前の決定）: 採らない。R2 は外向きの転送が無料で、#505 の成果物の置き場の候補とも同じになる。
- **Jinba Flow でワークフローを MCP 化する**: 採らない。理由は次のとおり。
  - クラウドで実行されるため、Mac 上の local store とヘッドレス Chrome に届かない。
  - 1 フロー = 1 ツールの粗い粒度は、ADR-0007 決定 0 に反する。
  - ローカルでのテスト手段がない。
  - TikTok・Instagram への投稿と、X への動画添付を持たない。
  - nyaucast の primitive tool は書いた時点で MCP tool になるので、「MCP 化」の手間はもともと小さい。
- **新規リポジトリで作り直す**: 採らない。技術スタックを TypeScript のまま据え置くので、auth・local store・ゲート・MCP の基盤をそのまま使える。基盤を 2 か所で保守することになるのを避ける。
- **長尺のサムネイルを HTML composition で描く**: 採らない。ADR-0005 決定 7 の Chrome 許可リストを広げずに済むよう、音楽と同じく画像生成で作る。人間は作り直しを指示するか、用意した画像に差し替えられる。
- **投稿は公開ゲートの承認の後に、agent が MCP の tool で作る**（決定 10 の前の案）: 採らない。人間が投稿文と予定時刻を見ないまま承認することになり、ADR-0007 決定 3 が消した「承認したものと作るものが違う」事故が戻る。
- **公開ゲートの対話で、人間が投稿文と予定時刻を入力する**: 採らない。投稿文は `distribution` codec を読んだ agent が書くもの（決定 2）で、人間の手間も大きい。
- **カットの採用を独立した事実として持つ**: 採らない。投稿が指すカットから導出でき、「採用したのに投稿が無い」余地を作るだけになる。
- **`video publish` に対話を省くフラグを置く**: 採らない。agent が承認を代行する経路が普通に通るようになる。TTY の検査は防御ではないが、うっかり叩いて通る形は残さない。
- **launchd の定期ジョブで予定時刻の投稿を実行する**（決定 4 の前の決定）: v0.1 では採らない。v0.1.0 のゲートは人間が CLI を叩いて完走できる。plist の置き方、排他、Mac が寝ていたときの扱いを v0.1 に乗せない。CLI を定期実行からそのまま叩ける形にしておき、v0.2 で足す（#511）。
- **Instagram と X も SNS 側で予約する**: できない。Instagram のリールのメディアコンテナには公開時刻の引数が無く、公開の API を呼んだ時点で公開される。X API v2 の投稿にも予約は無い。X Ads API の `scheduled_tweets` は予約できるが、広告アカウントと Ads API の個別の承認が要る。
- **投稿に公開の結果や ID の列を持たせ、行を更新する**: 採らない。行は少なくて済むが、「列が古い」余地を作り、ADR-0007 決定 2 の理由に反する。試行を独立した事実にすると、二重実行の防止と再試行の履歴が同じ行で賄える。
- **結果の無い試行を自動で再実行する、または SNS に照会して自動で判定する**: 採らない。前者は二重投稿になりうる。後者は SNS ごとに照会の手段がまちまちで、v0.1 に乗せるには大きい。
- **サムネイルを公開ゲートで確定する**（決定 8 の前の決定）: 採らない。描画まで費用をかけた後で、勝てないサムネイルに気づくことになる。
- **サムネイル専用のゲートを企画ゲートと公開ゲートの間に足す**（collection と同じ 3 段）: 採らない。ゲートを 2 つに絞った決定 1 を崩す。
- **文字を実フォントで後から重ねる**: 採らない。誤字が出ず書体もぶれない利点はあるが、文字の構図まで含めた画像を見て判断したい。経路を 2 本持つと、検査も鮮度の鍵も 2 通りになる。
- **選んだ候補をゲートの承認の記録に持たせる**: 採らない。ゲート記録を collection と同じ形にそろえる決定 7 を崩し、公開ゲートでの選び直しと差し替えの経路も分かれる。
- **解説動画の成果物をすべてファイルだけにし、進捗と鮮度をファイルの有無と鍵から導出する**（決定 11 の前の案）: 採らない。投稿にはカットを指す識別子が要り、公開ゲートの鮮度はカットが新しくなった時刻を要る。read model が「SQL 一発」で答える約束（CONTEXT.md の read model）からも外れる。
- **決定的な出力のすべて（段落の WAV ごと、トラックごと）に行を持つ**: 採らない。外から指されず、時刻で比べられもしない成果物の行は、ADR-0007 決定 2 が避けた「行と実体のずれ」を段落の数だけ増やす。
- **投稿が書き出しの行（id）を指す**: 採らない。描き直しても投稿は古いカットを指したままになり、決定 9 の「描き直したら確認待ち」と逆に動く。
- **agent が書く入力（台本・図解）の中身を local store に入れる**: 採らない。HTML や台本はファイルのほうが agent も人間も読み書きしやすい。消してはいけないことは、分類（決定 11）で表す。
- **カットの書き出しやサムネイルの候補を消す tool を置く**: 採らない。事実が append-only なので、新しい行が古い行を覆えば足りる。削除の tool は critical regression ②（データ破壊）の入口を増やすだけになる。
- **TikTok を Sandbox アプリの受信箱への Upload で通す**: 採らない。Sandbox は審査なしで使えるが、テスト用の環境で本番の運用を支える前提にならない。受信箱から仕上げて投稿するのは人間であり、API で投稿したことにもならない。
- **TikTok だけ人間が手で投稿し、投稿の URL を記録してゲートに数える**: 採らない。決定 2 の「実行は決定的な primitive tool が担う」を TikTok のためだけに崩す。Upload の init には `post_info` が無く、AI 生成の開示も人間の操作頼みになる。
- **TikTok の本番審査を v0.1 と並行して出す**: 採らない。自チャンネル専用のアプリとして審査され、落ちる見込みが高い。複数のクリエイターが認可して使うアプリとして出せる有償配布の時点まで待つ。
- **BGM を YouTube Audio Library から取る**: 申し立てを受けない約束は YouTube の Content ID についてだけで、Instagram と X で使えるかは一次情報で確かめられない。採らない。
- **BGM を Pixabay などのロイヤリティフリーの素材集から取る**: 投稿者が同じ曲を Content ID に登録していて申し立てを受けうることを、Pixabay 自身が認めている。異議を出すたびに書類が要る。採らない。
- **音楽チャンネルの曲を BGM プールに流用する**: 配信代行で Content ID に登録した曲は、解説動画が申し立てを受ける。配信代行の許可リストは動画単位で、申し立てを受けた後にしか使えない。採らない。

- **予定時刻を過ぎた YouTube の予約済みの投稿を、API を呼ばずに公開済みと導出する**: 採らない。監査を通っていないプロジェクトの動画は private のまま残り、処理に失敗した動画も公開されない。どちらも公開済みと誤って表示する。
- **公開の確認を人間の公開済みの記録だけで行う**: 採らない。予約した投稿すべてで人間が Studio を見ることになり、照合を自動化しても二重投稿の恐れは無い（読むだけで、何も投稿しない）。結果の無い試行に照会を使わない決定 9 とは、照会の目的が違う。
- **Instagram の `copyright_check_information` と X の `withheld.copyright` を照合で読み、申し立てを記録する**: 採らない。申し立ては公開の数日後に届き、公開を確かめた時点で終わる照合とは時期が合わない。YouTube は取れないので、検知の有無が SNS ごとにまちまちになる。v0.2 以降で扱う。
- **lifecycle の終点を公開ゲートの承認にする**: 採らない。v0.1.0 のゲートは 3 つの SNS へ公開するまでであり、承認の後に投稿が出ないまま終わったことにできてしまう。

## Consequences

- CONTEXT.md の `dogfood`・`knowledge codec`・データ 4 分類の ④ を、この決定にあわせて改訂した。
- 公開前の一次確認が残っている。対象は X の URL 付き投稿の単価、TikTok と X の自動投稿ポリシー、Instagram の 2026 年 4 月の規約強化。
- ElevenLabs の日本語ナレーションの品質は、Starter プランで聴き比べてから、チャンネルの既定のボイスを決める。
- ツール名は再帰的頭字語の方針に沿って nyaucast へ改めた（#438 / #446）。
- 決定 7 により、collection の CLI と人間の語彙にずれが残る（`collection reject <gate>`、ゲートの前後関係の未強制）。collection を BGM 動画として `video` に統合する作業は v0.2 以降に回す。
- 決定 8 により、文言の誤字は画像生成の偶然で出る。候補を複数作ることと、agent による足切りで吸収する。
- 決定 7 の「ゲートを動詞で叩く」と「差し戻しは記録しない」の組み合わせにより、作り直しの手順は `explainer-lifecycle` codec が持つ。
- 決定 3 の TikTok の改訂により、v0.1 では TikTok のショート向けの書き出しを実地で確かめない。9:16 のカットは YouTube のショート・Instagram のリール・X で確かめる。
- 決定 3 の Instagram の改訂により、Meta が R2 の署名付き URL を受け付けるかは、実機で確かめていない。Instagram の投稿を実装する ticket の受け入れ条件に、この確認を入れる。
- 決定 12 でも、申し立てがゼロになる保証は無い。生成元はどれも「似た曲や同じ曲を他のユーザーにも生成しうる」と規約に書いており、Meta は登録者の参照ファイルのほかに Audible Magic でも照合する。申し立てを受けたときの扱いは、決定 13 で人間が各 SNS で対応するとした（#526）。
- 決定 12 の生成元の条件は、2026-10-03 時点の各社の規約による。規約が変わったら、スキーマの条件と本 ADR を合わせて改訂する。
- 決定 4 の約束により、Instagram の一時公開を除いて、v0.1 は R2 も Turso も使わない。複数の環境で動かすときの認証情報の扱い（入れ替わるトークンを、暗号化して共有の local store に置くこと）は、#505 で決める。
- 決定 9 により、v0.1 では予定時刻に人間が CLI を叩かないと、Instagram と X の投稿は出ない。許容時間を超えたら確認待ちになるので、遅れて誤った時刻に出ることはない。
- 決定 11 により、ADR-0005 の「図解は ③」を改め、ADR-0007 の Consequences に残っていた「`force` / 実体行削除の使い所」は、解説動画については `force` だけとして片づいた。dogfood 実走時に残るのは、失敗したときの戻し方である。
- 決定 11 により、企画を上書きしたら、サムネイルを選び直すまで企画ゲートの承認待ちにならない。ショートの候補を直したら、そのカットを作り直し、投稿案を書き直すまで公開ゲートの承認待ちにならない。
- 決定 13 により、v0.1 では権利の申し立てに気づくのが人間の通知頼みになる。lifecycle が 1 周した後に申し立てを受けても、nyaucast の状態には現れない。
