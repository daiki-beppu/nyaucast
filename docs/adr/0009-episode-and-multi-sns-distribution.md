# 制作物に解説動画を加え、複数の SNS へ配信する。v0.1.0 のゲートは解説動画の 1 周に差し替える

## Status

accepted (2026-09-29) / 改訂 2026-10-01（#463。制作物の語「エピソード」を「解説動画」に改め、上位概念「動画」と解説動画のゲートの決定 7 を追加。ファイル名は歴史的識別子として据え置く）/ 改訂 2026-10-02（#468。長尺のサムネイルを plan 区間で作り、企画ゲートで判断する決定 8 を追加）/ 改訂 2026-10-02（#472。TikTok を v0.1 の配信先とゲートから外し、ゲートを 3 つの SNS にする。決定 2・3・5 を改訂）/ 改訂 2026-10-02（#473。Instagram に渡す動画の一時公開ホストを R2 にし、決定 3 を改訂。v0.1 を Mac だけで動かす決定 4 を確認し、後から状態を外へ移せるようにする約束を加える）

## Context

nyaucast はこれまで、音楽チャンネルの collection を YouTube へ出すことだけを対象にしてきた。運営者の次の目的は、`life` リポジトリの「動画ダイジェスト」と同じ型の動画を、非属人チャンネル向けに作ることにある。型は「台本と SVG 図解の HTML を AI 音声で解説動画にする」ものである。作った動画は YouTube・TikTok・Instagram・X へ AI エージェントが投稿する。

調べた範囲では、`nyaucast`・`life`・`youtube-automation` のどれも YouTube 以外への投稿を持たない。一方で、nyaucast がすでに決めている基盤はこの目的にそのまま使える。

- ADR-0005 の HTML composition 方式は、`life` のシーン（`window.__hf` 互換）を受け入れられる
- ADR-0007 の「codec を読んだ agent が区間を歩き、人間のゲートで区切る」実行モデルも使える

## Decision

1. **制作物を 2 種類にする。** 音楽の collection に、解説動画を並べる。解説動画は長尺・切り抜きショート・専用ショートのカットを持つ。lifecycle は `explainer-lifecycle` codec に書く。ゲートは企画ゲートと公開ゲートの 2 つとし、承認の方式は ADR-0007 と同じく CLI の実行そのものとする。
2. **配信先を複数の SNS にする。** v0.1 の配信先は YouTube・Instagram・X の 3 つとし、投稿の状態モデルと SNS ごとの API アダプタの境界は、SNS を後から足せる形にする（改訂 2026-10-02 / #472）。投稿は「1 カット × 1 アカウント」を単位とし、状態を持つ。投稿文・投稿時刻・AI 生成の開示は agent が判断し、`distribution` codec に書く。実行は決定的な API クライアントの primitive tool が担う（ADR-0002 のとおり、core は LLM を呼ばない）。ブラウザ操作による投稿はしない。
3. **SNS ごとの初期方針**
   - YouTube: 監査済みの API プロジェクトを使う。
   - TikTok: v0.1 では配信しない（改訂 2026-10-02 / #472）。投稿ガイドラインは自分やチームが管理するアカウントへのアップロードツールを不可とし、アプリ審査も私的利用のアプリを退ける。このため、Upload（受信箱への下書き）方式でも `video.upload` スコープの本番審査に通らない見込みが高い。API で投稿できない SNS に、手動投稿やブラウザ操作の経路は作らない。本番審査と Direct Post の監査は、有償配布の形が決まってから v0.2 以降で扱う（#502）。
   - Instagram: Instagram Login 方式（Facebook ページ不要）を使う。Instagram Login では resumable upload が使えず、公開 URL が必須になる。動画は R2 に置き、期限付きの署名付き URL（最長 7 日）で渡す（改訂 2026-10-02 / #473）。Meta がクエリ文字列付きの URL を受け付けないときは、推測できないキーで一時的に公開する。どちらでも、投稿が完了したら tool が R2 のオブジェクトを消し、失敗や中断で残ったものは R2 のライフサイクルルール（7 日）が消す。一時オブジェクトはデータ 4 分類の ③ に当たる。
   - X: 従量課金なので、URL を含めず動画を直接投稿する。
   - AI 生成であることは全 SNS で常に開示する。
4. **すべてローカルの Mac で実行する。** SNS が予約投稿を持たないため、投稿の予定時刻は local store に持つ。launchd の定期ジョブが CLI を叩き、時刻が来た投稿を実行する。予定時刻から大きく遅れた投稿は自動では実行せず、人間の確認に回す。
   - 実行環境（Mac と Devin の VM など）の間の引き渡しは v0.2 以降で扱う（#505。改訂 2026-10-02 / #473）。そのときに local store と成果物を実行環境の外へ移せるよう、v0.1 では次の 2 つを守る
     - DB を開く口は 1 か所にし、接続先の URL を差し替えられるようにする
     - 成果物は、チャンネルルートからの相対キーで記録する
5. **v0.1.0 のゲートを差し替える。** 新しいゲートは、解説動画チャンネルで解説動画を 1 周させ、YouTube・Instagram・X の 3 つの SNS に公開することとする（改訂 2026-10-02 / #472。当初は TikTok を含む 4 つ）。音楽チャンネルでの collection の 1 周は v0.2 以降に回す。
6. **認証情報の置き場所を分ける。** クライアントのシークレットは 1Password（`op read`）に置く。更新されるトークンは `~/.config/nyaucast/credentials/` にアカウント別に置き、権限は 0600 とする。
7. **「動画」を上位概念とし、解説動画のゲートを次のように持つ**（改訂 2026-10-01 / #463）。
   - 動画（`video`）は「1 つの企画から作り、企画ゲートと公開ゲートを経て投稿する制作物一式」であり、種類は解説動画と BGM 動画（collection）の 2 つ。1 つのチャンネルが作る動画は 1 種類に限り、種類はチャンネルの設定で決まる。旧語「エピソード」は使わない
   - 区間名は `plan` / `produce` / `publish` で、種類をまたいで共通。ゲートの承認は ADR-0007 決定 3 のとおり次の区間名を動詞にした CLI の実行そのもので、解説動画は `nyaucast video produce <id>` / `nyaucast video publish <id>`。打ち切りは `nyaucast video abandon <id>` で、承認待ちのゲートに NO-GO を書く。v0.1 の `video` コマンドは解説動画チャンネルでだけ動き、collection の CLI は変えない
   - NO-GO は「やめる」の意味だけを持つ。差し戻しは記録を書かず、承認待ちのまま作り直す。やめた動画を再開するときは、NO-GO より後に承認を積む。予約済みの投稿が残る動画はやめられず、取り消しは投稿単位で行う
   - `video publish` は企画ゲートの承認を事前条件とし、満たさなければ throw する
   - ゲート記録は collection と同形の append-only な承認・NO-GO の表を、解説動画専用に additive に足す（ADR-0001 決定 8・ADR-0004）。判定のロジックは collection と共有する
   - read model が返す承認待ちのゲートは、ゲートの事実に加え、publish については「プレビューできるカットがそろっていること」を条件に導出する
   - 公開ゲートの承認は、採用したカットと最後のサムネイルの選択のどれよりも新しくなければならない（collection のサムネ鮮度と同じ考え方。サムネイルについては決定 8）。この検査をどの tool の事前条件に置くかは投稿の設計で決める
   - tool のドメイン名は、`video.*` を種類に依存しない動画全体の操作に、`explainer.*` / `collection.*` を種類に固有の操作に使う。カットやファイル単位の操作は `video.` を名乗らない。本 ADR と ADR-0005・0007 に書かれた `video.render` などの名前は決定前の仮称であり、実際の名前は実装 ticket で決める

8. **長尺のサムネイルは plan 区間で作り、企画ゲートで判断する**（改訂 2026-10-02 / #468）。サムネイルが再生の大半を左右するので、台本・音声・描画に費用をかける前に「このサムネイルで勝てるか」を見る。
   - 区間は「題材収集 → 企画 → サムネイル →[企画ゲート]」になる。企画ゲートの承認は、サムネイルの選択があることを前提とする。公開ゲートでは作り直しと差し替えによる選び直しだけを受け、企画ゲートはやり直さない
   - サムネイルの文言も画像生成に描かせる。agent が渡すのは、サムネイルの文言（動画のタイトルとは別）と背景の描写だけで、画風・お手本の参照画像・禁止語・文字の指示・provider・候補の枚数はチャンネル設定の「サムネイルの型」に人間が宣言する。版権を避ける句と禁止語の検査は tool が保証する
   - 1 回の生成で候補を N 枚（既定 3）作る。provider は Gemini の画像生成 API と codex CLI の 2 本を v0.1 で実装し、チャンネル設定で必ず選ぶ（既定値なし、自動の切り替えなし）。codex CLI の扱いは ADR-0002 の改訂による
   - tool が決定的に検査するのは、16:9・1280x720 以上・2 MB 以下の 3 つだけとする。縮小して読めるか、文字が文言どおりか（誤字）は、agent が codec の手順で判断して候補を落とし、最後は人間がゲートで見る
   - 候補から 1 枚を選ぶのは CLI の実行で、append-only の「サムネイルの選択」として記録する。人間が用意した画像は、同じ検査を通して候補に足し、同時に選ぶ。ゲート記録の表の形は変えない
   - ショートは専用の画像を作らず、カットの中のフレームを表紙にする

## Why

- 目的に直結するのは解説動画と複数 SNS への配信で、v0.1 で作る基盤はどちらの lifecycle にも共通である。基盤とは `video.render`、アップロード、ゲート、認証を指す。順番を入れ替えても手戻りはほとんど出ない。
- `youtube-automation` の ADR-0021 追記で TS 版への移行計画は撤回されている。そのため、音楽の dogfood を先に済ませる外部要因は弱い。
- ゲートとローカルの local store という既存の設計に、何も手を入れずに載る。

## Considered Options

- **生成を GitHub Actions で行う（`life` の方式）**: 採らない。Actions のランナーからは Mac 上の `local.db` が見えず、「人間が CLI を叩いた事実が承認」という ADR-0007 のモデルと両立しない。Mac を常時起動できなくなったときは、Turso のリモート DB（または埋め込みレプリカ）による同期を再検討する。
- **v0.1 から状態を実行環境の外に置き、Devin の VM などでも動かす**（#473）: 採らない。v0.1.0 のゲートは Mac だけで完走できる。外に置くと、次の 4 つがまとめて v0.1 に乗る。
  - オフラインで動かない
  - ADR-0004 の `cp` によるバックアップの作り直し
  - 同時実行の排他
  - VM での secret の扱い
  さらに、VM で node-av と headless Chrome が動くかは確かめていない。この検証は「Devin の VM で nyaucast を動かす検証」（#506）で先に行い、移行は #505 で扱う。置き場の候補は、local store が Turso のリモート DB、成果物が R2 である。D1 は Workers の外で使う drizzle の実行時ドライバが無く、ADR-0004 の起動時 `migrate()` を保てないので、候補から外れる。
- **Instagram に渡す動画を GCS の署名付き URL で渡す**（決定 3 の前の決定）: 採らない。R2 は外向きの転送が無料で、#505 の成果物の置き場の候補とも同じになる。
- **Jinba Flow でワークフローを MCP 化する**: 採らない。理由は次のとおり。
  - クラウドで実行されるため、Mac 上の local store とヘッドレス Chrome に届かない。
  - 1 フロー = 1 ツールの粗い粒度は、ADR-0007 決定 0 に反する。
  - ローカルでのテスト手段がない。
  - TikTok・Instagram への投稿と、X への動画添付を持たない。
  - nyaucast の primitive tool は書いた時点で MCP tool になるので、「MCP 化」の手間はもともと小さい。
- **新規リポジトリで作り直す**: 採らない。技術スタックを TypeScript のまま据え置くので、auth・local store・ゲート・MCP の基盤をそのまま使える。基盤を 2 か所で保守することになるのを避ける。
- **長尺のサムネイルを HTML composition で描く**: 採らない。ADR-0005 決定 7 の Chrome 許可リストを広げずに済むよう、音楽と同じく画像生成で作る。人間は作り直しを指示するか、用意した画像に差し替えられる。
- **サムネイルを公開ゲートで確定する**（決定 8 の前の決定）: 採らない。描画まで費用をかけた後で、勝てないサムネイルに気づくことになる。
- **サムネイル専用のゲートを企画ゲートと公開ゲートの間に足す**（collection と同じ 3 段）: 採らない。ゲートを 2 つに絞った決定 1 を崩す。
- **文字を実フォントで後から重ねる**: 採らない。誤字が出ず書体もぶれない利点はあるが、文字の構図まで含めた画像を見て判断したい。経路を 2 本持つと、検査も鮮度の鍵も 2 通りになる。
- **選んだ候補をゲートの承認の記録に持たせる**: 採らない。ゲート記録を collection と同じ形にそろえる決定 7 を崩し、公開ゲートでの選び直しと差し替えの経路も分かれる。
- **TikTok を Sandbox アプリの受信箱への Upload で通す**: 採らない。Sandbox は審査なしで使えるが、テスト用の環境で本番の運用を支える前提にならない。受信箱から仕上げて投稿するのは人間であり、API で投稿したことにもならない。
- **TikTok だけ人間が手で投稿し、投稿の URL を記録してゲートに数える**: 採らない。決定 2 の「実行は決定的な primitive tool が担う」を TikTok のためだけに崩す。Upload の init には `post_info` が無く、AI 生成の開示も人間の操作頼みになる。
- **TikTok の本番審査を v0.1 と並行して出す**: 採らない。自チャンネル専用のアプリとして審査され、落ちる見込みが高い。複数のクリエイターが認可して使うアプリとして出せる有償配布の時点まで待つ。

## Consequences

- CONTEXT.md の `dogfood`・`knowledge codec`・データ 4 分類の ④ を、この決定にあわせて改訂した。
- 公開前の一次確認が残っている。対象は X の URL 付き投稿の単価、TikTok と X の自動投稿ポリシー、Instagram の 2026 年 4 月の規約強化。
- ElevenLabs の日本語ナレーションの品質は、Starter プランで聴き比べてから、チャンネルの既定のボイスを決める。
- ツール名は再帰的頭字語の方針に沿って nyaucast へ改めた（#438 / #446）。
- 決定 7 により、collection の CLI と人間の語彙にずれが残る（`collection reject <gate>`、ゲートの前後関係の未強制）。collection を BGM 動画として `video` に統合する作業は v0.2 以降に回す。
- 決定 8 により、文言の誤字は画像生成の偶然で出る。候補を複数作ることと、agent による足切りで吸収する。
- 決定 7 の「ゲートを動詞で叩く」と「差し戻しは記録しない」の組み合わせにより、作り直しの手順は `explainer-lifecycle` codec が持つ。
- 決定 3 の TikTok の改訂により、v0.1 では TikTok のショート向けの書き出しを実地で確かめない。9:16 のカットは YouTube のショート・Instagram のリール・X で確かめる。
- 決定 3 の Instagram の改訂により、Meta が R2 の署名付き URL を受け付けるかは、実機で確かめていない。Instagram の投稿を実装する ticket の受け入れ条件に、この確認を入れる。
- 決定 4 の約束により、Instagram の一時公開を除いて、v0.1 は R2 も Turso も使わない。複数の環境で動かすときの認証情報の扱い（入れ替わるトークンを、暗号化して共有の local store に置くこと）は、#505 で決める。
